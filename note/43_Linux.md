## 학습 전 필수 관문 — 프로세스 · 포트 · localhost

> **학습 순서:** 아래 정의를 읽고 → 굵은 용어를 자기 말로 풀고 → 틀린 문장을 반박하고 → 예제를 설명한 다음 → 답안을 가리고 면접처럼 말한다. 비유만 이해한 상태에서는 다음으로 넘어가지 않는다.

### 1. 정확한 정의

프로세스는 실행 중인 프로그램의 인스턴스이고, 포트는 네트워크 통신의 논리적 종단점을 구분하는 번호다. `localhost`는 일반적으로 자기 컴퓨터를 가리키는 이름이다.

### 2. 용어를 구분해야 하는 이유

포트 번호는 프로세스 ID(PID)가 아니다. `127.0.0.1`에만 바인딩한 서비스는 보통 외부에서 직접 접근할 수 없다.

### 3. 새로운 상황에 적용

서버가 8080 포트에서 동작해도 외부 접속이 안 될 때 프로세스·리스닝 주소·방화벽을 나누어 확인한다.

### 4. 면접 질문과 답변 기준

**질문:** 프로세스 · 포트 · localhost의 차이를 정의와 동작을 포함해 설명해 보세요.

**답변 기준:** 프로세스는 실행 단위이고 포트는 네트워크 서비스 식별에 사용됩니다. 접속 문제는 실행 상태, 바인딩 주소, 방화벽 등을 구분해 점검해야 합니다.

### 5. 정답을 가리고 설명하기

1. 위 정의에서 핵심 명사 세 개를 골라 각각 뜻을 설명한다.
2. 위의 **틀린 주장**이 왜 틀렸는지 반례를 든다.
3. 위 상황의 **실행 결과·처리 주체·변경되는 값**을 분리해 설명한다.
4. 답변 기준을 보지 않고 **정의 1문장 → 차이 1문장 → 예시 1문장**으로 말한다.
5. 다음 날 같은 질문에 답하지 못하면 예제가 아니라 **정의**부터 다시 확인한다.

## 1. 프로세스·권한·로그

**정의** — 프로세스는 실행 중인 프로그램 인스턴스이고 Linux 권한은 소유자·그룹·기타 사용자 등의 접근 제어를 표현한다. 로그는 동작·오류의 관찰 기록이다.

**목적과 책임** — 서비스 실행 상태와 실패 원인을 파악한다.

**구별해야 할 개념 / 흔한 오해** — chmod 777은 편한 해결책이 아니라 보안 위험을 만든다.

**실행·처리 흐름** — 서비스 실행 → 프로세스 확인 → 포트·로그 확인 → 원인 수정

**직접 구현·검증** — ps, ss, journalctl 또는 파일 로그로 서버 상태 확인. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

프로세스는 실행 중인 프로그램의 인스턴스다. Linux 파일 권한은 소유자·그룹·기타 사용자에 대해 읽기·쓰기·실행 권한을 표현한다. 로그는 실행 중 발생한 사건을 기록한다. 프로세스가 떠 있다고 서비스가 정상이라는 뜻은 아니다.

### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“프로세스는 실행 중인 프로그램 인스턴스이고 Linux 권한은 소유자·그룹·기타 사용자 등의 접근 제어를 표현한다. 로그는 동작·오류의 관찰 기록이다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“chmod 777은 편한 해결책이 아니라 보안 위험을 만든다.”* 반례를 하나 만들어 본다.

**3차: 면접 재현.** *“서비스가 안 뜰 때 어떤 순서로 확인하는가?”*에 대해 **정의 → 왜 필요한가 → 무엇과 다른가 → 코드·상황 하나** 순서로 30~60초 말한다. 답을 읽지 않고 말한 뒤 원문과 대조한다.

## 2. 환경 변수·비밀정보

**정의** — 환경 변수는 프로세스에 전달되는 실행 환경의 이름-값 데이터이며 비밀정보는 노출되면 위험한 인증 정보다.

**목적과 책임** — 설정과 코드를 분리하고 비밀을 안전하게 관리한다.

**구별해야 할 개념 / 흔한 오해** — 환경 변수에 넣는 것만으로 비밀이 완전히 보호되는 것은 아니다.

**실행·처리 흐름** — 배포 환경 설정 → 프로세스 시작 → 설정 로딩 → 외부 서비스 연결

### 배포 전 함정 체크 (Windows 개발 → Ubuntu 서버, 2026-11-23 보강, 미실행)

**참고**: 원본 자료와 출처, 확인 범위는 [부록 92](92_선별근거_원본연결.md)의 이 장 항목을 본다.

| 함정 | 증상 | 해결 방향 |
|---|---|---|
| `C:\` 경로가 코드에 박혀 있음 | 파일 업로드가 전부 실패 | 경로를 설정 파일이나 환경 변수로 빼고, OS에 맞게 `/`를 쓴다 |
| 저장 폴더 권한 | `Permission denied` | 톰캣 실행 계정(`ps aux`로 확인)이 폴더를 쓸 수 있게 `chown`·`chmod` |
| 코드의 `localhost` | 외부 로그인 콜백이 깨짐 | 외부가 읽는 주소는 실제 도메인이나 IP로. DB 주소는 같은 서버면 `localhost`가 맞다 |
| API 키를 소스에 적음 | 요금이 빠져나감 | 환경 변수나 별도 설정 파일로 분리하고 저장소에 올리지 않는다 |
| DB 접속 주소의 자리표시자 | 연결 실패 | 실제 주소·계정으로 바꾼다. 서버에서만 쓰는 계정을 만들고 권한을 최소로 준다 |
| 드라이버 위치 | 톰캣이 드라이버를 못 찾음 | 커넥션 풀을 만드는 톰캣의 `lib`에 드라이버를 둔다 |
| 중복 jar | 실시간 기능이 조용히 멈춤 | 같은 라이브러리의 여러 버전을 지운다 |
| 인코딩·시간대 | 한글 깨짐, 9시간 오차 | 서버 로캘과 시간대를 맞추고 UTF-8을 명시한다 |
| 방화벽·톰캣 버전 | 접속 자체가 안 됨 | 필요한 포트만 열고, 개발에 쓴 톰캣 버전과 맞춘다 |
| 대소문자 | 이미지가 404 | 리눅스는 파일 이름의 대소문자를 구별한다. 코드와 파일 이름을 똑같이 쓴다 |

**면접 기준**: "Windows에서 만든 프로젝트를 Linux에 올릴 때는 경로, 권한, 설정 분리, 인코딩, 파일 이름 대소문자를 먼저 확인합니다. 리눅스는 대소문자를 구별하고, 실행 계정에 쓰기 권한이 있어야 합니다."

## WSL2: Windows 안에서 Linux 실행하기 (2026-11-23 보강, 확인함)

**참고**: 원본 자료와 출처, 확인 범위는 [부록 92](92_선별근거_원본연결.md)의 이 장 항목을 본다.

**정의**: WSL2(Windows Subsystem for Linux 2)는 Windows 안에서 **실제 Linux 커널**을 실행하는 기능이다. VirtualBox처럼 가상 머신을 직접 만들고 OS를 설치하지 않아도 된다. Windows가 Linux 실행 환경을 관리하고, Ubuntu는 그 위에서 쓰는 배포판이다.

| 구분 | VirtualBox | WSL2 |
|---|---|---|
| 가상 머신 | 직접 만들고 OS를 설치한다 | Windows가 자동으로 관리한다 |
| 커널 | 설치한 Linux 커널 | 실제 Linux 커널 |
| 파일 공유 | 설정이 필요하다 | Windows와 Linux 경로가 연결된다 |
| 주된 용도 | 여러 OS를 완전히 격리 | 개발 도구를 Linux에서 쓰기 |

**확인 결과 (이 PC, 읽기만 함)**

```
  NAME              STATE           VERSION
* Ubuntu            Stopped         2
  docker-desktop    Running         2
```

`VERSION 2`는 WSL2로 실행되는 배포판이라는 뜻이다. `Stopped`는 지금 꺼져 있다는 뜻이고, `wsl -d Ubuntu`로 들어가면 켜진다. Docker Desktop도 같은 WSL2 기반이다.

**개발에서 쓰는 이유**: 배포 서버는 대부분 Linux다. Windows에서 개발하면서 Linux 명령과 권한, 파일 이름 대소문자를 WSL2에서 미리 확인할 수 있다(위 "배포 전 함정" 표와 연결).

**주의**
- WSL2 안의 파일(`~`)과 Windows 파일(`/mnt/c`)은 위치가 다르다. 성능이 필요한 작업은 Linux 쪽 파일 시스템에서 한다.
- 가상화 기능(Hyper-V 계열)이 꺼져 있으면 WSL2가 시작되지 않는다. 그럴 때는 BIOS나 Windows 기능 설정을 확인한다.

**면접 기준**: "WSL2는 Windows 안에서 실제 Linux 커널을 돌리는 기능입니다. 가상 머신을 직접 관리하는 VirtualBox와 달리 Windows가 관리하고, 배포 환경과 같은 Linux 명령을 로컬에서 확인할 때 씁니다."

## 4. 실무 명령어 치트시트 (2026-11-24, WSL Ubuntu 26.04에서 확인함)

> 추가 근거: 이 PC의 WSL Ubuntu에서 아래 명령을 실행해 결과를 확인했다. 임시 디렉터리(`/tmp`)에서만 작업하고 정리했다. 서버 전용 설정(방화벽, 운영 서버의 systemd 서비스 파일)은 실행하지 않았고 미실행으로 표시했다.

**1) 파일과 디렉터리**

| 명령 | 용도 | 확인 결과 |
|---|---|---|
| `ls -la` | 숨김 파일과 권한까지 보기 | 권한, 소유자, 크기가 한 줄씩 나온다 |
| `cp a.txt sub/`, `mv sub/a.txt sub/b.txt` | 복사, 이동과 이름 바꾸기 | `mv`는 이름 바꾸기와 같다 |
| `find . -name "*.txt"` | 이름으로 파일 찾기 | 하위 디렉터리까지 찾는다 |
| `grep -rn hello .` | 파일 안의 글자 찾기 | 파일명, 줄 번호, 줄 내용을 준다 |
| `tail -f 로그파일` | 로그 실시간 보기 | 종료는 `Ctrl+C`. 실행 중에는 프롬프트가 돌아오지 않는다 |

**2) 권한과 사용자**

| 명령 | 확인 결과 |
|---|---|
| `chmod 640 a.txt` → `ls -l a.txt` | `-rw-r-----`. 그룹은 읽기만 가능 |
| `chmod +x run.sh` | 실행 권한을 준다. 없으면 `Permission denied`(exit 126) |
| `id -un`, `id -u` | 현재 사용자 이름과 번호(`khbs_d_021`, `1000`) |
| `sudo -n true` | 암호를 묻지 않는 모드. 이 환경에서는 `interactive authentication is required`로 실패했다. 자동화 스크립트에서 `sudo`는 암호 입력이 필요하면 멈춘다 |

**3) 프로세스와 포트**

| 명령 | 확인 결과 |
|---|---|
| `ps -eo pid,args` | 모든 프로세스의 번호와 명령. `awk`나 `grep`과 함께 쓴다 |
| `ss -tlnp` | 열린 포트와 소유 프로세스(`users:(("python3",pid=582,...))`) |
| `kill 582` | 번호로 종료 요청. 응답하지 않으면 `kill -9 582` |
| `pgrep -f "문자열"` | 명령줄 문자열로 번호 찾기. **주의:** 이 명령을 실행하는 셸 자신도 같은 문자열을 가지므로 자기 자신을 찾는다 |

**4) 네트워크**

| 명령 | 확인 결과 |
|---|---|
| `curl -sI http://127.0.0.1:8765/a.txt` | 헤더만 보기. `HTTP/1.0 200 OK` |
| `ss -tlnp \| grep :8080` | 포트가 열렸는지 확인하는 가장 빠른 방법 |
| `lsof -i :8080` | 이 WSL에는 설치되어 있지 않았다(`lsof` 명령 없음). 다른 PC에서는 쓸 수 있을 수 있다 |

**5) 서비스와 로그**

| 명령 | 확인 결과 |
|---|---|
| `systemctl is-system-running` | `running`. 이 WSL은 systemd가 켜져 있다 |
| `journalctl -n 2 --no-pager` | 최근 시스템 로그 2줄 |
| `systemctl status 서비스명`, `journalctl -u 서비스명` | 사용자 단위 서비스는 확인함: `~/.config/systemd/user/`에 unit 파일을 만들고 `systemctl --user start`, `is-active`(active), HTTP 200 확인, `stop`, 파일 삭제까지 실행했다. 시스템 단위 서비스도 확인함(사용자 WSL, 2026-11-24): `/etc/systemd/system/`에 unit 파일을 만들고 `daemon-reload`, `start`, `is-active`(active), HTTP 200 확인, `stop`, 파일 삭제, `daemon-reload`까지 실행했다. |
| `systemctl status` (시스템 전체) | 확인함(사용자 WSL, 2026-11-24): `State: running`, `Failed: 0 units`. 서비스 트리에 chrony, cron, dbus 등이 보였다 |
| `sudo ufw ...` (방화벽) | 규칙 추가·삭제는 확인함(사용자 WSL, 2026-11-24): `ufw allow 8777/tcp`와 `ufw delete allow 8777/tcp`가 "Rules updated"로 끝났다. 다만 `Status: inactive`라서 방화벽은 켜져 있지 않았다. 차단이 실제로 걸리는지(`ufw enable` 후 접속 시험)는 WSL 네트워크를 건드릴 수 있어서 확인하지 않았다(미실행). |

**6) 디스크와 메모리**

| 명령 | 확인 결과 |
|---|---|
| `df -h /` | 파일 시스템 사용률 |
| `free -m` | 메모리 사용량(MB) |
| `du -sh 디렉터리` | 디렉터리 크기 합계 |

**7) 파이프와 리다이렉션**

| 명령 | 확인 결과 |
|---|---|
| `printf "a\nb\na\n" \| sort \| uniq -c` | `2 a`, `1 b` |
| `echo ok >> a.txt` | 끝에 덧붙이기. `>`는 덮어쓰기라서 실수하기 쉽다 |
| `wc -l < a.txt` | 줄 수 |

**실무에서 자주 막히는 지점 (실제로 재현함)**
- 포트 충돌: 같은 포트로 두 번째 서버를 띄우면 `Address already in use`가 나온다. 원인 확인은 `ss -tlnp`, 정리는 `kill`.
- 실행 권한: 스크립트가 `Permission denied`면 `ls -l`로 `x` 권한을 보고 `chmod +x`.
- 없는 파일: `No such file or directory`는 경로가 틀렸거나 작업 디렉터리가 다르다는 뜻이다. `pwd`로 먼저 확인한다.

## 5. 면접 응용: "Linux에서 시스템을 실행했는데 오류가 났습니다. 어떻게 하시겠습니까?"

이 질문은 명령어 목록을 묻는 것이 아니라 **문제를 좁혀 가는 순서**를 묻는 것입니다. 답은 다음 다섯 단계로 말합니다.

1. **재현과 범위 확인**: 언제부터, 어떤 요청이나 명령에서, 어떤 메시지가 나는지 확인한다. 최근 배포나 설정 변경이 있었는지 본다.
2. **증상 분류**: 프로세스가 아예 안 뜨는지(포트·권한·경로), 떴는데 요청이 실패하는지(로그의 예외), DB에 연결이 안 되는지(연결 설정·네트워크) 나눈다.
3. **로그와 상태 확인**: `journalctl -u` 또는 앱 로그의 첫 번째 오류 줄을 본다. 마지막 줄보다 **처음 원인이 되는 줄**이 중요하다. `ss -tlnp`로 포트 상태, `ps`로 프로세스 상태를 본다.
4. **가설을 하나씩 검증**: 예를 들어 "포트 충돌이다"라고 가설을 세우면 `ss -tlnp`로 확인하고, 아니면 다음 가설로 간다. 한 번에 여러 가지를 바꾸지 않는다.
5. **수정과 재발 방지**: 원인을 고치고 같은 명령으로 재확인한다. 이후에는 같은 문제를 막는 장치(설정 검사, 배포 체크리스트, 로그 알림)를 말한다.

**60초 답변 예시**: "먼저 언제부터 어떤 요청에서 실패하는지 확인하고, 로그에서 처음 나온 예외를 봅니다. 프로세스가 안 뜨는 경우라면 `ss -tlnp`로 포트 점유를 보고, 권한 문제면 `ls -l`과 `chmod`로 확인합니다. DB 연결 문제면 접속 정보와 네트워크를 봅니다. 원인을 하나씩 검증한 뒤 고치고, 같은 명령으로 재확인합니다. 마지막으로 재발을 막는 체크를 남깁니다."

**연습 (정답을 가리고 말해 보기)**: 아래 세 상황을 위 다섯 단계로 30초씩 말해 보세요.
- A. 앱을 실행하니 `Address already in use`가 나옵니다.
- B. 배포 스크립트를 실행하니 `Permission denied`가 나옵니다.
- C. 로그에 `No such file or directory`가 있는데 설정 파일은 분명 있습니다.

이 PC에서 A와 B는 위 명령으로 재현해 확인했습니다. C의 원인은 대부분 작업 디렉터리나 상대 경로 문제이므로 `pwd`와 경로 확인부터 말하면 됩니다.

## 개념 경계 정밀 보강 — 실제 코드에서 헷갈리는 지점


### 경계 1. 프로세스 / 스레드 / PID

**흔한 오해:** “프로세스와 스레드는 완전히 같은 실행 단위다”

**정확한 구분:** 프로세스는 독립적인 주소 공간 등 실행 자원을 가진 단위이고 스레드는 프로세스 안에서 자원을 공유하며 실행되는 흐름이다. PID는 프로세스 식별자다.

**코드·명령 해석:**

```bash
ps -ef | grep java
ps -T -p <PID>
```

**확인 방법:** 하나의 Java 프로세스에 여러 스레드가 보이는지 확인한다.

**직접 구현:** Tomcat 프로세스가 종료되면 그 스레드들은 어떻게 되는지 설명하라.

**면접 점검:** “프로세스 / 스레드 / PID”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 2. 포트 / PID / 소켓

**흔한 오해:** “8080은 Tomcat 프로세스 ID다”

**정확한 구분:** PID는 프로세스 식별 번호, 포트는 네트워크 종단의 서비스 구분 번호, 소켓은 통신 끝점을 나타낸다. 서로 독립적인 개념이다.

**코드·명령 해석:**

```bash
ss -ltnp | grep :8080
```

**확인 방법:** LISTEN 포트와 소유 프로세스 정보를 연결해서 읽는다.

**직접 구현:** 서버 포트를 8081로 바꿔도 PID가 같은지 비교하라.

**면접 점검:** “포트 / PID / 소켓”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 3. 파일 권한 / 사용자 / sudo

**흔한 오해:** “chmod 777이 권한 문제의 가장 좋은 해결책이다”

**정확한 구분:** 파일 권한은 소유자·그룹·기타 사용자에 대한 읽기/쓰기/실행 권한이다. sudo는 권한 상승 실행 수단이며 777은 과도한 권한을 부여할 수 있다.

**코드·명령 해석:**

```bash
ls -l app.sh
chmod u+x app.sh
```

**확인 방법:** 파일 실행 권한만 추가하고 다른 사용자 쓰기 권한은 부여하지 않는다.

**직접 구현:** 배포 계정과 서비스 계정의 최소 권한을 설계하라.

**면접 점검:** “파일 권한 / 사용자 / sudo”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.

### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“환경 변수는 프로세스에 전달되는 실행 환경의 이름-값 데이터이며 비밀정보는 노출되면 위험한 인증 정보다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“환경 변수에 넣는 것만으로 비밀이 완전히 보호되는 것은 아니다.”* 반례를 하나 만들어 본다.

**3차: 면접 재현.** *“왜 설정값과 소스 코드를 분리하는가?”*에 대해 **정의 → 왜 필요한가 → 무엇과 다른가 → 코드·상황 하나** 순서로 30~60초 말한다. 답을 읽지 않고 말한 뒤 원문과 대조한다.


## 3. 쉘 스크립트와 프로세스 생성 개념

- **쉘 스크립트:** 명령을 파일에 적어 한 번에 실행한다. 직전 명령의 종료 코드는 `$?`로 확인한다(0이면 성공).
- **파이프와 리다이렉션:** `ps -ef | grep java > out.txt`처럼 한 명령의 출력을 다음 명령의 입력으로 넘기거나 파일에 저장한다.
- **프로세스 생성 (유닉스 계열):**
  - **fork:** 현재 프로세스를 똑같이 복제한다. 부모와 자식은 PID가 다르다.
  - **exec:** 현재 프로세스의 내용을 다른 프로그램으로 바꾼다.
  - **wait:** 부모가 자식이 끝날 때까지 기다리고 종료 상태를 받는다.
  - 셸에서 명령을 실행하는 과정이 바로 fork 후 exec다.
- **시그널:** `SIGTERM`은 정상 종료 요청이고, `SIGKILL`은 강제 종료라서 프로그램이 잡을 수 없다.
- **실습:** 스크립트 안에서 `echo $$`로 현재 셸의 PID를 출력하고, 명령을 하나 더 실행해 PID가 어떻게 달라지는지 본다.
