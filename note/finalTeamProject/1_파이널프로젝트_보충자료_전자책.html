    제1장

    지금, 어떤 신입이 뽑히는가

    겁주려는 장이 아닙니다. 상황을 정확히 알아야 4주를 어디에 써야 할지 보입니다.

    회사 안에서 실제로 바뀐 것

    최근 몇 년 사이 Cursor, GitHub Copilot 같은 AI 코딩 도구가 실무에 빠르게 들어왔습니다. 그 결과 회사 입장에서는 다음과 같은 계산이 생겼습니다.

    • AI 도구 구독료가 신입 한 명 인건비보다 훨씬 쌉니다.
    • 경험 많은 개발자 한 명이 AI 여러 개를 동시에 돌리며 예전 여러 명 분량의 코드를 만듭니다.
    • 그래서 “시킨 화면을 그대로 코드로 옮기는 일”만 하는 신입 자리는 크게 줄었습니다.

    그런데 여기서 새로운 문제가 생깁니다. AI가 만든 코드는 혼자 테스트할 때는 잘 돌아가지만, 데이터가 쌓이거나 사용자가 동시에 몰리거나 나쁜 의도를 가진 사람이 들어오면 깨지는 경우가 많습니다. 이걸 잡아내는 일은 여전히 사람이 해야 하고, 그 일을 할 줄 아는 사람이 부족합니다. 여러분이 들어갈 자리가 바로 여기입니다.

    예전 신입 vs 지금 뽑히는 신입

    예전에 통하던 신입지금 뽑히는 신입포트폴리오에서 보이는 증거
    화면을 많이 만든 사람화면이 왜 느린지 설명하는 사람SQL 실행 횟수, 응답시간 Before/After
    기능 개수로 승부찾아낸 결함과 개선 수치로 승부AI 코드 검증 일지 표
    코드를 빨리 치는 사람AI 결과물을 검수할 줄 아는 사람“AI 초안 → 검증 후” 커밋 이력
    “열심히 했습니다”“측정했고, 고쳤고, 다시 측정했습니다”테스트 코드, 재현 절차
    기술 이름을 많이 아는 사람기술이 어떻게 동작하는지 아는 사람원인 설명이 JPA·DB 동작 수준으로 구체적

    여러분의 직함: AI 코드 검수자

    이 프로젝트에서 여러분이 스스로에게 붙일 직함은 “코드 작성자”가 아니라 “AI 코드 검수자”입니다. 검수자는 다음 네 가지를 합니다.

    1. 의심한다AI가 준 코드가 “데이터 1만 건일 때도, 100명이 동시에 눌러도, 나쁜 사람이 써도” 괜찮은지 질문합니다.
    2. 재현한다의심을 실제 상황으로 만들어 봅니다. 테스트 데이터를 넣고, 동시 요청을 보내고, 공격 입력을 넣어 봅니다.
    3. 측정한다결과를 숫자로 남깁니다. 쿼리 101회, 응답 1,840ms, 100건 중 37건 실패 같은 식입니다.
    4. 고치고 다시 측정한다원인을 JPA·DB·보안 동작으로 설명하고, 고친 뒤 같은 조건으로 다시 재서 비교합니다.

    💡 비전공자라서 불리하지 않습니다

    검수 능력은 전공 여부가 아니라 “기본 동작을 정확히 아는가”와 “귀찮아도 측정하는가”에서 갈립니다. 이 두 가지는 4주 동안 충분히 몸에 붙일 수 있습니다. 대신 기초(2장)를 건너뛰면 검수 자체가 불가능합니다.

    제2장

    요청 한 번이 지나가는 길

    에러가 어느 칸에서 났는지 말할 수 없으면, AI에게 물어도 엉뚱한 곳을 고칩니다. 이 장의 그림은 외워서 종이에 그릴 수 있어야 합니다.

    브라우저에서 DB까지 10단계

    사용자가 브라우저 주소창에 https://우리도메인/stores를 입력하고 엔터를 누르면 다음 순서로 일이 일어납니다.

    1. 브라우저주소를 해석하고 요청을 준비
    2. DNS도메인 이름을 EC2의 공인 IP 주소로 바꿈
    3. EC2 보안그룹80·443·8080 등 열린 포트인지 검사
    4. 내장 Tomcat스프링 부트 jar 안의 웹 서버가 요청 수신
    5. Security 필터 체인세션 로그인·JWT·권한 검사
    6. DispatcherServletURL에 맞는 컨트롤러 메서드 찾기
    7. Controller파라미터 받고 Service 호출
    8. Service트랜잭션 안에서 업무 처리
    9. Repository → MySQLJPA가 SQL을 만들어 실행
    10. ThymeleafModel 값으로 HTML 완성해 응답

    스프링 안쪽에서 일하는 객체들

    “스프링이 알아서 해 준다”는 말은 면접에서 감점입니다. 실제로 어떤 객체가 어떤 일을 하는지 정확히 알아 두세요.

    하는 일실제로 그 일을 하는 객체여러분이 보는 흔적
    @Service, @Repository 등을 객체로 만들어 보관스프링 컨테이너 안의 DefaultListableBeanFactory생성자 주입이 실패하면 부팅 시 UnsatisfiedDependencyException
    로그인·권한 검사SecurityFilterChain 안의 필터들 (JWT 검사 필터, AuthorizationFilter, ExceptionTranslationFilter)401·403 응답
    URL과 컨트롤러 메서드 연결DispatcherServlet이 RequestMappingHandlerMapping에게 물어봄못 찾으면 404
    컨트롤러 메서드 실행, 파라미터 변환RequestMappingHandlerAdapter타입 변환 실패 시 400
    @Transactional 시작·커밋·롤백Service 대신 주입된 프록시 객체가 TransactionInterceptor를 거쳐 JpaTransactionManager 호출예외 시 롤백
    Repository 인터페이스의 실제 구현SimpleJpaRepository 객체findAll(), save() 동작
    엔티티를 SQL로 바꿔 실행Hibernate의 EntityManager(구현체 SessionImpl)콘솔의 SQL 로그
    return "stores/list" → 템플릿 파일 찾기ThymeleafViewResolver못 찾으면 TemplateInputException
    th:text 등을 실제 값으로 바꿔 HTML 완성SpringTemplateEnginenull 접근 시 SpelEvaluationException

    응답 코드로 고장 난 칸 찾기

    응답막힌 곳가장 먼저 볼 곳비전공자가 자주 하는 실수
    접속 자체 안 됨1~4단계EC2 실행 여부, 보안그룹 인바운드 포트, 서버 프로세스 실행 여부보안그룹에 8080을 안 열었음
    401 / 4035단계 SecuritySecurityConfig의 URL 권한, 토큰 유무POST 폼에 CSRF 토큰이 없음 (8장)
    4046단계@GetMapping 주소 철자, 클래스 위 @RequestMapping/store 와 /stores 혼동
    4056단계폼 method와 @PostMapping 일치 여부폼은 POST인데 @GetMapping만 있음
    5007~10단계콘솔의 Caused by 줄 (10장)null 값, 템플릿 경로 오타, DB 제약 위반

    Review.java — 연관관계 매핑의 기준 예시
    @Entity
// Hibernate가 부팅할 때 이 클래스를 review 테이블과 연결된 엔티티로 등록한다
@Table(name = "review")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
// Hibernate가 DB 조회 결과로 Review 객체를 만들 때 기본 생성자를 사용하므로 반드시 필요
public class Review {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    // id 값은 MySQL의 AUTO_INCREMENT가 만든다. save() 직후 insert가 바로 실행되는 이유
    private Long id;

    @Lob
    private String content;

    private int rating;

    @ManyToOne(fetch = FetchType.LAZY)
    // @ManyToOne의 기본값은 EAGER(즉시 로딩)다. AI 초안은 이걸 생략하는 경우가 많다
    // LAZY로 두면 Hibernate가 진짜 Store 대신 프록시 객체를 넣어 두고,
    // store.getName()처럼 실제 값을 꺼낼 때 그제서야 select 를 실행한다
    @JoinColumn(name = "store_id")
    // review 테이블의 store_id 컬럼이 외래키. 이 필드가 연관관계의 주인
    private Store store;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "member_id")
    private Member writer;

    @OneToMany(mappedBy = "review", cascade = CascadeType.ALL, orphanRemoval = true)
    // mappedBy = "review": 외래키는 ReviewImage.review 쪽에 있으므로 여기서는 읽기만 한다
    // cascade ALL: Review를 저장·삭제할 때 사진도 함께 저장·삭제
    // @OneToMany의 기본 fetch는 LAZY. 컬렉션은 Hibernate의 PersistentBag 객체로 채워진다
    private List<ReviewImage> images = new ArrayList<>();
}

    ⚠️ AI 초안에서 꼭 확인할 3가지

    1. @ManyToOne에 fetch = LAZY가 있는가. 없으면 리뷰 목록을 조회할 때 맛집·회원을 무조건 함께 조회해 쿼리가 폭증합니다.
    2. 엔티티에 Lombok의 @Data나 @ToString이 붙어 있지 않은가. Review.toString()이 Store를, Store.toString()이 다시 reviews를 부르며 무한 반복해 StackOverflowError가 납니다. 엔티티에는 @Getter만 쓰세요.
    3. 컨트롤러가 엔티티를 그대로 JSON으로 반환하지 않는가. 양방향 관계 때문에 무한 반복이 나거나, 비밀번호 같은 필드가 그대로 밖으로 나갑니다. 반드시 DTO로 바꿔 반환합니다.

    JPA N+1 — 찾고, 재고, 고치기

    N+1은 AI 초안에서 가장 흔하게 나오고, 면접에서 가장 많이 묻고, 숫자로 증명하기 가장 쉬운 결함입니다. 첫 번째 포트폴리오 이야기로 가장 좋습니다.

    N+1이 생기는 원리

    맛집 목록을 보여 주면서 각 맛집의 리뷰 수를 함께 출력한다고 해 봅시다.

    StoreService.java — AI 초안
    @Transactional(readOnly = true)
// 이 메서드가 호출되면 StoreService 대신 주입된 프록시 객체가 TransactionInterceptor를 거쳐
// JpaTransactionManager에게 읽기 전용 트랜잭션 시작을 요청한다
public List<StoreListDto> findAll() {
    List<Store> stores = storeRepository.findAll();
    // SimpleJpaRepository.findAll() → EntityManager가 select * from store 를 1번 실행
    List<StoreListDto> result = new ArrayList<>();
    for (Store s : stores) {
        result.add(new StoreListDto(s.getName(), s.getReviews().size()));
        // s.getReviews()는 아직 비어 있는 PersistentBag 객체다
        // .size()를 부르는 순간 Hibernate가 select * from review where store_id=? 를 실행
        // 맛집가 100개면 이 줄에서 100번 → 총 1 + 100 = 101번
    }
    return result;
}

    처음 1번(맛집 목록)에 맛집 수 N번이 더해져 1+N번 쿼리가 실행되기 때문에 N+1이라고 부릅니다. 맛집가 10개일 때는 아무도 모릅니다. 1,000개가 되면 화면이 몇 초씩 멈춥니다. AI가 테스트하는 데이터는 대부분 몇 개뿐이라서 이 문제를 스스로 발견하지 못합니다.

    N+1이 숨어 있는 다른 장소

    • Thymeleaf 템플릿 안: th:each="s : ${stores}" 안에서 ${s.reviews.size()}를 쓰면 HTML을 만드는 도중에 쿼리가 나갑니다. 스프링 부트는 기본으로 spring.jpa.open-in-view=true라서 화면을 다 그릴 때까지 DB 연결을 유지하고, 그 사이에 지연 로딩이 실행됩니다. 부팅 로그에 이 설정에 대한 경고가 한 줄 나오는 이유입니다.
    • @ManyToOne 기본값 EAGER: 리뷰 100개를 findAll()하면 각 리뷰의 맛집·작성자를 즉시 조회하려고 추가 쿼리가 나갑니다.
    • DTO 변환 코드: reviews.stream().map(r -> r.getWriter().getNickname())처럼 변환 중에 연관 엔티티를 건드릴 때.

    동시성 — 혼자일 땐 멀쩡한 코드가 깨지는 이유

    동시성 결함은 “혼자 테스트하면 절대 안 보인다”는 점에서 AI 초안 검증의 꽃입니다. 테스트 코드로 깨지는 걸 보여 주는 순간 포트폴리오의 격이 달라집니다.

    갱신 유실이 일어나는 순서

    포인트 10,000점인 고객에 대해 매장 사장님이 두 기기에서 거의 동시에 100점 사용 요청을 보냈다고 해 봅시다.

    시간요청 A (스레드 1)요청 B (스레드 2)DB의 point
    1select → point = 10000 읽음10000
    2select → point = 10000 읽음10000
    310000 − 100 = 9900으로 update, 커밋9900
    410000 − 100 = 9900으로 update, 커밋9900 (원래 9800이어야 함)

    B는 A가 바꾸기 전 값을 보고 계산했기 때문에 A의 사용이 사라졌습니다. 이것을 갱신 유실(Lost Update)이라고 합니다. @Transactional만 붙인다고 막히지 않습니다. MySQL InnoDB의 기본 격리 수준(REPEATABLE READ)에서 일반 select는 잠금 없이 읽기 때문입니다.

    꼬리 질문과 모범 답안

    N+1 문제가 무엇이고 어떻게 해결했나요?

    목록 조회 1번 후, 각 항목의 연관 데이터를 지연 로딩하면서 항목 수만큼 쿼리가 추가로 실행되는 문제입니다. SQL 로그와 Hibernate 통계로 쿼리 수를 확인했고, 목록 화면은 필요한 값만 가져오는 DTO 직접 조회로, 상세 화면은 fetch join으로 해결했습니다.

    fetch join과 페이징을 같이 쓰면 어떻게 되나요?

    컬렉션을 fetch join하면 행이 늘어나 DB에서 limit을 걸 수 없어서, Hibernate가 전체를 메모리로 가져와 자릅니다. 경고 로그가 나오고 데이터가 많으면 메모리 문제가 생깁니다. 부모 엔티티만 페이징하고 컬렉션은 batch size로 가져오는 방식으로 해결했습니다.

    @Transactional만 붙이면 동시성 문제가 해결되지 않나요?

    해결되지 않습니다. MySQL InnoDB 기본 격리 수준에서 일반 select는 잠금 없이 읽기 때문에, 두 트랜잭션이 같은 값을 읽고 각자 계산해 저장하면 한쪽 수정이 사라집니다. 실제로 100스레드 테스트에서 재현했습니다.

    비관적 락과 낙관적 락은 언제 각각 쓰나요?

    충돌이 자주 일어나고 실패하면 안 되는 작업은 비관적 락으로 먼저 잠급니다. 충돌이 드문 작업은 @Version 낙관적 락으로 충돌 시에만 실패시키고 재시도하거나 안내합니다. 포인트 사용은 비관적 락, 고객 정보 수정은 낙관적 락을 썼습니다.

    비관적 락의 단점은 무엇인가요?

    잠금을 기다리는 동안 다른 요청이 대기하므로 처리량이 줄고, 여러 행을 서로 다른 순서로 잠그면 교착 상태가 생길 수 있습니다. 그래서 잠금 범위를 한 행으로 좁히고 트랜잭션을 짧게 유지했습니다.

    th:text와 th:utext의 차이는?

    th:text는 <, > 같은 문자를 이스케이프해 글자로 출력하고, th:utext는 HTML을 그대로 출력합니다. 사용자 입력이나 AI 출력은 th:utext로 출력하면 XSS가 발생하므로 th:text를 썼습니다.

    IDOR를 어떻게 발견했나요?

    계정 두 개를 만들고, A가 쓴 리뷰의 수정 요청을 B로 로그인한 상태에서 id만 바꿔 보냈더니 수정이 됐습니다. 서비스에서 작성자 id와 로그인 사용자 id를 비교해 다르면 403을 반환하도록 고쳤습니다.

    CSRF를 껐나요? 왜요?

    세션 로그인을 쓰는 화면은 브라우저가 쿠키를 자동으로 보내기 때문에 CSRF를 켜 두고, 폼에 th:action을 써서 토큰을 포함했습니다. JWT를 Authorization 헤더로 보내는 /api 요청만 CSRF 예외로 두었는데, 다른 사이트가 이 헤더를 자동으로 붙여 보낼 수 없기 때문입니다.

    AI가 DB에 없는 맛집이나 관광지를 추천하면 어떻게 하나요?

    AI에게 DB의 후보 목록을 번호와 함께 주고 번호로만 고르게 한 뒤, 돌아온 번호를 DB에서 다시 조회해 없는 번호는 버립니다. 그래서 화면에는 실제로 존재하는 데이터만 나옵니다.

    비밀키는 어디에 두었나요?

    저장소에는 두지 않았습니다. GitHub Actions Secrets에 저장하고 배포 시 EC2 환경변수로 전달했으며, S3 접근은 EC2에 IAM 역할을 부여해 접근 키 자체를 쓰지 않았습니다.

    AI를 얼마나 썼나요? 본인이 한 건 뭔가요?

    기능 초안은 AI를 활용했고, 저는 그 코드를 데이터 1만 건·동시 요청·공격 입력 조건에서 검증하고 측정해 고치는 일을 맡았습니다. 검증 일지와 커밋 이력에 AI 초안과 검증 후 코드가 따로 남아 있습니다.

    인덱스를 걸면 무조건 좋아지나요?

    아닙니다. 조회는 빨라지지만 insert·update 때마다 인덱스도 갱신해야 해서 쓰기가 느려지고 저장 공간도 늘어납니다. 그래서 EXPLAIN으로 실제 조회 조건에 쓰이는지 확인한 컬럼에만 걸었습니다.

    open-in-view는 무엇이고 어떻게 설정했나요?

    화면 렌더링이 끝날 때까지 DB 연결과 영속성 컨텍스트를 유지하는 설정으로, 스프링 부트 기본값은 켜져 있습니다. 켜져 있으면 템플릿에서 지연 로딩이 몰래 실행될 수 있어, 꺼 보고 예외가 나는 곳을 찾아 서비스에서 미리 조회하도록 고쳤습니다.
