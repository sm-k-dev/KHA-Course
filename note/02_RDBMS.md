## 학습 전 필수 관문 — 테이블 · 행 · 값 · 키

> **학습 순서:** 아래 정의를 읽고 → 굵은 용어를 자기 말로 풀고 → 틀린 문장을 반박하고 → 예제를 설명한 다음 → 답안을 가리고 면접처럼 말한다. 비유만 이해한 상태에서는 다음으로 넘어가지 않는다.

### 1. 정확한 정의

테이블은 행과 열로 구성되는 관계형 데이터의 표현이며, **행이 없음**과 **행 안의 열 값이 NULL**인 것은 다르다. PK는 행 식별 제약, FK는 참조 무결성 제약이다.

### 2. 용어를 구분해야 하는 이유

PK와 인덱스는 같은 말이 아니다. DBMS가 PK에 인덱스를 만들 수 있어도 식별 규칙과 접근 구조는 구분해야 한다.

### 3. 새로운 상황에 적용

사용자 ID 99를 조회해 결과가 0행이면 값이 `0` 또는 `NULL`인 행을 얻은 것이 아니다.

### 4. 면접 질문과 답변 기준

**질문:** 테이블 · 행 · 값 · 키의 차이를 정의와 동작을 포함해 설명해 보세요.

**답변 기준:** RDBMS는 테이블 사이의 관계와 제약 조건을 관리합니다. 기본 키는 행의 유일한 식별을 보장하고, 외래 키는 참조 관계의 유효성을 제한합니다.

### 5. 정답을 가리고 설명하기

1. 위 정의에서 핵심 명사 세 개를 골라 각각 뜻을 설명한다.
2. 위의 **틀린 주장**이 왜 틀렸는지 반례를 든다.
3. 위 상황의 **실행 결과·처리 주체·변경되는 값**을 분리해 설명한다.
4. 답변 기준을 보지 않고 **정의 1문장 → 차이 1문장 → 예시 1문장**으로 말한다.
5. 다음 날 같은 질문에 답하지 못하면 예제가 아니라 **정의**부터 다시 확인한다.

## 1. DB·DBMS·RDBMS

**정의** — DB는 조직화된 데이터 집합, DBMS는 이를 관리하는 소프트웨어, RDBMS는 관계형 모델을 바탕으로 데이터를 관리하는 DBMS다.

**목적과 책임** — 데이터의 지속 저장, 조회, 무결성, 동시 접근을 관리한다.

**구별해야 할 개념 / 흔한 오해** — SQL은 데이터베이스 자체가 아니라 질의·조작에 쓰이는 언어다.

**실행·처리 흐름** — 애플리케이션 → DB 드라이버 → DBMS → 저장 엔진 → 결과 반환

**직접 구현·검증** — 게시판의 사용자·게시글을 두 테이블로 나누어 설계. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — DB와 DBMS, RDBMS를 각각 정의하라.

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

데이터베이스는 조직화된 데이터 집합, DBMS는 이를 저장·조회·보호하는 소프트웨어다. RDBMS는 관계 모델을 기반으로 테이블, 키, 제약 조건, SQL 등의 기능을 제공한다. 테이블은 관계의 구현 표현이며 물리적 파일과 일대일 대응하지 않는다.

### 직접 읽고 구현하는 독립 예제

```sql
CREATE TABLE department (id BIGINT PRIMARY KEY, name VARCHAR(50) NOT NULL);
CREATE TABLE employee (id BIGINT PRIMARY KEY, department_id BIGINT,
 FOREIGN KEY (department_id) REFERENCES department(id));
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

테이블 구조를 조회하고 FK 제약 조건을 확인한다. MySQL 8 기준이다.

### 스스로 작성할 변형 실습

FK 없이 저장할 때와 FK를 선언할 때 잘못된 부서 ID 삽입 결과를 비교한다.

### 면접 답변의 기준 문장

> DB는 데이터 집합이고 DBMS는 이를 관리하는 소프트웨어이며 RDBMS는 관계 모델에 기반한 DBMS입니다.

**구술 확인:** 위 문장을 외우기보다, 정의와 책임을 구분해 말하고 실제 코드에서 해당 역할을 수행하는 줄을 가리켜 설명한다.


### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“DB는 조직화된 데이터 집합, DBMS는 이를 관리하는 소프트웨어, RDBMS는 관계형 모델을 바탕으로 데이터를 관리하는 DBMS다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“SQL은 데이터베이스 자체가 아니라 질의·조작에 쓰이는 언어다.”* 반례를 하나 만들어 본다.

**완료 기준:** 비유 없이 정의 가능 / 혼동되는 용어 구별 가능 / 처음 보는 예제에 적용 가능. 세 조건 중 하나라도 실패하면 해당 항목만 재학습한다.
## 2. 기본 키·외래 키·무결성

**정의** — 기본 키는 행을 유일하게 식별하도록 선택된 키이고, 외래 키는 다른 테이블의 후보 키 또는 기본 키를 참조하여 관계 제약을 표현한다.

**목적과 책임** — 중복 식별과 잘못된 참조를 방지한다.

**구별해야 할 개념 / 흔한 오해** — 기본 키는 논리적 식별 제약, 인덱스는 검색 성능을 위한 자료구조다. 구현에서 함께 생성될 수 있어도 동일 개념은 아니다.

**실행·처리 흐름** — INSERT → 제약 검사 → 성공 시 저장 / 위반 시 오류

**직접 구현·검증** — 회원·게시글 FK를 만들고 없는 회원 ID로 INSERT하여 제약 오류 확인. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — PK와 UNIQUE, FK는 각각 무엇을 보장하는가?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

기본 키(PK)는 행을 식별하도록 선택된 후보 키로 NULL과 중복을 허용하지 않는다. 외래 키(FK)는 다른 테이블의 후보 키 또는 적절한 유일 키를 참조하는 제약이다. PK가 자동으로 인덱스를 갖는 DB가 많지만 식별 제약과 검색 자료구조는 개념적으로 다르다.

### 직접 읽고 구현하는 독립 예제

```sql
INSERT INTO department VALUES (1, '개발');
INSERT INTO employee VALUES (10, 1);
-- 다음 문장은 FK 제약 위반
INSERT INTO employee VALUES (11, 999);
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

마지막 문장이 실패하는지 확인하고, 트랜잭션 모드에 따라 앞선 성공 행의 유지 여부를 확인한다.

### 스스로 작성할 변형 실습

부서 삭제 시 RESTRICT와 CASCADE의 의미를 각각 설명한다.

### 면접 답변의 기준 문장

> PK는 행의 식별과 유일성을 보장하고 FK는 참조 관계의 유효성을 제약합니다.

**구술 확인:** 위 문장을 외우기보다, 정의와 책임을 구분해 말하고 실제 코드에서 해당 역할을 수행하는 줄을 가리켜 설명한다.

## 3. 정규화·함수 종속

**정의** — 정규화는 함수 종속 등 데이터의 관계를 고려해 중복과 갱신 이상을 줄이도록 릴레이션을 분해하는 과정이다.

**목적과 책임** — 삽입·수정·삭제 이상을 줄이고 데이터 의미를 보존한다.

**구별해야 할 개념 / 흔한 오해** — 정규화는 무조건 테이블 수를 늘리는 기술이 아니다. 반정규화는 측정된 요구에 따라 선택한다.

**실행·처리 흐름** — 중복된 속성 파악 → 종속성 확인 → 테이블 분해 → JOIN으로 조회

**직접 구현·검증** — 주문과 고객 주소를 한 테이블에 저장했을 때의 갱신 이상을 찾아 분해. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 제1·2·3정규형을 설명하고 함수 종속을 예로 들어라.

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

함수 종속 X→Y는 같은 X값이 같은 Y값을 결정한다는 관계다. 정규화는 중복과 삽입·수정·삭제 이상을 줄이도록 관계를 분해한다. 1NF는 속성값의 원자성, 2NF는 부분 함수 종속 제거, 3NF는 비키 속성의 이행 종속 문제를 다룬다. 실제 설계에서는 성능과 일관성 요구를 함께 평가한다.

### 직접 읽고 구현하는 독립 예제

```sql
-- 중복 설계: order_id, customer_id, customer_name 반복
CREATE TABLE customer(id BIGINT PRIMARY KEY, name VARCHAR(50));
CREATE TABLE purchase(id BIGINT PRIMARY KEY, customer_id BIGINT NOT NULL,
 FOREIGN KEY(customer_id) REFERENCES customer(id));
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

고객 이름 변경이 한 테이블에서 끝나는지 확인한다.

### 스스로 작성할 변형 실습

정규화 이전 테이블에서 갱신 이상 2개를 구체적 데이터로 제시한다.

### 면접 답변의 기준 문장

> 정규화는 함수 종속을 바탕으로 중복과 데이터 이상을 줄이기 위한 관계 설계 과정입니다.

## 4. 트랜잭션·ACID

**정의** — 트랜잭션은 하나의 논리적 작업 단위로 취급하는 데이터베이스 연산 집합이며 ACID는 원자성·일관성·격리성·지속성의 성질을 가리킨다.

**목적과 책임** — 여러 변경이 부분적으로만 반영되지 않도록 제어한다.

**구별해야 할 개념 / 흔한 오해** — 원자성은 여러 SQL이 항상 동시에 실행된다는 뜻이 아니고, 격리성은 모든 동시성 문제가 자동으로 사라진다는 뜻도 아니다.

**실행·처리 흐름** — BEGIN → 변경 1 → 변경 2 → COMMIT 또는 ROLLBACK

**직접 구현·검증** — 계좌 이체에서 두 UPDATE 사이 오류를 발생시켜 ROLLBACK 검증. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 트랜잭션 격리 수준을 왜 설정하는가?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

트랜잭션은 함께 성공하거나 실패해야 하는 작업 단위다. 원자성·일관성·격리성·지속성은 트랜잭션의 성질이다. 일관성은 애플리케이션 규칙을 DB가 자동으로 모두 보장한다는 뜻이 아니다. 격리 수준은 동시성 이상과 성능 사이의 선택이며 DB 구현에 따라 실제 잠금·MVCC 동작이 다르다.

### 직접 읽고 구현하는 독립 예제

```sql
START TRANSACTION;
UPDATE account SET balance=balance-100 WHERE id=1 AND balance>=100;
-- 영향 행 수 확인 후 다음 문장 실행
UPDATE account SET balance=balance+100 WHERE id=2;
COMMIT;
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

첫 UPDATE가 0행이면 ROLLBACK하도록 애플리케이션 로직을 작성해야 한다. 예제 실행 전 account 테이블과 잔액을 준비한다.

### 스스로 작성할 변형 실습

두 연결에서 같은 계좌를 갱신하고 격리 수준별 결과를 비교한다.

### 면접 답변의 기준 문장

> 트랜잭션은 관련 작업의 원자적 완료를 위한 단위이고 ACID는 신뢰성 있게 처리하기 위한 성질입니다.

**구술 확인:** 위 문장을 외우기보다, 정의와 책임을 구분해 말하고 실제 코드에서 해당 역할을 수행하는 줄을 가리켜 설명한다.


### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“트랜잭션은 하나의 논리적 작업 단위로 취급하는 데이터베이스 연산 집합이며 ACID는 원자성·일관성·격리성·지속성의 성질을 가리킨다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“원자성은 여러 SQL이 항상 동시에 실행된다는 뜻이 아니고, 격리성은 모든 동시성 문제가 자동으로 사라진다는 뜻도 아니다.”* 반례를 하나 만들어 본다.

**완료 기준:** 비유 없이 정의 가능 / 혼동되는 용어 구별 가능 / 처음 보는 예제에 적용 가능. 세 조건 중 하나라도 실패하면 해당 항목만 재학습한다.
## 5. 인덱스·실행 계획

## 필수 기초 연결: 행·열·값·결과 집합

테이블의 **행(row)**은 한 레코드이고 **열(column)**은 속성이다. `SELECT` 결과는 일반적으로 행들의 집합적 결과(관계형 모델과 SQL의 중복 허용 차이 유의)다. **0행**은 행이 없다는 뜻이지 숫자 0이나 SQL `NULL`이라는 값이 들어 있는 행이 아니다. `NULL`은 특정 컬럼 값이 없거나 알려지지 않은 상태를 나타내는 마커이며 Java `null`과 역할이 비슷해 보여도 서로 다른 계층의 개념이다.

```sql
CREATE TABLE users (id BIGINT PRIMARY KEY, name VARCHAR(50) NOT NULL);
INSERT INTO users VALUES (1, 'Kim');
SELECT id, name FROM users WHERE id = 99; -- 결과 행 0개
SELECT COUNT(*) AS n FROM users WHERE id = 99; -- 행 1개, 값 0
SELECT NULL AS result; -- 행 1개, 컬럼 값 NULL
```

**검증:** DB 클라이언트에서 각 SQL의 결과 **행 수**와 **컬럼 값**을 따로 기록한다. `SELECT COUNT(*)`는 `GROUP BY`가 없는 이 예제에서 0을 담은 한 행을 반환한다. `GROUP BY`를 넣으면 그룹 자체가 없을 수 있으므로 결과 형태가 달라질 수 있다.

**연결:** DBMS는 Java `Optional`을 반환하지 않는다. JDBC의 `ResultSet.next()`가 다음 행의 존재 여부를 알려주고, JPA/Repository가 그 결과를 자신의 반환 계약에 맞게 변환한다.

**면접 질문:** “0 rows와 NULL을 구분하라.” “PK와 FK의 차이는?” “외래 키가 있으면 반드시 자식 행이 존재하는가?” (아니다. FK는 존재하는 참조의 유효성을 제약한다.)

## 개념 경계 정밀 보강 — 실제 코드에서 헷갈리는 지점

> 이 절은 기존 핵심 설명에 추가한 필수 기초 연결 학습이다. 아래 예제는 설명용 최소 코드로, SQL은 예시 테이블이 필요하고 Java는 import/클래스·실행 환경이 필요할 수 있다.


### 경계 1. 행 / 컬럼 / 셀 / NULL

**흔한 오해:** “NULL은 행이 없는 상태다”

**정확한 구분:** 행은 레코드 한 건, 컬럼은 속성, 셀은 행과 컬럼이 만나는 값이다. NULL은 특정 셀의 값이 없거나 알려지지 않았음을 나타내며, 행 자체가 없다는 뜻은 아니다.

**코드·명령 해석:**

```sql
SELECT id, nickname FROM users WHERE id = 999;
-- 0행일 수 있음
SELECT NULL AS nickname;
-- 1행, nickname 값은 NULL
```

**확인 방법:** 결과 집합의 행 수와 셀 값의 NULL 여부를 따로 측정한다.

**직접 구현:** NULL을 가진 행과 조회 결과 0행을 각각 만들어 차이를 설명하라.

**면접 점검:** “행 / 컬럼 / 셀 / NULL”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 2. PK / UNIQUE / FK / 인덱스

**흔한 오해:** “PK와 인덱스는 같은 것이다”

**정확한 구분:** PK는 행 식별을 위한 제약조건, UNIQUE는 중복 제한, FK는 참조 무결성 제약조건이다. 인덱스는 조회 최적화를 위한 자료구조이며 DBMS가 PK/UNIQUE를 지원하려고 인덱스를 사용할 수 있어도 개념은 다르다.

**코드·명령 해석:**

```sql
CREATE TABLE teams(id BIGINT PRIMARY KEY);
CREATE TABLE users(id BIGINT PRIMARY KEY, email VARCHAR(100) UNIQUE, team_id BIGINT, FOREIGN KEY(team_id) REFERENCES teams(id));
```

**확인 방법:** 존재하지 않는 team_id 삽입과 중복 email 삽입을 각각 시도한다. NULL 허용 정책은 DBMS에 따라 확인한다.

**직접 구현:** FK를 제거한 경우 잘못된 참조가 어떻게 생기는지 비교하라.

**면접 점검:** “PK / UNIQUE / FK / 인덱스”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 3. 트랜잭션 / 잠금 / 격리 수준

**흔한 오해:** “트랜잭션을 사용하면 동시성 문제가 전부 해결된다”

**정확한 구분:** 트랜잭션은 원자적 작업 경계를 제공하지만 격리 수준과 잠금 방식에 따라 동시성 이상 현상이 달라진다. COMMIT은 성공 확정, ROLLBACK은 미확정 변경 취소다.

**코드·명령 해석:**

```sql
START TRANSACTION;
UPDATE accounts SET balance=balance-100 WHERE id=1;
UPDATE accounts SET balance=balance+100 WHERE id=2;
COMMIT;
```

**확인 방법:** 두 번째 UPDATE가 실패할 때 ROLLBACK을 실행하고 두 잔액 합계가 유지되는지 확인한다.

**직접 구현:** 두 DB 세션으로 동일 계좌를 수정하며 잠금 대기를 관찰하라.

**면접 점검:** “트랜잭션 / 잠금 / 격리 수준”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.
