1. 퇴근 5분 TIL 루틴

권장 빈도: 주 2~3회, 1회 최대 5분. 기록 단위: 한 페이지 = 한 상황. 원칙: 예쁘게 정리하기보다 무엇을 오해했고 왜 해결됐는지 남긴다.

바로 복사해 쓰는 Markdown 템플릿

# 📌 TIL (Work) — [작성일 / 주제]

## 🧠 상황 (Context)
- 무엇을 하려다가 막혔는가?
- 어떤 환경이었는가? (서비스 / 스택 / 상황)

## ❓ 문제 (Problem)
- 정확히 무엇이 안 됐는가?
- 내가 처음에 잘못 생각한 지점은?

## 🔍 깨달음 (Insight)
- 핵심 원리 또는 오해를 바로잡은 내용 1~2줄

## 🔧 해결 방법 (How)
- 실제 적용한 해결책 (명령어 / 설정 / 코드)
- 해결되었음을 어떻게 확인했는가?

## 🪴 다음에 쓸 때 체크할 것
- 재발 방지 체크리스트

## 💬 연결 가능한 면접 질문
- Q[번호]. [질문]

태그: #실무 #Docker #API #DB

2. 작성 예시 — Docker / AWS EC2 접근 이슈

아래는 사용자가 제시한 사례를 읽기 쉽게 보완한 가상 예시이며, 실제 수행 경험으로 단정하지 않는다.

# TIL — EC2에서 FastAPI 컨테이너 외부 접속 불가 (예시)

## 🧠 상황
로컬에서 실행되던 FastAPI 컨테이너가 EC2에서는 외부에서 접속되지 않음.

## ❓ 문제
컨테이너 포트 공개, 서버의 네트워크 허용 규칙을 혼동함.

## 🔍 깨달음
Docker의 포트 매핑과 EC2 보안 그룹 인바운드 허용은 별개의 설정.
애플리케이션의 바인딩 주소(0.0.0.0)도 확인해야 함.

## 🔧 해결
컨테이너 실행 옵션(-p 8000:8000), 앱 바인딩 주소,
EC2 보안 그룹의 인바운드 규칙을 각각 점검·수정.
접속 테스트와 로그로 정상 동작 확인.

## 🪴 다음에 확인할 것
앱 리스닝 주소 → 컨테이너 포트 → 호스트 포트 →
보안 그룹/방화벽 → 외부 접근 경로 순으로 점검.

## 💬 연결 가능한 면접 질문
Q9. 서버에서만 발생한 문제를 해결한 경험이 있나요?
Q15. 설정 문제와 코드 문제를 어떻게 구분하나요?
보완 포인트: 원본의 ‘보안 그룹 → 컨테이너 포트’ 점검 순서는 한 가지 실무 휴리스틱이다. 실제 진단에서는 앱 바인딩 주소, 호스트 포트, 컨테이너 매핑, 보안 그룹과 방화벽을 함께 확인해야 한다.

3. 1년치 TIL을 A4 한 장으로 압축하기

연 1회 개인 저장소의 메인 페이지에 기록한다. 기술 이름을 나열하기보다 문제 유형, 판단 기준, 반복 실수, 개선, 다음 성장 목표를 중심으로 작성한다.

# 202X Engineering Growth Summary

1. 내가 다룬 문제 유형
   - 배포 및 환경 설정, API 연동, 인증/권한 문제
2. 내가 내린 주요 판단
   - 애플리케이션/인프라 구분, 로그→설정→코드 순 확인
3. 반복된 실수와 개선
   - 환경 설정 확인 누락 → 배포 체크리스트 도입
4. 기술적으로 깊어진 영역
   - Docker 배포, Linux 디버깅, REST API 설계
5. 다음 해 집중할 것
   - 모니터링·로그 체계, 아키텍처 설계

Track 2. 면접·이직에서 내 가치 증명하기

목표 · 사실 기록을 ‘왜 그렇게 판단했는가, 어떤 결과를 만들었는가’라는 채용 언어로 변환한다.

1. TIL → 이력서 문장 변환 공식

문제와 맥락
→
내 판단·행동
→
검증된 결과
→
간결한 이력서 문장
단계내용
원본 TILEC2의 FastAPI 컨테이너 외부 접속 불가 → 포트/보안 설정 점검 → 해결

예시는 실제 수행 여부를 확인한 뒤 사용해야 한다. 해결 시간, 장애 감소율 등 정량 성과는 측정한 경우에만 기재한다.

2. 면접 스토리텔링 프레임워크

프레임사용 상황답변 구조
S-P-T-R경험·문제 해결 질문Situation(상황) → Problem(문제) → Thinking(판단) → Result(결과)
Why–How–Trade-off기술 선택·설계 질문선택 기준 → 구현 방식 → 비용·한계·대안
No–Similar–Approach직접 경험 없는 기술 질문경험 없음 명시 → 유사 경험 → 검증 가능한 접근 순서

S-P-T-R 답변 틀: “당시 상황은 [상황]이었고, [문제]가 발생했습니다. 저는 [근거]를 바탕으로 [접근]을 선택했고, 그 결과 [검증된 결과]를 얻었습니다.”

Why–How–Trade-off 답변 틀: “중요한 기준은 [Why]였기 때문에 [How]로 구현했습니다. 다만 [Trade-off]가 있어 [조건]에서는 다른 대안도 검토할 수 있습니다.”

No–Similar–Approach 답변 틀: “직접 사용한 경험은 없습니다. 다만 [유사 경험]을 바탕으로 [접근·검증 순서]로 해결하겠습니다.”

4. 나를 정의하는 5문장 자기소개

  1. 소개: 나는 [주로 해결해 온 문제]에 강점을 가진 [직무] 개발자다.
  2. 판단 기준: 문제 발생 시 [내가 우선 확인하는 기준]을 적용한다.
  3. 증거·경험: [실제로 수행한 경험]을 통해 이를 입증했다.
  4. 성장: 그 과정에서 [개선한 사고·업무 습관]을 배웠다.
  5. 지향점: 앞으로 [목표 엔지니어상]으로 성장하고자 한다.
