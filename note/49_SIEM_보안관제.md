# SIEM과 보안 관제: 흩어진 로그를 모아 공격 패턴을 찾는다

> 중요도: **B** · 이 장의 목표: SIEM의 수집, 정규화, 상관분석, 알림, 대응 단계를 설명하고, 시간 창(슬라이딩 윈도우) 규칙으로 무차별 대입 시도를 탐지하고, 오탐을 줄이는 기준을 세운다.

## 1. SIEM이란

**정의** — SIEM(Security Information and Event Management)은 여러 장비와 애플리케이션의 로그를 **한곳에 모아 정규화하고, 상관분석해서 보안 이벤트를 찾아내는** 시스템이다.

| 단계 | 하는 일 | 예 |
|---|---|---|
| 수집 | 로그 원천에서 가져온다 | 방화벽, 웹 서버, 인증 서버, 클라우드 감사 로그 |
| 정규화 | 형식을 공통 필드로 바꾼다 | 시각, 출발지 IP, 사용자, 행위, 결과 |
| 상관분석 | 여러 이벤트를 엮어 규칙을 적용한다 | 5분 안에 같은 IP에서 로그인 실패 10회 |
| 알림 | 담당자에게 보낸다 | 우선순위와 함께 티켓 생성 |
| 대응 | 확인하고 차단하거나 기록한다 | IP 차단, 계정 잠금, 사후 분석 |

**핵심 구별**: 로그 수집은 SIEM의 시작일 뿐이다. 가치는 **규칙과 대응 절차**에서 나온다. 로그만 모으고 아무도 보지 않으면 관제가 아니다.

---

## 2. 정규화가 먼저다

장비마다 로그 형식이 다르다. 같은 "로그인 실패"도 방화벽, 웹, 인증 서버에서 다른 문장으로 찍힌다. 규칙을 만들려면 공통 형식이 있어야 한다.

```
원본(웹):   2026-11-23 10:00:01 POST /login 401 ip=203.0.113.9 user=kim
원본(인증): 10:00:02 auth FAIL user=kim src=203.0.113.9
정규화:     {time, src_ip, user, action=LOGIN_FAIL, source=web|auth}
```

**주의**: 시각대(UTC와 KST)를 정규화 단계에서 맞춘다(4장). 시각이 어긋나면 상관분석이 틀린다.

---

## 3. 상관분석 규칙: 슬라이딩 윈도우

**예 규칙**: 같은 출발지 IP에서 60초 안에 로그인 실패가 5회 이상이면 **무차별 대입 시도**로 본다.

슬라이딩 윈도우는 "최근 N초 안의 이벤트 수"를 계속 계산한다. 고정 구간(0–60초, 60–120초)으로 나누면 경계에서 실패를 놓칠 수 있다.

---

## 4. 검증 코드 (JDK 25에서 실행)

```java
import java.util.*;

public class SiemRuleCheck {
    record LoginFail(long epochSec, String srcIp, String user) {}

    static final int WINDOW_SEC = 60;
    static final int THRESHOLD = 5;

    // 같은 IP에서 WINDOW_SEC 안에 THRESHOLD 이상 실패하면 알림 대상
    static List<String> detect(List<LoginFail> events) {
        Map<String, Deque<Long>> byIp = new HashMap<>();
        Set<String> alerted = new LinkedHashSet<>();
        for (LoginFail e : events.stream().sorted(Comparator.comparingLong(LoginFail::epochSec)).toList()) {
            Deque<Long> window = byIp.computeIfAbsent(e.srcIp(), k -> new ArrayDeque<>());
            window.addLast(e.epochSec());
            while (!window.isEmpty() && e.epochSec() - window.peekFirst() >= WINDOW_SEC) {
                window.pollFirst();                       // 창 밖으로 나간 이벤트 제거
            }
            if (window.size() >= THRESHOLD) alerted.add(e.srcIp());
        }
        return new ArrayList<>(alerted);
    }

    public static void main(String[] args) {
        long t0 = 1_700_000_000L;
        List<LoginFail> events = new ArrayList<>();
        // 공격자 IP: 10초 간격으로 6회 (60초 안에 5회 이상 발생)
        for (int i = 0; i < 6; i++) events.add(new LoginFail(t0 + i * 10, "203.0.113.9", "admin"));
        // 정상 사용자: 실패가 5분 간격으로 흩어짐
        for (int i = 0; i < 6; i++) events.add(new LoginFail(t0 + i * 300, "198.51.100.7", "kim"));
        // 경계 테스트: 같은 IP가 60초 간격으로 5회 (창 밖으로 나가 알림이 없어야 한다)
        for (int i = 0; i < 5; i++) events.add(new LoginFail(t0 + i * 60, "192.0.2.5", "lee"));

        System.out.println("alerts = " + detect(events));
    }
}
```

**실행 결과 (확인함)**

```
alerts = [203.0.113.9]
```

**결과 읽기**
- `203.0.113.9`는 6회가 10초 간격이라 40초 시점에 60초 창 안에 5회가 들어가서 알림이 떴다. 20초 간격이었다면 창 안에 최대 3회라서 알림이 뜨지 않는다.
- `198.51.100.7`은 실패가 5분씩 떨어져 있어 알림이 없다.
- `192.0.2.5`는 60초 간격 5회다. 창 기준이 `>= 60`이므로 첫 실패는 창에서 빠진다. 알림이 없는 것이 맞다. 경계 조건을 이렇게 명시해야 한다.

## 5. 오탐을 줄이는 기준

| 오탐 원인 | 예 | 줄이는 방법 |
|---|---|---|
| 정상 사용자의 재시도 | 비밀번호를 잘못 입력한 뒤 재시도 | 임계치와 시간 창을 같이 조정, 성공 로그인 이후 실패 무시 |
| 공용 IP (NAT, 사무실) | 한 IP 뒤에 수백 명 | 계정 단위 규칙을 함께 사용 |
| 점검 작업, 부하 테스트 | 대량 로그인 | 작업 시간대와 테스트 IP를 예외 목록에 등록 (기한 포함) |

**원칙**: 규칙은 처음부터 완벽할 수 없다. 알림마다 "맞았는지"를 기록하고, 정기적으로 임계치를 조정한다. 알림이 쌓여 무시되면 탐지는 실패한다.

## 6. 관제 대응 흐름 (SOC)

1. 알림을 받는다. 우선순위(영향 계정, 성공 여부)를 확인한다.
2. 같은 IP나 계정의 최근 활동을 조회한다. 성공 로그인이 있었는지가 핵심이다.
3. 판단: 오탐, 의심(추적), 확정 사고. 확정이면 사고 대응 절차로 넘긴다(46장).
4. 조치: IP 차단, 계정 잠금, 비밀번호 재설정 안내. 조치 기록을 남긴다.
5. 규칙 개선: 오탐이었다면 예외 조건을 기록하고, 놓친 공격이었다면 규칙을 추가한다.

## 7. 목표 점검 연결

- **방화벽·IDS/IPS (48장)**: 장비가 만든 이벤트가 SIEM의 원천이다.
- **인증·인가 (30장, 31장)**: 로그인 실패, 권한 변경 로그가 핵심 원천이다.
- **관측성 (45장)**: 메트릭과 로그는 운영 관측용이고, SIEM은 보안 판단용이다. 같은 로그를 두 목적으로 쓸 수 있지만 보관 정책과 접근 권한은 따로 본다.
- **AI 에이전트 (55장)**: 에이전트의 도구 호출 감사 로그도 SIEM으로 모아 이상 행동을 탐지한다.

## 8. 실습 과제

1. 4절 규칙의 `THRESHOLD`를 3으로 낮추면 어떤 IP가 추가로 탐지되는지 예측하고 실행해 확인한다.
2. `WINDOW_SEC`를 120으로 바꿨을 때 `192.0.2.5`가 탐지되는지 확인하고 이유를 적는다.
3. 본인 프로젝트 로그인 API에서 남길 로그 필드 여섯 개(시각, 출발지, 사용자, 행위, 결과, 요청 ID)를 정규화 표로 정리한다. 비밀번호는 필드에 넣지 않는다.
