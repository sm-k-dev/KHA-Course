# AI가 만든 코드 검증하기: 결함 11개와 검증 루틴

> 중요도: **A** · 이 부록의 목표: AI가 만든 코드가 "화면에서는 돌아가는" 상태를 넘어, 데이터가 많을 때·동시에 쓸 때·나쁜 입력이 올 때 어떻게 깨지는지 찾아내고, 고친 뒤 숫자로 증명하는 방법을 익힌다.

> 2026-11-23 추가 부록. 결함 목록과 실습 흐름은 선생님 자료 `AI_Code_Defect★/2_AI코드검증_자습서.html`과 `JPA + AI 코드 검증 시험공부 자습서.html`을 바탕으로 정리했다. 아래 세 가지 검증 코드는 이 PC에서 실행해 확인했다. 실습 프로젝트(`defect-lab`) 전체는 JDK 21, MySQL 8, IntelliJ 환경이 필요해서 이 PC에서 실행하지 않았다(미실행).

---

## 1. 왜 검증해야 하나

AI가 만든 코드는 대개 **정상 입력 한 개**에서 잘 돈다. 실제 서비스에서는 다음 세 가지가 함께 온다.

| 상황 | 깨지는 모습 |
|---|---|
| 데이터가 많다 | 목록 화면이 느리다(N+1) |
| 여러 사람이 동시에 쓴다 | 숫자가 틀린다, 쿠폰이 여러 번 쓰인다 |
| 나쁜 입력이나 조작된 주소가 온다 | 남의 글이 수정된다, 스크립트가 실행된다 |

**원칙**: "돌아간다"는 검증이 아니다. **숫자로 재고, 고치고, 다시 재서 비교**해야 검증이다.

## 2. 결함 11개 (선생님 자료 기준)

| 번호 | 결함 | 생기는 일 | 관련 장 |
|---|---|---|---|
| ① | 목록이 느림 (N+1) | 맛집 50개를 보여 주는데 SQL 51번 | 25장 3절 |

| ⑤ | 스크립트 실행 (XSS) | 리뷰에 넣은 스크립트가 다른 사람 화면에서 실행됨 | 24장 |

| ⑩ | AI가 지어낸 관광지 | AI가 없는 관광지를 섞으면 화면이 500 에러 | 이 부록 3절 |
| ⑪ | 느린 외부 API | 날씨 API가 느리면 우리 화면도 5초 넘게 멈춤 | 이 부록 3절 |

**결함의 공통 원인 네 가지**

1. **주인 검사 누락**(④ ⑦): 로그인한 사람과 데이터의 주인이 같은지 확인하지 않는다. (IDOR: 주소의 번호만 바꿔 남의 데이터에 접근하는 취약점)
2. **확인과 변경이 나뉨**(② ③ ⑥ ⑨): SELECT로 확인하고 나중에 UPDATE한다. 사이에 다른 요청이 끼어든다. (33장)
3. **출력 전 이스케이프·마스킹 누락**(⑤ ⑧): 화면에 찍기 전에 특수 문자를 바꾸거나 일부를 가리지 않는다.
4. **외부 결과를 믿음**(⑩ ⑪): AI나 외부 API의 답을 DB와 대조하지 않고, 시간 제한도 없이 기다린다.

## 3. 검증 루틴: 다섯 단계

1. **실행**: 정상 입력으로 기능을 돌린다. 여기서 끝내지 않는다.
2. **재기**: 결함을 숫자로 잡는다. 예: SQL 개수, 동시 요청 후 최종 값, 다른 사람 데이터 접근 여부.
3. **고치기**: 원인에 맞게 고친다(조건을 UPDATE 안에 넣기, 주인 검사 추가, 이스케이프, 타임아웃).
4. **다시 재기**: 같은 측정을 다시 해서 Before와 After를 나란히 적는다.
5. **설명하기**: 3줄로 "무엇이, 왜 틀렸고, 어떻게 고쳤나"를 말할 수 있어야 끝이다.

**포트폴리오 증거**: Before/After 숫자가 있으면 "측정하고 고쳤다"는 증거가 된다. 코드 줄 수나 AI에게 물어본 횟수는 증거가 아니다.

## 4. 검증 코드 세 가지 (확인함)

### 4-1. AI가 고른 id를 DB와 대조하기 (결함 ⑩)

```java
import java.util.*;

public class AiCheck {
    record Spot(long id, String name) {}

    // AI가 고른 id를 DB 목록과 대조해서, 있는 것만 남긴다
    static List<Spot> onlyKnown(List<Long> aiPicks, Map<Long, Spot> db) {
        List<Spot> out = new ArrayList<>();
        for (Long id : aiPicks) {
            Spot s = db.get(id);
            if (s != null) out.add(s);              // 없는 id(9999)는 버린다
        }
        return out;
    }

    public static void main(String[] args) {
        Map<Long, Spot> db = Map.of(1L, new Spot(1, "haeundae"), 2L, new Spot(2, "gwangalli"));
        System.out.println(onlyKnown(List.of(1L, 9999L, 2L), db));
    }
}
```

**실행 결과 (확인함)**: `[Spot[id=1, name=haeundae], Spot[id=2, name=gwangalli]]`

9999번은 DB에 없어서 버려졌다. 원래 코드처럼 그대로 쓰면 없는 관광지를 화면에 그리다가 500 에러가 난다.

### 4-2. 느린 외부 호출에 시간 제한 걸기 (결함 ⑪)

```java
import java.util.concurrent.*;

public class TimeoutCheck {
    static String slowWeather() throws InterruptedException {
        Thread.sleep(3000);                          // 외부 API가 느린 상황을 흉내 낸다
        return "sunny";
    }

    public static void main(String[] args) throws Exception {
        ExecutorService ex = Executors.newSingleThreadExecutor();
        Future<String> f = ex.submit(TimeoutCheck::slowWeather);
        try {
            System.out.println(f.get(500, TimeUnit.MILLISECONDS));   // 500ms까지만 기다린다
        } catch (TimeoutException e) {
            System.out.println("timeout: fallback to default");     // 기본값으로 대신한다
            f.cancel(true);
        } finally {
            ex.shutdownNow();
        }
    }
}
```

**실행 결과 (확인함)**: `timeout: fallback to default`

실제 HTTP 호출에서는 `HttpClient`의 `timeout`, Spring의 `RestClient` 설정 같은 시간 제한을 쓴다. 이 PC에서는 소켓이 막혀서 HTTP 호출은 실행하지 않았다(미실행). 같은 원리로 "기다릴 시간을 정하고, 넘으면 대체 값을 쓴다"를 확인했다.

### 4-3. 출력 전 이스케이프 (결함 ⑤)

```java
public class EscapeCheck {
    static String escape(String s) {
        return s.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;")
                .replace("\"", "&quot;").replace("'", "&#x27;");
    }

    public static void main(String[] args) {
        System.out.println(escape("<script>alert('x')</script>"));
    }
}
```

**실행 결과 (확인함)**: `&lt;script&gt;alert(&#x27;x&#x27;)&lt;/script&gt;`

이렇게 바뀐 문자열은 브라우저에서 글자로만 보이고 스크립트로 실행되지 않는다. Thymeleaf에서는 `th:text`가 이 작업을 자동으로 한다(24장). 반대로 `th:utext`나 직접 HTML을 이어 붙이면 이스케이프가 빠진다. AI가 만든 답변을 출력할 때도 같은 규칙을 쓴다.

## 5. 동시성 결함(②③⑥⑨)과 N+1(①)

- 포인트·쿠폰·찜 숫자는 **확인과 변경을 UPDATE 한 문장으로 묶어서** 고친다. 실제 측정(잘못된 방식 20건 성공 → 900점 남음, 올바른 방식 10건 성공 → 0점 남음)은 **33장**에 있다.
- 중복 찜·북마크는 **유니크 제약**으로 DB가 막는다.
- N+1은 **연관 데이터를 읽는 줄 수**를 세어 확인한다. 측정 방법과 fetch join 해결은 **25장 3절**에 있다.

## 6. 흔한 실수

| 실수 | 결과 | 고치는 방법 |
|---|---|---|
| "화면이 돌아가니까 끝" | 동시 요청과 나쁜 입력에서 깨짐 | 정상 입력 외에 동시 요청·다른 사용자 주소를 시험 |
| 고치기 전 숫자를 안 적음 | 고쳤다는 증거가 없음 | 고치기 전 측정값을 먼저 기록 |
| AI가 준 id를 그대로 씀 | 없는 데이터로 500 에러 | DB 목록과 대조 |
| 주소의 id만 믿음 | 남의 데이터 수정 | 로그인한 사용자와 데이터의 주인을 비교 |
| 외부 호출에 시간 제한이 없음 | 우리 화면도 멈춤 | 타임아웃과 대체 값을 정함 |
