## 학습 전 필수 관문 — CSS 선택자 · 우선순위 · 상속

> **학습 순서:** 아래 정의를 읽고 → 굵은 용어를 자기 말로 풀고 → 틀린 문장을 반박하고 → 예제를 설명한 다음 → 답안을 가리고 면접처럼 말한다. 비유만 이해한 상태에서는 다음으로 넘어가지 않는다.

### 1. 정확한 정의

CSS 선택자는 스타일을 적용할 요소를 찾는 조건이고, 우선순위는 여러 선언이 충돌할 때 적용할 규칙의 일부다. **상속**과 **우선순위**는 별개다.

### 2. 용어를 구분해야 하는 이유

`!important`가 모든 경우 무조건 이긴다는 말은 부정확하다. 출처·중요도·계층·구체성·소스 순서 등을 함께 고려한다.

### 3. 새로운 상황에 적용

부모의 `color`가 자식에 상속되는 경우와 자식에 직접 지정된 `color`가 적용되는 경우를 구분한다.

### 4. 면접 질문과 답변 기준

**질문:** CSS 선택자 · 우선순위 · 상속의 차이를 정의와 동작을 포함해 설명해 보세요.

**답변 기준:** CSS는 캐스케이드에 따라 적용 스타일을 결정하며, 상속은 일부 속성이 부모에서 자식으로 전달되는 규칙입니다.

## 1. 캐스케이드·특이성

**정의** — 캐스케이드는 여러 CSS 선언이 충돌할 때 출처·중요도·계층·특이성·선언 순서 등의 규칙으로 적용 값을 결정하는 과정이다.

**목적과 책임** — 같은 요소에 적용된 여러 스타일을 결정한다.

**구별해야 할 개념 / 흔한 오해** — 특이성 숫자만 비교하면 모든 충돌을 설명할 수 없다.

**실행·처리 흐름** — 규칙 매칭 → 우선순위 비교 → 계산된 스타일

**직접 구현·검증** — 클래스·ID·인라인 스타일 충돌 사례 확인. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 스타일이 적용되지 않을 때 어떤 순서로 점검하는가?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

캐스케이드는 출처·중요도·레이어·특이성·소스 순서 등을 고려해 적용 선언을 결정하는 규칙이다. 특이성만으로 모든 충돌을 설명할 수 없다. 상속은 캐스케이드와 다른 메커니즘이다.

### 직접 읽고 구현하는 독립 예제

```html
<style>.note {color:blue} #msg {color:red}</style>
<p id="msg" class="note">결과</p>
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

Computed 스타일에서 빨간색이 적용된 근거를 확인한다.

### 스스로 작성할 변형 실습

inline style, !important, cascade layer가 추가되면 우선순위를 조사한다.

### 면접 답변의 기준 문장

> 캐스케이드는 충돌하는 CSS 선언을 결정하는 과정이고 특이성은 그 판단 요소 중 하나입니다.

**구술 확인:** 위 문장을 외우기보다, 정의와 책임을 구분해 말하고 실제 코드에서 해당 역할을 수행하는 줄을 가리켜 설명한다.


### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“캐스케이드는 여러 CSS 선언이 충돌할 때 출처·중요도·계층·특이성·선언 순서 등의 규칙으로 적용 값을 결정하는 과정이다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“특이성 숫자만 비교하면 모든 충돌을 설명할 수 없다.”* 반례를 하나 만들어 본다.

**3차: 면접 재현.** *“스타일이 적용되지 않을 때 어떤 순서로 점검하는가?”*에 대해 **정의 → 왜 필요한가 → 무엇과 다른가 → 코드·상황 하나** 순서로 30~60초 말한다. 답을 읽지 않고 말한 뒤 원문과 대조한다.

**완료 기준:** 비유 없이 정의 가능 / 혼동되는 용어 구별 가능 / 처음 보는 예제에 적용 가능. 세 조건 중 하나라도 실패하면 해당 항목만 재학습한다.
## 2. 박스 모델·Flex·Grid

**정의** — 박스 모델은 콘텐츠·패딩·테두리·마진으로 요소의 공간을 설명한다. Flex는 일차원, Grid는 이차원 레이아웃에 적합하다.

**목적과 책임** — 요소 크기와 배치를 설계한다.

**구별해야 할 개념 / 흔한 오해** — margin과 padding은 모두 여백이지만 테두리 안팎 위치가 다르다.

**실행·처리 흐름** — DOM·스타일 → 박스 계산 → 배치 → 그리기

**직접 구현·검증** — 카드 목록을 Grid로, 내비게이션을 Flex로 배치. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

박스 모델은 콘텐츠·패딩·테두리·마진의 크기 관계다. Flex는 주로 한 축의 정렬과 배치에, Grid는 행·열을 함께 설계하는 데 적합하다. `box-sizing:border-box`는 지정 크기에 padding과 border를 포함한다.

### 직접 읽고 구현하는 독립 예제

```css
*{box-sizing:border-box}
.cards{display:grid;grid-template-columns:repeat(auto-fit,minmax(180px,1fr));gap:12px}
.toolbar{display:flex;justify-content:space-between;align-items:center}
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

창 너비를 바꿔 Grid 카드 열 수와 Flex 정렬 변화를 관찰한다.

### 스스로 작성할 변형 실습

고정 폭과 minmax를 혼합할 때 오버플로가 생기는 조건을 찾아본다.

### 면접 답변의 기준 문장

> Flex는 일차원 배치, Grid는 이차원 레이아웃에 강점을 가진 CSS 배치 모델입니다.

**구술 확인:** 위 문장을 외우기보다, 정의와 책임을 구분해 말하고 실제 코드에서 해당 역할을 수행하는 줄을 가리켜 설명한다.

# 핵심 개념을 오해 없이 이해하기 위한 기초 연결

## 필수 기초 연결: HTML 구조와 CSS 표현을 구분하기

HTML은 문서의 의미·구조를 표현하고 CSS는 화면 표현을 제어한다. `display:none`은 요소를 화면 레이아웃에서 제외하지만 **DOM에서 삭제하지 않는다**. 브라우저의 개발자 도구에서 요소가 여전히 존재하는지 확인하라. `visibility:hidden`은 보이지 않지만 일반적으로 레이아웃 공간을 유지한다. 숨김 처리를 인증·인가 수단으로 쓰면 안 된다. 서버는 별도로 접근 권한을 검사해야 한다.

```html
<button id="toggle">토글</button><p id="secret">문구</p>
<style>.hidden { display: none; }</style>
<script>
  document.querySelector('#toggle').addEventListener('click', () => {
    document.querySelector('#secret').classList.toggle('hidden');
  });
</script>
```

**실습:** `display:none`, `visibility:hidden`, 요소 삭제(`remove()`)를 각각 적용한 뒤 DOM 존재 여부와 공간 점유 여부를 비교한다.

## 개념 경계 정밀 보강 — 실제 코드에서 헷갈리는 지점

> 이 절은 기존 핵심 설명에 추가한 필수 기초 연결 학습이다. 아래 예제는 설명용 최소 코드로, SQL은 예시 테이블이 필요하고 Java는 import/클래스·실행 환경이 필요할 수 있다.


### 경계 1. margin / padding / border

**흔한 오해:** “padding은 요소 바깥쪽 여백이다”

**정확한 구분:** padding은 콘텐츠와 테두리 사이 내부 여백, margin은 테두리 바깥 공간이다. border는 경계선이며 box-sizing에 따라 선언 width의 계산 방식이 달라진다.

**코드·명령 해석:**

```text
.card { width: 200px; padding: 20px; border: 2px solid; box-sizing: border-box; }
```

**확인 방법:** 개발자 도구 Box Model에서 실제 콘텐츠 영역 폭을 확인한다.

**직접 구현:** box-sizing: content-box로 변경하고 전체 폭 차이를 계산하라.

**면접 점검:** “margin / padding / border”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 2. display:none / visibility:hidden / opacity:0

**흔한 오해:** “세 속성은 화면에서만 안 보일 뿐 완전히 같다”

**정확한 구분:** display:none은 일반 레이아웃에서 제거한다. visibility:hidden은 공간을 남기며 보이지 않는다. opacity:0은 투명하게 표시하지만 레이아웃과 포인터 상호작용에 영향을 남길 수 있다.

**코드·명령 해석:**

```text
.a {display:none} .b {visibility:hidden} .c {opacity:0}
```

**확인 방법:** 세 요소의 공간과 클릭 가능성을 비교한다. 접근성 트리 차이는 브라우저와 사용 방식도 확인한다.

**직접 구현:** 키보드 탐색과 접근성 요구사항에 맞는 숨김 방식을 고르라.

**면접 점검:** “display:none / visibility:hidden / opacity:0”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 3. Flexbox / Grid / position

**흔한 오해:** “모든 배치는 position:absolute가 정답이다”

**정확한 구분:** Flexbox는 주로 한 축의 배치, Grid는 행·열의 2차원 배치에 강하다. position은 배치 기준과 위치 지정 방식이며 레이아웃 시스템을 무조건 대체하지 않는다.

**코드·명령 해석:**

```text
.layout {display:grid; grid-template-columns: 1fr 2fr; gap:12px;}
```

**확인 방법:** 화면 너비를 줄여 콘텐츠 넘침을 확인한다.

**직접 구현:** 카드 내부 버튼 정렬은 Flexbox, 페이지 2열은 Grid로 구현하라.

**면접 점검:** “Flexbox / Grid / position”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.
