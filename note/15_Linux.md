## 학습 전 필수 관문 — 프로세스 · 포트 · localhost

> **학습 순서:** 아래 정의를 읽고 → 굵은 용어를 자기 말로 풀고 → 틀린 문장을 반박하고 → 예제를 설명한 다음 → 답안을 가리고 면접처럼 말한다. 비유만 이해한 상태에서는 다음으로 넘어가지 않는다.

### 1. 정확한 정의

프로세스는 실행 중인 프로그램의 인스턴스이고, 포트는 네트워크 통신의 논리적 종단점을 구분하는 번호다. `localhost`는 일반적으로 자기 컴퓨터를 가리키는 이름이다.

### 2. 용어를 구분해야 하는 이유

포트 번호는 프로세스 ID(PID)가 아니다. `127.0.0.1`에만 바인딩한 서비스는 보통 외부에서 직접 접근할 수 없다.

### 3. 새로운 상황에 적용

서버가 8080 포트에서 동작해도 외부 접속이 안 될 때 프로세스·리스닝 주소·방화벽을 나누어 확인한다.

### 4. 면접 질문과 답변 기준

**질문:** 프로세스 · 포트 · localhost의 차이를 정의와 동작을 포함해 설명해 보세요.

**답변 기준:** 프로세스는 실행 단위이고 포트는 네트워크 서비스 식별에 사용됩니다. 접속 문제는 실행 상태, 바인딩 주소, 방화벽 등을 구분해 점검해야 합니다.

### 5. 정답을 가리고 설명하기

1. 위 정의에서 핵심 명사 세 개를 골라 각각 뜻을 설명한다.
2. 위의 **틀린 주장**이 왜 틀렸는지 반례를 든다.
3. 위 상황의 **실행 결과·처리 주체·변경되는 값**을 분리해 설명한다.
4. 답변 기준을 보지 않고 **정의 1문장 → 차이 1문장 → 예시 1문장**으로 말한다.
5. 다음 날 같은 질문에 답하지 못하면 예제가 아니라 **정의**부터 다시 확인한다.

## 1. 프로세스·권한·로그

**정의** — 프로세스는 실행 중인 프로그램 인스턴스이고 Linux 권한은 소유자·그룹·기타 사용자 등의 접근 제어를 표현한다. 로그는 동작·오류의 관찰 기록이다.

**목적과 책임** — 서비스 실행 상태와 실패 원인을 파악한다.

**구별해야 할 개념 / 흔한 오해** — chmod 777은 편한 해결책이 아니라 보안 위험을 만든다.

**실행·처리 흐름** — 서비스 실행 → 프로세스 확인 → 포트·로그 확인 → 원인 수정

**직접 구현·검증** — ps, ss, journalctl 또는 파일 로그로 서버 상태 확인. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 서비스가 안 뜰 때 어떤 순서로 확인하는가?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

프로세스는 실행 중인 프로그램의 인스턴스다. Linux 파일 권한은 소유자·그룹·기타 사용자에 대해 읽기·쓰기·실행 권한을 표현한다. 로그는 실행 중 발생한 사건을 기록한다. 프로세스가 떠 있다고 서비스가 정상이라는 뜻은 아니다.

### 직접 읽고 구현하는 독립 예제

```bash

ls -l app.log
tail -n 30 app.log
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

# 핵심 개념을 오해 없이 이해하기 위한 기초 연결

## 필수 기초 연결: 파일·프로세스·포트·서비스

파일은 디스크의 데이터, 프로세스는 실행 중인 프로그램의 인스턴스, 포트는 네트워크 통신 끝점을 구분하는 번호다. **포트가 열려 있음**과 **HTTP 애플리케이션이 정상 동작함**은 다르다. 프로세스가 살아 있어도 DB 연결 실패로 요청에 500을 반환할 수 있다.

```bash
ps -ef | grep java
ss -ltn
curl -i http://localhost:8080/actuator/health
```

**전제:** 마지막 URL은 Spring Boot Actuator 의존성과 해당 엔드포인트 노출 설정이 있을 때만 동작한다. `curl` 실패 시 DNS/연결 거부/타임아웃/HTTP 오류를 구분한다. 환경 변수에 비밀을 넣더라도 로그와 프로세스 노출 위험을 검토한다.

## 개념 경계 정밀 보강 — 실제 코드에서 헷갈리는 지점

> 이 절은 기존 핵심 설명에 추가한 필수 기초 연결 학습이다. 아래 예제는 설명용 최소 코드로, SQL은 예시 테이블이 필요하고 Java는 import/클래스·실행 환경이 필요할 수 있다.


### 경계 1. 프로세스 / 스레드 / PID

**흔한 오해:** “프로세스와 스레드는 완전히 같은 실행 단위다”

**정확한 구분:** 프로세스는 독립적인 주소 공간 등 실행 자원을 가진 단위이고 스레드는 프로세스 안에서 자원을 공유하며 실행되는 흐름이다. PID는 프로세스 식별자다.

**코드·명령 해석:**

```bash
ps -ef | grep java
ps -T -p <PID>
```

**확인 방법:** 하나의 Java 프로세스에 여러 스레드가 보이는지 확인한다.

**직접 구현:** Tomcat 프로세스가 종료되면 그 스레드들은 어떻게 되는지 설명하라.

**면접 점검:** “프로세스 / 스레드 / PID”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 2. 포트 / PID / 소켓

**흔한 오해:** “8080은 Tomcat 프로세스 ID다”

**정확한 구분:** PID는 프로세스 식별 번호, 포트는 네트워크 종단의 서비스 구분 번호, 소켓은 통신 끝점을 나타낸다. 서로 독립적인 개념이다.

**코드·명령 해석:**

```bash
ss -ltnp | grep :8080
```

**확인 방법:** LISTEN 포트와 소유 프로세스 정보를 연결해서 읽는다.

**직접 구현:** 서버 포트를 8081로 바꿔도 PID가 같은지 비교하라.

**면접 점검:** “포트 / PID / 소켓”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 3. 파일 권한 / 사용자 / sudo

**흔한 오해:** “chmod 777이 권한 문제의 가장 좋은 해결책이다”

**정확한 구분:** 파일 권한은 소유자·그룹·기타 사용자에 대한 읽기/쓰기/실행 권한이다. sudo는 권한 상승 실행 수단이며 777은 과도한 권한을 부여할 수 있다.

**코드·명령 해석:**

```bash
ls -l app.sh
chmod u+x app.sh
```

**확인 방법:** 파일 실행 권한만 추가하고 다른 사용자 쓰기 권한은 부여하지 않는다.

**직접 구현:** 배포 계정과 서비스 계정의 최소 권한을 설계하라.

**면접 점검:** “파일 권한 / 사용자 / sudo”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.
