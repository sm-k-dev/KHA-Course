## 1. 세 가지 방법이 푸는 문제

| 방법 | 무엇을 바꾸나 | 잘 맞는 문제 | 비용 |
|---|---|---|---|
| 프롬프트 설계 | 입력 문장 (지시, 예시, 형식) | 형식 맞추기, 역할 지정, 간단한 변환 | 가장 낮음 |
| RAG | 모델에 넣는 **근거 문서** | 최신 정보, 사내 문서, 출처가 필요한 답 | 검색 인프라와 평가 필요 |
| 파인튜닝 | 모델 **가중치** | 말투, 특정 형식을 안정적으로 반복, 긴 프롬프트를 줄이고 싶을 때 | 데이터 준비, 학습, 재평가 필요 |

**핵심**: RAG는 **지식을 빌려 쓰는** 방법이고, 파인튜닝은 **행동 방식을 배우게 하는** 방법이다. 회사 규정처럼 자주 바뀌는 지식을 파인튜닝으로 넣으면, 규정이 바뀔 때마다 다시 학습해야 한다.

## 2. 판단 순서

1. **프롬프트부터 시도한다.** 지시를 명확히 하고, 예시(few-shot)를 몇 개 넣고, 출력 형식을 정한다. 48장 구조화 출력 검증을 함께 쓴다.
2. **평가 세트를 만든다.** 정답이 있는 질문과 기대 출력을 50개 이상 모은다. 이 기준 없이는 어떤 방법이 나은지 말할 수 없다.
3. **근거가 부족하면 RAG를 붙인다.** 답이 틀리는 이유가 "모델이 모르는 정보"라면 RAG가 맞다. 49장의 recall@k와 권한 필터를 먼저 확인한다.
4. **행동이 문제라면 파인튜닝을 검토한다.** 같은 형식을 수천 번 지켜야 하거나, 프롬프트가 너무 길어서 비용과 지연이 커질 때가 여기에 해당한다.

**순서를 뒤집으면**: 프롬프트도 안 해 보고 파인튜닝부터 하면, 데이터와 학습 비용을 쓰고도 프롬프트로 해결할 수 있었던 문제를 남기게 된다.

### 2.1 판단 사례

| 기능 | 문제 | 선택 | 이유 |
|---|---|---|---|
| 고객 문의 분류 (5개 항목) | 분류 기준 설명만으로 대부분 맞음 | 프롬프트 + 평가 세트 | 근거 문서가 필요 없다 |
| 사내 규정 질의응답 | 규정이 분기마다 바뀜 | RAG | 지식이 자주 바뀌므로 문서를 갈아 끼운다 |
| 상담 응답 말투 통일 | 프롬프트가 1,500 토큰으로 길고 비용이 큼 | 파인튜닝 검토 | 행동을 굳히고 프롬프트를 줄인다 |
| 신입 상담원 교육 자료 생성 | 사실보다 문장 형식이 중요 | 프롬프트 | 파인튜닝 데이터 준비가 과하다 |

## 3. 파인튜닝 데이터 준비

### 3.1 데이터 형식 예시 (JSONL)

한 줄에 예시 하나를 넣는다. 형식은 제공자마다 다르니, 아래는 개념적인 구조다.

```json
{"messages": [{"role": "user", "content": "환불 기간은?"}, {"role": "assistant", "content": "구매 후 14일 이내 가능합니다."}]}
{"messages": [{"role": "user", "content": "배송은 얼마나 걸려요?"}, {"role": "assistant", "content": "보통 2~3영업일입니다."}]}
```

### 3.2 나누기: train, valid, test

| 집합 | 역할 | 쓰는 시점 |
|---|---|---|
| train | 학습에 쓴다 | 학습 |
| valid | 학습 중 점검, 설정 선택 | 학습 중 |
| test | 최종 점수만 낸다 | 마지막 1회 |

**규칙**: test는 여러 번 보지 않는다. test 결과를 보고 데이터를 고치면, test는 더 이상 공정한 점수가 아니다.

**나누는 방법**: 무작위로 나누면 같은 질문이 train과 test에 섞일 수 있다. **ID로 결정적으로 나누면** 재실행해도 같은 집합이 나온다(6절).

## 4. 누출(leakage) 점검

**정의** — 평가에 쓸 질문이나 답이 학습 데이터에 들어가면, 점수가 실제 성능보다 높게 나온다. 이를 누출이라고 한다.

**점검 방법**
- 질문 문장을 정규화(공백, 대소문자, 구두점 제거)하고 train과 test를 비교한다.
- 의미가 같은 질문도 찾는다. "환불은 며칠 안에?"와 "환불 기간은?"처럼 다른 말이지만 같은 질문인 경우다. 임베딩 유사도로 후보를 찾고 사람이 확인한다.

## 5. 비용과 위험

### 5.1 비용 손익분기

파인튜닝의 이득은 **프롬프트를 줄여서 생기는 호출 비용 절감**으로 계산한다. 학습 비용을 회수하는 데 걸리는 기간을 구한다.

```
월 절감액 = (긴 프롬프트 토큰 − 짧은 프롬프트 토큰) × 월 호출 수 × 토큰 단가
손익분기(개월) = 학습 비용 ÷ 월 절감액
```

예시 값(실제 가격이 아니다): 긴 프롬프트 3,000토큰, 짧은 프롬프트 300토큰, 월 10만 회, 1M 토큰당 1달러, 학습 비용 500달러. 월 절감액은 270달러이고 손익분기는 약 1.85개월이다.

**주의**: 이 계산에는 평가, 재학습, 모델 관리 비용이 빠져 있다. 손익분기는 이보다 길어진다고 생각하고 보수적으로 잡는다.

### 5.2 위험

- **안전성 약화**: 파인튜닝한 모델이 원래 모델의 안전 장치를 약화할 수 있다. 52장 AI 보안 점검을 다시 한다.
- **데이터 품질**: 나쁜 예시는 모델의 나쁜 습관이 된다. 샘플을 사람이 검수한다.
- **되돌리기**: 프롬프트는 몇 분이면 되돌릴 수 있지만, 파인튜닝 모델은 이전 버전을 보관하고 배포 경로를 유지해야 되돌릴 수 있다.

## 6. 검증 코드 (JDK 25에서 실행)

```java
import java.util.*;

public class FineTuneCheck {
    // 같은 ID는 항상 같은 쪽에 들어간다 (String.hashCode는 값이 정해져 있어서 재실행해도 같다)
    static String split(String id) {
        int h = Math.floorMod(id.hashCode(), 10);
        return h < 8 ? "train" : (h == 8 ? "valid" : "test");
    }

    public static void main(String[] args) {
        Map<String, Integer> counts = new TreeMap<>();
        for (int i = 1; i <= 1000; i++) counts.merge(split("q" + i), 1, Integer::sum);
        System.out.println("split counts = " + counts);
        System.out.println("stable: " + split("q42").equals(split("q42")));

        // 누출 점검: 학습과 테스트에 같은 질문이 있으면 안 된다
        List<String> trainQ = List.of("환불 기간은?", "배송은 얼마나?", "비밀번호 재설정은?");
        List<String> testQ = List.of("환불은 며칠 안에?", "배송은 얼마나?");
        Set<String> leak = new HashSet<>(trainQ);
        leak.retainAll(new HashSet<>(testQ));
        System.out.println("leaked questions = " + leak);

        // 비용 손익분기 (예시 단가와 호출 수, 실제 가격이 아님)
        double unitPricePerMTok = 1.0;      // 1M 토큰당 가격 (가정)
        int promptLongTok = 3000, promptShortTok = 300;
        int callsPerMonth = 100_000;
        double trainingCost = 500.0;        // 학습 1회 비용 (가정)
        double monthlySaving = (promptLongTok - promptShortTok) * (double) callsPerMonth / 1_000_000 * unitPricePerMTok;
        System.out.printf("monthly saving = %.2f%n", monthlySaving);
        System.out.printf("break-even months = %.2f%n", trainingCost / monthlySaving);
    }
}
```

**실행 결과 (확인함)**

```
split counts = {test=100, train=800, valid=100}
stable: true
leaked questions = [배송은 얼마나?]
monthly saving = 270.00
break-even months = 1.85
```

**결과 읽기**
- 같은 코드로 다시 실행해도 분할 결과가 같다. 재현 가능한 분할이다.
- "배송은 얼마나?"가 train과 test 양쪽에 있어서 누출로 잡혔다. 이 질문은 test에서 빼거나 train에서 뺀다.
- 손익분기 계산은 예시 단가이므로, 실제 프로젝트에서는 제공자의 가격표와 실제 호출 기록으로 다시 계산한다.

## 7. 실습 과제 (설계 과제)

1. 본인 프로젝트의 AI 기능 하나를 고른다. (예: 게시글 요약, 고객 문의 분류)
2. 그 기능을 **프롬프트, RAG, 파인튜닝** 세 방법으로 바꿨을 때 각각의 장점과 위험을 표로 적는다.
3. 질문 50개를 모아 6절 방식으로 train, valid, test로 나누고, 누출 여부를 확인한다.
4. 실제 호출 기록에서 월 호출 수와 평균 프롬프트 길이를 뽑아 손익분기를 계산한다.

- [ ] 프롬프트, RAG, 파인튜닝이 각각 무엇을 바꾸는지 구분할 수 있다.
- [ ] 파인튜닝보다 프롬프트와 평가 세트를 먼저 만들어야 하는 이유를 설명할 수 있다.
- [ ] train, valid, test의 역할을 구분하고, test를 여러 번 보면 안 되는 이유를 설명할 수 있다.

- [ ] 손익분기 기간을 계산하고, 계산에 빠진 비용을 말할 수 있다.
- [ ] 지식이 자주 바뀌는 정보를 파인튜닝으로 넣으면 안 되는 이유를 설명할 수 있다.
