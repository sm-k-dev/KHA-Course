# 모델 선택 판단: 프롬프트, RAG, 파인튜닝 중 무엇을 고를까

> 중요도: **B** · 이 장의 목표: 프롬프트 설계, RAG, 파인튜닝이 각각 해결하는 문제를 구분하고, 실제 프로젝트에서 어떤 순서로 시도할지 기준을 세운다.

> 2026-11-23 추가 장 (로드맵 2순위 "파인튜닝 판단 기준" 항목, 48장 LLM 평가와 49장 RAG 뒤에 둠). 이 장은 개념과 판단 순서를 다루며 코드 실행 예제는 없다. 파인튜닝 실습은 학습 데이터와 GPU 환경이 필요해서 이 교재 범위에서 실행하지 않는다.

---

## 1. 세 가지 방법이 푸는 문제

| 방법 | 무엇을 바꾸나 | 잘 맞는 문제 | 비용 |
|---|---|---|---|
| 프롬프트 설계 | 입력 문장 (지시, 예시, 형식) | 형식 맞추기, 역할 지정, 간단한 변환 | 가장 낮음 |
| RAG | 모델에 넣는 **근거 문서** | 최신 정보, 사내 문서, 출처가 필요한 답 | 검색 인프라와 평가 필요 |
| 파인튜닝 | 모델 **가중치** | 말투, 특정 형식을 안정적으로 반복, 짧은 지연 시간이 중요할 때 | 데이터 준비, 학습, 재평가 필요 |

**핵심**: RAG는 **지식을 빌려 쓰는** 방법이고, 파인튜닝은 **행동 방식을 배우게 하는** 방법이다. 회사 규정처럼 자주 바뀌는 지식을 파인튜닝으로 넣으면, 규정이 바뀔 때마다 다시 학습해야 한다.

---

## 2. 판단 순서

1. **프롬프트부터 시도한다.** 지시를 명확히 하고, 예시(few-shot)를 몇 개 넣고, 출력 형식을 정한다. 48장 구조화 출력 검증을 함께 쓴다.
2. **평가 세트를 만든다.** 정답이 있는 질문과 기대 출력을 50개 이상 모은다. 이 기준 없이는 어떤 방법이 나은지 말할 수 없다.
3. **근거가 부족하면 RAG를 붙인다.** 답이 틀리는 이유가 "모델이 모르는 정보"라면 RAG가 맞다. 49장의 recall@k와 권한 필터를 먼저 확인한다.
4. **행동이 문제라면 파인튜닝을 검토한다.** 같은 형식을 수천 번 지켜야 하거나, 프롬프트가 너무 길어서 비용과 지연이 커질 때가 여기에 해당한다.

**순서를 뒤집으면**: 프롬프트도 안 해 보고 파인튜닝부터 하면, 데이터와 학습 비용을 쓰고도 프롬프트로 해결할 수 있었던 문제를 남기게 된다.

---

## 3. 파인튜닝을 고려할 때 확인할 것

| 질문 | 예 | 아니오 |
|---|---|---|
| 학습 데이터가 1,000쌍 이상 있는가? | 검토 가능 | 프롬프트와 RAG를 먼저 |
| 데이터에 개인정보나 비밀이 없는가? | 정제 후 진행 | 진행하지 않음 |
| 데이터 품질을 사람이 검수할 수 있는가? | 샘플을 검수 | 데이터가 나빠서 모델도 나빠짐 |
| 지식이 자주 바뀌지 않는가? | 파인튜닝 가능 | RAG로 분리 |
| 프롬프트 개선으로는 목표 점수에 못 가는가? | 파인튜닝 검토 | 프롬프트 계속 개선 |

**데이터 함정**: 학습 데이터에 평가 세트 질문이 섞이면 점수가 실제보다 높게 나온다. 학습과 평가 데이터를 **먼저 분리**한다.

---

## 4. 비용과 위험

- **비용**: 데이터 정제, 학습 실행, 재평가, 모델 버전 관리, 배포 후 모니터링.
- **위험**: 파인튜닝한 모델이 원래 모델의 안전 장치를 약화할 수 있다. 52장 AI 보안 점검을 다시 한다.
- **되돌리기**: 프롬프트는 몇 분이면 되돌릴 수 있지만, 파인튜닝 모델은 이전 버전을 보관하고 배포 경로를 유지해야 되돌릴 수 있다.

## 5. 실습 과제 (설계 과제, 실행 없음)

1. 본인 프로젝트의 AI 기능 하나를 고른다. (예: 게시글 요약, 고객 문의 분류)
2. 그 기능을 **프롬프트, RAG, 파인튜닝** 세 방법으로 바꿨을 때 각각의 장점과 위험을 표로 적는다.
3. 판단 순서 1–4단계를 따라, 지금 단계에서 해야 할 일 하나를 정하고 이유를 쓴다.
