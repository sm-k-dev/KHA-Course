## 학습 전 필수 관문 — Git · GitHub · staging · commit

> **학습 순서:** 아래 정의를 읽고 → 굵은 용어를 자기 말로 풀고 → 틀린 문장을 반박하고 → 예제를 설명한 다음 → 답안을 가리고 면접처럼 말한다. 비유만 이해한 상태에서는 다음으로 넘어가지 않는다.

### 1. 정확한 정의

Git은 분산 버전 관리 도구이고 GitHub는 Git 저장소 호스팅과 협업 기능을 제공하는 서비스다. staging은 다음 커밋에 포함할 변경을 선택하는 단계다.

### 2. 용어를 구분해야 하는 이유

`git add`는 원격 저장소 업로드가 아니다. `git commit`도 `git push`와 다르다.

### 3. 새로운 상황에 적용

파일 수정 후 add 없이 commit했을 때와 add·commit·push를 순서대로 실행했을 때 원격 반영 차이를 설명한다.

### 4. 면접 질문과 답변 기준

**질문:** Git · GitHub · staging · commit의 차이를 정의와 동작을 포함해 설명해 보세요.

**답변 기준:** Git은 로컬에서 변경 이력을 관리하며, add는 스테이징, commit은 로컬 이력 기록, push는 원격에 커밋을 전달하는 작업입니다.

### 5. 정답을 가리고 설명하기

1. 위 정의에서 핵심 명사 세 개를 골라 각각 뜻을 설명한다.
2. 위의 **틀린 주장**이 왜 틀렸는지 반례를 든다.
3. 위 상황의 **실행 결과·처리 주체·변경되는 값**을 분리해 설명한다.
4. 답변 기준을 보지 않고 **정의 1문장 → 차이 1문장 → 예시 1문장**으로 말한다.
5. 다음 날 같은 질문에 답하지 못하면 예제가 아니라 **정의**부터 다시 확인한다.

## 1. 작업 트리·스테이지·커밋

**정의** — 작업 트리는 현재 파일 상태, 인덱스(스테이징 영역)는 다음 커밋에 포함할 스냅샷, 커밋은 부모와 트리 등을 참조하는 버전 기록이다.

**목적과 책임** — 변경 범위를 검토하고 재현 가능한 이력을 남긴다.

**구별해야 할 개념 / 흔한 오해** — git add는 원격 업로드가 아니며 git commit은 자동 push가 아니다.

**실행·처리 흐름** — 수정 → git diff → git add → git diff --cached → commit → push

**직접 구현·검증** — 두 파일 중 하나만 스테이징하여 커밋. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — git add와 git commit의 역할은?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

Git 작업 트리는 체크아웃된 파일 상태, 인덱스(스테이지)는 다음 커밋에 포함할 스냅샷 준비 영역, 커밋은 저장소 기록의 스냅샷이다. `git add`는 서버 업로드가 아니라 인덱스 갱신이다.

### 직접 읽고 구현하는 독립 예제

```bash
git status
git add README.md
git diff --cached
git commit -m "docs: 개념 정의 보강"
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

커밋 전후 git status와 git log를 비교한다.

### 스스로 작성할 변형 실습

수정 후 git add를 다시 하지 않으면 어떤 버전이 커밋되는지 실험한다.

### 면접 답변의 기준 문장

> Git의 스테이지는 다음 커밋에 기록할 변경을 준비하는 영역입니다.

**구술 확인:** 위 문장을 외우기보다, 정의와 책임을 구분해 말하고 실제 코드에서 해당 역할을 수행하는 줄을 가리켜 설명한다.


### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“작업 트리는 현재 파일 상태, 인덱스(스테이징 영역)는 다음 커밋에 포함할 스냅샷, 커밋은 부모와 트리 등을 참조하는 버전 기록이다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“git add는 원격 업로드가 아니며 git commit은 자동 push가 아니다.”* 반례를 하나 만들어 본다.

## 2. 브랜치·PR·충돌

**정의** — Git 브랜치는 커밋을 가리키는 이동 가능한 참조이며 Pull Request는 GitHub 등 호스팅 서비스의 변경 제안·리뷰 절차다.

**목적과 책임** — 작업 분리와 변경 검토를 돕는다.

**구별해야 할 개념 / 흔한 오해** — Git 브랜치와 GitHub PR은 같은 기능이 아니다.

**실행·처리 흐름** — 작업 브랜치 → 커밋 → push → PR → 리뷰 → merge

**직접 구현·검증** — 같은 파일을 두 브랜치에서 수정해 충돌 해결. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

# 핵심 개념을 오해 없이 이해하기 위한 기초 연결

## 필수 기초 연결: 파일의 현재 상태와 기록은 다르다

작업 디렉터리는 실제 편집 중인 파일, 스테이징 영역(index)은 다음 커밋에 포함할 스냅샷의 준비 상태, 커밋은 Git 객체 데이터베이스에 기록된 스냅샷이다. `git add`는 원격 저장소에 업로드하지 않으며 `git commit`도 곧바로 GitHub에 반영되지 않는다. `git push`가 원격에 관련 커밋을 전송한다.

```bash
git status
git add README.md
git diff --cached
git commit -m "docs: README 설명 보강"
git log --oneline -3
```

**실습:** 파일을 수정한 뒤 `git diff`와 `git diff --cached`의 차이를 확인한다. 실수로 비밀키를 커밋했다면 삭제 커밋만으로 과거 기록에서 비밀이 사라지지 않으므로 즉시 키를 폐기·교체해야 한다.

## 개념 경계 정밀 보강 — 실제 코드에서 헷갈리는 지점

> 이 절은 기존 핵심 설명에 추가한 필수 기초 연결 학습이다. 아래 예제는 설명용 최소 코드로, SQL은 예시 테이블이 필요하고 Java는 import/클래스·실행 환경이 필요할 수 있다.


### 경계 1. Git / GitHub / 원격 저장소

**흔한 오해:** “GitHub가 없으면 Git 커밋을 못 한다”

**정확한 구분:** Git은 로컬 버전 관리 시스템이고 GitHub는 Git 저장소 호스팅과 협업 기능을 제공하는 서비스다. commit은 로컬에서 가능하고 push가 원격에 전송한다.

**코드·명령 해석:**

```bash
git init
git add .
git commit -m "첫 커밋"
git remote -v
```

**확인 방법:** 네트워크 없이 로컬 commit이 가능한지 확인한다.

**직접 구현:** 원격 저장소를 연결한 뒤 push와 fetch의 차이를 설명하라.

**면접 점검:** “Git / GitHub / 원격 저장소”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 2. working tree / staging / commit

**흔한 오해:** “git add는 GitHub에 업로드한다”

**정확한 구분:** working tree는 작업 파일, index/staging은 다음 커밋 후보 스냅샷, commit은 로컬 기록이다. push는 원격 반영이다.

**코드·명령 해석:**

```bash
git status
git add README.md
git diff --cached
git commit -m "docs: 수정"
```

**확인 방법:** git diff와 git diff --cached의 출력 차이를 관찰한다.

**직접 구현:** 한 파일의 변경 중 일부만 stage하여 커밋하라.

**면접 점검:** “working tree / staging / commit”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 3. merge / rebase / reset / revert

**흔한 오해:** “revert는 과거 커밋을 삭제한다”

**정확한 구분:** merge는 이력 합치기, rebase는 커밋 기반을 재배치하며 해시를 바꿀 수 있다. reset은 HEAD/인덱스/작업트리 위치를 조정하고 revert는 취소 내용을 새 커밋으로 기록한다.

**코드·명령 해석:**

```bash
git log --oneline
git revert <commit-hash>
```

**확인 방법:** 공유 브랜치에서 revert가 왜 안전한 선택이 되는지 설명한다.

**직접 구현:** 연습 저장소에서 merge 충돌을 만들고 해결하라.

**면접 점검:** “merge / rebase / reset / revert”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.
