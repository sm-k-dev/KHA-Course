# 기술 커뮤니케이션: 결정을 쓰고, 발표하고, 면접에서 설명한다

> 중요도: **B** · 이 장의 목표: 기술 결정 기록(ADR)을 쓰고, 발표 구조를 짜고, 기술 면접에서 선택의 이유와 대안, 트레이드오프를 말할 수 있다.

> 2026-11-23 추가 장 (목표 점검 결과 보강: 목표 문서 3절 "문서·발표·면접에서 설명"의 빈 부분). 이 장은 글쓰기와 말하기 절차를 다루며 실행 코드는 없다. 예시 문서는 실제 프로젝트 내용으로 바꿔서 쓴다.

---

## 1. 왜 필요한가

개발자의 평가는 코드만으로 끝나지 않는다. "왜 이 기술을 골랐는지", "어떤 대안을 버렸는지", "실패했을 때 무엇을 배웠는지"를 설명하지 못하면 동료도 면접관도 판단할 수 없다. 이 장은 그 설명을 **문서, 발표, 면접**에서 같은 틀로 하는 법을 다룬다.

---

## 2. 결정 기록 (ADR, Architecture Decision Record)

**정의** — ADR은 중요한 기술 결정을 **상황, 결정, 결과**로 짧게 남기는 문서다. 한 결정당 한 문서를 쓴다.

**ADR 템플릿**

| 항목 | 내용 |
|---|---|
| 제목 | 결정을 한 문장으로 (예: "세션 대신 JWT를 쓰지 않고 서버 세션 사용") |
| 상태 | 제안, 승인, 폐기, 대체됨 |
| 상황 | 어떤 문제와 제약이 있었는가 |
| 검토한 대안 | 최소 두 개. 각각의 장점과 단점 |
| 결정 | 무엇을 골랐는가, 왜 |
| 결과 | 좋아진 것, 감수해야 할 것 |
| 되돌리는 조건 | 언제 이 결정을 다시 볼 것인가 |

**예시 (짧게)**

> **제목**: 로그인 상태를 서버 세션으로 관리한다.
> **상황**: 사내 관리자 페이지이고 동시 접속이 적다. 즉시 강제 로그아웃이 필요하다.
> **대안**: JWT(만료 전까지 취소 어려움), 세션(서버 저장소 필요).
> **결정**: 세션. 강제 로그아웃이 즉시 되고 구현이 단순하다.
> **결과**: 서버 저장소 관리가 필요하다. 여러 대 서버라면 세션 공유가 필요하다.
> **되돌리는 조건**: 사용자가 수만 명이 되어 세션 저장소 부하가 커지면.

**핵심 규칙**: 결정 문서는 **결정 당시의 정보**로 쓴다. 나중에 결과가 나빠도 과거 문서를 고쳐 쓰지 않고, 새 ADR로 "대체됨"을 기록한다.

---

## 3. 발표 구조

기술 발표는 "무엇을 만들었나"보다 **문제, 선택, 결과**를 먼저 말한다.

| 순서 | 내용 | 시간 (10분 기준) |
|---|---|---|
| 1. 문제 | 어떤 불편이나 위험이 있었는가 | 1분 |
| 2. 목표와 제약 | 성공 기준과 지켜야 할 조건 | 1분 |
| 3. 선택 | 대안 두 개와 고른 이유 | 3분 |
| 4. 구현 핵심 | 가장 중요한 구조 하나를 깊게 | 3분 |
| 5. 결과 | 숫자로 보여 준다 (응답 시간, 오류율, 작업 시간) | 1분 |
| 6. 배운 것과 다음 | 실패와 개선 계획 | 1분 |

**슬라이드 원칙**: 한 장에 메시지 하나. 코드는 세 줄 이내로 발췌하고, 전체 코드는 저장소 링크로 준다.

**질문 대응**: 모르는 질문은 "확인하지 않았습니다. 확인하면 이렇게 하겠습니다"라고 말한다. 추측으로 답하지 않는다.

---

## 4. 기술 면접에서 설명하는 법

면접관은 "정답"보다 **판단 과정**을 본다. 다음 순서를 따른다.

1. **정의**: 한 문장으로 정확히 말한다.
2. **이유**: 왜 이 기술이나 방식이 필요한지.
3. **대안과 비교**: 다른 선택지 하나 이상, 언제 그쪽이 나은지.
4. **트레이드오프**: 얻는 것과 잃는 것을 함께 말한다.
5. **내 경험**: 실제로 적용하거나 측정한 사례 하나.

**예 (캐시)**: "캐시는 자주 읽는 데이터를 빠른 저장소에 두는 방법입니다. 저는 상품 목록에 캐시-어사이드를 적용했습니다. 대안인 쓰기 스루는 쓰기가 느려지므로 읽기가 많은 목록에는 맞지 않았습니다. 대신 캐시 무효화 시점을 잘못 잡으면 오래된 값이 보이는 위험을 감수했고, 수정 시 키를 지우도록 했습니다."

**주의**: "잘 안 됐던 것"을 말할 때는 원인과 조치까지 말한다. 실패를 숨기면 질문이 깊어진다.

---

## 5. 흔한 실수

| 실수 | 문제 | 고치는 법 |
|---|---|---|
| 기술 이름 나열 | 왜 골랐는지 없음 | 문제 → 선택 → 이유 순서 |
| 결과 없는 설명 | 잘했는지 알 수 없음 | 숫자나 관찰 결과 한 개 |
| "우리 팀이" 중심 | 내 역할이 안 보임 | 내가 한 결정과 행동을 주어로 |
| 모든 기술을 다 안다고 말함 | 깊이 질문에서 막힘 | 아는 범위와 모르는 범위를 구분 |

---

## 6. 실습 과제

1. 최근 프로젝트에서 중요한 결정 하나를 골라 ADR로 쓴다. 대안은 최소 두 개 적는다.
2. 그 결정을 10분 발표 구조에 맞춰 3분 분량으로 말해 본다. 녹음해서 "정의-이유-대안-트레이드오프-경험" 순서를 지켰는지 확인한다.
3. 면접 질문 "왜 그 기술을 골랐나요?"에 대해 답변을 다섯 문장 이내로 쓴다.

---

## 단원 통과 기준

- [ ] ADR의 항목 일곱 개를 채우고, 결정 당시 정보로 쓴다는 원칙을 설명할 수 있다.
- [ ] 기술 발표를 문제, 목표, 선택, 구현, 결과, 다음 순서로 구성할 수 있다.
- [ ] 기술 질문에 정의, 이유, 대안, 트레이드오프, 경험 순서로 답할 수 있다.
- [ ] 모르는 질문에 추측하지 않고 확인 계획을 말할 수 있다.
