## 1. 서브넷과 CIDR

**정의** — IP 주소에서 앞부분은 네트워크, 뒷부분은 호스트를 나타낸다. `192.168.10.37/26`에서 `/26`은 앞 26비트가 네트워크 부분이라는 뜻이다.

**계산 방법**
- **네트워크 주소:** IP와 마스크를 AND 연산. `192.168.10.37` & `/26` → `192.168.10.0`
- **브로드캐스트:** 호스트 부분을 모두 1로 만든 주소 → `192.168.10.63`
- **사용 가능 호스트:** 전체 주소 수 − 2 (네트워크 주소와 브로드캐스트 제외). `/26`은 64 − 2 = 62개.

**자주 쓰는 크기**

| 프리픽스 | 주소 수 | 사용 가능 호스트 | 쓰임 |
|---|---|---|---|
| /24 | 256 | 254 | 작은 사무실 대역 |
| /26 | 64 | 62 | 부서 단위 |
| /30 | 4 | 2 | 라우터 두 대를 잇는 점대점 링크 |

**구현 (검증 완료)**

```java
static String networkOf(String ip, int prefix) {
    long addr = toLong(ip);
    long mask = prefix == 0 ? 0 : (0xFFFFFFFFL << (32 - prefix)) & 0xFFFFFFFFL;
    return toIp(addr & mask);
}
static long hostCount(int prefix) { return (1L << (32 - prefix)) - 2; }
```

- **확인:** `192.168.10.37/26`의 네트워크 주소는 `192.168.10.0`, 브로드캐스트는 `192.168.10.63`, 호스트 수는 62다. `/24`는 254, `/30`은 2다.

**AWS와의 연결:** VPC의 CIDR과 서브넷을 나누는 방식이 같다(44장). 서브넷이 너무 작으면 나중에 서버를 더 못 붙인다.

## 2. 스위치와 VLAN, STP

**스위치 (2계층)** — MAC 주소를 보고 목적지 포트로만 프레임을 보낸다. 같은 스위치 안의 장치끼리 통신한다.

**VLAN** — 한 스위치를 논리적으로 여러 네트워크로 나눈다. 부서별로 망을 분리하는 데 쓴다. VLAN끼리는 라우터를 거쳐야 통신한다.

**트렁크** — 여러 VLAN이 스위치 사이의 한 선을 공유하는 방식이다. 태그(802.1Q)로 어떤 VLAN의 프레임인지 구분한다.

**STP (스패닝 트리)** — 스위치를 여러 줄로 연결하면 루프가 생겨 프레임이 무한히 돌 수 있다. STP는 중복 경로를 막아 루프를 없앤다. 루트 브리지는 우선순위가 가장 낮은 스위치이고, 우선순위가 같으면 MAC 주소가 낮은 쪽이다.

**검증 완료:** 우선순위 4096인 스위치 두 대(MAC이 `...:05`, `...:09`)와 32768인 스위치 한 대가 있을 때, 루트는 `...:05`다.

**EtherChannel** — 여러 물리 링크를 하나의 논리 링크로 묶어 대역폭을 늘리고 한 링크가 죽어도 유지한다.

## 3. 라우팅

**라우터 (3계층)** — IP 주소를 보고 다른 네트워크로 패킷을 보낸다.

- **정적 라우팅:** 사람이 경로를 직접 적는다. 작은 네트워크에 적합하고, 변화에 대응하지 못한다.
- **동적 라우팅:** 라우터끼리 경로 정보를 교환한다.
  - **RIP:** 홉 수(거리)만 본다. 작은 망에서만 쓴다.
  - **OSPF:** 링크 상태를 공유하고 최단 경로를 계산한다. 기업 내부망에서 많이 쓴다.
  - **EIGRP:** 시스코 계열 장비의 거리 벡터 프로토콜. 빠르게 수렴한다.
  - **BGP:** 인터넷에서 서로 다른 조직(자율 시스템) 사이의 경로를 교환한다.

**AWS와의 비교:** VPC의 라우팅 테이블은 "목적지 CIDR → 다음 대상"을 적는 정적 라우팅과 같은 개념이다. 인터넷 게이트웨이, NAT 게이트웨이가 다음 대상이 된다.

## 4. 보안 장비와 접근 제어

- **ACL (접근 제어 목록):** 출발지, 목적지, 포트를 보고 허용 또는 차단을 정한다. 위에서부터 차례로 검사하고 처음 맞은 규칙을 적용한다.
- **방화벽:** 연결 상태를 추적해서 허용된 흐름만 통과시킨다. ACL보다 상태 정보를 더 쓴다.
- **IDS/IPS:** 침입 탐지(IDS)는 알리고, 침입 방지(IPS)는 차단한다. 패턴 기반과 이상 탐지 기반이 있다.
- **VPN:** 공용망 위에 암호화된 터널을 만들어 원격에서 내부망에 안전하게 접속한다.
- **SSH:** 원격 장비에 암호화된 셸로 접속한다. 비밀번호 로그인보다 키 기반 로그인을 쓰고, 기본 포트와 root 직접 로그인을 막는 설정을 한다.
- **Zero Trust:** 내부망이라도 믿지 않고, 요청마다 신원과 권한을 확인한다.

---

## 5. 관측 프로토콜

- **SNMP:** 장비의 상태(CPU, 인터페이스, 오류 수)를 수집하는 프로토콜. 메트릭 수집의 한 방식이다(46장).
- **Syslog:** 장비와 서버의 로그를 중앙 서버로 보내는 방식. 여러 장비의 로그를 한곳에서 본다.
- **NTP:** 장비들의 시간을 맞춘다. 로그의 시간이 어긋나면 사고 원인을 추적할 수 없다.

---

## 6. 주소 체계와 서비스

- **DHCP:** 장치에 IP, 게이트웨이, DNS 주소를 자동으로 준다. 임대 기간이 있다.
- **NAT/PAT:** 사설 주소를 공인 주소로 바꿔서 여러 장치가 하나의 공인 주소로 인터넷에 나간다. PAT는 포트 번호로 구분한다.
- **DNS:** 도메인 이름을 IP 주소로 바꾼다. 자세한 동작은 11장에서 다뤘다.
- **IPv6:** 주소가 128비트다. 주소가 넉넉해서 NAT 없이 직접 연결하는 구조가 가능하다.
- **무선(WLAN):** 전파를 쓰므로 암호화(WPA2/WPA3)와 인증이 필수다. 공용 무선망은 신뢰하지 않는다.
- **VoIP:** 음성을 IP 패킷으로 보낸다. 지연과 흔들림에 민감해서 QoS로 음성 트래픽을 우선한다.

## 9. OSI 7계층과 TCP/IP

| 계층 | 이름 | 하는 일 | 예 |
|---|---|---|---|
| 7 | 응용 | 사용자가 쓰는 서비스 | HTTP, DNS, SMTP |
| 6 | 표현 | 데이터 형식과 암호화 | TLS, 인코딩 |
| 5 | 세션 | 연결의 시작과 끝 관리 | 세션 관리 |
| 4 | 전송 | 신뢰성 있는 전달, 포트 | TCP, UDP |
| 3 | 네트워크 | IP 주소와 경로 | IP, 라우터 |
| 2 | 데이터 링크 | 같은 망 안의 전달, MAC 주소 | 이더넷, 스위치 |
| 1 | 물리 | 전기 신호와 케이블 | 케이블, 광 신호 |

- **TCP/IP 모델:** 실무에서는 4계층(응용, 전송, 인터넷, 네트워크 접근)으로 묶어 설명한다.
- **캡슐화:** 위에서 내려갈 때 각 계층이 헤더를 붙이고, 받는 쪽은 반대로 벗긴다.
- **면접 기준:** "OSI 7계층은 통신을 역할별로 나눈 기준 모델이고, 실무는 TCP/IP 4계층으로 설명합니다. 문제가 생기면 계층별로 좁혀 갑니다."

## 11. 방화벽 (Firewall)

- **정의:** 허용된 연결만 통과시키는 장비나 소프트웨어. 출발지, 목적지, 포트, 상태(연결이 시작됐는지)를 본다.
- **ACL과의 차이:** ACL은 규칙을 위에서부터 검사하는 단순 필터다. 방화벽은 연결 상태를 추적해서 응답 패킷까지 자연스럽게 허용한다.
- **구성:** 기본 정책을 거부로 두고, 필요한 포트만 허용한다.
- **면접 기준:** "방화벽은 기본 거부로 두고 필요한 연결만 허용하며, 연결 상태를 추적합니다."

## 12. SDN (소프트웨어 정의 네트워크)

- **정의:** 장비의 제어 기능(어디로 보낼지 결정)을 장비에서 떼어 중앙 컨트롤러가 맡는 구조다. 장비는 전달만 한다.
- **구성:** 제어 평면(컨트롤러)과 데이터 평면(스위치, 라우터). 컨트롤러가 API로 경로를 바꾼다.
- **장점:** 중앙에서 정책을 바꾸고 자동화할 수 있다. 클라우드 네트워크(예: VPC 라우팅)도 같은 생각이다.
- **면접 기준:** "SDN은 경로를 정하는 제어 기능을 중앙 컨트롤러로 옮겨서, 네트워크를 소프트웨어로 바꾸는 구조입니다."

## 13. 패킷 캡처로 원인 찾기 (실습 절차, 미실행)

**정의** — 패킷 캡처는 장비를 지나가는 실제 패킷을 기록해서 "요청이 어디까지 갔는가"를 확인하는 방법이다. 로그에 없는 연결 단계(핸드셰이크, 재전송, 응답 없음)를 볼 수 있다.

**도구**
- **Wireshark:** 그래픽 도구. 캡처 인터페이스를 고르고 표시 필터로 원하는 패킷만 본다.
- **tcpdump:** 명령줄 도구. Linux에서 쓰며, Windows에서는 같은 역할의 도구를 쓴다.

**자주 쓰는 표시 필터 (Wireshark)**
- `tcp.port == 8080`: 특정 포트의 TCP 연결
- `dns`: 이름 조회 요청과 응답
- `tls.handshake`: TLS 핸드셰이크 단계
- `ip.addr == 10.0.0.5`: 특정 주소와 주고받는 패킷

**절차 (본인 소유 서버에서만)**
1. 캡처를 먼저 켜고, 테스트 서버에 요청 한 번을 보낸다.
2. 필터로 해당 포트만 본다.
3. TCP 세 번 핸드셰이크(SYN → SYN-ACK → ACK), 요청, 응답 순서를 확인한다.
4. 응답이 없으면 어느 단계에서 멈췄는지 적는다: 이름 조회 실패(DNS), 연결 실패(TCP), 인증서 오류(TLS), 애플리케이션 오류(HTTP 500).

**tcpdump 예 (Linux, 관리자 권한 필요)**
```
sudo tcpdump -i any -nn port 8080
```

**안전 원칙:** 패킷 캡처는 본인 장비나 명시적 허가를 받은 네트워크에서만 한다. 남의 트래픽을 몰래 보는 것은 허용되지 않는다. 포트 스캔과 공격 재현도 같은 원칙을 따른다(0·30장).

**검증 상태:** 이 절은 절차와 필터 정의만 적었다. 실제 캡처 실행은 미실행이다. 실행하면 캡처 파일과 결과 표를 이 절에 추가하고 "확인함"으로 바꾼다.

**면접 기준:** "패킷 캡처로 연결이 어느 단계에서 끊기는지 확인하고, 이름 조회, TCP, TLS, 애플리케이션 중 원인을 좁힙니다."
