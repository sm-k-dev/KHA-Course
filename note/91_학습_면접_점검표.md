## 답변 템플릿

> **정의:** X는 무엇이다. **목적:** Y 문제를 해결한다. **책임:** Z를 담당한다. **비교:** A와 달리 B는 ... **예:** 내가 작성한 코드에서는 ...

정의가 불명확할 때 예제부터 암기하지 않는다. 반대로 정의만 외우고 코드를 작성하지 않은 상태도 학습 완료로 표시하지 않는다.

## 기술면접에서 당황하기 쉬운 질문과 응용법 (2026-11-24 추가)

이 절의 질문은 정답 문장을 외우는 용도가 아닙니다. 면접관은 **정해진 답이 없는 상황에서 어떤 순서로 생각하는지**를 봅니다. 아래 답변 틀은 말하는 순서의 예시이고, 내용은 각 장에서 직접 확인한 범위만 근거로 씁니다. 근거 장에 적힌 "미실행" 표시도 그대로 따르세요. 실행하지 않은 것을 실행한 것처럼 말하면 그 자체가 면접 감점입니다.

**공통 답변 순서**: 재현 또는 상황 확인 → 원인 후보 분류 → 가설 하나씩 검증 → 수정 → 재발 방지. 이 순서를 지키면 모르는 질문에서도 말을 이어갈 수 있습니다.

**Q1. 리눅스에서 시스템을 실행했는데 오류가 났습니다. 어떻게 하시겠습니까?**
- **면접관이 보는 것**: 명령어 목록이 아니라 문제를 좁혀 가는 순서.
- **답변 틀**: 언제부터 어떤 요청에서 실패하는지 확인 → 로그의 **처음** 오류 줄 확인 → 프로세스와 포트 상태(`ps`, `ss -tlnp`) → 원인을 하나씩 검증 → 수정 후 같은 명령으로 재확인.
- **근거**: [43장 5절](43_Linux.md). 포트 충돌과 권한 오류는 이 PC의 WSL에서 재현해 해결까지 확인함.
- **함정**: 마지막 오류 줄만 보고 결론 내리기. 여러 설정을 한꺼번에 바꾸기.
- **연습**: 같은 질문에 60초로 답하고, 틀을 벗어난 부분을 표시한다.

**Q2. 운영 중인 서비스 응답이 갑자기 느려졌습니다. 어디부터 보시겠습니까?**
- **면접관이 보는 것**: 병목을 어떤 지표로 나눠 보는지.
- **답변 틀**: 최근 배포나 트래픽 변화 확인 → 느린 구간 나누기(웹 서버, 애플리케이션, DB 커넥션, 외부 호출) → 커넥션 풀 대기와 쿼리 수 확인 → 관측 도구(로그, 지표)로 재확인.
- **근거**: [07-2 커넥션 풀 고갈 실험](07-2_트랜잭션_인덱스_격리.md)(MySQL에서 확인함), [46장 관측성](46_관측성_CICD_데이터파이프라인.md), [38장 부하 테스트](38_부하_테스트.md).
- **함정**: "서버를 늘리면 된다"부터 말하기. 원인 확인 없이 확장하는 것은 답이 아닙니다.

**Q3. 같은 요청이 두 번 들어와서 결제가 두 번 됐습니다. 어떻게 막으시겠습니까?**
- **면접관이 보는 것**: 중복 요청과 동시성을 DB 수준에서 막을 수 있는지.
- **답변 틀**: 중복 요청의 원인 구분(사용자 재클릭, 재시도, 두 서버 동시 처리) → DB에서 막는 방법(유니크 제약, 조건부 UPDATE로 한 문장 처리) → 애플리케이션 방어(요청 식별자)는 보조로 말하기.
- **근거**: [33장 동시성](33_동시성_심화.md)(같은 조건에서 SELECT 후 UPDATE는 20건, 조건부 UPDATE는 10건 성공으로 확인함), [07장 유니크 제약](07_RDBMS.md).
- **함정**: 애플리케이션 `if`문으로만 막겠다고 말하기. 두 요청이 동시에 들어오면 그 검사는 둘 다 통과합니다.

**Q4. 쿼리가 느린데, 인덱스를 추가하면 되나요?**
- **면접관이 보는 것**: 인덱스를 무조건 추가하지 않고 실행 계획을 보는지.
- **답변 틀**: 느린 쿼리를 먼저 특정 → 실행 계획(`EXPLAIN`)으로 풀스캔 여부 확인 → 조건과 정렬에 맞는 인덱스 후보 → 추가 후 같은 계획과 시간 재확인 → 쓰기 비용 함께 고려.
- **근거**: [07장](07_RDBMS.md), [08장 SQL](08_SQL.md). `EXPLAIN` 결과 비교는 이 PC에서 실행하지 않았다면 미실행으로 말하세요.
- **함정**: 인덱스는 쓰기를 느리게 한다는 점을 빼먹기. 실행 계획을 본 적이 없으면 "본 적이 없다"고 말하고 확인 절차를 말하는 쪽이 낫습니다.

**Q5. JWT를 쓰면 로그아웃은 어떻게 하나요? 토큰이 그대로 살아 있지 않나요?**
- **면접관이 보는 것**: 토큰 기반 인증의 한계를 알고 있는지.
- **답변 틀**: JWT는 서명으로 위조는 막지만 서버가 쉽게 취소하지 못한다는 점을 먼저 인정 → 짧은 만료 시간 → 재발급(refresh) 방식 → 필요하면 폐기 목록이나 저장소로 상태 관리하는 비용을 설명.
- **근거**: [31장 3-1절](31_보안_프레임워크_RBAC.md)(JWT 서명 검증 실행 확인함), [32장](32_OAuth_소셜_로그인.md)(재발급 Node 확인함).
- **함정**: "JWT는 안전하니까 로그아웃만 하면 된다"고 말하기. 토큰 자체는 서버에서 지워지지 않습니다.

**Q6. 스프링 실행 중 "No qualifying bean"(빈을 찾을 수 없음) 오류가 납니다. 무엇을 보시겠습니까?**
- **면접관이 보는 것**: 컴포넌트 스캔 범위와 빈 등록 원리를 이해하는지.
- **답변 틀**: 오류 메시지에서 어떤 타입을 찾는지 확인 → 그 클래스에 스테레오타입(`@Service` 등)이 있는지 → 메인 클래스 패키지 아래에 있는지(스캔 범위) → 생성자 주입 대상 타입이 맞는지.
- **근거**: [19장 스캔 범위 오류](19_Spring_Core.md)(`NoSuchBeanDefinitionException`을 실행으로 확인함).
- **함정**: 빈 이름과 타입을 혼동하기. 같은 타입 빈이 여러 개면 다른 오류가 납니다.

**Q7. 목록 화면 하나에서 SQL이 수백 번 나갑니다. 원인과 해결은요?**
- **면접관이 보는 것**: N+1을 말로만 알지 않고 측정해 봤는지.
- **답변 틀**: 로그로 반복 쿼리 패턴 확인 → 연관 로딩 시점(LAZY) 확인 → fetch join, batch size, DTO 조회 중 목적에 맞는 방법 선택 → 쿼리 수로 개선 확인.
- **근거**: [25-2 N+1 비교](25-2_연관관계와_N+1.md)(6/2/1 SQL을 실행으로 확인함), [25-4 기본 로딩 전략](25-4_로딩_운영_MyBatis.md)(학과 3개면 추가 3회).
- **함정**: fetch join을 모든 곳에 쓰기. 컬렉션을 페이징과 함께 쓰면 문제가 생길 수 있습니다.

**Q8. AI가 만든 코드를 어떻게 검증하시나요?**
- **면접관이 보는 것**: 생성물을 그대로 믿지 않는 검증 습관.
- **답변 틀**: 요구사항을 테스트로 먼저 쓰기 → 경계값과 예외 입력 실행 → 시간이나 외부 호출에 대한 방어 확인 → 결과를 DB나 원래 데이터와 대조.
- **근거**: [99장 AI 생성 코드 검증](99_AI_생성코드_검증.md)(결함 목록과 검증 코드 3종을 실행함).
- **함정**: "테스트가 통과했다"만 말하기. 테스트가 무엇을 검사하는지 말해야 합니다.

**Q9. 테스트가 가끔만 실패합니다. 어떻게 하시겠습니까?**
- **면접관이 보는 것**: 간헐적 실패(flaky)의 원인을 좁히는 방법.
- **답변 틀**: 실패 조건 기록(시간, 순서, 데이터) → 공유 상태와 실행 순서 의존 확인 → 시간이나 난수 고정 → 여러 번 반복 실행으로 재현.
- **근거**: [37장 테스트 심화](37_테스트_심화.md), [100장 디버깅](100_디버깅_기본.md).
- **함정**: "다시 돌리면 통과하니까 괜찮다"고 말하기.

### 추가 질문 6개 (2026-11-24)

**Q10. 같은 데이터를 두 트랜잭션이 동시에 읽고 쓰면 무슨 일이 생기나요? 격리 수준은 왜 있나요?**
- **면접관이 보는 것**: 격리 수준을 이름만 아는지, 어떤 이상 현상을 막는지 설명하는지.
- **답변 틀**: 커밋되지 않은 값을 읽는 문제(Dirty Read), 같은 행을 두 번 읽었을 때 값이 바뀌는 문제(Non-repeatable Read), 조건을 만족하는 행이 늘어나는 문제(Phantom Read)를 순서대로 말한다 → 수준이 높을수록 막는 이상 현상이 많고 동시성은 떨어진다 → MySQL InnoDB 기본값이 REPEATABLE READ라는 점을 덧붙인다.
- **근거**: [07-2 격리 수준](07-2_트랜잭션_인덱스_격리.md)의 격리 수준 표. 두 세션으로 이상 현상을 확인한 기록은 [96장](96_전과목_정밀보강_실측.md)에 있다.
- **함정**: 격리 수준을 높이면 항상 안전하다고 말하기. 높은 수준은 대기를 늘리고, 조건부 UPDATE처럼 DB에서 한 문장으로 처리하는 것이 더 실용적일 때도 많다([33장](33_동시성_심화.md)).

**Q11. 배치 작업이 중간에 실패해서 다시 돌렸더니 데이터가 두 번 들어갔습니다. 어떻게 막나요?**
- **면접관이 보는 것**: 멱등성(같은 작업을 여러 번 해도 결과가 같은 성질)을 설계에서 챙기는지.
- **답변 틀**: 재실행 가능한 단위(배치 ID, 행 키)를 정한다 → 중복 방지를 DB 제약으로 건다(유니크 키) → 재실행 결과를 행 수로 확인한다 → 실패 기록(격리 기록)은 멱등하지 않을 수 있으니 따로 중복 키로 관리한다.
- **근거**: [46장 멱등성 절](46_관측성_CICD_데이터파이프라인.md). 같은 배치를 재실행해 `stored`가 늘지 않는 것을 확인했고, 격리 기록은 늘어나는 것도 확인했다.
- **함정**: "재실행하지 않으면 된다"고 말하기. 실패는 항상 생기므로 재실행 가능성을 전제로 설계해야 합니다.

**Q12. 실수로 비밀번호가 들어간 커밋을 푸시했습니다. 어떻게 하시겠습니까?**
- **면접관이 보는 것**: 이력 되돌리기와 비밀 정보 폐기를 구분하는지.
- **답변 틀**: 먼저 비밀 값을 폐기하고 새 값으로 바꾼다(이력을 지워도 이미 노출되었다고 본다) → 이력은 `revert`로 되돌리거나 필요하면 저장소 기록을 정리한다 → 로그와 캐시에 남은 값도 확인한다 → 재발 방지로 저장소 검사 도구를 넣는다.
- **근거**: [01장 3절](01_Git_GitHub.md)의 reflog와 revert·reset 차이는 확인했다. 비밀 값 폐기와 저장소 정리는 [102장](102_시큐어_코딩.md)과 [23장](23_로깅_설정_비밀관리.md)의 원칙이며 실제 폐기 절차는 미실행이다.
- **함정**: `git reset --hard`로 지우면 끝이라고 말하기. 원격에 이미 푸시되었다면 값은 노출된 것으로 봐야 합니다.

**Q13. 브라우저에서 다른 도메인의 API를 부르면 CORS 오류가 납니다. 어떻게 해결하나요?**
- **면접관이 보는 것**: 브라우저의 동일 출처 정책을 이해하는지, 서버 설정과 개발 환경 우회를 구분하는지.
- **답변 틀**: 브라우저가 다른 출처의 응답을 막는 이유를 먼저 설명한다 → 서버가 허용 헤더를 주는 것이 정식 해결 → 개발 중에는 같은 출처로 맞추는 프록시를 쓸 수 있다.
- **근거**: [27장 6절](27_프론트엔드_React_TypeScript.md)에서 Vite 프록시로 같은 출처를 맞춘 화면을 확인했다. 서버에서 CORS 헤더를 설정해 실제 오류를 재현한 것은 미실행이다.
- **함정**: 서버를 열어 모든 출처를 허용하는 것을 해결책으로 말하기. 인증이 붙은 요청에서는 위험할 수 있습니다.

**Q14. 컨테이너 이미지가 너무 큽니다. 원인과 줄이는 방법은요?**
- **면접관이 보는 것**: 이미지가 레이어로 쌓인다는 구조를 아는지.
- **답변 틀**: 이미지는 레이어로 쌓이고, 각 명령이 레이어를 만든다 → 불필요한 빌드 도구와 캐시를 같은 레이어에서 지운다 → 가벼운 베이스 이미지를 고른다 → `docker inspect`나 이미지 목록으로 크기와 레이어를 확인한다.
- **근거**: [44장 3-1절](44_AWS_배포.md)에서 Docker Desktop으로 `docker build`, `docker run`, `docker inspect`를 실행해 레이어 구조를 확인했다. 베이스 이미지를 JDK에서 Alpine JRE로 바꾸자 654MB가 358MB로 줄었다(44장 3-1-2절, 확인함). 다단계 빌드의 효과는 아직 측정하지 않았다(미실행).
- **함정**: 이미지를 줄이려고 레이어를 무조건 합치기. 캐시가 깨져 빌드가 느려질 수 있습니다.

**Q15. 목록의 뒤쪽 페이지가 갈수록 느립니다. OFFSET 대신 무엇을 쓰나요?**
- **면접관이 보는 것**: 페이징 비용의 원인과 대안을 아는지.
- **답변 틀**: OFFSET은 건너뛸 행을 다 세므로 뒤로 갈수록 비싸다 → 마지막으로 본 정렬 값을 기준으로 다음 구간을 가져오는 키셋 방식을 쓴다 → 정렬 기준에 유일한 키(예: id)를 포함한다 → 데이터가 바뀔 때 중복과 누락이 생길 수 있다는 한계를 말한다.
- **근거**: [25-3장 4절](25-3_쿼리.md)의 Page 실행 결과(OFFSET 기반 페이징 결과 확인). 키셋 방식의 실측은 [08장 4-2절](08_SQL.md)에 있다. 30만 행에서 OFFSET은 깊이에 따라 약 150~380ms, 키셋은 약 0.1ms였다. 단 행 생성자 조건은 인덱스를 타지 못해 조건을 풀어 써야 했다.
- **함정**: 인덱스만 추가하면 된다고 말하기. 인덱스가 있어도 OFFSET은 건너뛰는 행을 읽습니다.

**확인 범위 요약**: Q10·Q11·Q14는 교재의 실행 기록을 근거로 했고, Q12·Q13의 해결 절차와 Q14의 다단계 빌드 효과는 미실행으로 표시했습니다. Q15의 키셋 실측은 08장 4-2절에 추가했습니다.

## 구술 기술면접 답변 요령 (2026-11-24 추가)

기술면접은 대부분 구술입니다. 아는 내용을 많이 말하는 것보다 **질문에 맞는 범위를, 정해진 순서로, 근거와 함께** 말하는 것이 점수를 올립니다. 코딩테스트는 별도로 문제를 직접 풀어 연습해야 하므로 이 절은 말로 답하는 방법만 다룹니다.

**1. 답변 구조: 정의 → 이유 → 비교 → 예시 → 선택 근거**
- 첫 문장에 정의를 한 줄로 말합니다. "X는 Y를 해결하기 위한 Z입니다."
- 왜 필요한지 한 문장으로 붙입니다. 면접관은 용어보다 문제 의식을 봅니다.
- 헷갈리기 쉬운 인접 개념과의 차이를 하나 말합니다. 비교가 있으면 이해했다는 신호가 됩니다.
- 내가 실제로 해 본 예를 한 줄 붙입니다.
- 마지막에 "그래서 저는 ~를 선택하겠다"처럼 판단을 말합니다.

**2. 첫 10초: 범위를 먼저 정합니다**
- 질문이 넓으면 답을 시작하기 전에 기준을 말합니다. 예: "운영 환경에서 소규모 서비스라는 가정으로 말씀드리겠습니다."
- 질문이 애매하면 되묻습니다. "배포 환경 기준으로 보는 것인지, 코드 수준으로 보는 것인지 여쭤봐도 될까요?"
- 면접관도 답을 기다리는 동안 생각할 시간이 필요합니다. 침묵보다 "먼저 확인할 것은 세 가지입니다"처럼 구조를 먼저 보여 주세요.

**3. 모를 때: 아는 부분부터, 모르는 부분은 표시하고 확인 방법을 말합니다**
- 모르는 것을 숨기고 추측으로 단정하면 꼬리질문에서 무너집니다.
- 좋은 예: "그 옵션의 정확한 기본값은 기억이 확실하지 않습니다. 대신 공식 문서의 해당 항목을 확인하고, 실행해서 SQL이 어떻게 나가는지 보겠습니다."
- 나쁜 예: "아마 그럴 겁니다" 또는 아무 말 없이 멈추기.
- 교재의 "미실행" 표시도 같은 태도입니다. 확인하지 않은 것은 확인하지 않았다고 말하는 것이 신뢰를 줍니다.

**4. 꼬리질문: 답의 범위를 넘으면 경계를 말합니다**
- "여기까지는 제가 확인한 범위이고, 그 다음은 ~로 확인하겠습니다"처럼 경계를 말하면 대화가 이어집니다.
- 꼬리질문이 같은 개념의 반대 상황이면 장점과 한계를 같이 말합니다. 예: 인덱스는 조회를 빠르게 하지만 쓰기를 느리게 합니다.

**5. 내 실습을 근거로 말합니다**
- "이론상 그렇다"보다 "제가 실행해 보니 이런 결과가 나왔다"가 강합니다.
- 교재에 확인된 결과가 있으면 숫자 하나를 넣습니다. 예: "같은 조건에서 SELECT 후 UPDATE는 20건이 성공했고, 조건부 UPDATE는 10건이었습니다."
- 실행하지 않은 것은 "제가 직접 실행하지는 않았지만 공식 문서 기준으로는 ~입니다"로 구분합니다.

**6. 말의 길이와 속도**
- 처음에는 30초 안에 핵심을 말하고, 면접관이 더 물으면 확장합니다. 처음부터 3분을 말하면 흐름을 잃기 쉽습니다.
- 답을 메모해서 읽지 않습니다. 구조 세 개(정의, 이유, 예시)만 머릿속에 두세요.
- 단어를 빠르게 던지기보다 한 문장씩 끊어 말합니다. 면접관이 받아 적을 시간을 줍니다.

**7. 자주 하는 실수**
- 외운 문장을 줄줄 읊기. 꼬리질문에서 바로 막힙니다.
- "당연히", "간단하게" 같은 말로 어려운 부분을 넘기기.
- 용어를 섞어 쓰기. JPA, Hibernate, Spring Data JPA를 구분하지 못하면 신뢰가 떨어집니다.
- 장점만 말하고 트레이드오프를 빼기.
- 질문의 키워드만 듣고 질문과 다른 주제로 바로 들어가기.

**8. 연습 루틴**
- 1분 답변을 휴대폰으로 녹음하고 다시 듣습니다. 군더더기 말과 "음", "그러니까"가 얼마나 많은지 확인합니다.
- 친구나 스터디원에게 키워드 세 개만 주고 그 주제로 답하게 합니다. 예: "트랜잭션, 격리 수준, 데드락"
- 면접관 역할을 맡은 사람이 꼬리질문을 세 번 던지게 합니다. 답이 막히면 어느 단계(정의, 이유, 예시)에서 막혔는지 기록합니다.

**9. 답변 전 자가 점검 (한 줄씩 체크)**
- [ ] 첫 문장에 정의가 있는가
- [ ] 왜 필요한지 한 문장이 있는가
- [ ] 인접 개념과의 차이가 있는가
- [ ] 내 실습이나 확인된 결과가 근거로 붙었는가
- [ ] 모르는 부분과 확인 방법을 구분했는가
- [ ] 마지막에 선택과 이유를 말했는가
