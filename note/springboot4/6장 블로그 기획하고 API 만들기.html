🎬 애니메이션: 글 한 건이 지나가는 길

  5. ⑤ 리포지터리가 DB에 행을 추가하고, 결과가 다시 위로 올라가 응답으로 돌아갑니다.
  6. ⑤ 리포지터리가 DB에 행을 추가하고, 결과가 다시 위로 올라가 응답으로 돌아갑니다.

1. API와 REST API

API(Application Programming Interface)는 프로그램끼리 주고받는 정해진 창구와 약속입니다. 말이 어렵게 느껴지니 식당에 가는 장면으로 생각해 봅시다.

우리는 주방에 직접 들어가지 않습니다. 대신 점원에게 주문합니다. 점원은 주방에 "이 요리를 만들어 주세요"라고 전달하고, 완성된 요리를 다시 우리에게 가져옵니다. 이때 손님은 클라이언트, 주방은 서버, 점원이 API입니다.

🎬 애니메이션: 손님 → 점원 → 주방 → 점원 → 손님

  1. ① 손님(클라이언트)은 주방(서버)에 직접 가지 않습니다.
  2. ② 손님이 점원(API)에게 주문합니다. 웹에서는 "이 주소로 이런 요청을 해 주세요"에 해당합니다.
  3. ③ 점원은 주방에 조리를 요청합니다. API는 요청을 서버에 그대로 전달하는 역할을 합니다.
  4. ④ 주방이 요리를 완성해 점원에게 돌려주고, 점원은 그 결과를 손님에게 전합니다.
  5. ⑤ 손님은 주방의 구조를 몰라도 주문표 하나로 원하는 결과를 얻습니다. 이것이 API의 장점입니다.
  6. ⑤ 손님은 주방의 구조를 몰라도 주문표 하나로 원하는 결과를 얻습니다. 이것이 API의 장점입니다.

🌐 REST API란?

REST(Representational State Transfer)는 자원(데이터)을 이름(주소)으로 구분하고, 그 자원을 어떻게 다룰지를 HTTP 메서드로 표현하는 설계 방식입니다. 이런 규칙에 맞게 만든 API를 REST API 또는 RESTful API라고 부릅니다.

📌 REST의 핵심 한 문장"주소는 무엇(자원)을, 메서드는 어떻게(행위)를 말한다."

REST API의 장점은 주소와 메서드만 봐도 어떤 일을 하는지 알 수 있다는 점입니다. 상태를 기억하지 않는 방식(무상태)이라서 서버를 여러 대 두기도 쉽습니다. 단점은 정해진 표준 문서가 따로 없어서, 팀끼리 규칙을 미리 맞춰야 한다는 점입니다.

2. REST API 설계 규칙

REST API를 만들 때 지켜야 할 대표 규칙은 두 가지입니다. 첫째, URL에는 동사를 쓰지 않고 자원을 표시합니다. 둘째, 동작은 HTTP 메서드로 표현합니다.

🎬 애니메이션: 같은 주소, 다른 메서드

  1. ① 같은 블로그 글이라도 하고 싶은 일에 따라 주소와 메서드 조합이 달라집니다.
  2. ② 조회는 GET, 목록 조회도 GET입니다. 주소 끝 숫자가 있으면 한 건, 없으면 전체입니다.
  3. ③ 추가는 POST입니다. 주소는 같은 /api/articles를 씁니다. "글 목록" 자원에 새 글을 넣는다는 뜻입니다.
  4. ④ 수정은 PUT, 삭제는 DELETE입니다. 두 경우 모두 한 건을 가리키기 위해 id를 주소에 붙입니다.
  5. ④ 수정은 PUT, 삭제는 DELETE입니다. 두 경우 모두 한 건을 가리키기 위해 id를 주소에 붙입니다.

✅ 규칙 1: URL에는 동사를 쓰지 않는다

잘못된 예이유좋은 예
/get-article?id=1get이라는 동사가 주소에 있음GET /api/articles/1
/articles/show/1show라는 동사가 있음GET /api/articles/1
/articles/delete/1행위를 주소에 적음DELETE /api/articles/1
📌 왜 동사를 빼나요?같은 기능을 어떤 개발자는 get, 어떤 개발자는 show로 부르면 주소가 제각각이 됩니다. 자원(명사)만 남기고 행위는 메서드로 정하면 규칙이 하나로 통일됩니다.

✅ 규칙 2: 동작은 HTTP 메서드로

메서드하는 일CRUD
POST새로 만들기Create
GET읽기Read
PUT수정하기Update
DELETE삭제하기Delete

🔢 자주 보는 응답 상태 코드

코드뜻언제
200 OK요청 성공조회, 수정, 삭제 성공
201 Created새 자원이 만들어짐글 추가 성공
400 Bad Request요청 값이 잘못됨필수 값이 빠짐
404 Not Found찾는 자원이 없음없는 id로 조회

4. 엔티티 만들기

이제 블로그 글을 담을 Article 엔티티를 만듭니다. 엔티티는 DB의 article 테이블과 짝이 되는 자바 클래스입니다. 먼저 어떤 표를 만들지 설계하고, 그 표와 같은 모양의 클래스를 씁니다.

🗂️ 테이블 설계표

컬럼명자료형NULL 허용키설명
idBIGINTN기본키일련번호, 자동 증가
titleVARCHAR(255)N글 제목
contentVARCHAR(255)N글 내용

🎬 애니메이션: 어노테이션을 하나씩 붙여 엔티티 완성

  1. ① 필드(id, title, content)를 먼저 정합니다. 설계표의 열과 같은 순서로 생각하면 쉽습니다.
  2. ② @Entity: "이 클래스는 DB 표와 연결된다"는 표시입니다. 표 이름은 기본으로 클래스 이름 article이 됩니다.
  3. ③ @Id: id 필드를 기본키(행을 구분하는 번호)로 지정합니다.
  4. ④ @GeneratedValue: 번호를 사람이 넣지 않고 DB가 1, 2, 3…으로 자동으로 채웁니다.
  5. ⑤ @Column(nullable = false): 제목과 내용은 비워 둘 수 없다는 규칙입니다.
  6. ⑥ 완성된 엔티티는 설계표와 한 줄씩 대응합니다.

📝 Article.java 전체 코드

패키지 domain을 만들고 그 안에 Article.java를 만듭니다. 빨간 줄이 나오는 import는 Alt + Enter로 가져옵니다.

package me.yourname.springbootdeveloper.domain; import jakarta.persistence.*; // JPA 어노테이션 묶음 (@Entity, @Id 등) import lombok.*; // getter, 생성자 등을 자동으로 만들어 줌 @Entity // ① DB 표와 연결된 엔티티 @Getter // ② 모든 필드의 값을 꺼내는 메서드 자동 생성 @NoArgsConstructor(access = AccessLevel.PROTECTED) // ③ JPA가 쓰는 기본 생성자(외부 new 금지) public class Article { @Id // ④ 기본키 지정 @GeneratedValue(strategy = GenerationType.IDENTITY) // ⑤ 번호 자동 증가 @Column(name = "id", updatable = false) // id 열. 수정 금지 private Long id; @Column(name = "title", nullable = false) // ⑥ 제목 열, 빈 값 금지 private String title; @Column(name = "content", nullable = false) // ⑦ 내용 열, 빈 값 금지 private String content; @Builder // ⑧ 빌더 패턴으로 객체를 만들 수 있게 함 (다음 페이지) public Article(String title, String content) { this.title = title; // 전달받은 제목을 필드에 저장 this.content = content; // 전달받은 내용을 필드에 저장 } }

🔎 @Column 속성 표

속성뜻기본값
name매핑할 열 이름필드 이름
nullableNULL 허용 여부true(허용)
updatable수정 가능 여부true(가능)
length문자열 최대 길이255
🚨 흔한 실수기본 생성자(@NoArgsConstructor)를 빼먹으면 JPA가 객체를 만들 수 없어 실행 중 오류가 납니다. 또 필드 이름과 @Column의 name을 다르게 쓰면 열과 연결이 어긋날 수 있으니 주의하세요.

Q. 엔티티의 기본키를 DB가 자동으로 1씩 늘리게 하려면 어떤 어노테이션을 함께 씁니까?

A. @Id와 @GeneratedValue(strategy = GenerationType.IDENTITY)입니다.

5. 빌더 패턴과 롬복

객체를 만들 때 생성자에 값을 넣으면, 어떤 값이 어떤 필드에 들어가는지 헷갈리기 쉽습니다. 빌더 패턴(Builder Pattern)은 "필드 이름을 붙여서 한 줄씩 값을 채운 뒤 build()로 완성"하는 방식입니다. 읽기 쉽고, 값을 빼먹거나 순서를 틀리는 실수를 줄여 줍니다.

🎬 애니메이션: 생성자 방식과 빌더 방식 비교

  1. ① 같은 객체를 두 방식으로 만들 수 있습니다.
  2. ② 생성자 방식은 짧지만, 두 값이 모두 문자열이라 순서를 틀려도 컴파일러가 알려 주지 않습니다.
  3. ③ 빌더 방식은 .title, .content처럼 이름이 붙어 있어 어떤 값이 어디에 들어가는지 바로 보입니다.
  4. ④ build()를 호출하는 순간 객체가 완성됩니다. 롬복의 @Builder가 이 코드를 자동으로 만들어 줍니다.
  5. ④ build()를 호출하는 순간 객체가 완성됩니다. 롬복의 @Builder가 이 코드를 자동으로 만들어 줍니다.

🧰 롬복 어노테이션 정리

어노테이션자동으로 만들어 주는 것
@Getter필드 값을 꺼내는 getXxx() 메서드
@NoArgsConstructor값이 없는 기본 생성자 (접근 제한 가능)
@AllArgsConstructor모든 필드를 받는 생성자
@Builder빌더 패턴 코드(builder(), build())
📌 직접 쓴 코드와 비교해 보기@Getter 한 줄이면 getTitle()을 직접 쓸 필요가 없습니다. 자바 코드가 짧아지고, 필드를 바꿔도 getter를 같이 고칠 필요가 없어 실수가 줄어듭니다.
🧠 확인 퀴즈 5

Q. 빌더로 Article을 만들 때 호출하는 마지막 메서드는?

A. build()입니다. build()를 호출해야 객체가 실제로 완성됩니다.

6. 리포지터리 만들기

리포지터리(Repository)는 엔티티를 저장하고 꺼내는 창구입니다. 서비스는 DB의 SQL을 몰라도, 리포지터리에게 "저장해 줘", "전체 목록 줘"라고 부탁하기만 하면 됩니다.

리포지터리는 클래스가 아니라 인터페이스로 만듭니다. JpaRepository를 상속받으면 저장, 조회, 삭제 기능이 자동으로 생깁니다. 우리가 직접 구현 코드를 쓰지 않아도 됩니다.

🎬 애니메이션: 인터페이스 상속 계단

  1. ① 가운데 JpaRepository가 핵심입니다. 나의 BlogRepository는 이것을 상속받습니다.
  2. ② 전체 조회 findAll()은 JpaRepository에 이미 있으므로 직접 만들 필요가 없습니다.
  3. ③ 저장 save()도 같은 방식으로 물려받아 씁니다.
  4. ④ 한 건 조회, 삭제 등도 같은 방식입니다. 상속 계단 위쪽의 기능까지 모두 사용할 수 있습니다.
  5. ④ 한 건 조회, 삭제 등도 같은 방식입니다. 상속 계단 위쪽의 기능까지 모두 사용할 수 있습니다.

📝 BlogRepository.java

패키지 repository를 만들고 그 안에 인터페이스를 만듭니다.

package me.yourname.springbootdeveloper.repository; import me.yourname.springbootdeveloper.domain.Article; import org.springframework.data.jpa.repository.JpaRepository; // JpaRepository<관리할 엔티티, 기본키 타입> public interface BlogRepository extends JpaRepository<Article, Long> { // 내용이 비어 있는 블로그 글만 찾는 메서드도 이름 규칙으로 만들 수 있음 (5장 복습) }

🔎 JpaRepository<Article, Long> 읽는 법

부분뜻
JpaRepository저장, 조회, 삭제 기능을 물려받음
Article이 창구가 다루는 엔티티(표)
LongArticle 기본키(id)의 자료형
⚠️ 클래스인지 인터페이스인지리포지터리는 public interface로 만듭니다. class로 만들고 구현 코드를 직접 쓸 필요가 없습니다. 이름은 나중에 테스트와 서비스에서 같이 쓰므로 정확히 맞춰 주세요.
🧠 확인 퀴즈 6

Q. BlogRepository를 JpaRepository로 상속받을 때 두 번째 인수로 무엇을 넣습니까?

A. 엔티티의 기본키 타입인 Long입니다.

7. 글 작성 API (POST)

이제 "글을 추가하는 API"를 만듭니다. 클라이언트가 보낸 JSON을 객체로 받고, 서비스에 저장을 맡기고, 저장된 결과를 응답으로 돌려주는 흐름입니다. 세 계층(컨트롤러, 서비스, 리포지터리)이 모두 등장하므로 천천히 따라 가세요.

🎬 애니메이션: POST /api/articles 요청 한 건의 여정

  1. ① 글 작성은 POST /api/articles 요청입니다. 본문(body)에 제목과 내용이 JSON으로 담깁니다.
  2. ② 컨트롤러의 @PostMapping이 이 주소와 POST 요청을 addArticle() 메서드에 연결합니다.
  3. ③ JSON은 자바 객체로 바뀌어 AddArticleRequest(DTO)에 담깁니다. 직렬화·역직렬화는 다음 장에서 자세히 다룹니다.
  4. ④ DTO의 toEntity()가 Article 엔티티를 만들고, 서비스가 리포지터리 save()로 저장합니다.
  5. ⑤ 저장되면 DB가 id를 채우고, 그 객체가 응답 body에 담겨 201 Created로 돌아갑니다.
  6. ⑥ 정리: 요청 → 컨트롤러 → 서비스 → 리포지터리 → DB, 그리고 응답은 반대 방향입니다.
  7. ⑥ 정리: 요청 → 컨트롤러 → 서비스 → 리포지터리 → DB, 그리고 응답은 반대 방향입니다.

📝 1단계: DTO 만들기 (AddArticleRequest.java)

DTO(Data Transfer Object)는 계층끼리 데이터를 주고받기 위한 운반용 객체입니다. 화면에서 받은 값을 DB 엔티티와 분리해 두면, 나중에 DB 구조가 바뀌어도 화면 쪽 코드를 덜 고쳐도 됩니다. 패키지 dto를 만들고 아래 코드를 넣습니다.

package me.yourname.springbootdeveloper.dto; import lombok.*; import me.yourname.springbootdeveloper.domain.Article; @NoArgsConstructor // JSON을 객체로 바꿀 때 기본 생성자가 필요 @AllArgsConstructor // 모든 필드를 받는 생성자 (테스트에서 사용) @Getter // 값 꺼내기 메서드 자동 생성 public class AddArticleRequest { private String title; // JSON의 "title" 값이 여기에 들어옴 private String content; // JSON의 "content" 값이 여기에 들어옴 public Article toEntity() { // DTO를 엔티티로 바꾸는 메서드 (빌더 사용) return Article.builder() // 빌더 시작 .title(title) // 제목 값 넣기 .content(content) // 내용 값 넣기 .build(); // 완성된 Article 객체 반환 } }

📝 2단계: 서비스 만들기 (BlogService.java)

패키지 service를 만들고 BlogService.java를 만듭니다. 서비스는 "업무의 순서"를 담당합니다. 지금은 저장만 하므로 한 줄입니다.

package me.yourname.springbootdeveloper.service; import lombok.RequiredArgsConstructor; import me.yourname.springbootdeveloper.domain.Article; import me.yourname.springbootdeveloper.dto.AddArticleRequest; import me.yourname.springbootdeveloper.repository.BlogRepository; import org.springframework.stereotype.Service; @RequiredArgsConstructor // final 필드를 받는 생성자 자동 생성 (의존성 주입) @Service // 서비스 계층 빈으로 등록 public class BlogService { private final BlogRepository blogRepository; // 리포지터리를 주입받음 // 블로그 글 추가 메서드 public Article save(AddArticleRequest request) { // DTO를 엔티티로 바꾼 뒤 리포지터리에 저장하고, 저장된 객체를 돌려줌 return blogRepository.save(request.toEntity()); } }

📝 3단계: 컨트롤러 만들기 (BlogApiController.java)

패키지 controller를 만들고 BlogApiController.java를 만듭니다.

package me.yourname.springbootdeveloper.controller; import lombok.RequiredArgsConstructor; import me.yourname.springbootdeveloper.domain.Article; import me.yourname.springbootdeveloper.dto.AddArticleRequest; import me.yourname.springbootdeveloper.service.BlogService; import org.springframework.http.HttpStatus; import org.springframework.http.ResponseEntity; import org.springframework.web.bind.annotation.*; @RequiredArgsConstructor // 서비스 주입용 생성자 자동 생성 @RestController // 반환 객체를 JSON으로 응답하는 컨트롤러 public class BlogApiController { private final BlogService blogService; // 서비스 주입 @PostMapping("/api/articles") // POST /api/articles 요청을 이 메서드에 연결 public ResponseEntity<Article> addArticle(@RequestBody AddArticleRequest request) { // @RequestBody: 요청 본문 JSON을 AddArticleRequest 객체로 바꿈 Article savedArticle = blogService.save(request); // 서비스에 저장을 맡김 // 201 Created 상태 코드와 함께 저장된 글을 body에 담아 응답 return ResponseEntity.status(HttpStatus.CREATED) .body(savedArticle); } }
💡 어노테이션 한 줄씩 읽기
  • @RestController: 클래스 전체를 "JSON으로 응답하는 컨트롤러"로 지정합니다.
  • @PostMapping("/api/articles"): 이 주소로 온 POST 요청을 이 메서드에 연결합니다.
  • @RequestBody: 요청 본문의 JSON을 객체로 바꿔 매개변수에 넣습니다.
  • ResponseEntity.status(...).body(...): 상태 코드와 응답 내용을 함께 만듭니다.
⚠️ 자주 틀리는 점@RestController는 클래스 위에 한 번만 붙입니다. @PostMapping 주소의 철자가 조금만 달라도 404 Not Found가 납니다.
🧠 확인 퀴즈 7

Q. 요청 본문의 JSON을 AddArticleRequest 객체로 바꾸는 어노테이션은?

A. @RequestBody입니다.

8. 글 목록 조회 API (GET)

전체 글을 가져오는 API입니다. 리포지터리의 findAll()로 DB의 모든 행을 리스트로 받고, 그 리스트를 응답용 객체로 바꿔 돌려줍니다. 이때 자바의 스트림(Stream)을 사용하면 리스트를 짧고 읽기 쉽게 변환할 수 있습니다.

🎬 애니메이션: 리스트가 응답 객체 리스트로 바뀌는 과정

  1. ① DB에 저장된 글 세 건이 리스트로 준비되어 있습니다.
  2. ② .stream()은 리스트의 원소를 하나씩 흘려보내는 "흐름"을 엽니다.
  3. ③ .map(ArticleResponse::new)는 흐르는 각 글을 응답용 객체로 한 건씩 바꿉니다.
  4. ④ .toList()는 바뀐 결과를 다시 리스트로 모읍니다.
  5. ⑤ 응답에는 id 같은 내부 정보 없이 제목과 내용만 담깁니다.
  6. ⑤ 응답에는 id 같은 내부 정보 없이 제목과 내용만 담깁니다.

📝 1단계: 응답 DTO 만들기 (ArticleResponse.java)

package me.yourname.springbootdeveloper.dto; import lombok.Getter; import me.yourname.springbootdeveloper.domain.Article; @Getter // getter 자동 생성 (JSON 변환에 필요) public class ArticleResponse { private final String title; // 응답에 보낼 제목 private final String content; // 응답에 보낼 내용 public ArticleResponse(Article article) { // 엔티티 한 건을 받아 필요한 값만 복사 this.title = article.getTitle(); // 엔티티에서 제목 꺼내기 this.content = article.getContent(); // 엔티티에서 내용 꺼내기 } }

📝 2단계: 서비스 메서드 추가 (BlogService.java)

// 전체 글 목록 조회: JpaRepository의 findAll() 사용 public List<Article> findAll() { return blogRepository.findAll(); // article 표의 모든 행을 리스트로 반환 }

📝 3단계: 컨트롤러 메서드 추가 (BlogApiController.java)

@GetMapping("/api/articles") // GET /api/articles 요청 연결 public ResponseEntity<List<ArticleResponse>> findAllArticles() { List<ArticleResponse> articles = blogService.findAll() // 서비스에서 전체 글 가져오기 .stream() // 리스트를 흐름(스트림)으로 바꿈 .map(ArticleResponse::new) // 글 한 건마다 ArticleResponse로 변환 .toList(); // 다시 리스트로 모으기 return ResponseEntity.ok() // 200 OK 상태 코드 .body(articles); // 변환된 목록을 body에 담아 응답 }
📌 ArticleResponse::new는 무슨 뜻?"글 한 건을 받아 ArticleResponse 생성자를 호출하라"는 짧은 표현입니다. article -> new ArticleResponse(article)와 같습니다.

🧪 확인: 포스트맨

서버를 재실행한 뒤 메서드 GET, 주소 http://localhost:8080/api/articles로 요청하면 글 목록이 JSON 배열로 보입니다. 아직 글이 없다면 빈 배열 []이 정상입니다.

🧠 확인 퀴즈 8

Q. 엔티티 리스트를 응답용 리스트로 바꿀 때 "한 건씩 변환"을 담당하는 스트림 메서드는?

A. map()입니다. 흐르는 각 원소를 다른 모양으로 바꿉니다.

9. 글 한 건 조회 API

이번에는 URL 안의 번호로 글 한 건을 찾습니다. 예를 들어 GET /api/articles/3이면 id가 3인 글을 찾아 보여 줍니다. URL 일부를 값으로 꺼내는 것이 @PathVariable입니다.

🎬 애니메이션: URL의 숫자가 메서드 매개변수로 들어가는 과정

  1. ① 요청 주소는 GET /api/articles/3입니다. 마지막 칸의 3이 찾을 글 번호입니다.
  2. ② 주소의 {id} 자리에 있는 값을 찾습니다.
  3. ③ @PathVariable이 붙은 매개변수 id에 값 3이 자동으로 들어갑니다.
  4. ④ 서비스의 findById(3)이 호출되어 DB에서 한 건을 찾습니다.
  5. ⑤ 찾은 글을 응답 객체로 바꿔 돌려줍니다. 없으면 예외가 발생합니다.

📝 1단계: 서비스 메서드 (BlogService.java)

// id로 글 한 건 찾기 public Article findById(long id) { return blogRepository.findById(id) // JpaRepository의 findById 사용 (Optional 반환) .orElseThrow(() -> new IllegalArgumentException("not found: " + id)); // 값이 없으면 "not found: id" 예외를 던짐 }
💡 Optional이란?findById는 "있을 수도, 없을 수도 있는 결과"를 Optional 상자에 담아 돌려줍니다. orElseThrow는 상자가 비어 있으면 예외를 던지고, 들어 있으면 안의 Article을 꺼냅니다.

📝 2단계: 컨트롤러 메서드 (BlogApiController.java)

@GetMapping("/api/articles/{id}") // {id} 자리에 오는 숫자를 변수로 사용 public ResponseEntity<ArticleResponse> findArticle(@PathVariable long id) { // @PathVariable: URL의 {id} 값을 매개변수 id에 넣음 Article article = blogService.findById(id); // 서비스에서 한 건 조회 return ResponseEntity.ok() // 200 OK .body(new ArticleResponse(article)); // 응답 객체로 바꿔 body에 담기 }
⚠️ 이름이 다르면?{id}와 @PathVariable 뒤의 변수 이름이 같아야 합니다. 이름을 다르게 쓰려면 @PathVariable("id")처럼 이름을 적어 줍니다.
🧠 확인 퀴즈 9

Q. GET /api/articles/5 요청에서 5를 메서드 매개변수로 받으려면 어떤 어노테이션을 씁니까?

A. @PathVariable입니다.

10. 글 수정 API (PUT)

글을 고치는 API입니다. 수정은 "한 건을 찾고 → 필드 값을 바꾸는" 순서로 진행됩니다. 이때 중요한 개념이 트랜잭션(Transaction)과 변경 감지입니다. 5장에서 본 내용을 실제 서비스에 적용하는 장면입니다.

🎬 애니메이션: 트랜잭션 묶음과 변경 감지

  1. ① 트랜잭션은 "함께 성공하거나 함께 실패해야 하는 작업 묶음"입니다. 계좌 이체처럼 생각하면 쉽습니다.
  2. ② 글을 조회하면 그 객체는 영속 상태가 됩니다(5장 복습).
  3. ③ update()로 필드 값만 바꿉니다. save()는 호출하지 않습니다.
  4. ④ 묶음 안에서 문제가 생기면, 지금까지의 변경을 모두 되돌립니다(롤백).
  5. ⑤ 문제가 없으면 변경 감지가 UPDATE를 만들어 DB에 확정합니다(커밋).
  6. ⑤ 문제가 없으면 변경 감지가 UPDATE를 만들어 DB에 확정합니다(커밋).

📝 1단계: 수정 요청 DTO (UpdateArticleRequest.java)

package me.yourname.springbootdeveloper.dto; import lombok.*; @NoArgsConstructor // JSON → 객체 변환용 기본 생성자 @AllArgsConstructor // 모든 필드 생성자 (테스트에서 사용) @Getter // getter 자동 생성 public class UpdateArticleRequest { private String title; // 새 제목 private String content; // 새 내용 }

📝 2단계: 엔티티에 수정 메서드 (Article.java)

// 제목과 내용을 새 값으로 바꾸는 메서드 public void update(String title, String content) { this.title = title; // 새 제목으로 교체 this.content = content; // 새 내용으로 교체 }

📝 3단계: 서비스 메서드 (BlogService.java)

@Transactional // 이 메서드 전체를 하나의 트랜잭션으로 묶음 public Article update(long id, UpdateArticleRequest request) { Article article = blogRepository.findById(id) // ① id로 글 조회 (영속 상태) .orElseThrow(() -> new IllegalArgumentException("not found: " + id)); article.update(request.getTitle(), request.getContent()); // ② 필드만 변경 return article; // ③ 저장 호출 없이 돌려줌 → 끝날 때 변경 감지로 UPDATE }
📌 save()를 안 불렀는데 왜 바뀌나요?@Transactional 안에서 조회한 엔티티는 영속 상태입니다. 메서드가 끝날 때 JPA가 처음 값과 지금 값을 비교해 바뀐 것만 UPDATE로 보냅니다(변경 감지). 5장 8페이지를 떠올려 보세요.

📝 4단계: 컨트롤러 메서드 (BlogApiController.java)

@PutMapping("/api/articles/{id}") // PUT /api/articles/{id} 요청 연결 public ResponseEntity<Article> updateArticle(@PathVariable long id, @RequestBody UpdateArticleRequest request) { Article updatedArticle = blogService.update(id, request); // 서비스에 수정 맡기기 return ResponseEntity.ok() // 200 OK .body(updatedArticle); // 수정된 글을 응답 body에 담기 }
🚨 @Transactional을 빼면?트랜잭션이 없으면 변경 감지가 제대로 묶이지 않아, 중간에 실패했을 때 일부만 바뀌는 상황이 생길 수 있습니다. 수정 메서드에는 반드시 @Transactional을 붙이세요.
🧠 확인 퀴즈 10

Q. 수정 서비스에서 save()를 호출하지 않는데도 DB가 바뀌는 이유는?

A. @Transactional 안에서 조회한 엔티티의 값이 바뀌면, 트랜잭션이 끝날 때 변경 감지가 UPDATE를 자동으로 만들기 때문입니다.

11. 글 삭제 API (DELETE)

마지막 기능은 삭제입니다. 삭제는 "id를 받아서 그 행을 지우는" 단순한 흐름입니다. 리포지터리의 deleteById()가 기본키로 행을 찾아 지웁니다.

🎬 애니메이션: 2번 글이 사라지는 과정

  1. ① 세 개의 글이 들어 있는 상태입니다.
  2. ② deleteById(2L)이 기본키 2인 행을 찾아 삭제합니다.
  3. ③ 삭제 후 목록을 조회하면 1번과 3번만 남습니다.
  4. ③ 삭제 후 목록을 조회하면 1번과 3번만 남습니다.

📝 1단계: 서비스 메서드 (BlogService.java)

// id로 글 삭제 public void delete(long id) { blogRepository.deleteById(id); // JpaRepository의 deleteById: id 행을 삭제 }

📝 2단계: 컨트롤러 메서드 (BlogApiController.java)

@DeleteMapping("/api/articles/{id}") // DELETE /api/articles/{id} 요청 연결 public ResponseEntity<Void> deleteArticle(@PathVariable long id) { blogService.delete(id); // 서비스에 삭제 맡기기 return ResponseEntity.ok().build(); // 200 OK, 본문 없이 응답 }
📌 Void는 무엇?응답 body에 담을 내용이 없다는 뜻입니다. 삭제는 결과 데이터가 필요 없으므로 ResponseEntity<Void>를 씁니다.
🧠 확인 퀴즈 11

Q. 삭제 API의 HTTP 메서드와 주소를 쓰세요. (글 번호는 1번)

A. DELETE /api/articles/1입니다.

12. 테스트와 포스트맨 실습

API를 만들 때마다 포스트맨으로 손으로 확인하면 시간이 많이 듭니다. 그래서 테스트 코드로 API를 자동으로 호출하고 결과를 검사합니다. 테스트 코드가 있으면 나중에 코드를 고쳐도 기존 기능이 깨졌는지 바로 알 수 있습니다.

🎬 애니메이션: 테스트 한 건의 given-when-then

  1. ① 테스트 한 건은 Given, When, Then 세 부분으로 나눠 씁니다.
  2. ② Given: 필요한 데이터를 준비합니다.
  3. ③ When: 실제 API를 호출합니다.
  4. ④ Then: 응답 코드와 저장된 값을 검사합니다. 틀리면 테스트가 실패합니다.
  5. ④ Then: 응답 코드와 저장된 값을 검사합니다. 틀리면 테스트가 실패합니다.

🧪 테스트 코드: 글 추가 API (BlogApiControllerTest.java)
