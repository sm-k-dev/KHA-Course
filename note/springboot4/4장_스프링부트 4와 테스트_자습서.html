0. 4장 지도

지금까지 우리는 서버를 실행하고 브라우저에서 눌러 보며 확인했습니다. 이 방법은 사람이 매번 해야 하고, 빠뜨리기 쉽습니다. 테스트 코드는 이 확인 과정을 프로그램이 스스로 반복하도록 만든 것입니다.

🎬 애니메이션: 이 장에서 쓰는 도구 네 가지

  2. 1단계: 테스트가 왜 필요한지 확인합니다.
  3. 2단계: JUnit 5가 테스트 메서드를 실행합니다.
  4. 3단계: AssertJ가 실행 결과가 기대한 값인지 검사합니다.
  5. 4단계: MockMvc가 웹 요청을 흉내 내어 컨트롤러를 검사합니다.

1. 왜 테스트가 필요한가

코드를 한 군데 고치면, 전혀 관계없어 보이는 다른 기능이 깨지는 일이 흔합니다. 이를 회귀(Regression) 버그라고 부릅니다. 테스트 코드가 있으면 고친 뒤 버튼 한 번으로 모든 기능을 다시 확인할 수 있습니다.

🎬 애니메이션: 테스트가 없을 때와 있을 때

  1. 같은 수정을 해도 결과를 아는 시점이 다릅니다.
  2. 1단계: 기능 하나를 고칩니다.
  3. 2단계: 테스트가 없으면 다른 기능이 깨졌는지 모른 채 넘어갈 수 있습니다.
  4. 3단계: 테스트가 있으면 수정 직후 실패 메시지로 바로 알 수 있습니다.
구분수동 확인자동 테스트
반복 속도느림빠름
빠뜨림사람이라 생길 수 있음정해진 것은 항상 확인
기록남기기 어려움코드로 남아 누구나 다시 실행
💡 테스트의 목적테스트는 "버그가 없다"를 증명하지 않습니다. "이미 확인한 약속이 아직 지켜지고 있다"를 계속 알려 주는 도구입니다.

Q. 수정한 기능과 무관한 다른 기능이 깨지는 현상을 무엇이라고 부르나요?

A. 회귀(Regression) 버그라고 합니다.

2. 테스트 종류

테스트는 확인하는 범위에 따라 여러 종류로 나눕니다. 범위가 작을수록 빠르고 원인을 찾기 쉽고, 범위가 클수록 실제 상황에 가깝습니다.

🎬 애니메이션: 작은 범위에서 큰 범위로

  1. 테스트는 작은 조각에서 큰 조각으로 넓혀 갑니다.
  2. 1단계: 단위 테스트는 메서드 하나만 따로 확인하고, 통합 테스트는 여러 계층을 함께 확인합니다.
  3. 2단계: 웹 테스트는 요청을 보내고 응답이 맞는지 확인합니다.
종류범위속도이 장에서
단위(Unit)메서드 하나매우 빠름계산기 예제
통합(Integration)여러 계층보통스프링 부트 테스트 소개
웹(Web)요청에서 응답까지보통MockMvc 예제
📌 대부분은 작은 테스트로테스트를 많이 쓰되, 작은 단위 테스트를 기본으로 하고 넓은 테스트는 중요한 흐름에만 씁니다.
🧠 확인 퀴즈 2

Q. 메서드 하나만 따로 떼어 확인하는 테스트 종류는 무엇인가요?

A. 단위 테스트(Unit Test)입니다.

3. JUnit 5 기본

JUnit 5는 테스트 메서드를 찾아 실행하는 도구입니다. 메서드 위에 @Test를 붙이면 테스트로 인식합니다. 또 @BeforeEach는 각 테스트 전에, @AfterEach는 각 테스트 후에 실행됩니다.

🎬 애니메이션: 테스트 한 개가 도는 순서

  1. @Test 메서드 하나가 실행될 때 주변 메서드가 함께 움직입니다.
  2. 1단계: 테스트 전에 @BeforeEach가 준비 작업을 합니다.
  3. 2단계: @Test 메서드가 실행되어 검사합니다.
  4. 3단계: 다음 테스트가 시작될 때는 준비가 다시 실행됩니다.
  5. 4단계: 테스트마다 준비와 정리가 반복되어 서로 영향을 주지 않습니다.

코드: 계산기 테스트의 뼈대

import org.junit.jupiter.api.BeforeEach; // 각 테스트 전에 실행할 메서드 표시 import org.junit.jupiter.api.Test; // 테스트 메서드 표시 class CalculatorServiceTest { private CalculatorService calculator; // 테스트에서 쓸 계산기 객체를 담아 둘 칸 @BeforeEach // 테스트 메서드 하나가 실행되기 직전마다 아래 메서드가 실행된다 void setUp() { calculator = new CalculatorService(); // 매번 새 계산기 객체를 만들어 이전 테스트의 영향을 없앤다 } @Test // 이 메서드는 테스트로 실행된다 void addTwoNumbers() { int result = calculator.add(2, 3); // 계산기의 add를 호출하고, 결과를 받는다 // 결과 검사는 다음 페이지의 AssertJ에서 다룬다 } }
⚠️ 테스트끼리 순서에 기대지 마세요JUnit은 테스트 실행 순서를 보장하지 않습니다. 각 테스트는 혼자서도 통과할 수 있게 @BeforeEach에서 준비하는 것이 원칙입니다.
🧠 확인 퀴즈 3

Q. 테스트마다 실행 전에 준비 작업을 하고 싶을 때 쓰는 표시는 무엇인가요?

A. @BeforeEach입니다.

4. AssertJ 검사

AssertJ는 "결과가 이래야 한다"를 읽기 쉬운 문장으로 쓰게 해 주는 검사 도구입니다. assertThat에 실제 값을 넣고, 뒤에 기대하는 조건을 이어 씁니다.

🎬 애니메이션: 실제 값과 기대 값 비교

  1. 검사는 실제 값을 감싸고, 기대 값과 비교하는 순서입니다.
  2. 1단계: 계산기가 돌려준 실제 값이 준비됩니다.
  3. 2단계: assertThat으로 감싸고 isEqualTo로 기대 값을 이어 씁니다.
  4. 3단계: 같으면 초록으로 통과하고, 다르면 실패 메시지에 두 값을 보여 줍니다.

코드: 자주 쓰는 검사 문장

import static org.assertj.core.api.Assertions.assertThat; // assertThat을 바로 쓰기 위해 가져온다 import static org.assertj.core.api.Assertions.assertThatThrownBy; // 예외 검사용 문장을 가져온다 @Test void assertionExamples() { int sum = calculator.add(2, 3); // 실제 계산 결과를 받는다 assertThat(sum).isEqualTo(5); // sum이 5와 같은지 검사한다 String name = "memo-app"; // 검사할 문자열을 준비한다 assertThat(name).startsWith("memo"); // 문자열이 memo로 시작하는지 검사한다 java.util.List<String> list = java.util.List.of("a", "b"); // 검사할 목록을 준비한다 assertThat(list).hasSize(2).contains("a"); // 크기가 2이고 "a"를 포함하는지 검사한다 assertThatThrownBy(() -> calculator.divide(10, 0)) // 0으로 나누는 호출을 실행해 본다 .isInstanceOf(IllegalArgumentException.class); // 그 때 예외 종류가 맞는지 검사한다 }
📌 AssertJ가 좋은 이유assertEquals(5, sum)처럼 쓰면 순서를 헷갈리기 쉽습니다. AssertJ는 "무엇을 검사하는가"가 앞에 와서 문장이 자연스럽습니다.
🧠 확인 퀴즈 4

Q. assertThat(sum).isEqualTo(5)는 무엇을 검사하나요?

A. sum 값이 5와 같은지 검사합니다. 같지 않으면 테스트가 실패합니다.

5. Given-When-Then

테스트 코드를 읽기 쉽게 쓰는 규칙이 Given-When-Then입니다. 순서대로 준비(given), 실행(when), 확인(then)을 나누어 적습니다.

🎬 애니메이션: 세 칸으로 나누어 읽기

  1. 세 칸은 항상 같은 순서로 나타납니다.
  2. 1단계: given에서 테스트에 필요한 값과 상황을 준비합니다.
  3. 2단계: when에서 검사할 기능을 한 번 실행합니다.
  4. 3단계: then에서 결과가 기대와 같은지 확인합니다.

코드: Given-When-Then 예시

@Test void divideNormally() { // given: 나누어질 수와 나눌 수를 준비한다 int dividend = 10; int divisor = 2; // when: 나눗셈을 한 번 실행하고 결과를 받는다 int result = calculator.divide(dividend, divisor); // then: 결과가 5인지 확인한다 assertThat(result).isEqualTo(5); }
💡 한 테스트에는 한 가지만검사 항목을 많이 넣으면 실패했을 때 어느 부분이 문제인지 헷갈립니다. 상황 하나당 테스트 하나를 권장합니다.
🧠 확인 퀴즈 5

Q. Given-When-Then에서 when 칸에는 무엇을 쓰나요?

A. 검사할 기능을 실행하는 행동을 씁니다.

6. Mockito 가짜 객체

서비스는 저장소(Repository)에게 데이터를 달라고 부릅니다. 테스트에서 실제 데이터베이스까지 연결하면 느리고 준비가 복잡합니다. 그래서 Mockito로 저장소를 가짜 객체(Mock)로 바꿔 "이렇게 대답하라"고 정해 줍니다.

🎬 애니메이션: 가짜 저장소가 대신 대답하는 흐름

  1. 서비스는 진짜 저장소 대신 가짜 저장소를 받습니다.
  2. 1단계: 테스트는 MemoService를 검사 대상으로 준비합니다.
  3. 2단계: 가짜 저장소에게 "목록을 달라고 하면 이 두 개를 돌려줘"라고 정해 둡니다.
  4. 3단계: 서비스가 호출하면 가짜가 정해진 값을 돌려주고, 서비스 로직만 검사됩니다.

코드: 가짜 저장소로 서비스 검사하기

import static org.assertj.core.api.Assertions.assertThat; import static org.mockito.Mockito.when; // 가짜 객체의 대답을 정하는 기능 import java.util.List; import org.junit.jupiter.api.Test; import org.junit.jupiter.api.extension.ExtendWith; import org.mockito.InjectMocks; // 가짜 객체를 서비스에 넣어 주는 표시 import org.mockito.Mock; // 가짜 객체를 만드는 표시 import org.mockito.junit.jupiter.MockitoExtension; // Mockito를 JUnit과 함께 켜는 설정 @ExtendWith(MockitoExtension.class) // 이 테스트에서 Mockito 기능을 켠다 class MemoServiceTest { @Mock MemoRepository memoRepository; // 진짜 대신 쓰는 가짜 저장소 @InjectMocks MemoService memoService; // 위 가짜 저장소를 생성자로 넣은 서비스 @Test void countMemos() { // given: 저장소가 목록을 달라고 하면 두 개짜리 목록을 돌려주도록 정해 둔다 when(memoRepository.findAllTitles()).thenReturn(List.of("장보기", "운동")); // when: 서비스의 개수 세기 기능을 실행한다 int count = memoService.countMemos(); // then: 서비스가 목록 크기 2를 올바르게 돌려주는지 확인한다 assertThat(count).isEqualTo(2); } }
⚠️ 가짜는 정해진 것만 대답합니다정해 두지 않은 메서드를 부르면 null이나 0을 돌려줍니다. 그 때문에 테스트가 이상하게 통과하거나 실패할 수 있으니 필요한 대답은 빠짐없이 정하세요.
🧠 확인 퀴즈 6

Q. Mockito의 Mock 객체는 무엇을 대신하나요?

A. 진짜 의존 객체(예: 데이터베이스 저장소)를 대신하는 가짜 객체입니다.

7. MockMvc 웹 테스트

MockMvc는 실제 서버를 켜지 않고도 웹 요청을 흉내 내서 컨트롤러가 올바른 상태 코드와 데이터를 돌려주는지 확인하게 해 줍니다. 1장에서 배운 요청과 응답을 코드로 다시 만나는 셈입니다.

🎬 애니메이션: 가짜 요청이 컨트롤러까지 가는 길

  1. MockMvc는 요청을 만들어 컨트롤러에 전달하고, 응답을 검사합니다.
  2. 1단계: perform으로 GET /memos/count 요청을 만듭니다.
  3. 2단계: 컨트롤러가 실행되어 응답을 만듭니다.
  4. 3단계: status와 jsonPath로 상태 코드와 응답 내용을 검사합니다.

코드: 컨트롤러 추가 부분과 테스트

// 컨트롤러에 추가할 메서드 (MemoController) @GetMapping("/count") // GET /memos/count 요청을 받는다 public Map<String, Integer> count() { int total = memoService.countMemos(); // 서비스에서 개수를 받는다 return Map.of("count", total); // {"count": 개수} 모양의 JSON으로 돌려준다 }
import static org.mockito.BDDMockito.given; // 가짜 서비스의 대답을 정하는 기능 import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get; import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath; import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status; @WebMvcTest(MemoController.class) // 이 컨트롤러 하나만 올려서 웹 테스트를 한다 class MemoControllerTest { @Autowired MockMvc mockMvc; // 요청을 흉내 내는 도구를 스프링이 넣어 준다 @MockitoBean MemoService memoService; // 실제 서비스 대신 쓰는 가짜 서비스 @Test void countEndpoint() throws Exception { given(memoService.countMemos()).willReturn(2); // 서비스가 2를 돌려주도록 정한다 mockMvc.perform(get("/memos/count")) // GET /memos/count 요청을 보낸다 .andExpect(status().isOk()) // 응답 상태 코드가 200인지 검사한다 .andExpect(jsonPath("$.count").value(2)); // 응답 JSON의 count 값이 2인지 검사한다 } }
📌 어노테이션 패키지 주의스프링 부트 4에서는 @WebMvcTest 같은 테스트 어노테이션의 패키지 경로가 모듈별로 나뉘어 바뀌었습니다. IDE의 Alt + Enter(import 추가)로 현재 버전 경로를 가져오세요.
🧠 확인 퀴즈 7

Q. MockMvc의 jsonPath("$.count")는 응답의 무엇을 검사하나요?

A. 응답 JSON 안에서 count라는 이름의 값을 찾아 검사합니다.

8. 테스트 범위 고르기

스프링 테스트에는 프로그램 전체를 올리는 방식과 일부 계층만 올리는 방식이 있습니다. 목적에 맞게 골라야 테스트가 빠르고 정확해집니다.

🎬 애니메이션: 얼마나 많이 올릴 것인가

  1. 테스트에 올리는 범위에 따라 속도와 확인 범위가 달라집니다.
  2. 1단계: @SpringBootTest는 프로그램 전체를 올려 실제에 가깝게 확인합니다.
  3. 2단계: 슬라이스 테스트는 웹 계층처럼 필요한 부분만 올려 빠르게 확인합니다.
구분@SpringBootTest슬라이스(@WebMvcTest 등)
올리는 범위전체 빈필요한 계층만
속도느림빠름
잘 맞는 곳여러 계층이 함께 도는 흐름컨트롤러 하나, 저장소 하나
💡 선택 기준평소에는 작은 단위와 슬라이스로 빠르게 확인하고, 전체 흐름이 중요한 곳에만 @SpringBootTest를 씁니다.
🧠 확인 퀴즈 8

Q. 컨트롤러만 빠르게 확인하고 싶을 때 적합한 방식은 무엇인가요?

A. @WebMvcTest 같은 슬라이스 테스트입니다.

9. 실습: 계산기 테스트

이제 직접 작성합니다. 계산기 서비스의 더하기와 0 나누기 예외를 테스트합니다. 작은 단위 테스트를 연습하는 가장 좋은 예입니다.

🎬 애니메이션: 작성 → 실행 → 결과

  1. 테스트 작성부터 결과 확인까지 세 단계입니다.
  2. 1단계: 테스트 클래스를 만들고 실행 버튼을 누릅니다.
  3. 2단계: 모든 테스트가 통과하면 초록 막대가 보입니다.

코드: 계산기 서비스

public class CalculatorService { public int add(int a, int b) { // 두 수를 받아 합을 돌려준다 return a + b; } public int divide(int a, int b) { // 나눗셈을 한다 if (b == 0) { // 0으로 나누려 하면 throw new IllegalArgumentException("0으로 나눌 수 없습니다"); // 예외를 던진다 } return a / b; // 정상이면 몫을 돌려준다 } }

코드: 계산기 테스트

import static org.assertj.core.api.Assertions.assertThat; import static org.assertj.core.api.Assertions.assertThatThrownBy; import org.junit.jupiter.api.BeforeEach; import org.junit.jupiter.api.DisplayName; import org.junit.jupiter.api.Test; class CalculatorServiceTest { private CalculatorService calculator; @BeforeEach void setUp() { calculator = new CalculatorService(); // 매 테스트마다 새 계산기를 준비한다 } @Test @DisplayName("두 수를 더하면 합이 나온다") // 실행 결과에 보일 설명 문장 void add() { // given int a = 2; int b = 3; // when int result = calculator.add(a, b); // 더하기 기능을 실행한다 // then assertThat(result).isEqualTo(5); // 결과가 5인지 확인한다 } @Test @DisplayName("0으로 나누면 예외가 발생한다") void divideByZeroThrows() { assertThatThrownBy(() -> calculator.divide(10, 0)) // 0으로 나누는 호출을 실행해 본다 .isInstanceOf(IllegalArgumentException.class) // 예외 종류가 맞는지 확인한다 .hasMessage("0으로 나눌 수 없습니다"); // 예외 메시지가 맞는지 확인한다 } }
📌 실행 방법테스트 클래스 이름이나 메서드 옆의 ▶ 버튼을 누르면 해당 테스트만 실행됩니다. 전체를 실행하려면 src/test/java 폴더를 우클릭해 Run을 누르세요.
🧠 확인 퀴즈 9

Q. @DisplayName은 무엇을 위해 쓰나요?

A. 테스트 실행 결과 화면에 보일 읽기 쉬운 설명을 적기 위해 씁니다.

10. 실패 메시지 읽기

테스트가 실패하면 빨간색 메시지가 나옵니다. 이 메시지를 읽는 것이 테스트를 잘 쓰는 핵심 기술입니다. 대부분 기대한 값과 실제 값이 함께 적혀 있습니다.

🎬 애니메이션: 실패 메시지에서 원인 찾기

  1. 빨간 메시지는 힌트 그 자체입니다.
  2. 1단계: Expected(기대)와 but was(실제) 값을 나란히 봅니다.
  3. 2단계: 차이가 나는 코드를 고치고 테스트를 다시 실행합니다.

자주 보는 실패 메시지

메시지 일부뜻확인할 곳
Expected: 5 but was: 6계산 결과가 기대와 다름계산 로직
NullPointerException가짜 객체가 값을 정해 주지 않음when 설정 누락
Expecting code to raise a throwable예외가 나야 하는데 안 남예외 처리 조건
UnnecessaryStubbingException정해 둔 대답을 쓰지 않음불필요한 when 설정
⚠️ 테스트를 고쳐서 통과시키는 것이 목적이 아닙니다기대 값이 틀린 것인지, 코드가 틀린 것인지 먼저 판단하세요. 기대 값이 맞다면 코드를 고치는 것이 맞습니다.
🧠 확인 퀴즈 10

Q. 테스트 실패 메시지에서 가장 먼저 봐야 할 두 가지는 무엇인가요?

A. Expected(기대 값)와 but was(실제 값)입니다.
