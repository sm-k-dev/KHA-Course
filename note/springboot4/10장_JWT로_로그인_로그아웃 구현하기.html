10장 · JWT로 로그인/로그아웃 구현하기

9장에서는 세션(Session) 기반으로 로그인했습니다. 이번 장에서는 토큰(Token) 기반 인증을 직접 구현합니다. 로그인한 사용자에게 JWT(JSON Web Token)를 발급하고, 요청할 때마다 그 토큰으로 본인을 증명하는 방식입니다. 토큰이 만료되면 리프레시 토큰으로 새 액세스 토큰을 받는 흐름까지 만듭니다.

10.1 사전 지식: 토큰 기반 인증

토큰 기반 인증이란?

사용자가 서버에 접근할 때 인증된 사용자인지 확인하는 방법은 여러 가지입니다. 대표적으로 서버 기반 인증(세션)과 토큰 기반 인증이 있습니다. 스프링 시큐리티는 기본적으로 세션 기반 인증을 제공하는데, 8·9장에서는 사용자마다 세션을 만들고 저장해서 인증했습니다.

토큰은 서버에서 클라이언트를 구분하기 위한 유일한 값입니다. 서버가 토큰을 생성해서 클라이언트에게 제공하면, 클라이언트는 이 토큰을 갖고 있다가 여러 요청을 보낼 때마다 이 토큰과 함께 신청합니다. 그러면 서버는 토큰만 보고 유효한 사용자인지 검증합니다.

토큰을 전달하고 인증받는 과정

  1. 클라이언트가 아이디와 비밀번호로 로그인을 요청합니다.
  2. 서버는 정보를 확인하고 유효하면 토큰을 만들어 응답합니다.
  3. 클라이언트는 받은 토큰을 저장합니다.
  4. 인증이 필요한 API를 부를 때 토큰을 함께 보냅니다.
  5. 서버는 토큰이 유효한지 검증합니다.
  6. 토큰이 유효하면 요청한 내용을 처리해 응답합니다.
  7. 토큰이 유효하면 요청한 내용을 처리해 응답합니다.
💡 세션과의 차이 세션 방식은 서버가 사용자 정보를 기억합니다. 토큰 방식은 사용자 정보를 담은 토큰을 클라이언트가 들고 다니고, 서버는 토큰만 검증합니다. 그래서 서버가 상태를 따로 저장하지 않아도 됩니다.

액세스 토큰과 리프레시 토큰

토큰의 유효기간이 하루라면 그 토큰이 노출되었을 때 하루 동안 누구든 사용할 수 있습니다. 그렇다고 유효기간을 너무 짧게 잡으면 사용자는 자주 다시 로그인해야 하니 불편합니다. 이 문제를 해결하기 위해 리프레시 토큰(refresh token)을 씁니다.

구분액세스 토큰(access token)리프레시 토큰(refresh token)
역할API 요청에 붙여 사용자를 인증합니다.액세스 토큰이 만료되었을 때 새 액세스 토큰을 발급받는 용도입니다.
유효기간짧게 설정합니다(예: 2시간).길게 설정합니다(예: 14일).
저장 위치클라이언트클라이언트와 DB(서버가 확인용으로 보관)
  1. 액세스 토큰으로 API를 요청합니다.
  2. 토큰이 만료되면 서버는 만료 에러를 보냅니다.
  3. 클라이언트는 리프레시 토큰과 함께 새 액세스 토큰을 요청합니다.
  4. 서버는 리프레시 토큰을 DB에서 조회해 비교합니다.
  5. 같으면 유효하다고 판단합니다.
  6. 새 액세스 토큰을 응답하고, 이후 요청은 새 토큰으로 합니다.
🚨 토큰이 노출되면 어떻게 될까요? 영화 티켓 정보가 노출되면 다른 사람이 그 티켓으로 영화를 볼 수 있습니다. 토큰도 마찬가지여서, 토큰을 가진 사람이 곧 인증된 사람이 됩니다. 그래서 액세스 토큰의 유효기간을 짧게 두고, 재발급에 쓰는 리프레시 토큰은 서버에서 따로 관리하는 방식이 필요합니다.

토큰 기반 인증의 특징 · JWT 구조

토큰 기반 인증의 세 가지 특징

특징설명
무상태성 (stateless)인증 정보가 담긴 토큰을 클라이언트가 갖고 있으므로 서버가 따로 저장할 필요가 없습니다. 서버는 상태를 유지하지 않고 토큰만 검증합니다.
확장성서버를 여러 대로 늘려도 상태를 공유할 필요가 없습니다. 같은 토큰으로 결제 서버와 주문 서버에 모두 요청할 수 있고, 다른 서비스와 로그인 방식을 공유하기도 쉽습니다.
무결성토큰은 HMAC 기법으로 서명되어 있습니다. 토큰을 발급한 뒤에는 내용을 바꿀 수 없고, 한 글자라도 바뀌면 서버는 유효하지 않은 토큰으로 판단합니다.

JWT란?

JWT는 토큰 기반 인증에서 주로 쓰는 토큰입니다. JSON 형식으로 사용자의 정보를 담습니다. 발급받은 JWT로 인증하려면 HTTP 요청 헤더의 Authorization 키에 Bearer + JWT 토큰값을 넣어 보내야 합니다.

Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJpc3MiOiJhanVmcmVzaEBnbWFpbC5jb20ifQ.서명값
  1. JWT는 점(.)을 기준으로 세 부분으로 나뉩니다.
  2. 첫 부분은 헤더로, 토큰 타입과 해싱 알고리즘을 담습니다.
  3. 둘째 부분은 내용으로, 토큰에 담을 정보를 담습니다.
  4. 셋째 부분은 서명으로, 토큰이 바뀌지 않았는지 확인합니다.
  5. 세 부분을 점으로 이어 붙인 것이 JWT입니다.
  6. 세 부분을 점으로 이어 붙인 것이 JWT입니다.
  7. 세 부분을 점으로 이어 붙인 것이 JWT입니다.

헤더와 서명

헤더에는 토큰의 타입과 해싱 알고리즘을 지정하는 정보를 담습니다. 아래 예는 JWT 토큰이고 HS256 해싱 알고리즘을 쓴다는 뜻입니다.

{ "typ": "JWT", "alg": "HS256" }
이름설명
typ토큰의 타입을 지정합니다. JWT라는 문자열이 들어갑니다.
alg해싱 알고리즘을 지정합니다.

서명은 토큰이 조작되었거나 변경되지 않았음을 확인하는 용도입니다. 헤더와 내용을 인코딩한 값을 합친 뒤, 주어진 비밀키로 해시값을 만듭니다. 서버는 받은 토큰에서 같은 방식으로 서명을 다시 계산해 비교합니다.

⚠️ 내용은 암호화되지 않습니다 JWT의 내용(payload)은 Base64로 인코딩된 것일 뿐이라 누구나 해석할 수 있습니다. 그래서 비밀번호 같은 민감한 정보는 JWT에 넣으면 안 됩니다. 서명은 “위조되지 않았음”을 보장하는 것이지, “내용을 숨기는” 기능이 아닙니다.

JWT 클레임(claim)

내용(payload)에는 토큰과 관련된 정보를 담습니다. 내용의 한 덩어리를 클레임(claim)이라고 부르며, 클레임은 키-값의 한 쌍으로 이루어져 있습니다. 클레임은 크게 세 종류로 나뉩니다.

등록된 클레임 (registered claim)

토큰에 대한 정보를 담는 데 사용합니다. JWT 표준에서 미리 정해 둔 이름입니다.

이름설명
iss토큰 발급자(issuer)
sub토큰 제목(subject)
aud토큰 대상자(audience)
exp토큰의 만료 시간(expiration). NumericDate 형식이며 항상 현재 시간 이후로 설정합니다.
nbf토큰의 활성 날짜(not before). 이 날짜가 지나기 전까지는 토큰이 처리되지 않습니다.
iat토큰이 발급된 시간(issued at)
jtiJWT의 고유 식별자. 주로 일회용 토큰에 사용합니다.

공개 클레임 (public claim)

공개되어도 상관없는 클레임입니다. 충돌을 방지할 수 있는 이름을 가져야 하며, 보통 클레임 이름을 URI 형태로 짓습니다.

비공개 클레임 (private claim)

공개되면 안 되는 클레임입니다. 클라이언트와 서버 간의 통신에 사용됩니다.

예시

{ "iss": "ajufresh@gmail.com", // 등록된 클레임 "iat": 1622370878, // 등록된 클레임 "exp": 1622372678, // 등록된 클레임 "https://shinsunyoung.com/jwt_claims/is_admin": true, // 공개 클레임 "email": "ajufresh@gmail.com", // 비공개 클레임 "hello": "안녕하세요!" // 비공개 클레임 }
💡 한눈에 구분하기 iss, iat, exp는 JWT 표준에서 정한 등록된 클레임입니다. URI 형태로 된 is_admin은 공개 클레임입니다. 그 밖의 email과 hello는 비공개 클레임입니다.

10.2 JWT 서비스 구현하기

이제 실제로 JWT를 만들고 검증하는 서비스를 구현합니다. 순서는 의존성 추가 → 설정 파일 → JwtProperties → TokenProvider → 테스트입니다.

01단계의존성 추가하기 (build.gradle)

build.gradle에 필요한 의존성을 추가하고, Gradle 탭에서 새로고침을 눌러 의존성을 내려받습니다.

// build.gradle dependencies { ... 생략 ... testAnnotationProcessor 'org.projectlombok:lombok' testImplementation 'org.projectlombok:lombok' implementation 'io.jsonwebtoken:jjwt:0.9.1' // 자바 JWT 라이브러리 implementation 'javax.xml.bind:jaxb-api:2.3.1' // XML 문서와 자바 객체 간 매핑 자동화 }
⚠️ 라이브러리 버전 참고 이 예제는 jjwt 0.9.1 버전 기준입니다. 이 버전의 API(setSigningKey, parseClaimsJws 등)는 이후 버전에서 바뀌었으니, 책의 코드를 따라 하려면 같은 버전을 쓰세요.

02단계설정 파일 수정하기 (application.yml)

JWT에 필요한 발급자(issuer)와 비밀키(secret_key)를 설정 파일에 선언합니다.

# application.yml spring: jpa: show-sql: true ... 생략 ... ai: openai: api-key: ... jwt: issuer: ajufresh@gmail.com secret_key: study-springboot
  1. 설정 파일에 jwt 항목을 선언합니다.
  2. issuer와 secret_key 값을 넣습니다.
  3. JwtProperties 클래스가 같은 이름의 필드를 가집니다.
  4. 설정 값이 필드에 자동으로 들어갑니다.
  5. 이름 규칙(secret_key → secretKey)을 기억하세요.
  6. 이름 규칙(secret_key → secretKey)을 기억하세요.
🚨 비밀키 관리 비밀키는 서명을 만드는 열쇠입니다. 이 키를 알면 누구나 토큰을 위조할 수 있습니다. 예제의 study-springboot는 학습용입니다. 실제 배포에서는 환경 변수 등으로 주입하고, 깃에 올라가지 않도록 관리하세요.

03단계JwtProperties 만들기

config/jwt 패키지에 JwtProperties.java를 만듭니다. 설정 파일의 jwt.issuer와 jwt.secret_key 값을 이 클래스의 필드로 가져옵니다.

// /config/jwt/JwtProperties.java @Setter // setter 자동 생성 @Getter // getter 자동 생성 @Component // 스프링 빈으로 등록 @ConfigurationProperties("jwt") // 설정 파일의 jwt 항목 값을 아래 필드에 넣음 public class JwtProperties { private String issuer; // 설정 파일의 jwt.issuer 값이 들어감 private String secretKey; // 설정 파일의 jwt.secret_key 값이 들어감 }
⚠️ import 빨간 줄 해결 Setter, Getter, Component, ConfigurationProperties에 빨간 줄이 생기면 해당 줄에서 Alt+Enter를 눌러 import를 추가하세요.

TokenProvider 만들기 (토큰 생성)

04단계토큰을 생성하고, 올바른 토큰인지 유효성을 검사하고, 토큰에서 필요한 정보를 가져오는 클래스 TokenProvider를 만듭니다. config/jwt 디렉터리에 TokenProvider.java를 만들고 아래 코드를 입력합니다.

// /config/jwt/TokenProvider.java @RequiredArgsConstructor // final 필드를 넣는 생성자 자동 생성 @Service // 서비스 빈으로 등록 public class TokenProvider { private final JwtProperties jwtProperties; // 설정 값(issuer, secretKey) 주입 // 만료 기간(expiredAt)을 받아 현재 시간 기준으로 만료 시각을 계산하고 토큰 생성 public String generateToken(User user, Duration expiredAt) { Date now = new Date(); // 지금 시각 return makeToken(new Date(now.getTime() + expiredAt.toMillis()), user); // 만료 시각 계산 후 makeToken 호출 } // ① JWT 토큰 생성 메서드 private String makeToken(Date expiry, User user) { Date now = new Date(); return Jwts.builder() .setHeaderParam(Header.TYPE, Header.JWT_TYPE) // 헤더 typ : JWT .setIssuer(jwtProperties.getIssuer()) // 내용 iss : 설정 파일에서 가져온 발급자 .setIssuedAt(now) // 내용 iat : 현재 시간 .setExpiration(expiry) // 내용 exp : 전달받은 만료 시각 .setSubject(user.getEmail()) // 내용 sub : 사용자의 이메일 .claim("id", user.getId()) // 비공개 클레임 id : 사용자 ID // 서명 : 비밀키와 함께 HS256 방식으로 암호화 .signWith(SignatureAlgorithm.HS256, jwtProperties.getSecretKey()) .compact(); // 최종 JWT 문자열로 만듦 } }
  1. generateToken이 사용자와 유효 기간을 받습니다.
  2. 현재 시각에 기간을 더해 만료 시각을 계산합니다.
  3. makeToken이 헤더와 내용 항목을 채웁니다.
  4. 비밀키로 서명한 뒤 하나의 문자열로 만듭니다.
  5. 비밀키로 서명한 뒤 하나의 문자열로 만듭니다.

코드 한 줄씩 이해하기

코드하는 일
generateToken(User, Duration)호출하는 쪽에서 사용자와 유효 기간(예: 14일)을 넘기면, 만료 시각을 계산해 makeToken에 넘깁니다.
makeToken(Date, User)실제 토큰을 만드는 private 메서드입니다. 외부에서 직접 쓰지 않습니다.
Jwts.builder()JWT를 조립하는 빌더를 시작합니다.
setSubject(user.getEmail())토큰의 주인을 이메일로 표시합니다.
claim("id", user.getId())나중에 토큰에서 사용자 ID를 꺼낼 수 있도록 id를 비공개 클레임으로 넣습니다.
signWith(HS256, secretKey)비밀키로 서명해서, 토큰이 바뀌면 검증에 실패하도록 만듭니다.

검증·인증 정보·테스트

04단계TokenProvider에 검증과 조회 메서드 추가하기

같은 TokenProvider 클래스에 아래 메서드를 추가합니다. 앞에서 만든 makeToken 아래에 이어서 씁니다.

// ② JWT 토큰 유효성 검증 메서드 public boolean validToken(String token) { try { Jwts.parser() .setSigningKey(jwtProperties.getSecretKey()) // 비밀키로 복호화 시도 .parseClaimsJws(token); // 서명과 만료 시각을 검사 return true; // 에러가 없으면 유효한 토큰 } catch (Exception e) { // 복호화 과정에서 에러가 나면 return false; // 유효하지 않은 토큰 } } // ③ 토큰 기반으로 인증 정보를 가져오는 메서드 public Authentication getAuthentication(String token) { Claims claims = getClaims(token); // 토큰의 클레임 정보 꺼내기 Set<SimpleGrantedAuthority> authorities = Collections.singleton(new SimpleGrantedAuthority("ROLE_USER")); // 권한은 ROLE_USER 하나 // 스프링 시큐리티의 User 객체를 만들어 인증 객체로 돌려줌 return new UsernamePasswordAuthenticationToken( new org.springframework.security.core.userdetails.User( claims.getSubject(), "", authorities), // 사용자 이메일(sub)을 이름으로 사용 token, authorities); } // ④ 토큰 기반으로 유저 ID를 가져오는 메서드 public Long getUserId(String token) { Claims claims = getClaims(token); // 클레임 정보 꺼내기 return claims.get("id", Long.class); // id 키의 값을 Long으로 꺼냄 } // 토큰을 비밀키로 복호화한 뒤 클레임(내용)만 꺼내는 private 메서드 private Claims getClaims(String token) { return Jwts.parser() .setSigningKey(jwtProperties.getSecretKey()) .parseClaimsJws(token) .getBody(); // 내용(클레임) 부분 반환 }
⚠️ 주의: 두 개의 User 클래스 getAuthentication에서 쓰는 User는 우리가 만든 domain.User가 아니라 스프링 시큐리티가 제공하는 User 클래스입니다. 전체 이름(org.springframework.security.core.userdetails.User)을 써서 구분하세요. 우리가 만든 User를 넣으면 타입이 맞지 않습니다.
  1. 토큰 문자열을 받습니다.
  2. 비밀키로 복호화해 클레임을 꺼냅니다.
  3. 클레임의 sub(이메일)를 사용자 이름으로 씁니다.
  4. 인증 객체를 만들어 돌려줍니다.

테스트 코드 작성하기

05단계토큰을 만드는 것을 테스트하기 위해 JwtFactory를 test 디렉터리에 만듭니다. 테스트에서 필요한 값만 골라 넣을 수 있도록 빌더 패턴을 씁니다.

// test/.../config/jwt/JwtFactory.java @Getter public class JwtFactory { private String subject = "test@email.com"; // 기본 제목(sub) private Date issuedAt = new Date(); // 기본 발급 시각 private Date expiration = new Date(new Date().getTime() + Duration.ofDays(14).toMillis()); // 기본 만료 시각(14일 뒤) private Map<String, Object> claims = emptyMap(); // 추가 클레임(기본은 비어 있음) // 빌더 패턴을 사용해 설정이 필요한 데이터만 선택 설정 @Builder public JwtFactory(String subject, Date issuedAt, Date expiration, Map<String, Object> claims) { this.subject = subject != null ? subject : this.subject; // 값이 있으면 쓰고 없으면 기본값 this.issuedAt = issuedAt != null ? issuedAt : this.issuedAt; this.expiration = expiration != null ? expiration : this.expiration; this.claims = claims != null ? claims : this.claims; } // 기본값으로만 만든 객체를 반환 public static JwtFactory withDefaultValues() { return JwtFactory.builder().build(); } // jjwt 라이브러리를 사용해 JWT 토큰 생성 public String createToken(JwtProperties jwtProperties) { return Jwts.builder() .setSubject(subject) .setHeaderParam(Header.TYPE, Header.JWT_TYPE) .setIssuer(jwtProperties.getIssuer()) .setIssuedAt(issuedAt) .setExpiration(expiration) .addClaims(claims) .signWith(SignatureAlgorithm.HS256, jwtProperties.getSecretKey()) .compact(); } }

// RefreshToken.java (domain 패키지) @NoArgsConstructor(access = AccessLevel.PROTECTED) // 기본 생성자는 외부에서 못 쓰게 제한 @Getter @Entity public class RefreshToken { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) @Column(name = "id", updatable = false) private Long id; @Column(name = "user_id", nullable = false, unique = true) // 한 유저당 리프레시 토큰은 하나 private Long userId; @Column(name = "refresh_token", nullable = false) private String refreshToken; public RefreshToken(Long userId, String refreshToken) { this.userId = userId; // 어떤 유저의 토큰인지 저장 this.refreshToken = refreshToken; // 토큰 문자열 저장 } // 새 리프레시 토큰으로 값을 바꾸는 메서드 public RefreshToken update(String newRefreshToken) { this.refreshToken = newRefreshToken; return this; // 자기 자신을 돌려줌 } }

토큰 필터 흐름

토큰 필터는 요청이 컨트롤러에 도착하기 전에 실행되어, 요청 헤더의 토큰을 확인합니다. 토큰이 유효하면 시큐리티 컨텍스트 홀더에 인증 정보를 저장합니다.

  1. 요청이 들어옵니다.
  2. 필터가 헤더의 토큰이 유효한지 확인합니다.
  3. 유효하면 시큐리티 컨텍스트 홀더에 인증 정보를 저장하고 서비스 로직을 실행합니다.
  4. 유효하지 않으면 인증 정보 없이 넘어가고, 인증이 필요한 API는 거부됩니다.

03단계TokenAuthenticationFilter 만들기

config 디렉터리에 TokenAuthenticationFilter.java를 만듭니다. 이 필터는 Authorization 헤더 값을 가져와 Bearer 접두사를 떼고, 토큰이 유효하면 인증 정보를 설정합니다.

// TokenAuthenticationFilter.java (config 패키지) @RequiredArgsConstructor public class TokenAuthenticationFilter extends OncePerRequestFilter { // 요청당 한 번 실행되는 필터 private final TokenProvider tokenProvider; private final static String HEADER_AUTHORIZATION = "Authorization"; // 헤더 이름 private final static String TOKEN_PREFIX = "Bearer "; // 토큰 앞에 붙는 접두사 @Override protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain) throws ServletException, IOException { // ① 요청 헤더의 Authorization 키의 값 조회 String authorizationHeader = request.getHeader(HEADER_AUTHORIZATION); // ② 가져온 값에서 접두사 제거 String token = getAccessToken(authorizationHeader); // ③ 가져온 토큰이 유효한지 확인하고, 유효할 때는 인증 정보 설정 if (tokenProvider.validToken(token)) { Authentication authentication = tokenProvider.getAuthentication(token); SecurityContextHolder.getContext().setAuthentication(authentication); } // ④ 다음 필터(또는 컨트롤러)로 요청 넘기기 filterChain.doFilter(request, response); } // Bearer 접두사를 제외한 토큰 값을 돌려줌 private String getAccessToken(String authorizationHeader) { if (authorizationHeader != null && authorizationHeader.startsWith(TOKEN_PREFIX)) { return authorizationHeader.substring(TOKEN_PREFIX.length()); } return null; // 헤더가 없거나 Bearer로 시작하지 않으면 null } }
⚠️ 필터 등록은 다음 단계에서 이 필터는 만들었지만, 시큐리티 설정 파일에 등록하는 코드(예: addFilterBefore)는 이 전자책에 아직 포함되어 있지 않습니다. 등록 방법은 책의 다음 페이지에 있으니, 해당 내용을 받은 뒤 보완하겠습니다.
💡 시큐리티 컨텍스트 홀더란? 시큐리티 컨텍스트(security context)는 인증 객체를 저장해 두는 보관소입니다. 시큐리티 컨텍스트 홀더(security context holder)는 이 보관소를 저장하는 객체입니다. 스레드마다 공간을 따로 줘서 다른 요청과 섞이지 않고, 코드 어디서나 getContext().getAuthentication()으로 꺼내 쓸 수 있습니다.

03단계TokenService 만들기

service 디렉터리에 TokenService.java를 만듭니다. 이 클래스의 createNewAccessToken()은 다음 순서로 동작합니다.

  1. 리프레시 토큰이 유효한지 검사합니다. 유효하지 않으면 예외를 던집니다.
  2. 리프레시 토큰으로 DB에서 리프레시 토큰 객체를 찾아 사용자 ID를 꺼냅니다.
  3. 사용자 ID로 사용자를 찾습니다.
  4. 토큰 제공자의 generateToken()으로 새 액세스 토큰을 만들어 돌려줍니다.
// TokenService.java (service 패키지) @RequiredArgsConstructor @Service public class TokenService { private final TokenProvider tokenProvider; // 토큰 생성·검증 담당 private final RefreshTokenService refreshTokenService; // 리프레시 토큰 조회 담당 private final UserService userService; // 사용자 조회 담당 public String createNewAccessToken(String refreshToken) { // ① 토큰 유효성 검사에 실패하면 예외 발생 if (!tokenProvider.validToken(refreshToken)) { throw new IllegalArgumentException("Unexpected token"); } // ② 리프레시 토큰으로 사용자 ID 찾기 Long userId = refreshTokenService.findByRefreshToken(refreshToken).getUserId(); // ③ 사용자 ID로 사용자 찾기 User user = userService.findById(userId); // ④ 새 액세스 토큰 생성(유효 기간 2시간) return tokenProvider.generateToken(user, Duration.ofHours(2)); } }
  1. 리프레시 토큰을 받습니다.
  2. 먼저 토큰이 유효한지 검사합니다.
  3. 리프레시 토큰 테이블에서 userId를 찾습니다.
  4. userId로 사용자를 찾습니다.
  5. 사용자 정보로 새 액세스 토큰을 만듭니다.
  6. 검사에 실패하면 예외가 발생합니다.
💡 세 서비스의 역할 분담 TokenProvider는 토큰을 만들고 검사하는 일만 합니다. RefreshTokenService는 DB에서 리프레시 토큰을 찾고, UserService는 사용자를 찾습니다. TokenService는 이 셋을 조합해 “재발급”이라는 업무를 완성합니다.

10.3 토큰 API 구현하기

리프레시 토큰을 받아 검증하고, 유효하면 새 액세스 토큰을 응답하는 API를 만듭니다. 순서는 DTO → 컨트롤러 → 테스트입니다.

01단계DTO 만들기 (요청과 응답)

dto 디렉터리에 CreateAccessTokenRequest.java와 CreateAccessTokenResponse.java를 만듭니다.

// CreateAccessTokenRequest.java (dto 패키지) @Getter @Setter public class CreateAccessTokenRequest { private String refreshToken; // 클라이언트가 보낼 리프레시 토큰 } // CreateAccessTokenResponse.java (dto 패키지) @AllArgsConstructor // 모든 필드를 받는 생성자 자동 생성 @Getter public class CreateAccessTokenResponse { private String accessToken; // 응답으로 돌려줄 새 액세스 토큰 }

02단계TokenApiController 만들기

controller 디렉터리에 TokenApiController.java를 만듭니다. /api/token으로 POST 요청이 오면 토큰 서비스에 리프레시 토큰을 넘겨 새 액세스 토큰을 받습니다.

// TokenApiController.java (controller 패키지) @RequiredArgsConstructor @RestController public class TokenApiController { private final TokenService tokenService; // 토큰 발급 로직을 맡은 서비스 @PostMapping("/api/token") // POST /api/token 요청을 받음 public ResponseEntity<CreateAccessTokenResponse> createNewAccessToken( @RequestBody CreateAccessTokenRequest request) { // JSON 바디를 요청 객체로 변환 // 리프레시 토큰으로 새 액세스 토큰 생성 String newAccessToken = tokenService.createNewAccessToken(request.getRefreshToken()); // 201 Created 상태와 함께 새 액세스 토큰을 응답 return ResponseEntity.status(HttpStatus.CREATED) .body(new CreateAccessTokenResponse(newAccessToken)); } }
  1. 클라이언트가 리프레시 토큰을 JSON으로 보냅니다.
  2. 컨트롤러가 요청을 받아 서비스에 넘깁니다.
  3. 서비스가 검증하고 새 액세스 토큰을 만듭니다.
  4. 201 Created와 함께 새 토큰을 응답합니다.
  5. 새 토큰의 유효 기간은 2시간입니다.

03단계테스트 코드로 확인하기

테스트는 직접 진행해 결과를 확인합니다. test/.../controller 패키지에 TokenApiControllerTest.java를 만들고, createNewAccessToken() 메서드를 테스트합니다.

단계하는 일
Given테스트 유저를 만들고, jjwt 라이브러리로 리프레시 토큰을 만들어 DB에 저장합니다. 토큰 생성 API의 요청 본문에 넣을 요청 객체를 만듭니다.
When토큰 추가 API에 요청을 보냅니다. 요청 타입은 JSON이며, given 절에서 만든 객체를 요청 본문으로 보냅니다.
Then응답 코드가 201 Created인지 확인하고, 응답으로 온 액세스 토큰이 비어 있지 않은지 확인합니다.
// test/.../controller/TokenApiControllerTest.java @SpringBootTest @AutoConfigureMockMvc class TokenApiControllerTest { @Autowired protected MockMvc mockMvc; // 실제 서버 없이 API를 호출하는 도구 @Autowired protected ObjectMapper objectMapper; // 객체를 JSON 문자열로 바꾸는 도구 @Autowired private WebApplicationContext context; // 스프링 애플리케이션 설정 정보 @Autowired JwtProperties jwtProperties; @Autowired UserRepository userRepository; @Autowired RefreshTokenRepository refreshTokenRepository; @BeforeEach public void mockMvcSetUp() { this.mockMvc = MockMvcBuilders.webAppContextSetup(context).build(); // MockMvc 준비 userRepository.deleteAll(); // 테스트 전에 유저 데이터 비우기 } @DisplayName("createNewAccessToken: 새로운 액세스 토큰을 발급한다.") @Test public void createNewAccessToken() throws Exception { // given: 테스트 유저 저장 final String url = "/api/token"; User testUser = userRepository.save(User.builder() .email("user@gmail.com") .password("test") .build()); // given: 리프레시 토큰을 만들어 DB에 저장 String refreshToken = JwtFactory.builder() .claims(Map.of("id", testUser.getId())) .build() .createToken(jwtProperties); refreshTokenRepository.save(new RefreshToken(testUser.getId(), refreshToken)); // given: 요청 객체를 만들고 JSON 문자열로 변환 CreateAccessTokenRequest request = new CreateAccessTokenRequest(); request.setRefreshToken(refreshToken); final String requestBody = objectMapper.writeValueAsString(request); // when: POST /api/token 요청 보내기 ResultActions resultActions = mockMvc.perform(post(url) .contentType(MediaType.APPLICATION_JSON_VALUE) .content(requestBody)); // then: 201 응답이고 accessToken 값이 비어 있지 않은지 확인 resultActions .andExpect(status().isCreated()) .andExpect(jsonPath("$.accessToken").isNotEmpty()); } }
💡 import 빨간 줄 해결 post는 MockMvcRequestBuilders.post에서, jsonPath는 MockMvcResultMatchers.jsonPath에서 가져오는 정적 import입니다. 빨간 줄이 생기면 해당 줄에서 Alt+Enter를 눌러 import를 추가하세요.

테스트 결과

테스트를 실행하면 TokenApiControllerTest의 createNewAccessToken이 성공으로 표시됩니다. 실제 실행 결과가 초록색 체크로 보이면 리프레시 토큰으로 새 액세스 토큰을 발급받는 흐름이 정상 동작하는 것입니다.

⚠️ 실행이 실패하면 확인할 것 · refreshTokenRepository.save에 넣은 토큰이 JwtFactory로 만든 것인지 확인하세요.
· userRepository.deleteAll()을 실행하면 리프레시 토큰이 가리키는 유저가 사라질 수 있으니, 테스트 순서와 데이터를 함께 확인하세요.
· 요청 JSON의 키 이름이 refreshToken인지 확인하세요.

학습 마무리

토큰 기반 인증의 특징과 토큰의 일종인 JWT를 알아보고 직접 토큰 제공자를 만들었습니다. 토큰 기반 인증은 대중적으로 사용되며, 토큰 기반 인증에서는 JWT 인기가 높으므로 잘 알아두기 바랍니다.

핵심 요약

  1. 토큰 기반 인증은 인증에 토큰을 사용하는 방식입니다. 토큰은 클라이언트를 구분하는 데 사용하는 유일한 값으로서, 서버에서 생성해 클라이언트에게 제공한 뒤 클라이언트는 요청할 때마다 토큰을 함께 보냅니다. 서버는 토큰으로 유효한 사용자인지 검증합니다.
  2. JWT는 토큰 기반 인증에서 주로 사용하는 토큰입니다. JSON 형식으로 사용자의 정보를 저장하며, 헤더·내용·서명 구조로 이루어져 있습니다. 헤더는 토큰의 타입과 해싱 알고리즘을, 내용은 토큰에 담을 정보(클레임)를, 서명은 토큰이 변경되지 않았음을 확인하는 데 씁니다.
  3. 리프레시 토큰은 액세스 토큰과 별개의 토큰입니다. 액세스 토큰이 만료되었을 때 새로운 액세스 토큰을 발급받는 용도로 사용합니다.
  4. 필터는 실제로 요청이 전달되기 전과 후에 URL 패턴에 맞는 모든 요청을 처리하는 기능을 제공합니다.
  5. 시큐리티 컨텍스트는 인증 객체가 저장되는 보관소로, 인증 정보가 필요할 때 언제든지 인증 객체를 꺼내 사용하도록 제공되는 클래스입니다. 이러한 시큐리티 컨텍스트 객체를 저장하는 객체가 시큐리티 컨텍스트 홀더입니다.
🚨 실습 후 꼭 정리할 보안 원칙 · 비밀키는 코드와 깃에 두지 않고 환경 변수로 주입합니다.
· JWT 내용은 누구나 읽을 수 있으니 비밀번호 같은 정보를 넣지 않습니다.
· 액세스 토큰은 짧게, 리프레시 토큰은 서버에서 관리하며 필요하면 폐기할 수 있게 설계합니다.

연습문제

문제 1. 서버에서 클라이언트를 구분하기 위해 만든 유일한 값으로, 클라이언트가 요청할 때마다 함께 보내는 것은 무엇일까요?

정답: 토큰(토큰 기반 인증의 토큰)

문제 2. JWT의 세 부분 중, 토큰의 타입과 해싱 알고리즘을 담는 부분은 무엇일까요?

정답: 헤더(header)

문제 3. 액세스 토큰이 만료되었을 때 새로운 액세스 토큰을 발급받기 위해 사용하는 토큰은 무엇일까요?

정답: 리프레시 토큰(refresh token)

문제 4. 요청 헤더의 Authorization 키에 넣어 보내는 토큰 값의 접두사는 무엇일까요?

정답: Bearer

문제 5. 인증 객체를 저장하는 보관소를 무엇이라고 할까요? (시큐리티 컨텍스트를 저장하는 객체)

정답: 시큐리티 컨텍스트 홀더(security context holder)

문제 6(추가). JWT의 내용(payload)에 비밀번호를 넣으면 안 되는 이유는 무엇일까요?

정답 예시: 내용은 Base64로 인코딩된 것이라 누구나 해석할 수 있기 때문입니다. 서명은 위조를 막을 뿐 내용을 숨기지는 않습니다.
