11장 · OAuth2로 로그인/로그아웃 구현하기

10장까지 만든 블로그는 JWT 토큰으로 API를 보호했습니다. 이번 장에서는 사용자가 직접 아이디와 비밀번호를 입력하는 대신, 구글 계정으로 로그인하도록 바꿉니다. 이때 쓰는 표준 방식이 OAuth2입니다.

이 장에서 얻는 것 서버가 사용자 비밀번호를 직접 관리하지 않고, 구글 같은 제3의 서비스에게 "이 사용자가 누구인지" 확인받는 흐름을 이해합니다. 로그인 성공 후에는 10장의 JWT 액세스 토큰과 리프레시 토큰을 발급해 블로그 API에 연결합니다.

이 장의 핵심 키워드

OAuth2권한 부여 코드(Authorization Code)클라이언트 ID리다이렉트 URI쿠키(Cookie)Set-CookieBearer 토큰401 Unauthorized작성자(author)

완성 화면은 이렇게 동작합니다

  1. 블로그 글 목록(/articles)에 접근하면 로그인 화면으로 이동합니다.
  2. 로그인 화면의 Sign in with Google 버튼을 누르면 구글 계정 선택 화면이 열립니다.
  3. 로그인이 끝나면 서버가 액세스 토큰을 URL 파라미터로 붙여 글 목록 화면으로 돌려보냅니다.
  4. 브라우저의 localStorage에 액세스 토큰이 저장되고, 리프레시 토큰은 쿠키에 저장됩니다.
  5. 글을 등록하면 로그인한 사용자 이름이 글쓴이(author)로 기록됩니다.
  6. 내가 쓴 글만 수정·삭제할 수 있습니다. 남의 글을 수정하거나 삭제하면 실패 메시지가 나옵니다.
먼저 알아둘 점 이 장의 코드는 구글 클라우드 콘솔에서 발급받은 클라이언트 ID와 보안 비밀번호가 있어야 실행됩니다. 실습 전에 11.2절의 설정을 먼저 끝내세요. 또한 액세스 토큰을 URL에 붙이는 방식은 학습용 단순화입니다. 실제 서비스에서는 주소창에 토큰이 노출되지 않도록 더 안전한 전달 방식을 씁니다. 이 내용은 마지막 장의 "보안 메모"에서 다시 다룹니다.

11.1 OAuth란 무엇인가

OAuth는 사용자가 자신의 비밀번호를 다른 서비스에 알려주지 않고도, 그 서비스가 사용자의 정보에 제한된 범위로 접근할 수 있도록 허락하는 권한 위임(delegation) 표준입니다. 앱이 "구글 계정으로 로그인" 버튼을 제공할 때 바로 이 방식을 씁니다.

용어를 먼저 정리합니다

용어뜻이 프로젝트에서의 예
리소스 오너(Resource Owner)자신의 정보를 가진 사용자구글 계정을 가진 나
클라이언트(Client)사용자의 정보를 가져오려는 앱우리가 만드는 블로그 서버
인증 서버(Authorization Server)사용자를 확인하고 허락을 받는 서버구글 로그인 서버
리소스 서버(Resource Server)실제 정보(프로필 등)를 가진 서버구글의 사용자 정보 API

클라이언트가 정보를 얻는 4가지 방법 (승인 타입)

OAuth2 표준에는 클라이언트가 액세스 토큰을 얻는 방법이 여러 가지 있습니다. 그중 웹 서버 앱에서 가장 많이 쓰는 방식이 권한 부여 코드(Authorization Code) 방식입니다.

  • 권한 부여 코드(Authorization Code): 서버 앱에 적합합니다. 이 장에서 사용합니다.
  • 암시적 승인(Implicit): 브라우저 중심 앱에 쓰였지만 현재는 권장하지 않습니다.
  • 리소스 오너 비밀번호 자격 증명(Password): 사용자 비밀번호를 앱이 직접 받으므로 위임의 의미가 약합니다.
  • 클라이언트 자격 증명(Client Credentials): 사용자 없이 앱끼리 통신할 때 씁니다.

권한 부여 코드 흐름 한눈에 보기

아래 애니메이션으로 다섯 단계를 따라가 보세요.

  1. 단계 0: 아직 시작하지 않았습니다. "다음"을 눌러 흐름을 따라가 보세요.
  2. 1단계: 로그인 버튼을 누르면 우리 서버가 사용자를 구글로 보냅니다.
  3. 2단계: 구글이 권한 요청 화면을 보여 줍니다. 사용자가 허락합니다.
  4. 3단계: 구글이 인증 코드(code)를 우리 서버로 돌려보냅니다.
  5. 4단계: 우리 서버가 인증 코드를 구글에 다시 보내 액세스 토큰을 받습니다.
  6. 5단계: 액세스 토큰으로 사용자 정보를 받아 로그인을 완료합니다.
핵심 포인트 사용자는 구글 로그인 화면에 비밀번호를 우리 서버에 보내지 않습니다. 구글과 사용자 사이에서만 로그인이 이뤄지고, 우리 서버는 구글이 발급한 인증 코드를 받아 액세스 토큰을 얻습니다.

권한 요청 · 인증 코드 · 토큰 응답 · 쿠키

① 권한 요청 URI의 파라미터

사용자를 구글 로그인 화면으로 보낼 때 우리 서버는 아래 형태의 주소로 리다이렉트합니다. 주소 뒤의 파라미터가 "누가, 어디로, 무엇을 요청하는지"를 알려줍니다.

파라미터의미
client_id구글 콘솔에서 발급받은 우리 앱의 ID
redirect_uri인증이 끝난 뒤 구글이 돌려보낼 주소. 콘솔에 미리 등록한 주소와 정확히 같아야 합니다.
response_type받고 싶은 응답 종류. 권한 부여 코드 방식은 code
scope요청하는 정보 범위. 예: email, profile, openid
# 권한 요청 URI 형태 (실제 값은 구글 콘솔에서 발급받음) https://accounts.google.com/o/oauth2/v2/auth ?client_id=발급받은_클라이언트_ID &redirect_uri=http://localhost:8080/login/oauth2/code/google &response_type=code &scope=email%20profile
주의: redirect_uri는 정확히 일치해야 합니다 한 글자라도 다르면(예: localhost와 127.0.0.1, 끝의 슬래시 유무) 구글이 요청을 거부합니다. 이 프로젝트에서는 http://localhost:8080/login/oauth2/code/google을 사용합니다.

② 인증 코드와 액세스 토큰

사용자가 구글에서 허락을 누르면 구글은 우리 서버로 인증 코드(code)를 보냅니다. 이 코드는 잠깐 쓰는 임시 열쇠이고, 서버가 이 코드를 구글에 다시 제출하면 액세스 토큰을 받습니다. 액세스 토큰으로 사용자의 이름과 이메일 같은 정보를 조회합니다.

  1. 단계 0: 사용자가 허락하면 구글이 인증 코드를 보냅니다.
  2. 1단계: 사용자가 허락하면 구글이 인증 코드를 보냅니다. 일회성 열쇠입니다.
  3. 2단계: 인증 코드를 구글에 제출하면 액세스 토큰을 받습니다.
  4. 3단계: 액세스 토큰으로 이름과 이메일을 조회해 DB에 저장합니다.

③ 쿠키(Cookie)란 무엇인가

쿠키는 서버가 브라우저에 맡겨 두는 작은 데이터 조각입니다. 서버가 응답 헤더에 Set-Cookie를 넣으면 브라우저가 저장하고, 같은 사이트로 요청을 보낼 때마다 Cookie 헤더에 실어 다시 보냅니다. 이 장에서는 리프레시 토큰과 인증 요청 정보를 쿠키에 담습니다.

  1. 단계 0: 서버가 응답에 쿠키를 담아 보냅니다.
  2. 1단계: 서버가 응답 헤더에 쿠키 저장을 맡깁니다(Set-Cookie).
  3. 2단계: 브라우저가 쿠키를 저장한 뒤 다음 요청을 준비합니다.
  4. 3단계: 브라우저는 같은 사이트 요청마다 Cookie 헤더로 쿠키를 되돌려 보냅니다.
쿠키 vs localStorage 쿠키는 요청마다 자동으로 서버에 전송되고, 서버가 만료 시간과 경로를 정할 수 있습니다. localStorage는 자바스크립트로만 읽고 쓰며 요청마다 자동 전송되지 않습니다. 이 장에서는 리프레시 토큰은 쿠키에, 액세스 토큰은 localStorage에 저장합니다.

11.2 구글 클라우드에서 토큰 발급받기

우리 서버가 구글 로그인을 쓰려면 먼저 구글에 "이런 앱이 있으니 로그인 기능을 허락해 달라"고 등록해야 합니다. 등록이 끝나면 구글이 클라이언트 ID와 보안 비밀번호(클라이언트 보안 비밀)를 발급합니다. 이 두 값이 우리 앱의 신분증 역할을 합니다.

콘솔 화면은 바뀔 수 있습니다 구글 클라우드 콘솔의 메뉴 이름과 위치는 시기에 따라 조금씩 달라질 수 있습니다. 아래 순서는 책의 흐름을 기준으로 정리한 것이며, 화면에 보이는 이름이 다르면 같은 의미의 메뉴를 찾아 주세요.

설정 순서 (12단계 요약)

  1. 1구글 클라우드 콘솔(cloud.google.com)에 접속해 구글 계정으로 로그인합니다.
  2. 2상단에서 새 프로젝트를 만듭니다. 이름은 예를 들어 springboot-developer로 정합니다.
  3. 3왼쪽 메뉴에서 API 및 서비스를 엽니다.
  4. 4그 아래 OAuth 동의 화면(또는 사용자 인증 정보 탭의 동의 화면 구성)으로 들어갑니다.
  5. 5사용자 유형에서 외부를 선택하고 만듭니다.
  6. 6앱 이름, 사용자 지원 이메일, 개발자 연락처 이메일을 입력합니다.
  7. 7데이터 액세스 범위에서 email과 openid(또는 profile)를 추가합니다.
  8. 8동의 화면 설정을 저장하고 완료합니다.
  9. 9사용자 인증 정보 → 사용자 인증 정보 만들기 → OAuth 클라이언트 ID를 선택합니다.
  10. 10애플리케이션 유형은 웹 애플리케이션으로 고릅니다.
  11. 11승인된 리디렉션 URI에 http://localhost:8080/login/oauth2/code/google을 입력합니다.
  12. 12만들기를 누르면 나오는 클라이언트 ID와 보안 비밀번호를 메모해 둡니다.
  1. 단계 0: 프로젝트를 만든 뒤, 동의 화면과 클라이언트 ID를 차례로 만듭니다.
  2. 1단계: 콘솔에서 발급받은 클라이언트 ID와 보안 비밀번호를 메모합니다.
  3. 2단계: 메모한 값을 application.yml의 google 등록 정보에 입력합니다.
테스트 사용자 동의 화면을 "테스트" 상태로 두면 구글 계정 중 테스트 사용자로 등록된 계정만 로그인할 수 있는 경우가 있습니다. 실습 중 "액세스 차단" 메시지가 나오면 본인 계정을 테스트 사용자에 추가했는지 확인하세요.
클라이언트 보안 비밀번호는 외부에 공개하지 마세요 보안 비밀번호가 GitHub 같은 공개 저장소에 올라가면 누구든 우리 앱을 사칭할 수 있습니다. 실제 서비스에서는 환경 변수나 별도 비밀 설정 파일로 분리합니다.

11.3 스프링 시큐리티로 OAuth2 구현하기

① 의존성 추가

OAuth2 로그인을 지원하는 스타터를 build.gradle에 추가합니다. 9장에서 추가한 시큐리티 스타터는 그대로 둡니다.

# build.gradle 의 dependencies 블록에 추가 implementation 'org.springframework.boot:spring-boot-starter-oauth2-client'

② application.yml에 구글 설정 추가

11.2절에서 메모한 값을 넣습니다. 기존 jwt 설정은 그대로 둡니다.

# src/main/resources/application.yml spring: security: oauth2: client: registration: google: client-id: <<구글에서 발급받은 클라이언트 ID>> client-secret: <<구글에서 발급받은 보안 비밀번호>> scope: - email - profile
여기서 google은 우리가 정한 이름입니다 registration 아래의 google은 스프링이 구글 설정을 찾기 위해 쓰는 이름입니다. 뒤에 나오는 리디렉션 주소 /login/oauth2/code/google의 google과 이 이름이 일치해야 스프링이 응답을 제대로 받습니다.

③ CookieUtil: 쿠키를 다루는 도구 클래스

쿠키를 추가하고, 삭제하고, 객체를 쿠키 값으로 바꾸거나 되돌리는 메서드를 한곳에 모읍니다. 이 클래스는 util 패키지에 만듭니다.

// src/main/java/me/shinsunyoung/springbootdeveloper/util/CookieUtil.java package me.shinsunyoung.springbootdeveloper.util; import jakarta.servlet.http.Cookie; import jakarta.servlet.http.HttpServletRequest; import jakarta.servlet.http.HttpServletResponse; import org.springframework.util.SerializationUtils; import java.util.Base64; public class CookieUtil { // 요청값(이름, 값, 만료 기간)을 바탕으로 쿠키를 추가 public static void addCookie(HttpServletResponse response, String name, String value, int maxAge) { Cookie cookie = new Cookie(name, value); cookie.setPath("/"); // 사이트 모든 경로에서 쿠키 사용 cookie.setMaxAge(maxAge); // 만료 시간(초 단위) response.addCookie(cookie); } // 쿠키 이름을 받아 같은 이름의 쿠키를 삭제 public static void deleteCookie(HttpServletRequest request, HttpServletResponse response, String name) { Cookie[] cookies = request.getCookies(); if (cookies == null) { return; } for (Cookie cookie : cookies) { if (name.equals(cookie.getName())) { cookie.setValue(""); // 값을 비우고 cookie.setPath("/"); cookie.setMaxAge(0); // 만료 시간을 0으로 하면 브라우저가 바로 지운다 response.addCookie(cookie); } } } // 객체를 직렬화한 뒤 Base64로 바꿔 쿠키 값으로 쓸 수 있게 만든다 public static String serialize(Object obj) { return Base64.getUrlEncoder().encodeToString(SerializationUtils.serialize(obj)); } // 쿠키 값을 Base64로 풀고 역직렬화해 원래 객체로 되돌린다 public static <T> T deserialize(Cookie cookie, Class<T> cls) { return cls.cast(SerializationUtils.deserialize(Base64.getUrlDecoder().decode(cookie.getValue()))); } }
왜 직렬화(serialize)가 필요한가요? 쿠키는 문자열만 담을 수 있습니다. 하지만 OAuth2 인증 요청 정보는 여러 필드를 가진 객체입니다. 객체를 바이트로 바꾸고(직렬화), 다시 문자열로 인코딩해 쿠키에 넣고, 나중에 꺼내 원래 객체로 되돌리는(역직렬화) 과정이 필요합니다.
  1. 단계 0: 객체 하나가 쿠키에 들어가기까지의 과정입니다.
  2. 1단계: 인증 요청 객체를 직렬화해 바이트 배열로 바꿉니다.
  3. 2단계: 바이트 배열을 Base64로 인코딩해 문자열로 만듭니다.
  4. 3단계: 문자열을 쿠키 값에 담아 브라우저에 저장합니다.

사용자 저장 로직과 OAuth2 서비스

구글 로그인이 성공하면 구글이 사용자 정보를 돌려줍니다. 우리 서버는 이 정보로 이미 가입한 사용자인지 확인하고, 없으면 새로 저장합니다. 이 일을 맡는 것이 OAuth2UserCustomService입니다.

① User 엔티티에 nickname 추가

구글에서 받은 이름을 블로그에서 보여 줄 별명으로 씁니다. 9장의 User 클래스에 nickname 컬럼을 추가하고, 빌더와 수정 메서드를 함께 갖춥니다.

비밀번호 인코더를 서비스 안에서 만드는 이유 책에서는 UserService의 PasswordEncoder 주입을 지우고 new BCryptPasswordEncoder()로 직접 만듭니다. 시큐리티 설정 클래스와 서비스 사이에서 순환 참조가 생기는 문제를 피하기 위한 선택입니다. 기능은 같습니다.

③ OAuth2UserCustomService: 구글 사용자 정보 처리

DefaultOAuth2UserService를 상속해 loadUser()에서 구글 정보를 받아 저장하도록 바꿉니다.

// src/main/java/.../service/OAuth2UserCustomService.java package me.shinsunyoung.springbootdeveloper.service; import lombok.RequiredArgsConstructor; import me.shinsunyoung.springbootdeveloper.domain.User; import me.shinsunyoung.springbootdeveloper.repository.UserRepository; import org.springframework.security.oauth2.client.userinfo.DefaultOAuth2UserService; import org.springframework.security.oauth2.client.userinfo.OAuth2UserRequest; import org.springframework.security.oauth2.core.OAuth2AuthenticationException; import org.springframework.security.oauth2.core.user.OAuth2User; import org.springframework.stereotype.Service; import java.util.Map; @RequiredArgsConstructor @Service public class OAuth2UserCustomService extends DefaultOAuth2UserService { private final UserRepository userRepository; // 구글이 사용자 정보를 돌려주면 호출된다 @Override public OAuth2User loadUser(OAuth2UserRequest userRequest) throws OAuth2AuthenticationException { OAuth2User user = super.loadUser(userRequest); // 구글 API에서 사용자 정보 조회 saveOrUpdate(user); // 우리 DB에 저장 또는 갱신 return user; } private User saveOrUpdate(OAuth2User oAuth2User) { Map<String, Object> attributes = oAuth2User.getAttributes(); String email = (String) attributes.get("email"); String name = (String) attributes.get("name"); User user = userRepository.findByEmail(email) .map(entity -> entity.update(name)) // 이미 있으면 이름만 갱신 .orElse(User.builder() // 없으면 새로 만든다 .email(email) .nickname(name) .build()); return userRepository.save(user); } }
  1. 단계 0: 구글이 준 정보를 받아 이메일로 기존 사용자를 찾습니다.
  2. 1단계: 구글이 준 이메일과 이름을 꺼냅니다.
  3. 2단계: 이메일로 우리 DB에서 기존 사용자를 찾습니다.
  4. 3단계: 이미 있는 사용자라면 이름만 갱신합니다.
  5. 4단계: 없는 사용자라면 새로 만들어 저장합니다.
map과 orElse의 역할 findByEmail은 Optional을 돌려줍니다. 값이 있으면 map이 이름을 갱신하고, 없으면 orElse가 새 사용자를 만듭니다. 한 줄로 "있으면 수정, 없으면 생성"을 표현한 것입니다.

① OAuth2AuthorizationRequestBasedOnCookieRepository

OAuth2 로그인은 "구글로 보내기 전 요청 정보"를 잠시 저장해 두었다가 돌아왔을 때 꺼내 씁니다. 기본 구현은 세션을 쓰지만, 우리는 STATELESS(무상태) 설정을 쓰므로 세션 대신 쿠키에 저장합니다. 이 클래스는 config.oauth 패키지에 만듭니다.

// src/main/java/.../config/oauth/OAuth2AuthorizationRequestBasedOnCookieRepository.java package me.shinsunyoung.springbootdeveloper.config.oauth; import jakarta.servlet.http.Cookie; import jakarta.servlet.http.HttpServletRequest; import jakarta.servlet.http.HttpServletResponse; import me.shinsunyoung.springbootdeveloper.util.CookieUtil; import org.springframework.security.oauth2.client.web.AuthorizationRequestRepository; import org.springframework.security.oauth2.core.endpoint.OAuth2AuthorizationRequest; import org.springframework.util.StringUtils; import java.util.Arrays; public class OAuth2AuthorizationRequestBasedOnCookieRepository implements AuthorizationRequestRepository<OAuth2AuthorizationRequest> { public static final String OAUTH2_AUTHORIZATION_REQUEST_COOKIE_NAME = "oauth2_auth_request"; public static final int COOKIE_EXPIRE_SECONDS = 18000; // 5시간 // 쿠키에서 인증 요청 정보를 꺼낸다 @Override public OAuth2AuthorizationRequest loadAuthorizationRequest(HttpServletRequest request) { Cookie cookie = findCookie(request, OAUTH2_AUTHORIZATION_REQUEST_COOKIE_NAME); return cookie == null ? null : CookieUtil.deserialize(cookie, OAuth2AuthorizationRequest.class); } // 인증 요청 정보를 직렬화해 쿠키에 저장한다 @Override public void saveAuthorizationRequest(OAuth2AuthorizationRequest authorizationRequest, HttpServletRequest request, HttpServletResponse response) { if (authorizationRequest == null) { removeAuthorizationRequestCookies(request, response); return; } CookieUtil.addCookie(response, OAUTH2_AUTHORIZATION_REQUEST_COOKIE_NAME, CookieUtil.serialize(authorizationRequest), COOKIE_EXPIRE_SECONDS); } // 로그인이 끝나면 쿠키 값을 읽어 돌려주기만 하고, 실제 삭제는 성공 핸들러에서 한다 @Override public OAuth2AuthorizationRequest removeAuthorizationRequest(HttpServletRequest request) { return this.loadAuthorizationRequest(request); } // 인증 요청 쿠키를 삭제한다 public void removeAuthorizationRequestCookies(HttpServletRequest request, HttpServletResponse response) { CookieUtil.deleteCookie(request, response, OAUTH2_AUTHORIZATION_REQUEST_COOKIE_NAME); } // 이름이 같은 쿠키를 찾는 보조 메서드 private Cookie findCookie(HttpServletRequest request, String name) { if (request.getCookies() == null) { return null; } return Arrays.stream(request.getCookies()) .filter(c -> StringUtils.hasText(c.getValue()) && c.getName().equals(name)) .findFirst() .orElse(null); } }
저장소 구현은 세 줄로 요약됩니다 "저장: 직렬화해서 쿠키에 넣기", "조회: 쿠키를 찾아 역직렬화하기", "삭제: 쿠키 지우기". 이 세 동작이 전부입니다.
세부 구현은 표준 방식으로 정리했습니다 이 페이지의 loadAuthorizationRequest와 findCookie 부분은 저장·조회·삭제라는 역할을 설명하기 위해 표준 구현 방식으로 정리한 것입니다. 책 원문의 세부 코드와 다를 수 있으니, 실습 때는 책의 코드를 기준으로 맞추세요.

OAuth2SuccessHandler: 로그인 성공 후 처리

구글 로그인이 성공하면 스프링은 OAuth2SuccessHandler를 호출합니다. 이 클래스가 하는 일은 네 가지입니다. ❶ 리프레시 토큰을 만들어 저장하고 쿠키에 넣기 ❷ 액세스 토큰을 만들기 ❸ 임시 인증 쿠키 지우기 ❹ 액세스 토큰을 붙여 글 목록으로 리다이렉트하기.

  1. 단계 0: 로그인이 성공하면 성공 핸들러가 호출됩니다.
  2. ❶ 리프레시 토큰을 만들어 DB와 쿠키에 저장합니다.
  3. ❷ 액세스 토큰을 만듭니다.
  4. ❸ 인증 요청 쿠키를 정리합니다.
  5. ❹ 액세스 토큰을 붙여 글 목록으로 이동합니다.

refreshTokenRepository.save(refreshToken); } // 리프레시 토큰을 쿠키에 담는다 (14일) private void addRefreshTokenToCookie(HttpServletRequest request, HttpServletResponse response, String token) { int cookieMaxAge = (int) REFRESH_TOKEN_DURATION.toSeconds(); CookieUtil.deleteCookie(request, response, REFRESH_TOKEN_COOKIE_NAME); CookieUtil.addCookie(response, REFRESH_TOKEN_COOKIE_NAME, token, cookieMaxAge); } // 액세스 토큰을 URL의 token 파라미터로 붙인 주소를 만든다 private String getTargetUrl(String token) { return UriComponentsBuilder.fromUriString(REDIRECT_PATH) .queryParam("token", token) .build() .toUriString(); } // 부모 클래스의 임시 인증 속성 정리 호출 private void clearAuthenticationAttributes(HttpServletRequest request) { super.clearAuthenticationAttributes(request); } }
URL에 토큰을 붙이는 방식의 한계 /articles?token=...처럼 주소에 토큰을 붙이면 브라우저 기록, 서버 로그, 다른 사이트로 가는 Referer 헤더에 토큰이 남을 수 있습니다. 이 장에서는 흐름을 이해하기 쉽도록 이 방식을 씁니다. 바로 다음 화면의 token.js가 주소에서 토큰을 꺼내 저장하고 주소창에서는 지우므로 노출 시간은 짧습니다.
리프레시 토큰은 두 곳에 있습니다 DB의 refresh_token 테이블(서버 쪽 기록)과 브라우저의 refresh_token 쿠키(클라이언트 쪽 열쇠)입니다. 10장의 /api/token은 쿠키의 값을 받아 DB 기록과 맞춰 본 뒤 새 액세스 토큰을 줍니다.

이제 article.js가 서버에 요청을 보낼 때마다 액세스 토큰을 붙이도록 바꿉니다. 여기서 가장 중요한 것은 httpRequest() 함수입니다. 요청이 401(권한 없음)로 실패하면 리프레시 토큰으로 새 액세스 토큰을 받아 같은 요청을 한 번 더 보냅니다.

① 토큰 재발급 흐름

  1. 단계 0: 액세스 토큰이 만료된 상태에서 글 등록을 시도합니다.
  2. 1단계: 만료된 액세스 토큰으로 요청하면 서버가 401을 돌려줍니다.
  3. 2단계: 화면은 refresh_token 쿠키가 있는지 확인합니다.
  4. 3단계: 리프레시 토큰을 담아 /api/token을 호출합니다.
  5. 4단계: 서버가 새 액세스 토큰을 응답합니다.
  6. 5단계: 화면이 localStorage의 액세스 토큰을 새 값으로 바꿉니다.
  7. 6단계: 같은 요청을 새 토큰으로 다시 보내 201 Created로 성공합니다.

② getCookie(): 쿠키 값 꺼내기

자바스크립트에서 쿠키는 document.cookie 문자열 하나로 보입니다. 이 함수는 원하는 이름의 값을 찾아 돌려줍니다.

// 쿠키를 가져오는 함수 function getCookie(key) { var result = null; var cookie = document.cookie.split(";"); // "a=1; b=2" 를 ";" 기준으로 나눔 cookie.some(function (item) { item = item.replace(" ", ""); // 앞의 공백 제거 var dic = item.split("="); // ["이름", "값"] 으로 나눔 if (key === dic[0]) { result = dic[1]; return true; // 찾았으면 반복 중단 } }); return result; }

③ httpRequest(): 토큰을 붙이고, 401이면 재발급

// HTTP 요청을 보내는 함수 function httpRequest(method, url, body, success, fail) { fetch(url, { method: method, headers: { // 로컬 스토리지에서 액세스 토큰 값을 가져와 헤더에 추가 Authorization: "Bearer " + localStorage.getItem("access_token"), "Content-Type": "application/json", }, body: body, }).then((response) => { if (response.status === 200 || response.status === 201) { return success(); } const refresh_token = getCookie("refresh_token"); if (response.status === 401 && refresh_token) { // 리프레시 토큰으로 새 액세스 토큰 요청 fetch("/api/token", { method: "POST", headers: { Authorization: "Bearer " + localStorage.getItem("access_token"), "Content-Type": "application/json", }, body: JSON.stringify({ refreshToken: getCookie("refresh_token"), }), }) .then((res) => { if (res.ok) { return res.json(); } }) .then((result) => { // 재발급이 성공하면 로컬 스토리지 값을 새 액세스 토큰으로 교체 localStorage.setItem("access_token", result.accessToken); httpRequest(method, url, body, success, fail); // 원래 요청을 다시 보냄 }) .catch((error) => fail()); } else { return fail(); } }); }
함수가 자기 자신을 다시 부르는 구조입니다 httpRequest 안에서 httpRequest를 다시 호출하는 재귀 호출입니다. 새 토큰도 거절되면 또 401이 나오고, 리프레시 토큰이 남아 있으면 같은 과정을 반복할 수 있습니다. 학습용 코드에서는 이 흐름을 이해하는 것이 목적이며, 실제 서비스라면 재시도 횟수를 1회로 제한하는 장치를 넣어야 합니다.
책의 흐름과 맞물리는 이유 10장에서 만든 TokenService는 리프레시 토큰이 유효하면 새 액세스 토큰을 줍니다. 그리고 11장의 WebOAuthSecurityConfig는 인증이 없는 /api/** 요청에 401을 돌려줍니다. 이 두 가지가 있어야 위의 재발급 흐름이 작동합니다.

authorizeArticleAuthor의 원리 (개념 예시) 이 메서드의 본문은 이 페이지의 원문에 나오지 않아, 원리를 보여 주는 예시로 정리합니다. 시큐리티 컨텍스트에서 로그인한 사용자 이름을 꺼내 글의 author와 비교합니다. 다르면 예외를 던집니다. 책의 실제 코드와 비교해 보세요.
// 개념 예시: 요청자와 작성자 비교 private void authorizeArticleAuthor(Article article) { String userName = SecurityContextHolder.getContext().getAuthentication().getName(); if (!article.getAuthor().equals(userName)) { throw new IllegalArgumentException("not authorized"); // 남의 글이면 예외 } }
예외가 500으로 나오는 이유 학습용 코드는 IllegalArgumentException을 그대로 던지므로 응답이 500 Internal Server Error로 나옵니다. "권한 없음"을 정확히 알리려면 403 Forbidden을 돌려주는 별도 예외 처리를 추가하는 것이 바람직합니다. 11장 과제에서 한 번 도전해 보세요.

서버를 실행하고 브라우저에서 직접 확인해 봅니다. 아래 순서대로 따라 하면 OAuth2 로그인과 토큰 재발급, 그리고 작성자 권한 확인이 모두 동작하는지 볼 수 있습니다.

① 로그인 흐름 확인

  1. 1브라우저에서 http://localhost:8080/articles에 접속합니다. 로그인하지 않았으므로 /login 화면으로 이동해야 합니다.
  2. 2구글 버튼을 눌러 계정을 고르고 허락합니다.
  3. 3글 목록으로 돌아오면 주소창에 ?token=...이 잠깐 보였다가 사라지는지 확인합니다.
  4. 4개발자 도구(F12)의 Application 탭에서 localStorage에 access_token이 저장되어 있는지, Cookies에 refresh_token이 있는지 봅니다.
  5. 5H2 콘솔에서 SELECT * FROM users를 실행해 내 이메일과 닉네임이 저장되었는지 확인합니다.

② 토큰 재발급 흐름 확인

  1. 1개발자 도구의 Application 탭에서 access_token을 삭제합니다. 리프레시 토큰 쿠키는 그대로 둡니다.
  2. 2/new-article 화면으로 이동해 글을 작성하고 등록을 누릅니다.
  3. 3Network 탭을 보면 articles 요청이 401로 실패한 뒤, token 요청이 200으로 성공하고, 이어서 articles가 다시 요청되어 성공합니다.
  4. 4글이 정상으로 등록되면 성공입니다. 사용자는 중간 과정을 보지 못하지만, 개발자 도구에서는 이 과정이 모두 보입니다.
이 흐름이 보이면 장 전체가 연결된 것입니다 401 → 리프레시 토큰으로 재발급 → 같은 요청 재시도. 이 세 단계는 이 장의 httpRequest 함수, 10장의 TokenService와 /api/token, 11장의 WebOAuthSecurityConfig가 함께 만들어 낸 결과입니다.

③ 남의 글 수정·삭제 확인

  1. 1샘플 글(작성자가 user1 등)의 상세 화면에서 삭제를 누릅니다.
  2. 2"삭제 실패했습니다." 알림이 뜨고 글이 지워지지 않는지 확인합니다.
  3. 3Network 탭에서 해당 요청의 상태 코드를 확인합니다. 학습용 코드에서는 500으로 나옵니다.
  4. 4내가 등록한 글은 수정과 삭제가 모두 성공하는지도 확인합니다.

④ 로그아웃 과제: 서버 쪽 토큰까지 정리하기

이 프로젝트는 토큰을 수동으로 지우는 방식으로 로그아웃을 마무리했습니다. 깔끔하게 끝내려면 로그아웃 버튼을 누를 때 서버의 리프레시 토큰 기록도 삭제해야 합니다. 그래서 DELETE /api/refresh-token API를 완성하는 것이 과제입니다. 아래 파일을 수정하세요.

  • controller/TokenApiController.java: DELETE 요청을 받는 메서드 추가
  • repository/RefreshTokenRepository.java: 사용자 ID로 리프레시 토큰을 찾는 메서드 확인
  • service/RefreshTokenService.java: 리프레시 토큰을 삭제하는 메서드 추가
  • static/js/article.js: 로그아웃 버튼의 요청이 이 API를 부르는지 확인
  • templates/articleList.html: 로그아웃 버튼 연결 확인
  • test/.../controller/TokenApiControllerTest.java: 삭제 API 테스트 추가
힌트 서버는 쿠키를 직접 지울 수 없고, 응답 헤더로 지우라고 알려 줄 수 있습니다. 이 장의 CookieUtil.deleteCookie()를 떠올리세요. 응답에서 쿠키를 지우면서 DB의 리프레시 토큰 행도 삭제하는 것이 목표입니다.

보안 메모: 학습용과 실제 서비스의 차이

이 장의 방식실제 서비스에서 더 안전한 방식
액세스 토큰을 URL 파라미터로 전달응답 본문이나 HttpOnly 쿠키로 전달하고 주소창에 노출하지 않음

CSRF 보호 끄기쿠키 기반 인증을 쓸 때는 CSRF 토큰 또는 SameSite 쿠키 설정 적용

남의 글을 수정하거나 삭제할 때 500 대신 403 Forbidden을 돌려주도록 예외 처리를 추가해 보세요. 힌트: 권한 예외를 따로 만들고, 예외 처리 메서드에서 응답 상태를 지정합니다.

DELETE /api/refresh-token을 구현하고, 응답에서 refresh_token 쿠키를 지우도록 만드세요. 그다음 로그아웃 버튼 흐름을 다시 테스트합니다.

문제 4. 재시도 횟수 제한하기

확인 퀴즈

Q1. 권한 부여 코드 방식에서 구글이 우리 서버에 먼저 주는 것은?

정답: 인증 코드(code). 서버는 이 코드를 구글에 다시 보내고 액세스 토큰을 받습니다.

Q2. 쿠키에 객체를 담으려면 직렬화가 필요한 이유는?

정답: 쿠키는 문자열 값만 담을 수 있기 때문입니다. 객체를 바이트로 바꾸고 Base64로 인코딩해 문자열로 만든 뒤 저장합니다.

Q3. 화면의 요청이 401을 받았을 때 올바른 처리 순서는?

정답: 리프레시 토큰으로 /api/token을 호출 → 새 액세스 토큰을 localStorage에 저장 → 같은 요청을 다시 보냄.

Q4. redirect_uri가 콘솔 등록값과 다르면 어떻게 될까?

정답: 구글이 요청을 거부합니다. 한 글자라도 다르면 인증 자체가 진행되지 않습니다.

Q5. 내가 쓰지 않은 글을 삭제하면 왜 실패할까?

정답: authorizeArticleAuthor에서 요청자 이름과 글의 author가 달라 예외가 발생하기 때문입니다.
