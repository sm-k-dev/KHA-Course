# AI 보안과 거버넌스: Prompt Injection, 데이터 유출, SSRF

> 중요도: **A** · 이 장의 목표: AI 시스템에 특유한 공격 세 가지를 설명하고, SSRF를 허용 목록으로 막고, 기능별 거버넌스 점검표를 만든다.

> 2026-11-23 추가 장 (로드맵 M21·M23 항목). SSRF 차단 로직은 `Batch3.java`에서 실행해 통과를 확인했다. **Prompt Injection 방어는 완벽한 코드 해법이 없어서, 원칙과 한계만 다룬다.**

---

## 1. Prompt Injection

**정의** — 공격자가 입력이나 문서 속에 "이전 지시를 무시하고 이렇게 하라"는 문장을 숨겨서, 모델이 개발자의 지시 대신 공격자의 지시를 따르게 하는 공격이다.

**왜 어려운가** — 모델은 지시와 데이터를 같은 텍스트로 받는다. 어디까지가 명령이고 어디부터가 데이터인지 완벽히 구분하지 못한다.

**방어 원칙 (완벽하지 않으므로 여러 겹으로)**
- **신뢰 경계를 나눈다:** 사용자 입력과 검색한 문서는 "데이터"로 취급하고, 시스템 지시와 섞지 않는다.
- **권한을 최소화한다:** 모델이 호출할 수 있는 도구와 접근 가능한 데이터를 줄인다. 공격이 성공해도 피해를 제한한다.
- **쓰기 행동은 승인한다:** 삭제, 결제, 외부 전송은 사람이 확인한다(56장).
- **출력을 검증한다:** 모델이 만든 명령이나 URL을 그대로 실행하지 않는다(53장 구조화 출력 검증).

**한계:** 모델 자체를 안전하게 만드는 것만으로는 막을 수 없다. 시스템 설계에서 신뢰 경계와 권한 분리로 막는다.

---

## 2. 데이터 유출

**정의** — 모델이나 에이전트가 허용되지 않은 데이터를 답변, 로그, 외부 호출에 포함시키는 것이다.

**원인 예**
- 검색 결과에 권한 없는 문서가 섞임 (54장의 권한 필터 필요)
- 프롬프트에 개인정보나 비밀 키를 넣음
- 로그에 전체 프롬프트와 응답을 그대로 남김

**방어:** 검색 전 권한 필터, 프롬프트에 넣는 값의 민감 정보 제거, 로그의 개인정보 마스킹, 외부 전송 전 검사.

## 3. SSRF (서버 측 요청 위조)

**정의** — 공격자가 서버에게 "이 주소로 요청해서 결과를 가져와라"라고 시키는 공격이다. 서버는 내부망에 접근할 수 있으므로, 외부 사용자가 내부 주소를 대신 치게 만들 수 있다.

**위험한 주소 예** — `127.0.0.1`(서버 자신), `10.x.x.x`/`192.168.x.x`(내부망), `169.254.169.254`(클라우드 메타데이터 — 여기에 접근하면 서버의 임시 자격 증명이 새어 나갈 수 있다).

**방어 원칙**
- **허용 목록:** 허용한 호스트와 스키마(https)만 통과시킨다. 차단 목록보다 안전하다.
- **주소 검사:** 사설, 루프백, 링크 로컬 주소를 막는다.
- **DNS 재확인:** 이름을 해석한 결과 주소도 다시 검사한다. 이름 검사만으로는 우회될 수 있다(DNS 재결합).
- **리다이렉트:** 허용된 주소가 다른 주소로 넘기면 그 주소도 검사한다.

**구현 (검증 완료)**

```java
static final Set<String> ALLOWED_HOSTS = Set.of("api.example.com");

static boolean isSafeUrl(String url) {
    try {
        URI u = new URI(url);
        if (!"https".equals(u.getScheme())) return false;                  // https만 허용
        String host = u.getHost();
        return host != null && ALLOWED_HOSTS.contains(host);               // 허용 목록에 있는 호스트만
    } catch (Exception e) { return false; }
}

static boolean isPrivateLiteralIp(String host) {
    try {
        InetAddress a = InetAddress.getByName(host);
        return a.isLoopbackAddress() || a.isSiteLocalAddress() || a.isLinkLocalAddress() || a.isAnyLocalAddress();
    } catch (Exception e) { return true; }                                 // 해석 실패는 안전하게 차단
}
```

- **확인:** `https://api.example.com`은 통과하고, `http://`, 허용 목록 밖의 호스트, `http://169.254.169.254/...`는 차단된다. `127.0.0.1`과 `10.0.0.5`는 사설 주소로 감지되고, `8.8.8.8`은 감지되지 않는다(검증 완료).
- **주의:** `isPrivateLiteralIp`는 주소 문자열만 검사한다. 이름을 해석하는 시점에 따라 결과가 바뀔 수 있으므로, 실제 요청 직전에 해석한 주소로 다시 검사한다.

## 4. AI 거버넌스 점검표

**정의** — AI 기능을 만들 때 개인정보, 편향, 책임 주체, 사고 대응을 기능별로 확인하는 기록이다.

**기능마다 답할 질문**
- 어떤 데이터를 쓰는가? 개인정보가 포함되는가? 보관 기간은?
- 잘못된 답이 나오면 누가 피해를 보는가? 얼마나 큰 피해인가?
- 결과를 사람이 확인하는가? 자동으로 실행되는가?
- 편향을 어떻게 측정했는가? (집단별 정확도 차이)
- 사고가 나면 누가 어떻게 막는가? 기록은 남는가?

**예:** 고객 문의 분류 기능이라면, 개인정보가 로그에 남지 않는지, 환불 판단을 사람이 최종 확인하는지, 특정 고객군에서 오분류가 몰리지 않는지를 적는다.

**면접 기준:** "AI 기능은 데이터, 편향, 책임, 사고 대응을 기능별로 점검합니다. 자동으로 실행되는 쓰기 행동은 사람의 승인을 거칩니다."

## 4-1. 위협 모델링 (STRIDE와 AI 기능)

**정의** — 시스템을 그림으로 그린 뒤, 데이터가 신뢰 경계를 넘는 지점마다 "무엇이 잘못될 수 있는가"를 체계적으로 찾는 작업이다. 취약점 목록을 외우는 것이 아니라 설계 단계에서 위험을 먼저 찾는다.

**절차**
1. **자산 정리:** 보호할 데이터와 기능을 적는다 (예: 고객 문의 내용, 환불 도구).
2. **흐름 그리기:** 사용자, 서버, 모델, 도구, DB를 선으로 잇고 신뢰 경계(인터넷과 내부, 모델과 도구 사이)를 표시한다.
3. **위협 찾기 (STRIDE):** 각 선과 노드에 여섯 범주를 대 본다.
   - Spoofing(위장), Tampering(변조), Repudiation(부인), Information disclosure(정보 노출), Denial of service(서비스 거부), Elevation of privilege(권한 상승)
4. **대응 선택:** 줄이기, 받아들이기, 옮기기, 피하기 중 하나를 고르고 이유를 적는다.
5. **검증:** 대응마다 테스트를 하나 붙인다. 테스트가 없는 대응은 검증되지 않은 대응이다.

**AI 기능에 적용한 예:** SentinelOps의 읽기 전용 분석 Agent (M19)를 본다.
- 사용자 문서 입력 → 모델: 악성 문장이 지시로 해석됨 (Tampering, Prompt Injection, 1절)
- 모델 → URL 조회 도구: 내부 주소 접근 (Elevation of privilege, SSRF, 3절)
- 모델 → 로그와 응답: 다른 고객 정보 노출 (Information disclosure, 2절)
- 도구 호출 반복: 비용 폭주 (Denial of service, 56장의 반복 상한)

**상태:** 정의와 절차만 추가했다. 실제 프로젝트 모델 작성은 아래 실습 과제이며 미실행이다.

**면접 기준:** "위협 모델은 신뢰 경계마다 STRIDE로 위협을 찾고, 대응마다 테스트를 붙이는 방식으로 만듭니다."

## 4-2. AI 공급망 보안

**정의** — AI 기능이 기대는 외부 요소(모델 파일, 학습 데이터, 플러그인, 도구 서버, 라이브러리)의 출처와 무결성을 확인하는 일이다. 어느 하나가 바뀌어도 서비스 동작이 바뀔 수 있다.

**점검 항목**
- **모델 파일:** 출처를 공식 배포처로 한정하고, 해시나 서명으로 변조 여부를 확인한다. 신뢰하지 않은 모델 파일을 역직렬화(pickle 등)하면 코드가 실행될 수 있으므로 안전한 형식을 쓴다.
- **버전 고정:** 모델 이름만 쓰지 말고 버전을 고정한다. 제공자가 모델을 바꾸면 같은 입력에 다른 결과가 나온다. 평가 데이터로 재검증한 뒤에만 바꾼다.
- **도구와 플러그인(MCP 서버 포함):** 신뢰하는 서버만 연결하고, 도구 설명과 권한을 리뷰한다. 설명 문장도 모델 입력이므로 Prompt Injection의 통로가 될 수 있다.
- **학습·평가 데이터:** 출처와 사용 허락(라이선스)을 기록한다. 개인정보가 섞였는지 확인한다.
- **라이브러리:** 의존성 목록(SBOM)을 만들고 취약점을 주기적으로 확인한다 (101장, 46장).

**구별:** 공급망 보안은 "이 부품을 믿어도 되는가"이고, Prompt Injection은 "입력 안의 문장이 지시로 해석되는가"다. 둘 다 막아야 하며 방어 위치가 다르다.

**상태:** 정의와 점검 항목만 추가했다. 실제 모델 해시 검증 실습은 미실행이다.

## 4-3. 국내 규정 입문

**정의** — 국내에서 개인정보와 정보보호를 다루는 대표 법령과 인증 체계를 이름과 역할 수준으로 아는 것이다. 법 조문을 외우는 것이 목적이 아니고, 설계에서 "무엇을 확인해야 하는가"를 떠올리는 것이 목적이다.

| 이름 | 무엇을 규정하나 | 설계에서 확인할 것 |
|---|---|---|
| 개인정보 보호법 | 개인정보의 수집, 이용, 보관, 파기, 유출 시 대응 | 수집 목적, 보관 기간, 파기 방법, 유출 신고 절차 |
| 정보통신망법 | 정보통신서비스의 보안 조치와 침해사고 관련 의무 | 접근 통제, 로그, 침해사고 대응 |
| 정보보호 및 개인정보보호 관리체계(ISMS-P) | 관리 체계를 갖췄는지 인증 | 정책, 위험 관리, 접근 기록, 사고 대응 문서 |

**흔한 오해:** 암호화를 했다고 개인정보 보호법을 모두 충족하는 것은 아니다. 목적 외 이용과 보관 기간 관리도 필요하다.

**상태:** 법령 이름과 역할만 정리했다. 세부 조문, 기한, 최신 개정은 법제처 원문으로 직접 확인해야 하며 이 장에서는 확인하지 않았다(미실행).
