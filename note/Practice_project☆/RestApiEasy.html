비유 없이, 그림에 나온 글자 하나하나를 뜻 그대로 풀어서 설명합니다.

📌 0. 결론 한 줄

REST API = 서버가 데이터를 정해진 주소(URL)와 정해진 동작 이름(GET·POST·PATCH·DELETE)으로 주고받게 만든 약속이고, 주고받는 데이터 형식은 JSON이라는 글자 모양을 씁니다.

💡 왜 어렵게 느껴지나요?
한 문단에 새 용어가 6개(서버, 클라이언트, 자원, 설계 방식, 종속, JSON)가 한꺼번에 나오기 때문입니다. 아래에서 하나씩 나눠서 정의합니다.

🖼️ 1. 그림 읽는 순서

그림에는 크게 3덩어리가 있습니다. 번호 순서대로 읽으세요.

📎 위 그림은 책 그림을 문서 안에서 다시 그린 것입니다. 글자 배치는 책과 조금 다를 수 있습니다.

번호그림 속 부분뜻
①클라이언트(왼쪽 점선 상자)데이터를 요청하는 쪽의 프로그램·기기. 브라우저, 앱, 워치, 카메라, 도어락이 모두 해당합니다.
②요청 화살표(→)클라이언트가 서버로 보내는 메시지. "게시글 목록 주세요" 같은 내용이 들어 있습니다.
③데이터 응답 화살표(←)서버가 클라이언트로 돌려보내는 메시지. 내용은 JSON 형식입니다.
④REST API(가운데 상자)요청을 받아서 처리하고 응답을 만드는 서버 프로그램입니다.
⑤오른쪽 5개 목록서버가 받아들이는 요청의 종류. 동작 이름 + 주소 한 쌍이 한 종류입니다.
✅ 이 그림의 핵심 한 줄
왼쪽의 기기가 무엇이든(브라우저든 도어락이든) 같은 주소로 요청하면, 같은 JSON 형식의 응답을 받는다.

📖 2. 책 본문 문장 풀이

책 문장쉬운 말로 바꾸면
서버 자원을서버에 저장된 데이터(게시글, 회원 정보, 상품 등)를
클라이언트에 구애받지 않고요청하는 기기의 종류가 무엇이든 상관없이
사용할 수 있게 하는가져다 쓸 수 있도록 만드는
설계 방식입니다.서버를 만드는 규칙(약속)입니다.
클라이언트에서 정보를 요청하면기기가 "이 데이터 주세요"라고 보내면
서버는 특정 기기에 종속되지 않고서버는 아이폰용, 안드로이드용을 따로 만들지 않고
모든 기기에서 통용할 수 있는 JSON 데이터를어느 기기든 읽을 수 있는 JSON 형식 글자를
응답으로 보냅니다.답장으로 보내줍니다.
💡 "구애받지 않는다 / 종속되지 않는다"
둘 다 같은 뜻입니다. 서버가 기기 종류에 따라 응답 형식을 바꾸지 않는다는 뜻입니다. 서버 하나, 응답 형식 하나로 모든 기기를 처리합니다.

🔤 3. 용어 정의표

용어정의예시
서버요청을 받으면 데이터를 처리해서 응답을 돌려주는 프로그램(또는 그 프로그램이 실행되는 컴퓨터)Spring Boot로 만든 프로그램
클라이언트서버에 요청을 보내는 프로그램크롬 브라우저, 스마트폰 앱
요청(Request)클라이언트가 서버로 보내는 메시지GET /articles
응답(Response)서버가 클라이언트로 돌려보내는 메시지JSON 글자와 상태 코드
자원(Resource)서버가 관리하는 데이터 한 종류articles(게시글)
URL / 주소어떤 자원인지 가리키는 글자/articles/3 = 게시글 중 3번
HTTP 메서드그 자원으로 무엇을 할지 나타내는 단어GET, POST, PATCH, DELETE
JSON데이터를 {"이름":"값"} 모양의 글자로 적는 형식{"id":1,"title":"안녕"}
API프로그램끼리 요청하고 응답받는 방법을 정해놓은 규칙 모음위 5개 요청 목록
RESTAPI를 만들 때 "주소는 자원을 가리키고, 동작은 메서드로 구분한다"로 정한 규칙GET /articles

🧩 4. 그림 오른쪽 5개 요청 해설

메서드주소하는 일보내는 데이터받는 응답
GET/articles게시글 전체 목록 조회없음게시글 여러 개 (JSON 배열)
GET/articles/11번 게시글 하나 조회없음게시글 1개 (JSON 객체)
POST/articles새 게시글 생성제목, 내용 (JSON)생성된 게시글 (번호 포함)
PATCH/articles/11번 게시글의 일부 수정바꿀 항목만 (JSON)수정된 게시글
DELETE/articles/11번 게시글 삭제없음본문 없음 (상태 코드만)
⚠️ 그림의 /articles/id에서 id는 실제 글자 "id"가 아니라 번호가 들어갈 자리입니다. 실제로는 /articles/1, /articles/2처럼 숫자를 넣습니다.
💡 규칙 2가지만 기억하세요
1) 주소에는 자원 이름(명사)만 쓴다. (/articles)
2) 무엇을 할지는 메서드로 정한다. (조회=GET, 생성=POST, 수정=PATCH, 삭제=DELETE)

📨 6. 요청과 응답의 실제 글자 모양


6-1. 요청 (POST /articles)


POST /articles HTTP/1.1
Host: localhost:8080
Content-Type: application/json

{
  "title": "첫 번째 글",
  "content": "안녕하세요"
}




줄의미


POST /articles HTTP/1.1메서드(POST) + 주소(/articles) + 통신 규약 버전


Host: localhost:8080요청을 받을 서버의 주소와 포트 번호


Content-Type: application/json아래에 붙은 본문이 JSON 형식이라는 표시


빈 줄 아래 { ... }본문(Body). 서버에 전달할 데이터




6-2. 응답


HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 1,
  "title": "첫 번째 글",
  "content": "안녕하세요"
}


✅ 이렇게 읽으면 성공
첫 줄의 숫자 201 = "생성 성공". 아래 JSON에 서버가 새로 붙여준 id가 보이면 정상입니다.

☕ 7. Spring Boot 코드로 보기 (한 줄씩)


그림 오른쪽 5개 요청을 Spring Boot로 만들면 아래와 같습니다. 줄마다 누가 호출하고, 어디로 값을 돌려주는지를 적었습니다.


@RestController
@RequestMapping("/articles")
public class ArticleController {

    private final ArticleService articleService;

    public ArticleController(ArticleService articleService) {
        this.articleService = articleService;
    }

    @GetMapping
    public List<ArticleDto> list() {
        return articleService.findAll();
    }

    @GetMapping("/{id}")
    public ArticleDto detail(@PathVariable Long id) {
        return articleService.findById(id);
    }

    @PostMapping
    public ResponseEntity<ArticleDto> create(@RequestBody ArticleCreateRequest request) {
        ArticleDto saved = articleService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(saved);
    }

    @PatchMapping("/{id}")
    public ArticleDto update(@PathVariable Long id, @RequestBody ArticleUpdateRequest request) {
        return articleService.update(id, request);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        articleService.delete(id);
        return ResponseEntity.noContent().build();
    }
}




코드설명 (호출 위치 → 리턴 위치 포함)


@RestController이 클래스가 요청을 받는 컨트롤러이고, 메서드가 리턴한 값을 JSON 글자로 바꿔 응답 본문에 넣으라는 표시입니다. 스프링이 프로그램 시작 시 이 클래스를 찾아 등록합니다.


@RequestMapping("/articles")이 클래스 안의 모든 메서드 주소 앞에 /articles가 붙습니다.


public class ArticleController컨트롤러 클래스 선언. 클라이언트의 요청이 가장 먼저 도착하는 클래스입니다.


private final ArticleService articleService;실제 데이터 처리를 맡는 ArticleService 객체를 담는 변수입니다. final이므로 한 번 넣으면 바꿀 수 없습니다.


public ArticleController(ArticleService articleService)생성자. 스프링이 컨트롤러를 만들 때 ArticleService 객체를 찾아 이 매개변수로 넣어줍니다.


this.articleService = articleService;받은 객체를 위의 변수에 저장합니다. 이후 모든 메서드가 이 변수로 서비스를 호출합니다.


@GetMapping메서드가 GET /articles 요청을 처리한다는 표시입니다.


public List<ArticleDto> list()게시글 목록을 리턴하는 메서드. 스프링이 요청을 받으면 이 메서드를 호출하고, 리턴값은 스프링에게 돌아가 JSON 배열로 변환됩니다.


return articleService.findAll();서비스의 findAll()을 호출해 전체 목록을 받고, 그 값을 그대로 리턴합니다. 최종적으로 클라이언트에게 200 응답으로 전달됩니다.


@GetMapping("/{id}")GET /articles/1 형태의 요청을 처리합니다. 주소의 {id} 자리에 들어온 숫자가 변수가 됩니다.


@PathVariable Long id주소에서 꺼낸 번호를 id 변수에 넣습니다. /articles/3이면 id는 3입니다.


return articleService.findById(id);서비스에 번호를 넘겨 해당 게시글 1개를 받아 리턴합니다. 리턴값은 JSON 객체로 변환되어 응답됩니다.


@PostMappingPOST /articles 요청을 처리합니다.


@RequestBody ArticleCreateRequest request요청 본문의 JSON(제목, 내용)을 ArticleCreateRequest 객체로 바꿔 request에 넣습니다.


ArticleDto saved = articleService.create(request);서비스의 create()를 호출해 저장하고, 저장된 결과(번호 포함)를 saved에 받습니다.


return ResponseEntity.status(HttpStatus.CREATED).body(saved);상태 코드 201과 saved를 본문으로 묶어 리턴합니다. 스프링이 이를 HTTP 응답으로 만들어 클라이언트에 보냅니다.


@PatchMapping("/{id}")PATCH /articles/1 요청을 처리합니다.


return articleService.update(id, request);번호와 수정 내용을 서비스에 넘기고, 수정된 게시글을 받아 리턴합니다.


@DeleteMapping("/{id}")DELETE /articles/1 요청을 처리합니다.


articleService.delete(id);서비스에 삭제를 요청합니다. 리턴값이 없는 호출입니다.


return ResponseEntity.noContent().build();본문 없이 상태 코드 204만 담은 응답을 리턴합니다.




⚠️ ArticleService, ArticleDto, ArticleCreateRequest, ArticleUpdateRequest는 별도 파일로 직접 만들어야 합니다. 이 문서는 컨트롤러의 구조만 보여줍니다.
