팀장의 Git 병합 완전 정복

팀장 전용 Git Merge GitHub PR

팀장이 따라하면서 팀원 코드를 병합(Merge)하는 실전 가이드 · 기본 가이드(git.html)를 먼저 읽고 오세요!

👑 팀장 역할

팀장이 해야 할 일은 딱 3가지입니다

팀장은 코드를 합치는(병합하는) 중심 역할입니다. 이 자습서는 팀장이 처음부터 끝까지 따라하면 팀원 코드를 안전하게 합칠 수 있도록 만들었습니다.

📖
git.html — 기본 가이드를 먼저 읽으셨나요?
Git 설치, 개념, 기본 명령어를 아직 모른다면 이 가이드를 먼저 읽고 오세요. 클릭하면 이동합니다.

👑 팀장의 3대 역할

🏗️
1. 저장소 세팅
GitHub 저장소 생성, 팀원 초대, 첫 프로젝트 업로드. 딱 1번만 하면 끝!
🔀
2. 코드 병합 (Merge)
팀원이 올린 코드를 main에 안전하게 합치기. 팀장의 핵심 역할!
🛡️
3. main 브랜치 관리
main은 완성된 코드만! 문제가 생기면 되돌리기. 품질 관리 책임!
❓ 병합(Merge)이란?

팀원이 자기 브랜치에서 만든 코드를 main(메인) 브랜치에 합치는 것입니다. 팀장이 직접 합치거나, GitHub에서 Pull Request를 통해 합칩니다.

📋 비유: 팀장은 편집장입니다. 기자(팀원)가 각자 기사를 쓰면, 편집장(팀장)이 검토하고 신문(main)에 실는 것과 같습니다.

🗺️ 팀장의 병합 흐름 한눈에 보기

팀원이 브랜치에서코드 작성 & push
→
GitHub에서 PR 생성팀원이 "합쳐주세요" 요청
→
👑 팀장이 코드 확인리뷰 & 승인
→
Merge 버튼 클릭!main에 합치기
→
팀원 전원 pull최신 코드 받기

📋 이 자습서의 순서

Phase 1: 저장소 세팅

GitHub 저장소 만들기 + 팀원 초대 (최초 1회)

Phase 2: 첫 프로젝트 업로드

Eclipse 프로젝트를 GitHub에 올리기 (최초 1회)

Phase 3: Pull Request 병합

GitHub 웹에서 팀원 코드 리뷰 & 병합 (매번 사용)

같은 파일을 수정했을 때 충돌 해결 (가끔 발생)

터미널에서 merge 명령어로 직접 합치기 (선택)

Phase 6: 팀장의 일일 루틴

매일 반복하는 팀장 워크플로우

③ .gitignore 파일 만들기

❓ 왜 .gitignore가 필요한가요?

Eclipse 설정 파일(.settings, .classpath 등)은 각 PC마다 달라서 공유하면 오류가 납니다. Git에 올리지 말아야 할 파일 목록을 적는 겁니다.

🚫 비유: 택배 보낼 때 "이건 포장하지 마" 목록입니다.
Git Bash — .gitignore 생성 (전체 복사 → 붙여넣기 → Enter)
cat > .gitignore <<'EOF'
# Eclipse 설정 (각 PC마다 달라서 공유하면 오류!)
.settings/
.project
.classpath

# 컴파일 결과물 (빌드하면 자동 생성)
bin/
build/
target/
*.class
*.war
*.ear

# Tomcat 서버 관련
.tomcat/
work/
Servers/

# OS 자동 생성 파일
Thumbs.db
Desktop.ini
.DS_Store

# 기타 IDE 설정
*.iml
.idea/
.vscode/
*.log
EOF
✅ 확인

cat .gitignore 입력 → 위 내용이 보이면 성공!

Phase 3 진행률0 / 5
❓ Pull Request(PR)란?

팀원이 "내 코드를 main에 합쳐주세요!"라고 요청하는 것입니다. 팀장은 코드를 확인한 후 「Merge」 버튼을 눌러 합칩니다.

📋 비유: 팀원이 보고서를 올리면, 팀장이 검토 후 승인하는 결재 과정과 같습니다.
팀원: 브랜치 pushfeature/login → GitHub
→
팀원: PR 생성"합쳐주세요" 요청
→
👑 팀장: 코드 리뷰Files changed 확인
→
👑 팀장: Merge!main에 합치기

① 팀원이 PR을 만드는 과정 (팀원에게 알려주세요!)

ℹ️ 팀원이 할 일 (팀장은 기다리면 됩니다)

팀원이 자기 브랜치에서 작업 완료 후:
1. git add -A → git commit -m "메시지" → git push origin feature/login
2. GitHub 사이트 접속 → 노란 배너의 「Compare & pull request」 클릭
3. PR 제목과 설명 작성 → 「Create pull request」 클릭

팀장의 병합 순서 (GitHub 웹에서!)

Pull requests 탭 → "로그인 기능" PR 클릭
→ Files changed 확인 → 문제 없으면

# === 3번째, 4번째도 동일하게 반복! ===
⚠️ 중요: 한 번에 하나씩!

③ 방법 B: Git Bash에서 충돌 해결

ℹ️ 이 방법은 GitHub 웹에서 해결이 안 될 때 사용합니다

복잡한 충돌이거나, 파일이 많을 때는 Git Bash에서 직접 해결하는 게 더 편합니다.

Git Bash — 충돌 해결 전체 과정
# 1. main 브랜치로 이동
git checkout main

# 2. 최신 코드 받기
git pull origin main

# 3. 팀원 브랜치를 main에 합치기 시도 (충돌 발생!)
git merge feature/carlist

# → 충돌 메시지가 나옴:
# CONFLICT (content): Merge conflict in src/main/webapp/Top.jsp
# Automatic merge failed; fix conflicts and then commit.

# 4. Eclipse에서 충돌 파일(Top.jsp) 열기
#    → <<<<<<< 표시 찾기 → 코드 정리 → 저장

# 5. 충돌 해결 후 저장 & 업로드
git add -A
git commit -m "merge 충돌 해결: Top.jsp (로그인+차량검색 메뉴 통합)"
git push origin main

# 6. 팀 단톡방: "충돌 해결하고 merge 완료! 전원 pull!"
❌ merge가 너무 꼬였을 때 — 취소하고 다시!

merge 도중 너무 복잡해지면 취소할 수 있습니다:

Git Bash — merge 취소 (진행 중일 때만!)
git merge --abort

→ merge 전 상태로 되돌아갑니다. 처음부터 다시 시도하세요!

📥

Git Bash — 직접 병합 전체 과정 (순서대로 실행!)

🚨 팀장이 자주 겪는 문제 & 해결법

🔥 팀장 문제 모음
❌ PR에서 "This branch has conflicts" — Merge 버튼이 안 눌림!
해결: Phase 4 참고. 「Resolve conflicts」 버튼으로 웹에서 해결하거나, Git Bash에서 직접 merge 후 충돌 해결.
❌ 팀원이 main에 직접 push 해버렸어요!
해결: 일단 git pull origin main으로 받고, 문제 없으면 OK. 앞으로 브랜치 사용 규칙을 다시 공지하세요!
❌ merge 후 프로젝트가 에러나요!
해결: Eclipse에서 프로젝트 우클릭 → Refresh (F5) → Properties → Java Build Path에서 JRE 확인 → Targeted Runtimes에서 Tomcat 체크 → Project Clean
❌ 이미 merge한 걸 되돌리고 싶어요!
해결: git log --oneline으로 merge 전 커밋 해시를 찾은 후, git revert -m 1 해시값으로 되돌리기. 또는 팀원과 상의 후 수동으로 코드 수정.
❌ 팀원 브랜치가 git branch -r에 안 보여요!
해결: git fetch --all을 실행하면 모든 원격 브랜치 정보를 받아옵니다.
