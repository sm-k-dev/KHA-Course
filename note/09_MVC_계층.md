## 학습 전 필수 관문 — Controller · Service · Repository · DTO

> **학습 순서:** 아래 정의를 읽고 → 굵은 용어를 자기 말로 풀고 → 틀린 문장을 반박하고 → 예제를 설명한 다음 → 답안을 가리고 면접처럼 말한다. 비유만 이해한 상태에서는 다음으로 넘어가지 않는다.

### 1. 정확한 정의

Controller는 요청과 응답을 연결하고, Service는 애플리케이션 유스케이스를 조정하며, Repository는 데이터 접근을 추상화한다. DTO는 계층 간 전달용 데이터 구조다.

### 2. 용어를 구분해야 하는 이유

Entity와 DTO는 같은 말이 아니다. DB에 대응하는 영속성 객체를 그대로 외부 응답에 노출하면 결합과 보안 문제가 생길 수 있다.

### 3. 새로운 상황에 적용

회원 상세 조회 시 Controller가 HTTP 요청을 받고 Service가 조회 정책을 수행하며 Repository가 데이터에 접근하는 흐름을 추적한다.

### 4. 면접 질문과 답변 기준

**질문:** Controller · Service · Repository · DTO의 차이를 정의와 동작을 포함해 설명해 보세요.

**답변 기준:** 계층을 분리하는 이유는 책임과 변경 영향을 분리하기 위해서입니다. 각 계층은 자신이 담당하는 규칙을 처리하고 다른 계층과 계약으로 협력합니다.

### 5. 정답을 가리고 설명하기

1. 위 정의에서 핵심 명사 세 개를 골라 각각 뜻을 설명한다.
2. 위의 **틀린 주장**이 왜 틀렸는지 반례를 든다.
3. 위 상황의 **실행 결과·처리 주체·변경되는 값**을 분리해 설명한다.
4. 답변 기준을 보지 않고 **정의 1문장 → 차이 1문장 → 예시 1문장**으로 말한다.
5. 다음 날 같은 질문에 답하지 못하면 예제가 아니라 **정의**부터 다시 확인한다.

## 1. MVC·Controller·Service·Repository

**정의** — MVC는 입력·표현·상태 관심사를 분리하는 아키텍처 패턴이다. 일반적인 계층형 웹 앱에서 Controller는 HTTP 경계, Service는 유스케이스, Repository/DAO는 데이터 접근을 맡는다.

**목적과 책임** — 변경 이유를 분리해 테스트와 유지보수를 돕는다.

**구별해야 할 개념 / 흔한 오해** — MVC의 Model을 Service 또는 Entity 하나와 동일시하면 안 된다. Service/Repository는 MVC와 별개의 계층 구분이다.

**실행·처리 흐름** — HTTP → Controller → Service → Repository → DB → Service → View/JSON

**직접 구현·검증** — Controller에서 SQL을 제거하고 서비스·저장소로 분리. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — Controller와 Service를 구분하는 기준은?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

MVC는 입력 처리·모델·표현 책임을 분리하는 패턴이다. Controller는 요청을 응용 기능에 연결하고 Service는 유스케이스·업무 규칙을 수행하며 Repository/DAO는 저장소 접근을 추상화한다. MVC의 Model과 DB Entity는 동의어가 아니다.

### 직접 읽고 구현하는 독립 예제

```java
// 개념적 의존 방향
// Controller -> OrderService -> OrderRepository
// Controller: HTTP 입력/응답
// Service: 주문 생성 규칙/트랜잭션
// Repository: 저장/조회
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

주문 가격 검증을 Controller가 아니라 Service에 두어야 하는 이유를 설명한다.

### 스스로 작성할 변형 실습

Service 없이 단순 조회를 구현할 때의 장단점을 비교한다.

### 면접 답변의 기준 문장

> Controller는 요청 흐름, Service는 유스케이스, Repository는 영속성 접근을 담당하도록 분리합니다.

**구술 확인:** 위 문장을 외우기보다, 정의와 책임을 구분해 말하고 실제 코드에서 해당 역할을 수행하는 줄을 가리켜 설명한다.


### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“MVC는 입력·표현·상태 관심사를 분리하는 아키텍처 패턴이다. 일반적인 계층형 웹 앱에서 Controller는 HTTP 경계, Service는 유스케이스, Repository/DAO는 데이터 접근을 맡는다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“MVC의 Model을 Service 또는 Entity 하나와 동일시하면 안 된다. Service/Repository는 MVC와 별개의 계층 구분이다.”* 반례를 하나 만들어 본다.

**3차: 면접 재현.** *“Controller와 Service를 구분하는 기준은?”*에 대해 **정의 → 왜 필요한가 → 무엇과 다른가 → 코드·상황 하나** 순서로 30~60초 말한다. 답을 읽지 않고 말한 뒤 원문과 대조한다.

**완료 기준:** 비유 없이 정의 가능 / 혼동되는 용어 구별 가능 / 처음 보는 예제에 적용 가능. 세 조건 중 하나라도 실패하면 해당 항목만 재학습한다.
## 2. DTO·Entity·도메인 모델

**정의** — DTO는 계층·프로세스 간 데이터를 전달하기 위한 구조이고 Entity는 식별성과 생명주기를 갖는 도메인 또는 영속 객체를 가리킨다.

**목적과 책임** — 외부 API 계약과 내부 데이터 모델을 분리한다.

**구별해야 할 개념 / 흔한 오해** — JPA Entity를 요청·응답 DTO로 그대로 노출하면 결합과 보안 위험이 생길 수 있다.

**실행·처리 흐름** — 요청 DTO → 검증 → 서비스 → Entity → 응답 DTO

**직접 구현·검증** — 회원 Entity와 회원 응답 DTO를 분리해 민감 필드 제거. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

DTO는 계층·프로세스 간 데이터 전달용 객체이고 Entity는 식별성을 가진 도메인 개념 또는 ORM 관리 대상이다. 도메인 모델은 비즈니스 규칙과 개념을 표현하며 JPA Entity와 항상 동일하지 않다. 외부 API에 Entity를 직접 노출하면 결합·민감정보·지연 로딩 문제가 생길 수 있다.

### 직접 읽고 구현하는 독립 예제

```java
record UserResponse(long id,String nickname) {}
// Controller는 UserEntity 대신 UserResponse 반환
UserResponse toResponse(UserEntity e){return new UserResponse(e.getId(),e.getNickname());}
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

엔티티에 비밀번호 필드가 추가되어도 응답 DTO가 노출하지 않는지 확인한다.

### 스스로 작성할 변형 실습

DTO의 불변성과 검증 책임을 구분한다.

### 면접 답변의 기준 문장

> DTO는 전달 경계를 위한 데이터 구조이고 Entity는 식별성을 갖는 모델 개념입니다.

**구술 확인:** 위 문장을 외우기보다, 정의와 책임을 구분해 말하고 실제 코드에서 해당 역할을 수행하는 줄을 가리켜 설명한다.

# 핵심 개념을 오해 없이 이해하기 위한 기초 연결

## 필수 기초 연결: 계층마다 ‘없음’을 해석하는 방식이 다르다

1. **Repository:** 저장소 조회 계약을 제공한다. 단건 조회의 부재를 `Optional.empty()`로 표현할 수 있다.
2. **Service:** 부재가 비즈니스적으로 어떤 의미인지 판단한다. 예: 없는 사용자라면 `UserNotFoundException` 발생.
3. **Controller:** 예외를 HTTP 응답 계약으로 변환한다. 예: 404와 오류 JSON.
4. **View/Client:** 404를 받아 사용자에게 “사용자 없음”을 표시한다.

이 흐름에서 **DB의 0행**, **Java의 Optional.empty**, **도메인 예외**, **HTTP 404**는 같은 값이 아니라 계층별로 표현된 **서로 다른 결과**다.

```java
// 개념 예시: 의존성 주입·예외 매핑 설정은 별도 필요
User user = repository.findById(id)
    .orElseThrow(() -> new UserNotFoundException(id));
return new UserResponse(user.getId(), user.getName());
```

**실습:** 단건 조회(없음 → 404)와 목록 조회(없음 → 빈 배열 200)를 구현하고 왜 반환 계약이 다른지 문장으로 정리한다. Controller에서 직접 SQL을 실행하지 않도록 책임을 나눈다.

## 개념 경계 정밀 보강 — 실제 코드에서 헷갈리는 지점

> 이 절은 기존 핵심 설명에 추가한 필수 기초 연결 학습이다. 아래 예제는 설명용 최소 코드로, SQL은 예시 테이블이 필요하고 Java는 import/클래스·실행 환경이 필요할 수 있다.


### 경계 1. Controller / Service / Repository

**흔한 오해:** “Controller가 SQL까지 처리하면 MVC다”

**정확한 구분:** Controller는 HTTP 입력/출력 경계, Service는 유스케이스와 업무 규칙, Repository/DAO는 데이터 접근을 담당한다. MVC의 Model과 서비스 계층은 일대일 동의어가 아니다.

**코드·명령 해석:**

```java
// Controller: GET /users/{id} → service.find(id)
// Service: 조회 및 부재 정책 결정
// Repository: DB 조회
```

**확인 방법:** 각 계층을 단위 테스트할 때 무엇을 가짜로 대체할지 정한다.

**직접 구현:** Controller에 있던 가격 할인 계산을 Service로 옮겨라.

**면접 점검:** “Controller / Service / Repository”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 2. DTO / Entity / View Model

**흔한 오해:** “DB Entity를 그대로 응답하면 항상 편리하다”

**정확한 구분:** Entity는 영속성 매핑과 도메인 상태를 표현하고 DTO는 계층 간 전송 목적의 데이터 구조다. Entity 직접 노출은 비밀번호 등 민감 필드, 지연 로딩, API 계약 결합 위험이 있다.

**코드·명령 해석:**

```java
record UserResponse(Long id, String name) {}
UserResponse dto = new UserResponse(user.getId(), user.getName());
```

**확인 방법:** Entity 필드를 하나 추가해도 응답 계약이 자동 변경되지 않는지 확인한다.

**직접 구현:** 비밀번호 필드가 있는 User를 안전한 응답 DTO로 변환하라.

**면접 점검:** “DTO / Entity / View Model”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 3. DAO / Repository / ORM

**흔한 오해:** “Repository는 무조건 JPA이고 DAO는 JDBC다”

**정확한 구분:** DAO는 데이터 접근 객체 패턴, Repository는 도메인 관점의 저장소 추상화다. JDBC/JPA는 구현 기술이며 이름만으로 기술이 고정되지는 않는다.

**코드·명령 해석:**

```java
interface UserRepository { Optional<User> findById(long id); }
```

**확인 방법:** 인터페이스만으로 DB 연결이 일어나는지, 구현이 필요함을 설명한다.

**직접 구현:** 메모리 구현과 JDBC 구현을 같은 인터페이스로 교체하라.

**면접 점검:** “DAO / Repository / ORM”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.
