# 문자, 시간, 정규표현식: 한국어 서비스에서 자주 터지는 세 가지

> 중요도: **A** · 이 장의 목표: UTF-8과 문자열 길이의 차이를 설명하고, 시간을 UTC로 저장해 KST로 보여 주며, 정규표현식으로 입력을 검증할 때의 함정을 피한다.

> 2026-11-23 추가 장 (로드맵 1순위 "시간대·인코딩"과 2순위 "정규표현식" 항목). 아래 Java 예제는 JDK 25에서 실행해 결과를 확인했다.

---

## 1. 문자 인코딩

**정의** — 문자를 바이트 열로 바꾸는 규칙이다. 한국 서비스는 보통 **UTF-8**을 쓴다. 과거 파일과 DB에는 **MS949(CP949)**나 **EUC-KR**이 섞여 있는 경우가 많다.

### 1.1 길이는 문자 수와 다르다

| 문자열 | `length()` | 코드 포인트 수 | UTF-8 바이트 수 |
|---|---|---|---|
| `한` | 1 | 1 | 3 |
| `A` | 1 | 1 | 1 |
| `👍` | 2 | 1 | 4 |

`length()`는 UTF-16 코드 유닛 수다. 이모지는 두 칸으로 센다. DB 컬럼 길이(`VARCHAR(10)`)는 보통 **문자 수** 또는 **바이트 수** 중 하나 기준이라, 둘을 헷갈리면 저장이 실패한다.

### 1.2 깨짐 (mojibake)의 원인

인코딩과 디코딩이 다르면 글자가 깨진다.

```
원본 "한글" → MS949로 저장 → UTF-8로 읽음 → 깨진 문자
```

**규칙**: 파일, DB, HTTP 응답, 콘솔에 **인코딩을 명시**한다. 기본값에 기대지 않는다.

- HTTP: `Content-Type: text/html; charset=UTF-8`
- MySQL: `utf8mb4` (4바이트 이모지까지 저장). `utf8`은 3바이트뿐이라 이모지가 실패한다.
- Java 소스: `javac -encoding UTF-8`

## 2. 시간과 시간대

**정의** — 같은 순간을 나타내는 방법은 여러 가지다. 서버는 **UTC 기준 순간(Instant)**으로 저장하고, 화면에 보일 때 **사용자의 시간대(KST, Asia/Seoul)**로 바꾼다.

| 타입 | 뜻 | 쓰는 곳 |
|---|---|---|
| `Instant` | UTC 기준 한 순간 | DB 저장, 이벤트 시각 |
| `ZonedDateTime` | 시간대가 붙은 날짜·시각 | 화면 표시, 변환 |
| `LocalDateTime` | 시간대 없는 날짜·시각 | "매일 오전 9시"처럼 지역 기준 일정 |
| `LocalDate` | 날짜만 | 생일, 마감일 |

**실수 예**

- `LocalDateTime.now()`를 DB에 저장하면, 서버 시간대가 바뀌거나 다른 지역 서버에서 실행될 때 값이 달라진다.
- 날짜만 비교할 때 `Instant`를 쓰면 KST 자정 근처에서 하루가 어긋난다.

### 2.1 검증 코드

```java
import java.time.*;
import java.time.format.DateTimeFormatter;

public class TimeCheck {
    public static void main(String[] args) {
        Instant saved = Instant.parse("2026-11-23T00:30:00Z");          // DB에 저장된 값 (UTC)
        ZonedDateTime seoul = saved.atZone(ZoneId.of("Asia/Seoul"));     // 화면용 (KST)
        ZonedDateTime ny = saved.atZone(ZoneId.of("America/New_York"));  // 뉴욕 사용자
        DateTimeFormatter f = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm z");
        System.out.println("UTC   : " + saved);
        System.out.println("KST   : " + seoul.format(f));
        System.out.println("NY    : " + ny.format(f));
        // 날짜만 보면 UTC 기준으로는 22일, KST 기준으로는 23일이다
        System.out.println("UTC 날짜: " + saved.atZone(ZoneOffset.UTC).toLocalDate());
        System.out.println("KST 날짜: " + seoul.toLocalDate());
    }
}
```

**실행 결과 (확인함)**

```
UTC   : 2026-11-23T00:30:00Z
KST   : 2026-11-23 09:30 KST
NY    : 2026-11-22 19:30 EST
UTC 날짜: 2026-11-23
KST 날짜: 2026-11-23
```

이 예제의 시각은 UTC 00:30이라 날짜가 같다. 자정 직전 UTC 시각(예: `2026-11-22T20:00:00Z`)으로 바꾸면 KST 날짜는 23일, UTC 날짜는 22일이 된다. 날짜 경계는 시간대를 정한 뒤에만 계산한다.

## 3. 정규표현식 (Regex)

**정의** — 문자열의 패턴을 기호로 쓰는 방법이다. 입력 형식 검증, 로그 파싱, 치환에 쓴다.

| 패턴 | 뜻 |
|---|---|
| `\d` | 숫자 한 개 |
| `[a-z]` | 소문자 한 개 |
| `+`, `*`, `?` | 1회 이상, 0회 이상, 0또는 1회 |
| `^`, `$` | 문자열의 시작과 끝 |
| `{n,m}` | n에서 m회 반복 |

### 3.1 검증에 쓸 때 주의

```java
import java.util.regex.Pattern;

public class RegexCheck {
    // 한국 휴대폰 번호 예: 010-1234-5678 (형식만 검사, 실제 존재 여부는 확인하지 않는다)
    static final Pattern PHONE = Pattern.compile("^01[016789]-\\d{3,4}-\\d{4}$");

    public static void main(String[] args) {
        System.out.println(PHONE.matcher("010-1234-5678").matches());   // true
        System.out.println(PHONE.matcher("010-1234-5678\n").matches()); // false: 끝의 줄바꿈까지 막아야 한다
        System.out.println(PHONE.matcher("02-123-4567").matches());     // false
    }
}
```

**실행 결과 (확인함)**: `true`, `false`, `false`

- `matches()`는 **전체 문자열**이 패턴과 맞아야 참이다. `find()`는 부분 일치다. 검증에는 보통 `matches()`를 쓴다.
- 패턴 문자열의 `\`는 Java에서 `\\`로 쓴다.
- `(a+)+$` 같은 중첩 반복은 입력이 길고 틀리면 **백트래킹 폭발**로 CPU를 많이 쓴다. 정규식으로 이메일 전체를 완벽히 검증하려 하지 말고, 길이 제한과 형식 확인을 나눈다.
- 보안: 사용자가 입력한 문자열을 그대로 패턴에 넣으면 정규식 주입이 된다. `Pattern.quote()`로 감싼다.

## 4. 실습 과제

1. `"👍".length()`와 `"👍".codePointCount(0, 2)`를 출력해 차이를 확인한다.
2. `TimeCheck`에서 시각을 `2026-11-22T20:00:00Z`로 바꿔 KST와 UTC 날짜가 어떻게 달라지는지 적는다.
3. `PHONE` 패턴을 `^010-\d{4}-\d{4}$`로 고칠 때 통과하지 않아야 하는 입력 세 개를 적는다.

## 단원 통과 기준

- [ ] `length()`가 문자 수가 아닌 이유를 설명하고, `utf8mb4`가 필요한 이유를 설명할 수 있다.
- [ ] `Instant`와 `LocalDateTime`의 차이를 설명하고, UTC로 저장하는 이유를 설명할 수 있다.
- [ ] `matches()`와 `find()`의 차이를 설명할 수 있다.
- [ ] 정규표현식을 사용자 입력에 그대로 넣으면 안 되는 이유를 설명할 수 있다.
