# 부하 테스트: 느린지, 얼마나 버티는지 숫자로 본다

> 중요도: **B** · 이 장의 목표: 부하 테스트의 목적과 지표(처리량, 응답 시간 분포, 에러율)를 구분하고, 평균 대신 백분위수(p95, p99)로 판단하며, k6로 간단한 시나리오를 작성한다.

> 2026-11-23 추가 장 (로드맵 1순위 "부하 테스트" 항목, 35장 테스트 심화 후속). **이 장의 k6 스크립트는 실행 결과를 확인했다**(설치 방법과 실행 결과는 본문 6절). 실제 운영 서버를 대상으로 부하를 주지 않는다. 테스트는 **허가된 로컬 또는 테스트 환경**에서만 한다.

---

## 1. 무엇을 알고 싶은가

| 질문 | 측정값 |
|---|---|
| 한 번에 몇 요청까지 버티는가 | 처리량 (RPS, 초당 요청 수) |
| 사용자가 얼마나 기다리는가 | 응답 시간 분포 (p50, p95, p99) |
| 실패가 얼마나 나는가 | 에러율 (5xx, 타임아웃) |
| 병목이 어디인가 | DB 쿼리 시간, 스레드 풀 대기, GC |

**평균은 속인다.** 응답 시간 평균이 100ms라도 p99가 5초일 수 있다. 느린 1%의 사용자가 불만을 만든다. 그래서 **p95, p99**를 본다.

| 값 | 뜻 |
|---|---|
| p50 | 절반의 요청이 이 시간 안에 끝남 (중앙값) |
| p95 | 95%의 요청이 이 시간 안에 끝남 |
| p99 | 99%의 요청이 이 시간 안에 끝남 |

---

## 2. 테스트 종류

| 종류 | 목적 | 부하 모양 |
|---|---|---|
| 스모크 | 스크립트와 시스템이 정상인지 확인 | 1–2명, 짧게 |
| 부하 (Load) | 예상 사용량에서 목표 지표를 만족하는지 | 평소 사용량 |
| 스트레스 (Stress) | 한계점과 붕괴 방식 확인 | 점점 증가 |
| 스파이크 (Spike) | 갑자기 몰릴 때 회복하는지 | 짧은 급증 |
| 내구 (Soak) | 오래 돌릴 때 메모리 누수 확인 | 중간 부하, 수 시간 |

---

## 3. 목표 지표 정하기 (SLO)

"빠르게 해 주세요"는 측정할 수 없다. 측정 가능한 목표를 먼저 정한다.

> 예: 상품 목록 API는 동시 사용자 100명에서 **p95 응답 시간 300ms 이하**, **에러율 1% 이하**.

이 기준이 없으면 결과가 좋은지 나쁜지 판단할 수 없다.

---

## 4. k6 스크립트 예제

k6는 JavaScript로 시나리오를 쓰는 부하 도구다. 아래 스크립트는 로컬 서버 `http://localhost:8080/health`를 대상으로 한다.

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 10,                 // 동시 가상 사용자 수
  duration: '20s',
  thresholds: {
    http_req_duration: ['p(95)<300'],   // p95 300ms 이하
    http_req_failed: ['rate<0.01'],     // 실패율 1% 미만
  },
};

export default function () {
  const res = http.get('http://localhost:8080/health');
  check(res, { 'status is 200': r => r.status === 200 });
  sleep(0.1);
}
```

**읽는 법**

- `thresholds`는 **기준을 넘으면 테스트를 실패로 끝낸다.** 사람이 그래프를 보지 않아도 CI에서 판단할 수 있다.
- `sleep(0.1)`은 사용자가 요청 사이에 잠깐 쉬는 것을 흉내 낸다. 0으로 두면 서버를 한계까지 몰아붙인다.

---

## 5. 결과를 읽는 순서

1. **에러율**부터 본다. 실패가 많으면 응답 시간 숫자는 의미가 없다.
2. **p95, p99**를 본다. 평균은 마지막에 본다.
3. **처리량이 오르는데 응답 시간이 급증하는 지점**을 찾는다. 그 지점이 현재 한계다.
4. 한계에서 서버 지표(CPU, 메모리, DB 연결 수, GC)를 함께 본다. 병목이 어디인지 추정한다.

**흔한 실수**

- 부하 생성기(k6를 돌리는 PC)가 먼저 한계에 닿아서, 서버가 느린 것으로 착각한다.
- 캐시가 따뜻한 상태에서만 측정하고 실제 배포 직후를 무시한다.
- 테스트 데이터가 적어서 DB 인덱스 문제가 드러나지 않는다.

---

## 6. 실행 확인

이 장의 스크립트는 k6 v2.4.0으로 실행했다. 대상은 이 컴퓨터에서 띄운 Node.js 더미 서버(`127.0.0.1:8080`)로, `/health`에 `ok`만 응답한다.

```powershell
winget install --id GrafanaLabs.k6 -e
k6 run health-check.js
```

**결과**: 10명이 동시에 20초 동안 요청해서 1,910개의 요청이 모두 성공했다. 실패는 0개, 체크는 100% 통과했고, `p(95)=3.55ms`로 두 임계값을 모두 지켰다. 응답이 거의 즉시 돌아오는 더미 서버라서 이 숫자는 **스크립트 동작 확인용**이다. 실제 서비스의 성능 기준으로 쓰지 않는다.

---

## 7. 실습 과제

1. 스크립트의 `vus`를 10에서 50으로 바꾸고 `p(95)` 값이 얼마나 올라가는지 기록한다.
2. `thresholds`에 `p(99)<500`을 추가하고 통과 여부를 확인한다.
3. 자신의 프로젝트 API 하나를 골라 SLO 문장을 한 문장으로 쓴다.
