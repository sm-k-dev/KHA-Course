# 시큐어 코딩: 입력, 출력, 권한, 비밀 정보를 지키는 기본기

> 중요도: **A** · 이 부록의 목표: 코드를 쓸 때 보안 실수가 생기는 열 가지 지점을 알고, 각 지점에서 무엇을 확인해야 하는지 말할 수 있다.

> 2026-11-24 추가 부록. 흩어진 보안 내용을 한곳에 모았다. 각 항목 옆의 **확인됨**은 이 PC에서 실행해 결과를 본 것이고, **원칙**은 설명과 점검 기준이다. 자세한 실행 과정은 해당 장에 있다.

---

## 1. SQL 인젝션: 입력을 SQL 구조로 해석하지 않는다

- **위험한 방식**: 입력을 SQL 문자열에 이어 붙인다.
- **안전한 방식**: `PreparedStatement`로 값을 따로 보낸다.
- **확인됨**: 같은 입력(`' OR '1'='1' -- `)에 대해 문자열 연결은 2행을 돌려줬고, 바인딩은 0행이었다(30장 2절).

```java
// 위험
String sql = "SELECT COUNT(*) FROM users WHERE email='" + email + "'";
// 안전
PreparedStatement ps = con.prepareStatement("SELECT COUNT(*) FROM users WHERE email=?");
ps.setString(1, email);
```

**점검 질문**: 이 SQL에 사용자 입력이 문자열로 들어가는가? 들어간다면 바인딩으로 바꿨는가?

---

## 2. XSS: 출력은 맥락에 맞게 인코딩한다

- **위험**: 사용자 입력을 HTML에 그대로 출력하면 스크립트가 실행된다.
- **확인됨**: `<`, `>`, `"`, `'`, `&`를 바꾸면 `&lt;script&gt;...`로 글자만 보인다(99장 4-3).
- **Thymeleaf**: `th:text`는 자동으로 이스케이프하고, `th:utext`는 하지 않는다(24장).
- **원칙**: 사용자 입력과 AI 답변을 출력할 때 기본은 이스케이프다. Markdown을 HTML로 바꾸는 라이브러리는 원시 HTML 출력 옵션을 확인한다(25장, 미실행).

**점검 질문**: 이 출력은 HTML인가, JavaScript인가, URL인가? 맥락에 맞는 인코딩을 쓰는가?

---

## 3. 접근 통제: 역할만 검사하지 않고 주인도 검사한다 (IDOR)

- **위험**: 주소의 번호만 바꿔서 남의 데이터를 본다. 역할(USER)은 맞아도 **데이터의 주인**이 아닐 수 있다.
- **원칙**: 로그인한 사용자 번호와 데이터의 주인 번호를 비교한다(31장 3절).
- **점검 질문**: 번호로 조회하는 모든 기능에서 주인 검사가 있는가? 목록 조회에도 조건이 붙는가?

```java
// 역할 검사만으로는 부족하다. 주인 검사를 함께 한다.
if (!post.ownerId().equals(currentUser.id())) {
    throw new AccessDeniedException("본인 글이 아닙니다");
}
```

---

## 4. CSRF: 로그인된 브라우저가 악용되지 않게 한다

- **위험**: 다른 사이트가 사용자의 로그인 상태를 빌려 요청을 보낸다.
- **방어**: CSRF 토큰을 확인하고, 쿠키에 `SameSite` 속성을 준다(27장, 30장, 31장).
- **원칙**: 상태를 바꾸는 요청(`POST`, `PUT`, `DELETE`)에 토큰을 요구한다. 조회(`GET`)는 상태를 바꾸지 않게 만든다.

**점검 질문**: 상태를 바꾸는 요청에 토큰이 있는가? `GET`으로 삭제하는 주소가 있는가?

---

## 5. 입력 검증: 형식과 길이를 서버에서 확인한다

- **원칙**: 화면에서 검사해도 서버에서 한 번 더 검사한다. 화면은 우회될 수 있다.
- **확인됨**: `@NotBlank`, `@Min`과 `BindingResult`로 빈 이름과 음수 나이를 걸러냈다(22장).
- **허용 목록**: 외부 주소처럼 범위가 정해진 값은 "막을 것"보다 "허용할 것"을 목록으로 둔다(57장 SSRF).

**점검 질문**: 모든 입력에 형식, 길이, 허용 범위가 있는가?

---

## 6. 동시성: 확인과 변경을 한 문장으로 묶는다

- **위험**: 잔액을 읽고 나중에 쓰면 동시 요청이 끼어든다. 잔액보다 많이 쓰이거나 쿠폰이 여러 번 쓰인다.
- **확인됨**: 같은 조건에서 SELECT 후 UPDATE는 20건이 성공했고, 조건부 UPDATE는 10건만 성공했다(33장).
- **중복**: 중복 방지는 **유니크 제약**으로 DB가 막는다(07장).

**점검 질문**: 읽고 계산하고 쓰는 순서가 있는가? 그 사이에 다른 요청이 들어와도 괜찮은가?

---

## 7. 외부 호출: 서버가 대신 보내는 요청을 제한한다 (SSRF)

- **위험**: 사용자가 준 주소로 서버가 요청을 보내서, 내부 주소나 메타데이터 주소에 접근한다.
- **확인됨**: 허용 목록(https만, 허용 호스트만)으로 `http://`, 허용 밖 호스트, `169.254.169.254`를 차단했다(57장 3절).
- **시간 제한**: 느린 외부 호출에 시간 제한과 대체 값을 둔다(99장 4-2, 18장).

**점검 질문**: 사용자가 준 주소를 서버가 그대로 호출하는가? 호출에 시간 제한이 있는가?

---

## 8. 비밀 정보: 코드와 저장소에 넣지 않는다

- **원칙**: DB 비밀번호, API 키, 토큰은 환경 변수나 별도 설정 파일로 빼고, 실제 파일은 `.gitignore`로 제외한다(16장 JNDI, 23장).
- **샘플 파일**: 저장소에는 `context.xml.sample`처럼 빈칸이 있는 샘플만 올린다.
- **확인됨**: JWT는 서명으로 위조를 막지만, 페이로드는 누구나 읽을 수 있으므로 비밀을 넣지 않는다(31장 3-1).

**점검 질문**: 저장소를 검색했을 때 키나 비밀번호가 나오는가?

---

## 9. 오류 정보: 사용자에게는 짧게, 서버 로그에는 자세히

- **위험**: 스택 트레이스나 SQL 문장이 화면에 나오면 공격자가 구조를 알게 된다.
- **원칙**: 사용자 응답에는 일반 메시지와 상태 코드만 준다. 자세한 원인은 서버 로그에 남긴다.
- **로그 마스킹**: 로그에도 비밀번호, 주민번호, 토큰을 그대로 남기지 않는다(23장, 99장).

**점검 질문**: 예외가 나면 화면에 무엇이 보이는가? 로그에 민감한 값이 있는가?

---

## 10. 의존성과 암호: 검증된 것을 쓰고 업데이트한다

- **비밀번호 저장**: 원문을 저장하지 않고, bcrypt 같은 해시를 쓴다(31장). 직접 해시 함수를 만들지 않는다.
- **의존성**: 라이브러리의 알려진 취약점을 주기적으로 확인하고, 버전을 올린다(18장, 22장, 46장에서 언급). 취약점 점검 도구 실습은 아직 없다(101 부록 3절).
- **점검 질문**: 비밀번호가 원문으로 저장되는가? 라이브러리 버전을 언제 마지막으로 확인했는가?
