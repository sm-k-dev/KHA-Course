## 1. 형상관리(Configuration Management)란

**정의** — 소프트웨어 산출물(소스, 문서, 설정, 빌드 결과)을 **식별하고, 변경을 통제하고, 상태를 기록하고, 감사**하는 활동이다.

왜 필요한가: 같은 파일을 여러 명이 고치면 무엇이 최신인지, 운영에 어떤 버전이 올라갔는지 알 수 없다. 형상관리는 이 질문에 항상 답할 수 있게 한다.

### 1.1 네 가지 활동

| 활동 | 뜻 | Git에서의 예 |
|---|---|---|
| 식별 (Identification) | 무엇을 관리할지 이름과 번호를 붙인다 | 저장소, 파일 경로, 커밋 해시, 태그 `v1.2.0` |
| 통제 (Control) | 변경을 요청·검토·승인한 뒤 반영한다 | Pull Request 리뷰, 브랜치 보호 규칙 |
| 상태 기록 (Status Accounting) | 현재 어떤 버전이 어디 있는지 기록한다 | 태그, 릴리스 노트, 배포 이력 |
| 감사 (Audit) | 기록과 실제 산출물이 일치하는지 확인한다 | 태그된 커밋에서 다시 빌드해 같은 결과인지 확인 |

### 1.2 베이스라인

**베이스라인**은 검토와 승인을 거쳐 확정된 기준 버전이다. 베이스라인 이후의 변경은 변경 요청 절차를 거친다.

| 종류 | 예 |
|---|---|
| 기능 베이스라인 | 요구사항 명세서 승인본 |
| 설계 베이스라인 | 승인된 아키텍처 문서와 ERD |
| 제품 베이스라인 | 운영에 배포된 릴리스 `v1.0.0` |

Git에서는 보통 **태그**가 베이스라인 역할을 한다.

```bash
git tag -a v1.0.0 -m "1차 배포 승인본"
git push origin v1.0.0
```

## 2. 변경 요청 흐름

베이스라인을 바꾸려면 다음 순서를 따른다.

1. **요청:** 변경 이유와 영향 범위를 적는다 (이슈 또는 변경 요청서).
2. **영향 분석:** 어떤 파일, 테스트, 배포 절차가 바뀌는지 본다.
3. **검토·승인:** 리뷰어나 변경 위원회가 승인한다.
4. **반영:** 브랜치에서 작업하고 Pull Request로 합친다.
5. **기록:** 릴리스 노트와 태그를 남긴다.

Git 흐름에서 이 절차는 다음과 같이 대응한다.

```
issue #42 (변경 요청) → feature/42-login-fix (작업) → PR 리뷰·CI 통과 → develop 병합 → release 태그
```

**실수 예** — 운영 버전을 `main`에서 직접 고치면, 태그와 실제 코드가 어긋나서 감사할 수 없게 된다. 긴급 수정도 핫픽스 브랜치를 만들고 같은 리뷰를 거친다.

## 3. 프로젝트 관리의 여섯 영역

| 영역 | 질문 | 산출물 |
|---|---|---|
| 범위 (Scope) | 무엇을 만드는가, 무엇은 안 하는가 | WBS, 범위 기술서 |
| 일정 (Schedule) | 언제 끝나는가 | 간트 차트, 임계 경로 |
| 원가 (Cost) | 얼마가 드는가 | 인력 단가 × 기간 |
| 품질 (Quality) | 기준을 만족하는가 | 테스트 계획, 검토 체크리스트 |
| 위험 (Risk) | 무엇이 틀어질 수 있는가 | 위험 목록, 대응 계획 |
| 이해관계자 (Stakeholder) | 누구와 소통하는가 | 보고 주기, 의사결정자 목록 |

### 3.1 WBS (작업 분해 구조)

WBS는 최종 산출물을 더 작은 작업으로 **계층적으로 나눈 표**다. 한 작업이 한 사람이 1–5일 안에 끝낼 수 있는 크기가 되면 충분히 나눈 것이다.

```
1. 로그인 기능
  1.1 화면 설계
  1.2 인증 API
    1.2.1 회원가입 엔드포인트
    1.2.2 로그인 엔드포인트
  1.3 테스트 작성
```

## 4. 일정 추정: PERT와 임계 경로

### 4.1 PERT 3점 추정

작업마다 세 가지 시간을 적는다.

- **O (낙관값):** 모든 것이 잘 될 때
- **M (most likely, 가능성 높은 값):** 보통 걸리는 시간
- **P (비관값):** 많이 꼬일 때

기대 시간과 표준편차는 다음과 같다.

```
E = (O + 4M + P) / 6
σ = (P − O) / 6
```

예: O=2일, M=4일, P=12일이면 E = (2 + 16 + 12) / 6 = 5일, σ = (12 − 2) / 6 ≈ 1.67일.

### 4.2 임계 경로 (Critical Path)

**정의** — 선행 관계로 연결된 작업들 중 **가장 긴 경로**다. 이 경로의 작업이 늦어지면 전체 프로젝트가 늦어진다. 임계 경로가 아닌 작업은 여유(float)가 있다.

다음 작업표로 계산해 본다.

| 작업 | 기간(일) | 선행 작업 |
|---|---|---|
| A 요구 분석 | 3 | 없음 |
| B DB 설계 | 2 | A |
| C 화면 설계 | 4 | A |
| D API 구현 | 5 | B |
| E 화면 구현 | 3 | C, D |

다음 코드는 가장 빨리 끝나는 시점(EF, Earliest Finish)을 계산하고 임계 경로를 찾는다.

```java
import java.util.*;

public class CriticalPathCheck {
    public static void main(String[] args) {
        // 작업 순서가 정해진 목록 (선행 작업이 먼저 나옴)
        String[] names = {"A", "B", "C", "D", "E"};
        int[] duration = {3, 2, 4, 5, 3};
        Map<String, List<Integer>> preds = new HashMap<>();
        preds.put("A", List.of());
        preds.put("B", List.of(0));       // A
        preds.put("C", List.of(0));       // A
        preds.put("D", List.of(1));       // B
        preds.put("E", List.of(2, 3));    // C, D

        int n = names.length;
        int[] es = new int[n], ef = new int[n];
        int[] from = new int[n];           // 시작을 결정한 선행 작업
        Arrays.fill(from, -1);
        for (int i = 0; i < n; i++) {      // 선행 작업이 항상 앞에 있으므로 순서대로 계산
            String key = names[i];
            for (int p : preds.get(key)) {
                if (ef[p] > es[i]) { es[i] = ef[p]; from[i] = p; }
            }
            ef[i] = es[i] + duration[i];
        }
        int end = 0;
        for (int i = 1; i < n; i++) if (ef[i] > ef[end]) end = i;

        // 끝에서 거슬러 올라가 임계 경로를 복원
        Deque<String> path = new ArrayDeque<>();
        for (int cur = end; cur != -1; cur = from[cur]) path.addFirst(names[cur]);

        System.out.println("프로젝트 기간 = " + ef[end] + "일");
        System.out.println("임계 경로 = " + String.join(" -> ", path));
    }
}
```

실행 결과: 프로젝트 기간 = 13일, 임계 경로 = A -> B -> D -> E.

계산을 손으로 확인하면 A(3) → B(2) → D(5) → E(3) = 13일이다. C 경로는 A(3) → C(4) → E(3) = 10일이라 여유가 3일 있다.

## 5. 정보처리기사 구축관리 필기와 연결

- 형상관리의 네 활동과 베이스라인을 정의 수준으로 답할 수 있어야 한다.
- PERT 공식과 임계 경로 계산은 필기에서 반복해서 나오는 유형이다.
- 위험 관리는 **식별 → 분석 → 대응 계획 → 모니터링** 순서로 외운다.

## 6. 실습 과제

1. 위 `CriticalPathCheck`에서 C의 기간을 6으로 바꾸고, 임계 경로가 바뀌는지 손으로 계산한 뒤 실행해 비교한다.
2. 내 졸업 작품이나 팀 과제 하나를 WBS로 나누고, 각 작업의 PERT 값을 적는다.
3. 최근 프로젝트에서 한 번이라도 베이스라인 없이 바뀐 것이 있었는지 떠올리고, 그때 생긴 문제를 한 문장으로 적는다.
