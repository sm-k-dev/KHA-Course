## 1. 관측성 (Observability)

**정의** — 시스템 내부 상태를 밖에서 보고 이해할 수 있는 능력이다. 세 가지 신호로 본다.

| 신호 | 무엇인가 | 예 |
|---|---|---|
| 로그 | 개별 사건 기록 | "주문 1001 결제 실패: 잔액 부족" |
| 메트릭 | 시간에 따른 수치 | 초당 요청 수, 오류율, p95 지연 시간 |
| 트레이스 | 한 요청이 여러 서비스를 지난 경로 | 게이트웨이 → 주문 서비스 → DB, 각 구간 시간 |

**구별해야 할 것** — 로그를 많이 남긴다고 관측성이 높은 것이 아니다. 무엇을 알고 싶은지 정하고, 그 답을 주는 신호를 남겨야 한다. 민감 정보(비밀번호, 개인정보)는 로그에 남기지 않는다.

**도구 (개념)**
- **Prometheus:** 메트릭을 주기적으로 수집해 저장한다.
- **Grafana:** 메트릭을 대시보드로 보여 준다.
- **ELK (Elasticsearch, Logstash, Kibana):** 로그를 모아 검색하고 시각화한다.

**알림 설계:** 오류율이 임계치를 넘었을 때 알린다. 알림이 너무 많으면 사람이 무시하게 된다(알림 피로).

**면접 기준:** "로그는 사건, 메트릭은 수치 추세, 트레이스는 요청 경로입니다. 셋을 함께 보면 어디서 느려졌는지 찾을 수 있습니다."

## 2. CI/CD 파이프라인

**정의** — 코드를 올리면 자동으로 빌드, 테스트, 배포까지 진행하는 흐름이다. CI(지속적 통합)는 병합할 때마다 빌드와 테스트를 돌리는 것이고, CD(지속적 배포)는 통과한 결과를 배포하는 것이다.

**일반적인 흐름**
1. 개발자가 브랜치에 push한다.
2. 파이프라인이 빌드하고 단위 테스트, 통합 테스트를 돌린다.
3. 정적 분석과 보안 검사(35장)를 통과해야 한다.
4. PR이 승인되고 `main`에 병합되면 이미지를 만든다.
5. 스테이징에 배포하고 확인한 뒤 운영에 배포한다.
6. 문제가 생기면 이전 버전으로 롤백한다.

**GitHub Actions (개념):** 저장소의 `.github/workflows/*.yml`에 단계를 적으면, 이벤트(push, PR)가 생길 때 GitHub가 실행한다. 실행 환경은 GitHub가 제공하는 가상 머신이다.

**주의:** 비밀 값(DB 비밀번호, 클라우드 키)은 파이프라인 설정 파일에 적지 않고, 저장소의 비밀 저장소(Secrets)에 둔다.

## 3. 데이터 파이프라인과 ETL

**정의** — 원본 데이터를 가져오고(Extract), 정리하고 변환하고(Transform), 대상 저장소에 적재하는(Load) 흐름이다. ELT는 적재한 뒤 변환하는 순서다.

**핵심 원칙: 멱등성 (Idempotency)** — 같은 작업을 여러 번 돌려도 결과가 같아야 한다. 파이프라인은 실패하면 재실행되는데, 재실행 때마다 데이터가 중복되면 안 된다.

**구현 (검증 완료): 같은 ID는 덮어쓰기(upsert), 잘못된 행은 격리**

```java
record Row(String id, String name) {}
static Map<String, Row> target = new HashMap<>();
static List<String> quarantine = new ArrayList<>();

static void load(List<Row> batch) {
    for (Row r : batch) {
        if (r.id() == null || r.id().isBlank()) { quarantine.add("빈 ID: " + r.name()); continue; }  // 잘못된 행 격리
        target.put(r.id(), r);                       // 같은 ID면 덮어쓰기 -> 재실행해도 중복이 없다
    }
}
```

- **확인:** 같은 배치를 두 번 돌려도 대상 테이블은 2건이고, 결과가 첫 실행과 같다. 같은 ID가 두 번 들어오면 마지막 값이 남는다. 빈 ID 행은 대상에 들어가지 않고 격리된다.
- **흔한 실수:** 적재 방식을 `INSERT`만 쓰면 재실행할 때 같은 행이 두 번 들어간다. 고유 키를 정하고 `INSERT ... ON DUPLICATE KEY UPDATE`(MySQL)처럼 upsert를 쓴다.

**재처리 설계**
- 실패한 배치만 다시 돌릴 수 있게 배치 ID와 상태를 기록한다.
- 격리된 행은 원인을 로그에 남기고 사람이 확인할 수 있게 한다.
- 원본 데이터 개수와 적재 개수를 비교하는 검사를 넣는다.

**pandas (개념):** 파이썬의 데이터 처리 라이브러리다. 표 형태 데이터를 읽고 정리하고 집계한다. 공공데이터 CSV나 로그 파일을 정리할 때 쓴다. (이 장에서는 파이썬 환경이 없어 실행하지 않았다.)

**면접 기준:** "ETL은 추출, 변환, 적재입니다. 재실행해도 결과가 같도록 고유 키 기준으로 upsert하고, 잘못된 행은 격리해서 추적합니다."
