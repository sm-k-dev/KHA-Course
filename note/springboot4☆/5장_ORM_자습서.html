1데이터베이스란?

핵심 한 줄 데이터베이스(DB)는 데이터를 정해진 구조로 저장하고, 필요한 데이터를 빠르게 찾아 주는 저장소입니다. 서버 프로그램이 꺼져도 회원 정보·게시글이 사라지지 않게 하려면 프로그램 메모리가 아니라 DB에 저장해야 합니다.

1-1. DBMS와 관계형 DBMS(RDBMS)

DB를 만들고 운영하는 소프트웨어를 DBMS(Database Management System)라고 합니다. MySQL, Oracle, H2가 모두 DBMS입니다. 여러 사용자가 동시에 같은 데이터에 접근해도 데이터가 깨지지 않도록 DBMS가 접근을 조율합니다. 아래 그림은 3개의 요청이 하나의 DBMS를 거쳐 데이터에 도달하는 구조입니다.

1-2. 개발용 H2와 서비스용 MySQL — 앱을 재시작하면?

이 자습서(교재)는 개발·테스트에는 H2, 실제 서비스에는 MySQL을 사용합니다. 차이는 데이터가 저장되는 위치입니다. H2(인메모리)는 스프링 부트 앱 안쪽 메모리에 데이터를 두기 때문에 앱이 종료되면 사라집니다. MySQL은 앱과 별도의 프로세스(서버)이므로 앱이 재시작되어도 데이터가 남습니다.

1-4. 기본키와 자동 증가 — 행을 추가하면 id는 누가 정하나?

새 행을 추가할 때 id를 쓰지 않아도 되는 이유는 id 열에 AUTO_INCREMENT(자동 증가) 속성이 있기 때문입니다. DB가 "마지막 번호 + 1"을 새 행의 id로 넣습니다. 반대로 기본키는 중복될 수 없으므로 이미 있는 id를 직접 넣으면 DB가 거부합니다.

2-3. INSERT — 추가

INSERT 예시SQL
-- 어디에(테이블과 열)  /  어떤 값을
INSERT INTO customers (name, phone_number, age)
VALUES ('박사번', '010-4444-4444', 40);

id를 쓰지 않았는데 4번 행이 생기는 이유는 id 열의 AUTO_INCREMENT 때문입니다. DB가 마지막 id에 1을 더한 값을 넣습니다. 이어서 '최오번'을 추가하면 5번 행이 됩니다. 한 번 사용한 번호는 그 행을 지워도 다시 쓰지 않습니다.

2-4. DELETE — 삭제

DELETE 예시SQL
-- id가 5인 행을 삭제
DELETE FROM customers WHERE id = 5;

2-5. UPDATE — 수정

UPDATE 예시SQL
-- 이름이 '김일번'인 행의 age를 11로 변경
UPDATE customers
SET age = 11
WHERE name = '김일번';
⚠️ UPDATE · DELETE에서 WHERE를 빼면 테이블의 모든 행이 수정·삭제됩니다. 실행기에서 "WHERE 없이"라고 표시된 버튼을 눌러 결과를 확인해 보세요. 실행 전에 WHERE가 있는지 항상 먼저 확인합니다.

3ORM이란? — 객체와 테이블을 서로 변환

핵심 한 줄 ORM(Object-Relational Mapping)은 자바의 객체(Object)와 관계형 DB의 표(Relational)를 서로 대응(Mapping)시켜서, 자바 코드만으로 DB 데이터를 다룰 수 있게 해 주는 기술입니다.

3-1. 자바와 DB는 데이터를 표현하는 방식이 다릅니다

자바는 데이터를 객체(클래스에서 만든 값 묶음)로 다루고, DB는 표의 행으로 다룹니다. 이 둘을 사람이 직접 옮기면 SQL 작성과 값 옮기기가 반복됩니다. ORM은 아래의 대응 규칙으로 이 작업을 자동으로 수행합니다. 버튼을 눌러 대응되는 곳을 확인하세요.

자바 세상 (코드)
class Member {
Long id;
String name;
}
new Member("홍길동") → id=1, name="홍길동"
DB 세상 (표)
테이블 이름: member
idname
1홍길동

3-3. ORM이 없을 때와 있을 때의 코드

같은 일(id가 1인 회원 1명 조회)을 두 방식으로 작성한 것입니다. 왼쪽 방식은 SQL 문장을 직접 쓰고, 결과의 각 열을 객체의 필드에 하나씩 옮겨야 합니다.

ORM 없이 — JDBC로 직접 작성 (예시)JAVA
// 1) 실행할 SQL을 직접 문자열로 작성한다.
String sql = "SELECT id, name FROM member WHERE id = ?";

try (Connection con = dataSource.getConnection();
     PreparedStatement ps = con.prepareStatement(sql)) {
    ps.setLong(1, 1L);                          // 2) ? 자리에 값을 직접 넣는다.
    try (ResultSet rs = ps.executeQuery()) {     // 3) SQL을 실행한다.
        if (rs.next()) {
            Member m = new Member();             // 4) 결과의 열을 객체의 필드로 하나씩 옮긴다.
            m.setId(rs.getLong("id"));
            m.setName(rs.getString("name"));
            return m;
        }
    }
}

3-4. ORM의 장점과 단점

장점 4가지 ① SQL을 직접 쓰지 않고 자바 코드로 DB를 사용
② 객체 중심으로 작성하므로 비즈니스 로직에 집중
③ DB 종류에 대한 의존이 줄어듦 (예: MySQL → PostgreSQL로 바꿔도 코드 수정이 거의 없음)
④ 객체와 테이블의 대응 정보가 코드(어노테이션)에 명확히 있어 유지보수에 유리
단점 2가지 ① 프로젝트가 복잡해질수록 사용 난이도가 올라감 (내부 동작을 알아야 함 → 이 자습서 6~7장)
② 매우 복잡하고 무거운 쿼리는 ORM만으로 해결하기 어려운 경우가 있음 (이때는 SQL을 직접 쓰는 방법을 함께 사용)
🛠️ 미션 3
  • "클래스 ↔ 테이블", "필드 ↔ 열", "객체 ↔ 행" 버튼을 각각 눌러 대응되는 위치를 확인한다.
  • ORM 애니메이션을 처음부터 끝까지 재생하고, SQL이 만들어지는 단계를 말해 본다.
  • JDBC 코드와 findById() 한 줄을 비교해, 사람이 직접 하던 일 2가지를 찾는다.

4JPA와 하이버네이트

핵심 구분 — 이름 3개, 역할 3개 JPA는 "자바에서 ORM을 이렇게 사용한다"는 규칙(인터페이스 모음)입니다. 규칙만 있고 실제로 실행되는 코드는 없습니다.
하이버네이트는 그 규칙을 실제로 구현한 라이브러리입니다. SQL을 만들고 DB로 보내는 일은 하이버네이트가 합니다.
스프링 데이터 JPA는 JPA를 더 쉽게 쓰도록 스프링이 만든 모듈입니다. 인터페이스 하나만 선언하면 CRUD 메서드가 생깁니다.

4-2. "인터페이스"와 "구현체"가 코드에서 어떻게 다른가

인터페이스는 메서드의 이름과 매개변수·반환형만 적어 둔 것이고, 구현체는 그 메서드의 본문(실제 처리 코드)을 가진 클래스입니다. 우리는 코드에서 항상 JPA의 인터페이스 이름(EntityManager)만 사용하고, 그 뒤에서 하이버네이트의 구현체가 실제로 일합니다.

JPA(인터페이스)와 하이버네이트(구현체) 관계 — 개념 예시JAVA

public interface EntityManager {
    void persist(Object entity);                       // 엔티티를 영속성 컨텍스트에 등록

// 위 인터페이스를 구현하고, persist() 안에 실제 처리 코드(SQL 생성 등)가 들어 있다.
// 우리가 이 클래스 이름을 직접 쓰는 일은 거의 없다.

// ── 우리 코드: 인터페이스 이름으로만 사용한다 ──
@PersistenceContext

5엔티티와 엔티티 매니저

핵심 한 줄 엔티티는 DB 테이블과 연결된 자바 객체이고, 엔티티 매니저는 그 엔티티를 저장·조회·수정·삭제하는 JPA의 핵심 객체입니다. 엔티티 매니저는 요청 하나당 하나씩 만들어서 쓰고, 만드는 곳이 엔티티 매니저 팩토리입니다.

5-1. 엔티티(Entity)

엔티티는 본질적으로 평범한 자바 객체입니다. 다만 @Entity 어노테이션으로 "이 클래스는 DB 테이블과 연결된다"고 선언했고, 그 객체가 엔티티 매니저에게 맡겨지면 그 객체에 일어난 변화가 DB 쿼리로 이어진다는 점이 일반 객체와 다릅니다.

엔티티 클래스 (Member.java 요약)JAVA
@Entity                       // 테이블 member 와 연결
public class Member {
    @Id                       // 이 필드가 기본키(PK)
    private Long id;          // 열 id

    private String name;      // 열 name
}
엔티티의 필수 요소이유

@Id 필드행을 구분하는 기본키가 필요함
기본 생성자
(public 또는 protected)		JPA가 DB 결과로 객체를 만들 때 사용

어노테이션 하나하나의 의미는 레슨 10에서 코드를 한 줄씩 보며 자세히 다룹니다.

5-2. 엔티티 매니저(EntityManager)

엔티티 매니저는 엔티티와 DB 사이에서 다음 일을 합니다.

  • 엔티티를 저장(persist) · 조회(find) · 삭제(remove)하고, 값이 바뀐 엔티티를 수정으로 반영
  • 다루는 엔티티를 자기 안의 영속성 컨텍스트(레슨 6)에 보관하고 추적
  • DB에 쿼리를 보내야 할 때(flush/commit) DB 커넥션을 사용해 SQL을 전송

5-3. 🎬 엔티티 매니저 팩토리 vs 엔티티 매니저

🏭 EntityManagerFactory (팩토리) • 애플리케이션 전체에서 1개만 만든다
• 만드는 비용이 크다 (DB 접속 설정, 매핑 정보 분석 등)
• 여러 스레드가 함께 써도 안전하다(thread-safe)
👤 EntityManager (매니저) • 요청(트랜잭션)이 올 때마다 팩토리가 새로 1개 만든다
• 만드는 비용이 거의 없다
• 여러 스레드가 함께 쓰면 안 된다(thread-safe 아님). 요청이 끝나면 닫는다(close)

6영속성 컨텍스트 ⭐ — JPA에서 가장 중요한 개념

정의 영속성 컨텍스트(Persistence Context)는 엔티티 매니저가 엔티티를 보관하고 추적하는 메모리 영역입니다. "엔티티를 영구 저장하는 환경"이라는 뜻의 이름이고, 엔티티 매니저 1개당 영속성 컨텍스트 1개가 연결됩니다.
JPA 사용자는 쿼리를 직접 쓰지 않아도 되지만, 언제 SQL이 나가는지는 이 영역의 동작 때문에 결정됩니다. 내용을 모르고 쓰면 의도하지 않은 결과가 나올 수 있어서, 기본 동작을 정확히 알아 두어야 합니다.

6-1. 1차 캐시와 동일성 보장

영속성 컨텍스트는 안에 1차 캐시를 가지고 있습니다. 캐시의 키는 엔티티의 @Id(기본키) 값, 값은 엔티티 객체입니다. find()가 호출되면 DB보다 먼저 이 캐시를 확인하고, 있으면 그 객체를 반환합니다. 없으면 DB에서 조회해 캐시에 저장한 뒤 반환합니다.

🎬 같은 id를 두 번 조회하면 SQL은 몇 번 나갈까? (다음 ▶)
1차 캐시 — 코드로 보기JAVA
Member m1 = em.find(Member.class, 1L);   // 캐시에 없음(MISS) → DB 조회(SQL 1번) → 캐시에 저장 → 반환
Member m2 = em.find(Member.class, 1L);   // 캐시에 있음(HIT)   → SQL 없음 → 같은 객체 반환

System.out.println(m1 == m2);            // true  (같은 id로 조회한 엔티티는 같은 객체)
알아 둘 점 3가지 ① 1차 캐시는 엔티티 매니저(영속성 컨텍스트) 하나의 안에서만 유효합니다. 보통 트랜잭션이 끝나면 사라지므로, 서비스 전체가 공유하는 캐시가 아닙니다.
② 캐시가 쓰이는 조회는 기본키로 찾는 find()입니다. findByName() 같은 쿼리 메서드는 항상 SQL을 실행합니다. (결과 id가 이미 캐시에 있으면 새 객체를 만들지 않고 캐시의 객체를 돌려줍니다.)
③ 이름은 "1차"이지만, 개발자가 켜고 끄는 기능이 아니라 항상 동작하는 기본 기능입니다.

6-2. 쓰기 지연 (Transactional Write-Behind)

persist()를 호출해도 INSERT가 바로 DB로 가지 않습니다. 영속성 컨텍스트 안의 쓰기 지연 SQL 저장소에 SQL을 모아 두었다가, 트랜잭션이 commit될 때 flush하면서 DB로 보냅니다. INSERT가 3개라면 persist 3번 동안은 SQL이 0개이고, commit 시점에 3개가 전송됩니다.

🎬 persist() 3번 → commit
id 생성 전략
⚠️ 교재의 Member처럼 IDENTITY 전략이면 INSERT는 모이지 않습니다 IDENTITY는 id를 DB가 만들어 주는 방식(MySQL의 AUTO_INCREMENT)입니다. 엔티티를 1차 캐시에 넣으려면 id를 알아야 하므로, persist() 시점에 INSERT를 즉시 실행해서 id를 받아 옵니다. 위 화면에서 IDENTITY를 선택해 비교해 보세요. 따라서 INSERT의 쓰기 지연 효과는 SEQUENCE 같은 전략에서 나타나고, UPDATE와 DELETE는 전략과 상관없이 commit(flush) 때까지 지연됩니다. 실습에서 persist() 직후 로그에 INSERT가 찍혀도 이상한 것이 아닙니다.

6-3. 변경 감지 (Dirty Checking)

엔티티를 조회하면 영속성 컨텍스트는 그 시점의 값을 스냅샷(최초 상태 복사본)으로 함께 저장합니다. 이후 개발자가 엔티티의 값을 바꾸기만 하면, flush 때 JPA가 현재 값과 스냅샷을 비교해서 달라진 엔티티에 대해 UPDATE를 자동으로 만들어 보냅니다. 그래서 JPA에는 "update 메서드"가 없습니다. 아래에서 세 가지 경우를 비교하세요.

🎬 값을 바꾸면 UPDATE는 언제, 어떻게 나갈까?
경우 선택
MemberService.java — 변경 감지로 수정하기JAVA
@Transactional                                   // 트랜잭션 안에서만 변경 감지가 동작한다
public void updateName(Long id, String newName) {
    Member member = memberRepository.findById(id).get();  // ① 조회 → 영속 상태 + 스냅샷 저장
    member.changeName(newName);                           // ② 필드 값만 변경 (SQL 없음)
    // memberRepository.save(member);  ← 호출하지 않아도 된다.
}                                                // ③ 메서드 종료 = commit → flush → 스냅샷 비교 → UPDATE 자동 실행
정리 • 변경 감지는 영속 상태의 엔티티에만 적용됩니다 (비영속·준영속은 대상이 아님).
• 트랜잭션(commit)이 있어야 flush가 일어나 UPDATE가 전송됩니다. 서비스 메서드에는 @Transactional을 붙입니다. (테스트의 @DataJpaTest는 이 트랜잭션 관리가 이미 포함되어 있습니다.)
• 값 변경은 setName() 같은 단순 setter 대신 changeName()처럼 의미 있는 이름의 메서드로 작성하는 것이 관례입니다.

6-4. 지연 로딩 (Lazy Loading)

게시글(Article)이 작성자(Member)를 참조한다고 합시다. 게시글을 조회할 때 작성자까지 항상 함께 가져오면, 작성자 정보를 쓰지 않는 코드에서도 쓸데없이 쿼리가 실행됩니다. 지연 로딩은 연관된 엔티티를 실제로 사용하는 순간(예: getName() 호출)에 조회합니다. 그 전까지는 프록시(껍데기 객체)를 대신 넣어 둡니다. 반대 방식인 즉시 로딩(EAGER)은 조회할 때 연관 데이터까지 모두 가져옵니다.

• 기본값은 연관 방식에 따라 다릅니다. @ManyToOne, @OneToOne은 기본이 EAGER, @OneToMany, @ManyToMany는 기본이 LAZY입니다. 그래서 @ManyToOne(fetch = FetchType.LAZY)처럼 직접 지정하는 경우가 많습니다.
• 영속성 컨텍스트가 이미 닫힌 뒤(준영속 상태)에 프록시를 사용하면 LazyInitializationException이 발생할 수 있습니다.

6-5. flush — 영속성 컨텍스트와 DB를 맞추는 작업

flush는 영속성 컨텍스트의 변경 내용(변경 감지로 만든 UPDATE 포함)을 DB로 전송하는 작업입니다. flush는 commit과 다릅니다. flush로 SQL이 DB에 도착해도 트랜잭션이 끝나기 전에는 확정(COMMIT)되지 않고 롤백될 수 있습니다.

flush가 일어나는 때설명
① em.flush() 직접 호출원하는 시점에 SQL을 DB로 보내 확인하고 싶을 때
② 트랜잭션 commit 직전 (자동)가장 흔한 경우. @Transactional 메서드가 끝날 때
③ JPQL 쿼리 실행 직전 (자동)findAll(), findByName() 같은 쿼리는 DB에서 읽기 때문에, 아직 모아 둔 변경이 있으면 먼저 반영해야 조회 결과가 맞음
  • flush는 1차 캐시를 비우지 않습니다. 엔티티는 계속 영속 상태입니다. (캐시를 비우는 것은 clear())
  • em.find()(기본키 조회)는 flush를 일으키지 않습니다.

🧠 퀴즈 6-1 · 1차 캐시

같은 영속성 컨텍스트 안에서 em.find(Member.class, 1L)을 두 번 호출했습니다. 올바른 설명은?

정답은 B입니다. 처음에는 캐시가 비어 있어 DB에서 조회하고 캐시에 저장합니다. 두 번째는 캐시에 있으므로 SQL 없이 같은 객체를 돌려주고, 그래서 m1 == m2가 true입니다.

🧠 퀴즈 6-2 · 쓰기 지연

id 생성 전략이 SEQUENCE일 때, em.persist(a); em.persist(b); em.persist(c); 직후(commit 전)의 상태는?

정답은 C입니다. persist 시점에 엔티티는 영속 상태가 되어 1차 캐시에 들어가고, INSERT SQL은 저장소에 보관됩니다. commit(flush) 때 DB로 전송됩니다. (IDENTITY 전략이면 INSERT가 persist 때 바로 전송됩니다.)

🧠 퀴즈 6-3 · 변경 감지

다음 중 UPDATE가 자동으로 실행되지 않는 경우는?

정답은 D입니다. 준영속 엔티티는 영속성 컨텍스트가 더 이상 추적하지 않으므로 변경 감지 대상이 아닙니다. A·B는 정상 동작하고, C는 변경 감지 덕분에 save() 없이도 UPDATE가 실행됩니다.

🧠 퀴즈 6-4 · 지연 로딩

@ManyToOne(fetch = FetchType.LAZY)인 author 필드가 있습니다. 게시글을 조회한 직후 article.getAuthor()에는 무엇이 들어 있나요?

정답은 A입니다. 지연 로딩은 껍데기(프록시)만 먼저 넣어 두고, 실제 값이 필요한 시점에 DB에서 조회해 채웁니다.

🧠 퀴즈 6-5 · flush

flush에 대한 설명으로 올바른 것은?

정답은 B입니다. flush 후에도 엔티티는 영속 상태로 1차 캐시에 남아 있고, 트랜잭션은 아직 끝나지 않았으므로 롤백될 수 있습니다.

7-4. 코드로 보기 — 줄을 눌러 상태 변화를 확인하세요

참고교재에는 4가지 상태 이름을 한 번에 보여 주려고 persist → detach → remove를 나란히 적은 예시가 있습니다. 상태 이름을 이해하는 용도이고, 이 순서 그대로 실행하면 준영속 객체에 remove()를 호출하게 되어 예외가 납니다. 위 예시는 실제로 실행 가능한 순서로 고친 것입니다.
🛠️ 미션 7
  • 상태 이동 화면에서 persist → detach → merge → remove → commit 순서로 눌러 객체의 이동 경로를 확인한다.
  • 비영속 상태로 되돌린 뒤 detach, remove를 눌러 거부 메시지를 확인한다.
  • 준영속 상태에서 persist를 눌러 예외가 나는 것을 확인하고, 대신 merge를 사용한다.
  • 6장의 JPA 실험실 시나리오 ④(준영속 + merge)를 다시 실행하며 상태 배지 색이 바뀌는 것을 확인한다.

🧠 퀴즈 7-2

정답은 C입니다. 값은 자바 객체에서 바뀌지만 영속성 컨텍스트의 추적 대상이 아니므로 DB에는 반영되지 않습니다. 반영하려면 merge()로 영속 상태로 되돌려야 합니다.

🧠 퀴즈 7-3

정답은 A입니다. B·C는 준영속에 쓰면 예외가 납니다. 준영속 → 영속은 merge()이며, 반환된 객체가 영속입니다.

9-5. 쿼리 메서드와 @Query

findAll(), findById()는 기본으로 제공되지만, name처럼 값이 없을 수도 있는 열로 찾는 메서드는 기본으로 없습니다. 이때 findBy + 필드명 규칙대로 메서드를 선언하면 JPA가 쿼리를 만들어 줍니다. 구현은 필요 없고, 선언한 뒤 가져다 쓰기만 하면 됩니다.

MemberRepository.javaJAVA
@Repository
public interface MemberRepository extends JpaRepository<Member, Long> {

    Optional<Member> findByName(String name);          // 이름 규칙으로 쿼리 자동 생성

    // 쿼리가 너무 복잡하거나 성능상 직접 써야 할 때는 @Query에 JPQL을 직접 작성한다.
    @Query("select m from Member m where m.name = ?1")
    Optional<Member> findByNameQuery(String name);
}
JPQL이란?테이블이 아니라 엔티티 클래스(Member)와 필드(m.name)를 대상으로 쓰는 쿼리 언어입니다. 하이버네이트가 이를 실제 SQL로 변환합니다.
🛠️ 미션 9
  • 실행기에서 @Sql → findAll → findById(2L) → findByName("C")를 순서대로 눌러, 매번 SQL이 나가는 것을 확인한다.
  • 수정 테스트(changeName("BC") → findById(2L).get().getName())에서 SQL이 나가지 않는 것을 확인하고, flush()를 눌렀을 때 UPDATE가 나가는 것을 확인한다.
  • deleteAll()을 누르고 로그에서 select 1번과 delete 여러 번이 나가는지 확인한다.
  • 코드 해설 탭 8개를 모두 열어 각 줄의 "호출되는 곳 / 반환되는 곳"을 읽는다.

🧠 퀴즈 9-1

정답은 B입니다. findBy + 필드명 규칙대로 선언하면 구현 없이 쿼리가 만들어집니다. findById는 기본키(Long)로만 찾습니다.

🧠 퀴즈 9-2

정답은 C입니다. id로 조회하는 find는 1차 캐시를 먼저 확인합니다. 그래서 UPDATE가 나가기 전에도 변경된 값이 보입니다. UPDATE가 실제로 나가는 시점은 flush/commit입니다.

10-3. 기본 생성자가 반드시 필요하고, 왜 protected인가

  • JPA(하이버네이트)는 DB에서 읽은 행을 엔티티 객체로 만들 때 파라미터 없는 기본 생성자로 객체를 먼저 만든 뒤 필드를 채웁니다. 그래서 엔티티에는 기본 생성자가 필수이고, 접근 제어자는 public 또는 protected여야 합니다.
  • public으로 두면 아무 코드에서나 new Member()로 이름 없는 객체를 만들 수 있지만, protected로 두면 개발자가 의도하지 않게 빈 객체를 만드는 것을 막으면서 JPA는 사용할 수 있습니다. 그래서 protected를 권장합니다.
  • Lombok의 @NoArgsConstructor(access = AccessLevel.PROTECTED)가 이 생성자를 자동으로 만들어 줍니다.
