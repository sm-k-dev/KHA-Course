레슨 0CI/CD가 무엇인지 알기

💡 왜 하나요?

12장에서는 코드를 고칠 때마다 jar를 직접 빌드하고 빈스톡에 손으로 올렸습니다. 이번 장에서는 깃허브에 코드를 올리기만 하면 빌드·테스트·배포가 자동으로 실행되게 만듭니다.

CI (지속적 통합)
코드가 저장소에 올라올 때마다 빌드와 테스트를 자동으로 실행하는 과정입니다. 테스트가 실패하면 그 자리에서 멈추고 알려 줍니다.
CD (지속적 제공·배포)
CI를 통과한 코드를 서버에 자동으로 배포하는 과정입니다. 이번 실습에서는 일래스틱 빈스톡에 jar를 올립니다.
깃(Git)
내 PC에서 파일의 변경 이력을 저장하는 프로그램입니다.
깃허브(GitHub)
깃 저장소를 인터넷에 올려 두는 서비스입니다. 저장소 1개를 리포지토리라고 부릅니다.
커밋 / 푸시
커밋은 변경 내용을 내 PC 저장소에 기록하는 것, 푸시는 그 기록을 깃허브로 올리는 것입니다.
깃허브 액션 / 워크플로
깃허브 액션은 푸시 같은 일이 생기면 깃허브의 리눅스 가상머신에서 명령을 실행해 주는 기능입니다. 실행할 명령을 적은 yml 파일을 워크플로라고 부릅니다.

준비물확인 방법

chapter12 프로젝트인텔리제이에서 build가 성공합니다
깃허브 계정github.com에 로그인됩니다

빈스톡 환경 상태가 OK인지 확인하고, 애플리케이션 이름과 환경 이름을 메모장에 적어 두세요. 레슨 8에서 그대로 씁니다.

🧠 퀴즈

테스트가 실패하면 서버에 배포되지 않게 막아 주는 과정은?

CI 단계에서 빌드·테스트가 실패하면 워크플로가 멈추므로 배포 단계까지 가지 않습니다.

레슨 1깃 설치하고 사용자 정보 설정하기

💡 왜 하나요?

깃이 있어야 내 PC의 프로젝트를 깃허브로 올릴 수 있습니다. 커밋할 때마다 기록되는 이름과 이메일도 미리 정해 둡니다.

  1. git-scm.com/download/win에 접속해 Click here to download를 누릅니다.
  2. 설치 화면은 모두 기본값으로 두고 Next와 Install을 누릅니다.
  3. 설치가 끝나면 인텔리제이를 다시 시작하고 아래쪽 Terminal을 엽니다.
  4. 아래 명령을 입력합니다.
터미널
git --version
✅ 이렇게 나오면 성공

git version 2.xx.x.windows.1처럼 버전 숫자가 출력됩니다.

  1. 깃허브 가입에 쓴 아이디와 이메일로 바꿔 아래 2줄을 실행합니다.
터미널
git config --global user.name "깃허브아이디"
git config --global user.email "깃허브이메일주소"

실제 입력 예시: git config --global user.name "hong1234"

설정 확인
git config --global --list
✅ 이렇게 나오면 성공

user.name=…, user.email=… 두 줄이 내가 입력한 값으로 보입니다.

⚠️ “git은(는) 내부 또는 외부 명령… 아닙니다” 오류

설치 직후 열려 있던 터미널은 새 경로를 모릅니다. 인텔리제이를 완전히 껐다가 다시 켜고 터미널을 새로 여세요.

🛠️ 미션

git --version으로 설치를 확인하고, 사용자 이름과 이메일을 설정하세요.

🧠 퀴즈

git config의 user.email은 언제 쓰이나요?

커밋 기록에 작성자 이름과 이메일이 함께 저장됩니다.

레슨 2SSH 키 만들고 깃허브에 등록하기

💡 왜 하나요?

푸시할 때마다 깃허브 암호를 입력하지 않도록, 내 PC를 증명하는 SSH 키를 깃허브에 등록합니다.

SSH 키
한 쌍으로 만들어지는 파일 2개입니다. id_rsa(개인 키)는 내 PC에만 두고, id_rsa.pub(공개 키)는 깃허브에 등록합니다.
  1. 터미널에 아래 명령을 입력합니다.
  2. 질문이 3번 나오면 아무것도 입력하지 않고 Enter만 누릅니다.
터미널
ssh-keygen -t rsa -C "깃허브이메일주소"
✅ 이렇게 나오면 성공

Your public key has been saved in C:\Users\내계정/.ssh/id_rsa.pub 문장과 네모난 그림(randomart)이 출력됩니다.

⚠️ “Overwrite (y/n)?”가 나와요

이미 SSH 키가 있다는 뜻입니다. n을 입력해 취소하고, 기존 키를 그대로 다음 단계에 쓰면 됩니다.

  1. 아래 명령으로 공개 키 내용을 출력하고, ssh-rsa부터 이메일까지 한 줄 전체를 복사합니다.
터미널 (PowerShell)
cat ~/.ssh/id_rsa.pub
✅ 이렇게 나오면 성공

ssh-rsa AAAAB3Nza…긴 문자열… 깃허브이메일주소 한 줄이 출력됩니다.

  1. 깃허브 오른쪽 위 프로필 사진 → Settings를 누릅니다.
  2. 왼쪽 SSH and GPG keys → New SSH key를 누릅니다.
  3. Title에 이름을 적고, Key에 복사한 공개 키를 붙여넣습니다.
  4. Add SSH key를 누릅니다.
  1. 연결을 확인합니다. 처음 접속하면 질문이 나오는데 yes를 입력합니다.
터미널
ssh -T git@github.com
✅ 이렇게 나오면 성공

Hi 깃허브아이디! You've successfully authenticated, but GitHub does not provide shell access.가 출력됩니다.

⚠️ “Permission denied (publickey)” 오류

깃허브에 붙여넣은 값이 id_rsa.pub가 아니거나 일부만 복사된 경우입니다. cat ~/.ssh/id_rsa.pub 결과 한 줄 전체를 다시 등록하세요.

🛠️ 미션

SSH 키를 깃허브에 등록하고 ssh -T git@github.com에서 Hi 아이디! 문장을 확인하세요.

🧠 퀴즈

깃허브에 등록하는 파일은?

.pub이 붙은 공개 키만 등록합니다. id_rsa(개인 키)는 절대 다른 곳에 올리지 않습니다.

레슨 3리포지토리 만들고 첫 푸시하기

💡 왜 하나요?

깃허브 액션은 깃허브 리포지토리에 있는 코드로 실행됩니다. 먼저 프로젝트 전체를 깃허브에 올립니다.

① 민감한 값부터 바꾸기

⚠️ 푸시 전에 꼭 확인하세요

깃허브에 올린 파일은 누구나 볼 수 있습니다. application.yml의 구글 OAuth 값, JWT 키, OpenAI 키를 가짜 값으로 바꾸세요. 실제 값은 12장에서 빈스톡 환경 속성에 넣었으므로 서버에서는 그 값이 쓰입니다.

application.yml (바꿀 부분)
  security:
    oauth2:
      client:
        registration:
          google:
            client-id: test_id
            client-secret: test_secret
            scope:
              - email
              - profile
jwt:
  issuer: ajufresh@gmail.com
  secret_key: test_key
application.yml (OpenAI 키)
  ai:
    openai:
      api-key: test_api_key

② 리포지토리 만들기

  1. 깃허브 오른쪽 위 + → New repository를 누릅니다.
  2. Repository name에 아래 이름을 넣습니다.
  3. 공개 범위를 고르고, Add a README file은 체크하지 않은 채 Create repository를 누릅니다.
  4. 생성된 화면의 Quick setup에서 SSH 탭을 누르고 주소를 복사합니다.
Repository name
springboot-developer

실제 입력 예시: git@github.com:hong1234/springboot-developer.git

③ 내 프로젝트를 깃 저장소로 만들고 연결하기

  1. 인텔리제이 터미널이 프로젝트 폴더인지 확인하고 아래 명령을 실행합니다.
터미널
git init
✅ 이렇게 나오면 성공

Initialized empty Git repository in …/springboot-developer/.git/가 출력됩니다.

터미널
git remote add origin git@github.com:깃허브아이디/springboot-developer.git
git remote -v
✅ 이렇게 나오면 성공

origin git@github.com:깃허브아이디/springboot-developer.git (fetch)와 (push) 두 줄이 보입니다.

④ 커밋하고 푸시하기

터미널
git add .
git commit -m "project init"
git branch -M main
git push origin main
✅ 이렇게 나오면 성공

마지막에 * [new branch] main -> main이 출력됩니다. 깃허브 리포지토리 화면을 새로고침하면 src, build.gradle 등 파일이 보입니다.

⚠️ “failed to push some refs” 오류

리포지토리를 만들 때 README를 추가했으면 납니다. 아래 명령을 실행한 뒤 다시 push 하세요.

터미널
git pull origin main --rebase
⚠️ 주소를 https로 연결했어요

push 할 때 브라우저 로그인 창이 뜹니다. SSH로 바꾸려면 아래 명령을 실행하세요.

터미널
git remote set-url origin git@github.com:깃허브아이디/springboot-developer.git
🛠️ 미션

민감한 값을 가짜 값으로 바꾼 뒤, 프로젝트를 깃허브 main 브랜치에 푸시하세요.

🧠 퀴즈

git add . → git commit → git push 중 깃허브로 파일을 올리는 명령은?

add는 올릴 파일을 고르고, commit은 내 PC에 기록하고, push가 깃허브로 전송합니다.

레슨 4CI 워크플로 만들기 (ci.yml)

💡 왜 하나요?

main 브랜치에 푸시할 때마다 깃허브가 자동으로 빌드와 테스트를 실행하게 만듭니다.

  1. 프로젝트 최상단 폴더를 우클릭 → 새로 만들기 → 디렉터리로 .github 폴더를 만듭니다.
  2. .github 안에 workflows 폴더를 만듭니다. 이름 끝에 s가 있어야 합니다.
  3. workflows 안에 ci.yml 파일을 만들고 아래 내용을 붙여넣습니다.
.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6

      - uses: actions/setup-java@v5
        with:
          distribution: 'corretto'
          java-version: '25'

      - name: Grant execute permission for gradlew
        run: chmod +x gradlew

      - name: Build with Gradle
        run: ./gradlew clean build
줄뜻
name: CI깃허브 Actions 탭에 보이는 워크플로 이름입니다
on: push: branches: [ main ]main 브랜치에 푸시될 때 실행합니다
runs-on: ubuntu-latest깃허브가 빌려주는 우분투 리눅스 가상머신에서 실행합니다
actions/checkout@v6리포지토리 코드를 가상머신으로 내려받습니다
actions/setup-java@v5아마존 Corretto JDK 25를 설치합니다
chmod +x gradlew윈도우에서 올린 gradlew에 리눅스 실행 권한을 줍니다
./gradlew clean build컴파일 → 테스트 → jar 생성을 실행합니다. 테스트가 실패하면 여기서 멈춥니다
터미널
git add .
git commit -m "CI 추가"
git push origin main
  1. 깃허브 리포지토리의 Actions 탭을 엽니다.
  2. CI 추가 실행 항목을 눌러 진행 상황을 봅니다.
✅ 이렇게 나오면 성공

1~3분 뒤 실행 항목 앞이 초록 체크(✅)로 바뀝니다. build를 눌러 보면 모든 단계에 초록 체크가 있습니다.

⚠️ Actions 탭에 아무것도 안 보여요

폴더 이름이 .github/workflows가 맞는지 확인하세요. workflow(s 없음)나 github(점 없음)이면 실행되지 않습니다.

⚠️ Build with Gradle 단계가 빨간 X

실패한 단계를 눌러 로그 끝부분을 보세요. FAILED 앞에 실패한 테스트 이름이 나옵니다. 내 PC에서 같은 테스트를 고친 뒤 다시 푸시하세요.

🛠️ 미션

ci.yml을 푸시하고 Actions 탭에서 초록 체크를 확인하세요.

🧠 퀴즈

워크플로 파일을 넣어야 하는 폴더는?

깃허브는 리포지토리의 .github/workflows 폴더 안 yml 파일만 워크플로로 인식합니다.

레슨 5jar 파일 1개만 만들게 설정하기

💡 왜 하나요?

build를 하면 jar가 2개 생깁니다. 자동 배포 스크립트는 build/libs에 있는 파일 이름을 그대로 읽으므로, 실행 가능한 jar 1개만 남겨야 합니다.

파일설명
springboot-developer-0.0.1-SNAPSHOT.jar라이브러리까지 들어 있어 java -jar로 실행됩니다
springboot-developer-0.0.1-SNAPSHOT-plain.jar내 클래스만 들어 있어 단독 실행이 안 됩니다 (플레인 아카이브)
  1. build.gradle 맨 아래에 아래 코드를 추가합니다.
  2. 오른쪽 Gradle 탭의 새로고침(⟳)을 누릅니다.
  3. Gradle → Tasks → build → build를 더블클릭합니다.
build.gradle
jar {
    enabled = false
}
✅ 이렇게 나오면 성공

build/libs 폴더에 -plain이 없는 jar 1개만 보입니다.

⚠️ 예전 plain.jar가 아직 보여요

이전 빌드 결과가 남은 것입니다. Gradle → Tasks → build → clean을 먼저 실행한 뒤 build를 다시 하세요.

🛠️ 미션

build.gradle에 jar { enabled = false }를 추가하고 build/libs에 jar가 1개만 생기는지 확인하세요.

🧠 퀴즈

jar { enabled = false }를 넣는 이유는?

자동 배포 스크립트가 jar 1개만 찾아 올릴 수 있도록 plain.jar 생성을 끕니다.

레슨 6깃허브 액션용 IAM 사용자와 액세스 키 만들기

💡 왜 하나요?

깃허브 액션이 내 AWS 계정의 빈스톡에 배포하려면 AWS 로그인 정보가 필요합니다. 배포 권한만 가진 전용 사용자를 만들고 액세스 키를 발급합니다.

액세스 키
프로그램이 AWS에 로그인할 때 쓰는 아이디(액세스 키)와 암호(비밀 액세스 키) 한 쌍입니다.
  1. AWS 콘솔 검색창에 IAM → 왼쪽 사용자 → 사용자 생성을 누릅니다.

레슨 8CD 워크플로로 바꾸고 자동 배포하기 (cicd.yml)

💡 왜 하나요?

CI 단계 뒤에 빈스톡 배포 단계를 붙이면, 푸시 한 번으로 빌드·테스트·배포가 모두 끝납니다.

  1. ci.yml을 우클릭 → Refactor → Rename으로 이름을 cicd.yml로 바꿉니다.
  2. 파일 내용을 모두 지우고 아래 코드를 붙여넣습니다.
  3. application_name과 environment_name을 내 빈스톡 이름으로 바꿉니다.
.github/workflows/cicd.yml
name: CI/CD

on:
  push

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v6

      - uses: actions/setup-java@v5
        with:
          distribution: 'corretto'
          java-version: '25'

      - name: Grant execute permission for gradlew
        run: chmod +x gradlew

      - name: Build with Gradle
        run: ./gradlew clean build

      - name: Get current time
        uses: josStorer/get-current-time@v2.0.2
        id: current-time
        with:
          format: YYYY-MM-DDTHH-mm-ss
          utcOffset: "+09:00"

      - name: Set artifact
        run: echo "artifact=$(ls ./build/libs)" >> $GITHUB_ENV

      - name: Beanstalk Deploy
        uses: einaregilsson/beanstalk-deploy@v20
        with:
          aws_access_key: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws_secret_key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          application_name: springboot-developer
          environment_name: Springboot-developer-env
          version_label: github-action-${{steps.current-time.outputs.formattedTime}}
          region: ap-northeast-2
          deployment_package: ./build/libs/${{env.artifact}}
추가된 단계하는 일
Get current time현재 한국 시간을 구해 배포 버전 이름에 붙입니다. 빈스톡은 같은 버전 이름을 두 번 쓸 수 없습니다
Set artifactbuild/libs 안의 jar 파일 이름을 artifact 변수에 저장합니다
Beanstalk Deployjar를 빈스톡에 업로드하고 새 버전으로 환경을 교체합니다
터미널
git add .
git commit -m "ci.yml > cicd.yml"
git push origin main
  1. 깃허브 Actions 탭 → 맨 위 실행 항목 → build를 눌러 단계별 진행을 봅니다.
  2. 모두 초록 체크가 되면 빈스톡 환경 개요의 실행 버전을 확인합니다.
✅ 이렇게 나오면 성공

빈스톡 환경 개요의 실행 버전이 github-action-2026-11-03T16-00-00 형식으로 바뀌고, 상태가 OK입니다. 사이트에 접속하면 방금 푸시한 코드가 반영되어 있습니다.

⚠️ “Error: Environment still has health Yellow 30 seconds after update finished!”

배포는 끝났지만 서버가 아직 시작 중이라는 뜻입니다. 1~2분 뒤 빈스톡 상태가 OK가 되면 정상입니다.

⚠️ “Environment not found” 또는 “No Application named …”

application_name·environment_name이 빈스톡 화면과 다릅니다. 빈스톡 환경 개요에서 그대로 복사해 다시 푸시하세요.

🛠️ 미션

cicd.yml을 푸시해 Actions가 초록 체크로 끝나고, 빈스톡 실행 버전이 github-action-…으로 바뀐 것을 확인하세요.

레슨 9워크플로 오류 해결하기

💡 왜 하나요?

깃허브 액션이 실패하면 어느 단계에서 왜 멈췄는지 로그에 정확히 나옵니다.

  1. Actions 탭에서 빨간 X 실행 항목을 누릅니다.
  2. build를 누르고 빨간 X가 붙은 단계를 펼칩니다.
  3. 맨 아래 Error 문장을 읽고 아래 표에서 찾습니다.

실패한 실행 항목 오른쪽 위의 Re-run jobs를 누르면 같은 커밋으로 다시 실행됩니다. 시크릿만 고친 경우에 씁니다.

🛠️ 미션

Actions 탭에서 지난 실행 항목의 build 로그를 열어 Build with Gradle 단계의 BUILD SUCCESSFUL 문장을 찾아보세요.

🧠 퀴즈

로그에 “The security token included in the request is invalid”가 보입니다. 먼저 고칠 곳은?

AWS가 액세스 키를 인정하지 않는다는 뜻입니다. 시크릿 값을 다시 등록하세요.

레슨 10실습 끝나면 정리하기

💡 왜 하나요?

EC2와 RDS는 켜 둔 시간만큼 요금이 계산됩니다. 액세스 키도 남겨 두면 유출되었을 때 위험합니다.

  1. 빈스톡 → 환경 → 내 환경 선택 → 작업 → 환경 종료를 누릅니다. EC2와 데이터베이스가 함께 삭제됩니다.
  2. S3 → 내 버킷 선택 → 비어 있음 → 삭제를 누릅니다.
  3. IAM → 사용자 → github-action → 보안 자격 증명 → 액세스 키 작업 → 비활성화 후 삭제를 누릅니다.
  4. 깃허브 리포지토리의 Secrets 2개도 삭제합니다.
  5. 환경을 지운 뒤 푸시하면 Beanstalk Deploy 단계가 실패하므로, cicd.yml을 ci.yml로 되돌려 CI만 남깁니다.
✅ 이렇게 나오면 성공

빈스톡 환경 목록·RDS 목록·내 S3 버킷이 비어 있고, github-action 사용자의 액세스 키가 0개입니다.

⚠️ 버킷이 삭제되지 않아요

안에 파일이 남아 있으면 삭제할 수 없습니다. 먼저 비어 있음을 실행하세요.

🛠️ 미션

실습을 마친 뒤 환경 종료 → 버킷 삭제 → 액세스 키 삭제까지 마치세요.

🧠 퀴즈

실습 후 액세스 키를 삭제하는 가장 큰 이유는?

액세스 키는 AWS 로그인 정보입니다. 쓰지 않으면 삭제하는 것이 안전합니다.

깃허브와 AWS 화면은 수시로 바뀝니다. 버튼 이름이 조금 달라도 같은 위치의 메뉴를 찾으면 됩니다.
