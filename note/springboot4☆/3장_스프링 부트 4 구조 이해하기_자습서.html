0. 3장 지도

2장에서는 스프링 부트를 실행해 보았습니다. 이번 장은 실행 전에 프로젝트가 어떻게 생겼는지 읽는 법을 배웁니다. 파일 하나하나의 역할을 알면, 나중에 오류가 났을 때 어디를 봐야 할지 알 수 있습니다.

🎬 애니메이션: 프로젝트를 읽는 네 가지 관문

  1. 프로젝트를 읽는 순서입니다. 네 관문을 차례로 통과합니다.
  2. 1단계: 프로젝트를 만들 때 고른 설정이 출발점입니다.
  3. 2단계: 폴더는 코드와 설정 파일을 역할별로 나눠 둡니다.
  4. 3단계: build.gradle은 어떤 라이브러리를 쓸지 적어 둔 목록입니다.
  5. 4단계: application.yml은 실행할 때 쓸 설정 값을 적어 둡니다.
관문파일 또는 폴더한 줄 역할
1Initializr 설정프로젝트의 뼈대를 정함
2src 폴더코드, 설정, 테스트를 나눠 담음
3build.gradle의존성(라이브러리)과 빌드 방법
4application.yml포트, 데이터베이스 같은 실행 설정

1. 프로젝트 만들기

스프링 부트 프로젝트는 직접 폴더를 만들기보다 Spring Initializr(start.spring.io)에서 만드는 것이 일반적입니다. 여기서 고른 값이 build.gradle과 폴더 구조의 바탕이 됩니다.

🎬 애니메이션: Initializr에서 고르는 순서

  1. 웹 화면에서 항목을 하나씩 고릅니다.
  2. 1단계: 빌드 도구는 Gradle을 고릅니다. 이 책은 Groovy 방식을 기준으로 합니다.
  3. 2단계: 언어는 Java를 고릅니다.
  4. 3단계: Spring Boot 버전은 안정 버전(정식 출시)을 고릅니다.
  5. 4단계: 자바 버전은 설치한 JDK와 맞춥니다. 21을 권장합니다.
항목고르는 값이유
ProjectGradle - Groovybuild.gradle 파일로 설정함
Groupcom.example패키지 이름의 앞부분이 됨
Artifactdemo프로젝트 이름이 됨
DependenciesSpring Web웹 요청을 받을 수 있게 함
📌 Dependencies 칸은 나중에도 추가할 수 있습니다처음에 Spring Web만 골라도 됩니다. 필요할 때 build.gradle에 한 줄을 더 넣으면 됩니다.
⚠️ 자바 버전 불일치Initializr에서 고른 Java 버전이 실제 설치된 JDK와 다르면 빌드가 실패합니다. IDE의 프로젝트 JDK 설정도 같은 버전인지 확인하세요.
🧠 확인 퀴즈 1

Q. Initializr에서 Group 값 com.example은 나중에 무엇이 되나요?

A. 패키지 이름의 앞부분입니다. 예: com.example.demo 패키지.

2. 폴더 구조

스프링 부트 프로젝트의 폴더는 무엇을 담는지에 따라 나뉘어 있습니다. 자바 코드는 java 폴더에, 설정과 화면 파일은 resources 폴더에, 테스트는 test 폴더에 둡니다.

🎬 애니메이션: 폴더를 역할별로 나눠 보기

  1. 폴더 이름 하나에 역할이 하나씩 붙어 있습니다.
  2. 1단계: src/main/java에는 실제 프로그램 코드가 들어갑니다.
  3. 2단계: src/main/resources에는 설정 파일과 화면, 정적 파일이 들어갑니다.
  4. 3단계: src/test/java에는 자동으로 기능을 확인하는 테스트 코드가 들어갑니다.
  5. 4단계: build.gradle은 src 밖, 프로젝트 맨 위에 있습니다.

트리 모양으로 보기

demo/ ├── build.gradle // 의존성과 빌드 설정 ├── settings.gradle // 프로젝트 이름 설정 └── src/ ├── main/ │ ├── java/com/example/demo/ │ │ └── DemoApplication.java // 시작 파일 │ └── resources/ │ └── application.yml // 실행 설정 └── test/ └── java/com/example/demo/ └── DemoApplicationTests.java // 테스트
⚠️ 패키지 경로와 폴더는 일치해야 합니다com.example.demo 패키지의 클래스는 com/example/demo 폴더 안에 있어야 합니다. 이 규칙이 어긋나면 컴파일 오류가 나거나, 스프링이 빈을 찾지 못합니다.
🧠 확인 퀴즈 2

Q. 테스트 코드는 어느 폴더에 두나요?

A. src/test/java 폴더입니다.

3. build.gradle 읽기

build.gradle은 프로젝트의 설계도 겸 재료 목록입니다. 어떤 플러그인을 켤지, 어떤 라이브러리를 가져올지, 테스트를 어떻게 실행할지를 적습니다.

🎬 애니메이션: build.gradle의 세 블록

  1. build.gradle은 블록 단위로 읽으면 쉽습니다.
  2. 1단계: plugins 블록은 자바와 스프링 부트 기능을 빌드에 켭니다.
  3. 2단계: dependencies 블록은 필요한 라이브러리를 나열합니다.
  4. 3단계: 의존성 한 줄이 라이브러리 하나 또는 묶음 하나를 뜻합니다.

코드: build.gradle 일부

plugins { id 'java' // 자바 프로그램을 빌드하는 기능을 켠다 id 'org.springframework.boot' version '4.0.0' // 스프링 부트 기능을 켠다. 버전은 Initializr가 정한 값을 그대로 둔다 id 'io.spring.dependency-management' version '1.1.7' // 라이브러리 버전을 자동으로 맞춰 준다 } group = 'com.example' // 패키지 이름의 앞부분 version = '0.0.1-SNAPSHOT' // 프로젝트 버전 java { toolchain { languageVersion = JavaLanguageVersion.of(21) // 컴파일에 쓸 자바 버전 } } dependencies { implementation 'org.springframework.boot:spring-boot-starter-web' // 웹 요청을 받는 기능 묶음 testImplementation 'org.springframework.boot:spring-boot-starter-test' // 테스트 도구 묶음 } tasks.named('test') { useJUnitPlatform() // 테스트를 JUnit 5 방식으로 실행한다 }
키워드뜻
implementation실행과 컴파일 모두에 필요한 의존성
testImplementation테스트를 실행할 때만 필요한 의존성
starter관련 라이브러리를 한 번에 가져오는 묶음 이름
📌 의존성을 추가하는 법라이브러리 이름을 찾아 dependencies 블록 안에 한 줄 넣고, 화면 오른쪽 위의 Gradle 새로고침(코끼리 아이콘)을 누르면 내려받습니다.
🧠 확인 퀴즈 3

Q. build.gradle의 dependencies 블록에는 무엇을 적나요?

A. 프로젝트가 필요로 하는 라이브러리(의존성) 목록을 적습니다.

4. application.yml

application.yml은 프로그램이 실행될 때 읽는 설정 파일입니다. 포트 번호, 데이터베이스 주소, 로그 수준 같은 값을 여기서 바꿉니다. 코드를 고치지 않고도 동작을 바꿀 수 있어 편리합니다.

🎬 애니메이션: 설정 항목이 하나씩 쌓이는 순서

  1. 설정 파일에는 값이 키와 함께 적힙니다.
  2. 1단계: server.port는 서버가 열릴 포트 번호입니다.
  3. 2단계: spring.application.name은 이 프로그램의 이름입니다.
  4. 3단계: logging.level은 어떤 로그까지 화면에 보일지 정합니다.

코드: application.yml 예시

server: port: 8080 # 서버가 요청을 받을 포트 번호 spring: application: name: memo-app # 프로그램 이름. 로그 등에 표시된다 logging: level: root: INFO # 기본 로그 수준. 정보성 로그까지 출력한다 com.example.demo: DEBUG # 우리 패키지 로그만 더 자세히 출력한다
⚠️ 들여쓰기가 문법입니다yml은 칸 수(들여쓰기)로 소속을 나타냅니다. 탭 문자를 쓰면 오류가 나므로 스페이스 2칸으로 맞추세요.
📌 properties 파일과 같은 역할application.properties 파일도 같은 일을 합니다. 형식만 다르고, 한 프로젝트에 둘 중 하나만 쓰는 것이 좋습니다.
🧠 확인 퀴즈 4

Q. application.yml에서 서버 포트를 바꾸려면 어떤 항목을 고치나요?

A. server.port 항목입니다.

5. 3계층 구조

스프링 부트 웹 프로그램은 대개 세 계층으로 나눕니다. 요청을 받는 Controller, 업무 규칙을 처리하는 Service, 데이터를 저장하고 꺼내는 Repository입니다. 각 계층이 한 가지 일만 맡으면 수정할 때 영향 범위가 작아집니다.

🎬 애니메이션: 요청이 세 계층을 지나는 길

  1. 요청은 Controller에서 시작해 Repository까지 내려갔다가 응답으로 올라옵니다.
  2. 1단계: Controller가 요청을 받아 Service에 일을 맡깁니다.
  3. 2단계: Service가 규칙을 확인하고 Repository에 저장이나 조회를 요청합니다.
  4. 3단계: 결과가 Service와 Controller를 거쳐 응답으로 돌아갑니다.

코드: 메모 앱의 세 계층 (뼈대)

package com.example.demo.controller; import org.springframework.web.bind.annotation.*; // 요청 관련 표시들을 한 번에 가져온다 @RestController // 이 클래스는 웹 요청을 받는 입구다 @RequestMapping("/memos") // 이 클래스의 모든 주소는 /memos로 시작한다 public class MemoController { private final MemoService memoService; // Service를 담아 둘 칸 public MemoController(MemoService memoService) { // 스프링이 MemoService 객체를 넣어 준다 this.memoService = memoService; } @GetMapping // GET /memos 요청이 오면 아래 메서드가 실행된다 public String list() { return memoService.findAllTitles(); // Service에 목록을 달라고 요청하고, 받은 값을 그대로 돌려준다 } }
package com.example.demo.service; import org.springframework.stereotype.Service; // 업무 로직 담당 표시 @Service // 스프링이 이 클래스의 객체를 만들어 관리한다 public class MemoService { private final MemoRepository memoRepository; // 저장소 담당 객체를 담아 둘 칸 public MemoService(MemoRepository memoRepository) {// 스프링이 MemoRepository 객체를 넣어 준다 this.memoRepository = memoRepository; } public String findAllTitles() { // 저장소에 전체 목록을 달라고 요청하고, 받은 결과를 그대로 호출한 곳으로 돌려준다 return memoRepository.findAll(); } }
package com.example.demo.repository; import org.springframework.stereotype.Repository; // 데이터 접근 담당 표시 @Repository // 스프링이 이 클래스의 객체를 만들어 관리한다 public class MemoRepository { // 실제 DB 대신 임시로 메모 목록을 문자열로 돌려준다 (학습용) public String findAll() { return "장보기, 운동 계획"; // 이 값이 Service를 거쳐 Controller로 돌아간다 } }
📌 호출 방향은 한 방향입니다Controller는 Service를 부르고, Service는 Repository를 부릅니다. 반대로 Repository가 Controller를 부르면 구조가 엉킵니다.
🧠 확인 퀴즈 5

Q. 요청을 가장 먼저 받는 계층은 무엇인가요?

A. Controller 계층입니다.

6. 패키지 설계

코드가 많아지면 패키지를 어떻게 나눌지 정해야 합니다. 대표적인 방법은 계층별과 기능별입니다. 이 책은 입문 단계에서 계층별로 시작하고, 기능이 늘면 기능별로 묶는 방법도 소개합니다.

🎬 애니메이션: 두 가지 나누기 방식

  1. 같은 코드도 나누는 기준에 따라 찾기 쉬움이 달라집니다.
  2. 1단계: 계층별로 나누면 controller 폴더에는 입구 코드만 모입니다.
  3. 2단계: 기능별로 나누면 memo 폴더 하나에 그 기능의 계층이 모두 모입니다.
방식폴더 예장점주의
계층별controller, service, repository역할이 명확함기능이 늘면 한 폴더에 섞임
기능별memo, user, article관련 코드가 한곳에 모임기능 간 연결 규칙을 정해야 함
💡 이 책의 기준1장부터 4장까지는 계층별 패키지를 씁니다. 이후 장에서 기능이 늘어날 때 그 이유를 함께 설명합니다.
🧠 확인 퀴즈 6

Q. 기능이 많아질 때 관련 코드를 한곳에 모으기 쉬운 방식은 무엇인가요?

A. 기능별 패키지 나누기입니다.

7. 의존성 방향

의존성 방향은 "누가 누구를 알고 부르는가"를 말합니다. 규칙은 간단합니다. 바깥 계층이 안쪽 계층을 부르고, 안쪽 계층은 바깥을 모르게 합니다.

🎬 애니메이션: 화살표는 한 방향만

  1. 화살표는 Controller에서 Repository로만 흐릅니다.
  2. 1단계: Controller는 Service를 호출합니다.
  3. 2단계: Service는 Repository를 호출합니다.
  4. 3단계: Repository가 Controller를 호출하는 것은 금지입니다.
🚫 거꾸로 호출하면 생기는 문제저장소가 화면 주소를 알게 되면, 화면 구조를 바꿀 때 저장소 코드까지 고쳐야 합니다. 그래서 방향을 지키는 것이 수정 비용을 줄입니다.
🧠 확인 퀴즈 7

Q. Repository가 Controller의 메서드를 호출하면 안 되는 이유는 무엇인가요?

A. 계층 사이의 의존 방향이 뒤엉켜 수정이 어려워지기 때문입니다.

8. 실행 확인과 로그

설정과 구조를 익혔으니 실행해 확인합니다. 로그를 읽는 습관은 오류를 빨리 찾는 데 큰 도움이 됩니다.

🎬 애니메이션: 실행부터 확인까지

  1. 실행 후 로그와 브라우저로 두 번 확인합니다.
  2. 1단계: 콘솔에 서버가 포트 8080에서 시작되었다는 로그가 보이는지 확인합니다.
  3. 2단계: 브라우저에서 /memos 주소를 열어 응답이 오는지 확인합니다.

로그에서 볼 줄

로그 문장뜻
Tomcat started on port 8080서버가 8080 포트에서 준비되었다
Started DemoApplication스프링 부트 시작이 끝났다
Port 8080 was already in use다른 프로그램이 8080을 쓰고 있다 (포트 충돌)
⚠️ 실행 전에 확인할 것build.gradle에 의존성을 추가했다면 Gradle 새로고침을 먼저 하세요. 새로고침을 하지 않으면 새 라이브러리를 찾지 못해 오류가 납니다.
🧠 확인 퀴즈 8

Q. 로그에 "Port 8080 was already in use"가 보이면 무엇이 문제인가요?

A. 다른 프로그램이 8080 포트를 이미 쓰고 있어 새 서버가 열리지 못하는 상황입니다.
