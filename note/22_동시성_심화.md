## 1. 경쟁 조건 (Race Condition)

**정의** — 여러 스레드가 같은 데이터를 동시에 읽고 쓸 때, 실행 순서에 따라 결과가 달라지는 상태다.

**원인** — `value++`는 한 줄처럼 보여도 실제로는 "읽기 → 더하기 → 쓰기" 세 단계다. 두 스레드가 같은 값을 읽고 각자 더하면 한 번의 증가가 사라진다.

**구현 (검증 완료): 경쟁 조건 재현과 해결**

```java
static class UnsafeCounter { int value; void inc() { value++; } }    // 보호 없음

static class SafeCounter {
    private int value;
    synchronized void inc() { value++; }                             // 한 번에 한 스레드만 실행
    synchronized int get() { return value; }
}
```

- **확인:** 두 스레드가 각각 100,000번 증가시키면 기대값은 200,000이다. 보호 없는 카운터는 실행마다 다른 값(예: 196,871, 197,501)이 나온다. `synchronized`, `AtomicInteger`, `ReentrantLock` 카운터는 항상 200,000이다.
- **주의:** 경쟁 조건은 항상 틀리지 않고, 가끔 틀린다. 그래서 테스트에 잘 안 걸린다. 재현하려면 반복 횟수를 늘리고 여러 번 돌려야 한다.

---

## 2. 해결 도구

| 도구 | 특징 | 언제 쓰나 |
|---|---|---|
| `synchronized` | 블록/메서드 단위 상호 배제. 간단하다 | 단순한 공유 상태 |
| `ReentrantLock` | 시간 제한 락, 공정성 옵션, `tryLock` 가능 | 락을 더 세밀하게 제어할 때 |
| `AtomicInteger` 같은 원자 클래스 | 락 없이 한 연산을 원자적으로 수행 (CAS) | 카운터처럼 단일 값 |
| `ConcurrentHashMap` | 맵을 여러 스레드가 안전하게 사용 | 공유 맵 |

**흔한 실수**
- 락을 잡은 채로 DB 호출이나 네트워크 호출을 해서 대기 시간이 길어진다.
- 락을 잡는 순서가 스레드마다 달라서 **교착 상태(deadlock)** 가 생긴다. 모든 스레드가 같은 순서로 락을 잡게 한다.
- `synchronized`를 붙였는데 읽기 메서드에는 빠뜨린다. 쓰기와 읽기를 함께 보호한다.

## 3. 스레드 풀

**정의** — 작업마다 스레드를 새로 만들지 않고, 미리 만들어 둔 스레드들이 작업 큐에서 일을 가져가 처리하는 구조다.

**목적과 책임** — 스레드 생성 비용을 줄이고, 동시에 실행되는 작업 수를 제한한다. 제한하지 않으면 요청이 몰릴 때 메모리와 CPU가 바닥난다.

**구현 (검증 완료)**

```java
ExecutorService pool = Executors.newFixedThreadPool(4);          // 스레드 4개
List<Future<Integer>> results = new ArrayList<>();
for (int i = 1; i <= 10; i++) {
    final int n = i;
    results.add(pool.submit(() -> n * n));                        // 작업 제출, 결과는 Future로 받음
}
int sum = 0;
for (Future<Integer> f : results) sum += f.get();                 // 결과 대기
pool.shutdown();                                                  // 새 작업을 받지 않고 끝냄
```

- **확인:** 1²부터 10²까지의 합은 385다. 스레드 4개가 10개의 작업을 나눠 처리해도 결과가 같다.
- **주의:** `Executors.newFixedThreadPool`의 큐는 제한이 없어서 메모리가 쌓일 수 있다. 운영에서는 `ThreadPoolExecutor`로 큐 크기를 제한하는 것을 검토한다.
- **Spring:** `@Async`나 웹 서버의 요청 스레드 풀도 같은 원리다. 풀 크기를 정하는 기준은 CPU 코어 수와 작업이 I/O를 기다리는 비율이다.

## 4. DB 락 (개념)

**정의** — 데이터베이스가 행이나 테이블에 거는 잠금이다. 여러 트랜잭션이 같은 행을 동시에 수정하지 못하게 막는다.

**종류**
- **공유 락(S):** 읽기용. 여러 트랜잭션이 함께 가질 수 있다.
- **배타 락(X):** 쓰기용. 다른 트랜잭션은 읽기도 쓰기도 기다려야 한다(잠금 읽기 기준).
- **낙관적 락:** 버전 번호로 충돌을 나중에 감지한다. 충돌이 적을 때 쓴다. JPA의 `@Version`이 여기에 해당한다.
- **비관적 락:** 읽을 때 바로 락을 건다. `SELECT ... FOR UPDATE`가 여기에 해당한다. 충돌이 많을 때 쓴다.

**예 (재고 차감):** 재고 1개를 두 사람이 동시에 주문하면, 락 없이 둘 다 "재고 있음"을 읽고 둘 다 차감해서 재고가 -1이 될 수 있다. `FOR UPDATE`로 읽으면 한 사람이 끝날 때까지 다른 사람은 기다린다.

**실습 (선택):** MySQL 세션 두 개에서 같은 행에 `SELECT ... FOR UPDATE`를 실행하고, 두 번째 세션이 기다리는지 확인한다.

---

## 5. 정리: 어떤 도구를 쓸까

- 같은 JVM 안의 공유 변수 → `synchronized`, 원자 클래스, `ConcurrentHashMap`
- 여러 서버에 걸친 데이터 → DB 락 또는 낙관적 락, 필요하면 분산 락(Redis 등)
- 작업을 나눠 처리 → 스레드 풀과 작업 큐

**면접 기준:** "경쟁 조건은 공유 상태를 여러 스레드가 동시에 바꿀 때 생깁니다. 같은 JVM이면 락이나 원자 연산으로, 여러 서버면 DB 락이나 낙관적 락으로 막습니다."
