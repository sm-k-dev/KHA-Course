# 설계 원칙: SOLID, UML, 기술 부채

> 중요도: **A** · 이 장의 목표: SOLID 다섯 원칙을 예제로 설명하고, 설계를 UML로 그리고, 기술 부채를 판단할 수 있다.

> 2026-11-23 추가 장 (로드맵 M10 항목). SOLID 예제는 `Batch1.java`에서 실행해 통과를 확인했다.

---

## 1. 왜 설계 원칙이 필요한가

**정의** — 설계 원칙은 코드를 바꾸기 쉽고, 테스트하기 쉽고, 이해하기 쉽게 만드는 기준이다.

**목적과 책임** — 요구사항이 바뀔 때 고칠 곳을 최소화한다. 한 곳을 고쳤는데 여러 곳이 깨지는 구조를 피한다.

**구별해야 할 개념 / 흔한 오해** — 원칙은 규칙이 아니라 판단 기준이다. 작은 프로그램에 모든 원칙을 적용하면 오히려 복잡해진다. "원칙을 지켰다"보다 "변경 이유가 한 가지인가"를 본다.

## 2. SOLID

| 원칙 | 뜻 | 한 줄 점검 |
|---|---|---|
| S: 단일 책임 | 클래스는 바꾸는 이유가 하나여야 한다 | 주문 계산과 DB 저장을 한 클래스에 두지 않았나 |
| O: 개방-폐쇄 | 확장에는 열려 있고, 수정에는 닫혀 있어야 한다 | 새 정책을 추가할 때 기존 클래스를 고치는가 |
| L: 리스코프 치환 | 하위 타입은 상위 타입 자리에 바로 들어갈 수 있어야 한다 | 상위 타입 계약을 깨는 구현이 없나 |
| I: 인터페이스 분리 | 쓰지 않는 메서드에 의존하게 하지 않는다 | 구현체가 빈 메서드를 억지로 채우지 않나 |
| D: 의존 역전 | 구체 클래스보다 추상(인터페이스)에 의존한다 | 생성자에서 구체 클래스를 `new`로 만들고 있지 않나 |

### 2-1. OCP와 DIP 예제 (검증 완료)

할인 정책이 늘어날 때 `OrderService`를 고치지 않도록 설계했다.

```java
interface DiscountPolicy { int apply(int price); }

class RateDiscount implements DiscountPolicy {          // 정률 할인
    public int apply(int p) { return p * 9 / 10; }
}

class FixedDiscount implements DiscountPolicy {         // 정액 할인 (0 미만이 되지 않음)
    public int apply(int p) { return Math.max(0, p - 1000); }
}

class OrderService {
    private final DiscountPolicy policy;                // 구체 클래스가 아니라 인터페이스에 의존 (DIP)
    OrderService(DiscountPolicy policy) { this.policy = policy; }
    int total(int price) { return policy.apply(price); }
}
```

- **확인:** `new OrderService(new RateDiscount()).total(10000)`은 9000, `new OrderService(new FixedDiscount()).total(10000)`도 9000이다. 정책 클래스를 새로 만들어도 `OrderService`는 바뀌지 않는다.
- **흔한 실수:** `OrderService` 안에 `if (type == "RATE") ... else if ...`를 쓰면 정책이 늘 때마다 이 클래스를 고쳐야 한다(OCP 위반).

### 2-2. 나머지 원칙 한 줄 예

- **SRP:** 주문 금액 계산(`OrderCalculator`)과 주문 저장(`OrderRepository`)을 나눈다. 저장 방식이 바뀌어도 계산 클래스는 그대로다.
- **LSP:** `Bird.fly()`를 상속한 `Penguin`이 예외를 던지면 LSP 위반이다. 이 경우 `Flyable` 인터페이스를 따로 둔다.
- **ISP:** `Printer` 하나에 `print`, `scan`, `fax`를 모두 넣고 간단한 프린터가 `fax`를 빈 구현으로 두면 인터페이스를 쪼갠다.

**면접 기준:** "SOLID는 변경에 강한 설계를 위한 다섯 원칙입니다. 특히 OCP와 DIP를 지키면 새 정책을 추가할 때 기존 코드를 거의 고치지 않습니다."

## 3. UML: 설계를 그림으로 말하기

**정의** — UML은 소프트웨어 구조와 동작을 표준 기호로 그리는 표기법이다.

**자주 쓰는 다이어그램**

- **유스케이스 다이어그램:** 사용자가 시스템으로 무엇을 할 수 있는지 (예: 고객이 주문한다)
- **클래스 다이어그램:** 클래스, 필드, 메서드, 관계(상속, 구현, 연관). 위 `OrderService`와 `DiscountPolicy` 관계가 여기에 해당한다.
- **시퀀스 다이어그램:** 객체들이 시간 순서대로 메시지를 주고받는 모습. API 한 개의 흐름을 설명할 때 가장 많이 쓴다.
- **ER 다이어그램:** 테이블과 관계 (데이터 모델링). 07장의 기본 키, 외래 키와 연결된다.

**구별해야 할 개념** — 개념 모델(무엇이 있나), 논리 모델(속성과 관계), 물리 모델(실제 테이블과 타입)은 서로 다르다. ER은 논리·물리 모델에 가깝고, 개념 모델은 업무 용어로 그린다.

**실습:** 기존 API 하나를 골라 시퀀스 다이어그램으로 Controller, Service, Repository, DB의 호출 순서를 그린다. 그다음 그림에서 실패 경로(예: 사용자 없음)도 추가한다.

**면접 기준:** "시퀀스 다이어그램으로 API 한 개의 호출 흐름을 그리고, 클래스 다이어그램으로 책임과 의존 관계를 설명합니다."

## 4. 기술 부채

**정의** — 빠르게 만들기 위해 나중에 고쳐야 할 설계나 코드를 남겨 둔 상태를 말한다. 이자처럼 시간이 지날수록 변경 비용이 늘어난다.

**구별해야 할 개념 / 흔한 오해** — 기술 부채는 나쁜 코드와 같지 않다. 의도적으로 빚을 지고 기록해 두는 것은 전략이 될 수 있다. 기록 없이 쌓이면 문제가 된다.

**관리 방법**
- 부채를 기록한다: 무엇을, 왜 미뤘고, 언제 갚을지
- 변경이 잦은 곳부터 갚는다
- 부채를 갚는 작업을 일정에 넣는다 (기능 개발 중 일부)

**프로젝트 적용:** SentinelOps에서 미뤄 둔 것을 목록으로 만든다. 예: 응답 DTO 분리, 예외 처리 통일, 테스트 누락 구간. 이 목록은 포트폴리오의 "개선 과정" 근거가 된다.

**면접 기준:** "기술 부채는 빠른 개발을 위해 미룬 설계 비용입니다. 기록하고 변경이 잦은 곳부터 갚습니다."
