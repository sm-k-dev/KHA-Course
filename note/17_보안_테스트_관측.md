## 1. 인증·인가·세션 보안

**정의** — 인증은 사용자가 누구인지 확인하는 과정이고 인가는 확인된 주체가 특정 자원·동작에 접근할 권한이 있는지 결정하는 과정이다.

**목적과 책임** — 보호된 기능에 허용된 주체만 접근하도록 한다.

**구별해야 할 개념 / 흔한 오해** — 로그인 성공이 모든 관리자 기능에 대한 인가를 의미하지 않는다.

**실행·처리 흐름** — 요청 → 인증 상태 확인 → 권한 검사 → 업무 처리/거부

**직접 구현·검증** — 일반 사용자가 관리자 URL에 접근했을 때 403 처리 검증. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 인증과 인가의 차이는?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

인증(Authentication)은 사용자가 누구인지 확인하고 인가(Authorization)는 해당 자원에 접근할 권한이 있는지 판단한다. 세션은 인증 상태 유지에 활용될 수 있지만 세션 식별자 보호가 필수다. 관리자 UI 숨김은 서버 권한 검사를 대체하지 않는다.

### 직접 읽고 구현하는 독립 예제

```java
if (session == null || session.getAttribute("userId") == null) {
 resp.sendError(401); return;
}
if (!"ADMIN".equals(session.getAttribute("role"))) {
 resp.sendError(403); return;
}
```

**코드 읽기 순서:** 입력·전제조건을 확인하고, 어느 객체/계층이 무엇을 담당하는지 표시한 다음, 정상 경로와 실패 경로를 각각 따라간다. 코드 조각은 문맥상 필요한 클래스·import·설정이 생략될 수 있으며, 실행 전 직접 보완한다.

### 실행 검증 체크포인트

로그인 안 된 요청과 일반 사용자 요청이 각각 401/403인지 확인한다.

### 스스로 작성할 변형 실습

세션 고정 공격을 줄이기 위해 로그인 성공 후 세션 ID를 갱신하는 이유를 설명한다.

### 면접 답변의 기준 문장

> 인증은 신원 확인이고 인가는 요청한 작업에 대한 권한 확인입니다.

**구술 확인:** 위 문장을 외우기보다, 정의와 책임을 구분해 말하고 실제 코드에서 해당 역할을 수행하는 줄을 가리켜 설명한다.


### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“인증은 사용자가 누구인지 확인하는 과정이고 인가는 확인된 주체가 특정 자원·동작에 접근할 권한이 있는지 결정하는 과정이다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“로그인 성공이 모든 관리자 기능에 대한 인가를 의미하지 않는다.”* 반례를 하나 만들어 본다.

**3차: 면접 재현.** *“인증과 인가의 차이는?”*에 대해 **정의 → 왜 필요한가 → 무엇과 다른가 → 코드·상황 하나** 순서로 30~60초 말한다. 답을 읽지 않고 말한 뒤 원문과 대조한다.

**완료 기준:** 비유 없이 정의 가능 / 혼동되는 용어 구별 가능 / 처음 보는 예제에 적용 가능. 세 조건 중 하나라도 실패하면 해당 항목만 재학습한다.
## 2. SQL 인젝션·XSS·CSRF

**정의** — SQL 인젝션은 입력이 SQL 구조로 해석되도록 만드는 공격, XSS는 신뢰하지 않는 스크립트가 웹 페이지 맥락에서 실행되는 문제, CSRF는 사용자의 인증 상태를 악용한 의도치 않은 요청을 유도하는 공격이다.

**목적과 책임** — 입력 경계·출력 인코딩·요청 위조 방어를 각각 적용한다.

**구별해야 할 개념 / 흔한 오해** — SQL 파라미터 바인딩은 XSS를 해결하지 않고, HTML 이스케이프는 SQL 인젝션을 해결하지 않는다.

**실행·처리 흐름** — 입력 수신 → 문맥별 검증·인코딩 → 권한·CSRF 검증 → 처리

**직접 구현·검증** — PreparedStatement와 HTML 출력 인코딩, CSRF 방어 점검. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 세 공격의 원인과 방어책을 구분하라.

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

SQL 인젝션은 입력이 SQL 명령 구조로 해석되는 취약점, XSS는 신뢰하지 않는 데이터가 브라우저에서 스크립트로 실행되는 취약점, CSRF는 사용자 인증 상태를 악용해 원치 않는 요청을 보내게 하는 공격이다. 방어 지점이 서로 다르다.


### 실행 검증 체크포인트

SQL 입력에 따옴표가 포함되어도 쿼리 구조가 바뀌지 않는지 확인한다.

### 스스로 작성할 변형 실습

HTML 텍스트·속성·URL·JavaScript 문맥별 출력 인코딩이 다른 이유를 설명한다.

### 면접 답변의 기준 문장

# 핵심 개념을 오해 없이 이해하기 위한 기초 연결

## 필수 기초 연결: 인증·인가·검증·예외·로그

인증(authentication)은 “누구인가”, 인가(authorization)는 “이 작업을 해도 되는가”를 판단한다. 입력 검증(validation)은 입력 형식·제약을 확인하는 것이고 SQL 인젝션 방어의 핵심은 사용자 입력을 SQL 문자열에 직접 연결하지 않고 **파라미터 바인딩**을 사용하는 것이다. 인증에 성공한 사용자라도 다른 사용자의 데이터에 접근할 권한은 없을 수 있다.

```java
// PreparedStatement: 사용자 입력을 SQL 코드가 아닌 파라미터로 전달
PreparedStatement ps = connection.prepareStatement("SELECT id FROM users WHERE email = ?");
ps.setString(1, email);
```

**관측:** HTTP 404와 500은 서로 다르다. 조회 결과 0행을 무조건 서버 장애(500)로 기록하면 오류 통계가 왜곡된다. 반대로 예상치 못한 DB 연결 실패를 404로 감추면 장애 원인 분석이 어려워진다. 로그에는 비밀번호·토큰·개인정보를 직접 기록하지 않는다.

**실습:** 존재하지 않는 ID(404), 인증되지 않은 요청(401), 권한 없는 요청(403), DB 연결 장애(500 또는 503 등 정책에 따른 5xx)를 구분해 테스트한다. 인증되지 않은 요청의 상태 코드는 실제 보안 구성에 따라 리다이렉트 등으로 달라질 수 있다.

## 개념 경계 정밀 보강 — 실제 코드에서 헷갈리는 지점

> 이 절은 기존 핵심 설명에 추가한 필수 기초 연결 학습이다. 아래 예제는 설명용 최소 코드로, SQL은 예시 테이블이 필요하고 Java는 import/클래스·실행 환경이 필요할 수 있다.


### 경계 1. 인증 / 인가 / 세션

**흔한 오해:** “로그인만 되면 모든 관리자 API에 접근해도 된다”

**정확한 구분:** 인증은 사용자가 누구인지 확인하고 인가는 특정 작업을 수행할 권한이 있는지 검사한다. 세션은 인증 상태를 유지하는 한 방식이다.

**코드·명령 해석:**

```text
GET /admin/users → 인증 확인 → ADMIN 권한 검사
```

**확인 방법:** 일반 사용자와 관리자 계정으로 같은 URL을 요청해 401/403 정책을 확인한다.

**직접 구현:** 로그인하지 않은 사용자와 권한 없는 사용자를 구분해 응답 설계하라.

**면접 점검:** “인증 / 인가 / 세션”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 2. 단위 테스트 / 통합 테스트 / E2E

**흔한 오해:** “Mock을 쓰면 항상 통합 테스트다”

**정확한 구분:** 단위 테스트는 작은 동작 단위를 격리해 확인한다. 통합 테스트는 실제 구성 요소의 협력을 검증한다. E2E는 외부 인터페이스부터 전체 흐름을 확인한다. Mock은 격리 수단이지 테스트 종류를 자동 결정하지 않는다.

**코드·명령 해석:**

```text
// 단위: Service + 가짜 Repository
// 통합: 실제 DB + Repository
// E2E: HTTP 요청 → DB 변경 확인
```

**확인 방법:** 각 테스트가 발견할 수 있는 결함과 놓치는 결함을 구분한다.

**직접 구현:** 같은 회원 가입 기능에 단위·통합 테스트를 각각 설계하라.

**면접 점검:** “단위 테스트 / 통합 테스트 / E2E”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 3. 로그 / 메트릭 / 트레이스 / 예외

**흔한 오해:** “로그를 남기면 모든 장애 원인을 알 수 있다”

**정확한 구분:** 로그는 개별 사건 기록, 메트릭은 수치의 시간 추세, 트레이스는 분산 요청의 호출 경로다. 예외는 프로그램의 오류 신호이며 기록과 대응은 별도 정책이다.

**코드·명령 해석:**

```text
log.error("order failed orderId={}", id, exception);
```

**확인 방법:** 개인정보와 비밀값이 로그에 노출되지 않는지 확인한다.

**직접 구현:** 500 오류율 메트릭과 요청 추적 ID를 함께 설계하라.

**면접 점검:** “로그 / 메트릭 / 트레이스 / 예외”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.

### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“로그는 사건 기록, 메트릭은 시간에 따른 수치 측정, 트레이스는 요청이 여러 처리 단계를 거치는 경로를 연결해 관찰하는 데이터다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“로그를 많이 남기는 것과 관측성이 높은 것은 다르다. 개인정보·토큰 로그는 위험하다.”* 반례를 하나 만들어 본다.

**3차: 면접 재현.** *“로그·메트릭·트레이스는 어떻게 다른가?”*에 대해 **정의 → 왜 필요한가 → 무엇과 다른가 → 코드·상황 하나** 순서로 30~60초 말한다. 답을 읽지 않고 말한 뒤 원문과 대조한다.

**완료 기준:** 비유 없이 정의 가능 / 혼동되는 용어 구별 가능 / 처음 보는 예제에 적용 가능. 세 조건 중 하나라도 실패하면 해당 항목만 재학습한다.
