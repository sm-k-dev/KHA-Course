1. 결론 요약

페이징 자체는 동작합니다. 문제는 "부모 엔티티를 페이징하면서, 같은 쿼리에서 1:N 자식 컬렉션을 join fetch 로 함께 가져올 때"입니다. 이 조합에서는 SQL 의 LIMIT 이 부모 개수가 아니라 행(row) 개수에 적용되어 결과가 틀어집니다. Hibernate 는 이를 막기 위해 LIMIT 없이 전체를 읽은 뒤 메모리에서 자르고, 경고 로그를 남깁니다.

해결의 핵심은 부모는 fetch join 없이 페이징하고, 자식은 필요할 때 IN 조건으로 한꺼번에 조회하는 것입니다.

이 문서에서 쓰는 용어의 한 줄 정의 "1:N" = 부모 1건이 자식 여러 건을 가지는 관계 (예: 회원 1명 → 주문 여러 건)

용어프로그래밍 관점의 정의이 문서에서의 역할
JPA자바 객체(클래스)와 관계형 DB 테이블 사이를 SQL 없이 연결하는 표준 명세Member 객체를 member 테이블 행과 연결
HibernateJPA 명세를 구현한 실제 라이브러리 (Spring Boot 기본 구현체)SQL 생성, 경고 로그 출력, 자식 조회 실행
Entity(엔티티)@Entity 가 붙어 DB 테이블과 1:1 로 대응되는 클래스Member, Order
Spring Data JPARepository 인터페이스만 선언하면 구현 객체를 자동 생성해 주는 Spring 모듈MemberRepository 구현, Page 반환
영속성 컨텍스트 (PersistenceContext)트랜잭션 동안 엔티티를 보관하는 Hibernate 내부 저장소(1차 캐시)조회된 Member/Order 객체를 보관
지연 로딩 (Lazy Loading)연관 데이터를 "실제로 접근하는 순간" 조회하는 방식member.getOrders() 를 처음 호출할 때 SQL 실행
즉시 로딩 (Eager Loading)부모를 조회할 때 연관 데이터도 바로 조회하는 방식기본값과 비교용으로만 언급
fetch joinJPQL 에서 join fetch 를 써서 연관 엔티티를 한 번의 SQL JOIN 으로 함께 가져오는 방식문제의 원인이 되는 조회 방식
Pageable / PagePageable 은 "몇 페이지, 몇 건, 어떤 정렬"을 담은 요청 객체, Page 는 결과 목록과 전체 건수 정보를 담은 응답 객체페이징 요청/응답 타입
LIMIT / OFFSETSQL 에서 결과 행을 "몇 개 건너뛰고 몇 개를 가져올지" 지정하는 절실제 페이징이 실행되는 위치
@BatchSize지연 로딩 컬렉션을 여러 건씩 묶어 IN (...) 쿼리로 조회하게 하는 Hibernate 어노테이션해결 방법 1 의 핵심
DTO화면 전달 전용으로 만든 단순 데이터 객체 (엔티티가 아님)해결 방법 3

3. 예제 엔티티 (1:N 구조)

부모 엔티티는 Member, 자식 엔티티는 Order 입니다. 외래키(FK, orders.member_id)는 자식 테이블인 orders 에 있습니다. 따라서 연관관계의 주인(외래키를 실제로 관리하는 쪽)은 Order.member 입니다.

Java · Member.java (부모) 
@Entity                                   // Hibernate 가 이 클래스를 DB 테이블과 연결된 엔티티로 관리
@Table(name = "member")                   // 연결할 실제 테이블 이름은 member
public class Member {

    @Id                                   // 이 필드가 기본키(PK)임을 표시
    @GeneratedValue(strategy = GenerationType.IDENTITY)
                                          // 값 생성은 DB 의 AUTO_INCREMENT 에 맡김 (INSERT 시 DB 가 번호 부여)
    private Long id;                      // member.id 컬럼과 대응

    private String name;                  // member.name 컬럼과 대응

    // 1:N 연관관계. 이 필드는 DB 컬럼이 아님 (테이블에 orders 컬럼은 없음)
    @OneToMany(mappedBy = "member")       // 외래키를 가진 쪽은 Order.member 필드. 거기서 관계를 관리하겠다는 뜻
    private List orders = new ArrayList<>();
                                          // 기본 fetch 전략은 LAZY 이므로, 이 필드는 처음 접근할 때까지 SQL 이 나가지 않음

    public List getOrders() { return orders; }
    public String getName() { return name; }
}
Java · Order.java (자식) 
@Entity
@Table(name = "orders")                   // "order" 는 SQL 예약어라 충돌을 피하기 위해 orders 사용
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;                      // orders.id 컬럼

    private int amount;                   // orders.amount 컬럼 (주문 금액)

    @ManyToOne(fetch = FetchType.LAZY)    // N:1 관계. 여러 주문이 한 회원을 가리킴
                                          // LAZY: Member 를 실제로 쓰는 순간에만 member 테이블을 조회
    @JoinColumn(name = "member_id")       // orders 테이블의 member_id 컬럼이 외래키 (member.id 를 참조)
    private Member member;
}

4. 문제 상황 재현

회원 목록을 페이지 단위(2명씩)로 가져오면서, 각 회원의 주문도 함께 가져오려고 아래처럼 작성했다고 가정합니다.

Java · MemberRepository.java (문제 코드) 
public interface MemberRepository extends JpaRepository<Member, Long> {

    // ❌ 문제 코드: 컬렉션 fetch join + 페이징을 한 쿼리에서 같이 사용
    @Query("select m from Member m join fetch m.orders")
    Page findAllWithOrders(Pageable pageable);
    // 1) join fetch m.orders : Member 와 Order 를 SQL JOIN 으로 함께 조회
    // 2) Pageable            : 페이지 번호(0), 페이지 크기(2) 를 담은 요청 객체
    // 3) Page 반환    : 결과 목록 + 전체 건수 정보를 담은 응답 객체
}

서비스 호출 흐름은 다음과 같습니다.

순서호출 위치하는 일
1MemberController요청 파라미터 page, size 를 받아 PageRequest.of(page, size) 로 Pageable 생성
2MemberServicePageable 을 그대로 MemberRepository 메서드에 전달
3MemberRepository (Spring Data 가 만든 구현 객체)JPQL 문자열을 EntityManager 의 createQuery() 로 넘기고, Pageable 의 페이지 정보를 쿼리 힌트로 전달
4HibernateJPQL 을 SQL 로 변환하고 DB 에 실행
5MemberController반환된 Page 객체에서 회원 목록을 꺼내 화면(View)에 전달

5. 왜 페이징이 깨지는가 (SQL 수준 설명)

5-1. fetch join 이 만드는 SQL

SQL (Hibernate 가 생성하는 형태, 단순화) 
SELECT m.id, m.name,
       o.id, o.amount, o.member_id
  FROM member m
  INNER JOIN orders o ON o.member_id = m.id   -- 회원과 주문을 외래키로 연결
 LIMIT 2;                                     -- 여기서 LIMIT 은 "행(row)" 2개에 적용됨

5-2. JOIN 결과 행이 늘어나는 모습

1:N 을 JOIN 하면 결과 행 수는 회원 수가 아니라 주문 수만큼 생깁니다.

행 번호m.idm.nameo.ido.amount
11김철수10110000
21김철수10225000
31김철수1037000
42이영희20112000
52이영희2025000

회원은 2명인데 JOIN 결과는 5행입니다. 여기서 LIMIT 2 를 적용하면 어떻게 될까요?

LIMIT 2 를 적용한 결과 (잘못된 결과) 행 1, 2 만 남습니다. 두 행 모두 김철수(id=1) 이므로, 페이지 1 에는 회원이 1명만 나오고 이영희는 빠집니다. 페이지 크기를 2명으로 요청했지만 실제로는 행 2개가 잘린 것이라 의도와 다릅니다.

5-3. 페이지 번호가 틀어지는 이유

LIMIT/OFFSET 은 "행" 기준으로 동작하기 때문에, 회원 기준의 페이지 경계가 주문 개수에 따라 달라집니다. 예를 들어 김철수의 주문이 3건, 이영희가 2건이면 "회원 2명씩"과 "행 2개씩"은 서로 맞지 않습니다. 결과적으로 같은 회원이 여러 페이지에 걸쳐 나오거나, 아예 누락되는 현상이 생깁니다.

5-4. Page 의 전체 건수(count) 쿼리도 꼬입니다

Page 를 만들려면 전체 건수가 필요하므로 Spring Data JPA 는 별도의 count 쿼리를 실행합니다. fetch join 쿼리에서 자동 생성된 count 쿼리는 행 수를 세거나 중복 회원을 세는 방식이 되기 쉬워, totalElements 값도 실제 회원 수와 달라질 수 있습니다.

6. Hibernate 가 보내는 경고의 의미

Hibernate 는 위 상황을 감지하면 LIMIT 을 SQL 에서 제거하고 전체 행을 읽은 뒤, 메모리에서 잘라냅니다. 이때 콘솔에 다음과 같은 경고가 찍힙니다.

콘솔 로그 (경고) 
WARN ... HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory!
의미 "컬렉션 fetch join 에 페이징 값(firstResult, maxResults)을 같이 지정했으므로, DB 에서 자르지 않고 애플리케이션 메모리에서 자르겠다"는 뜻입니다. 데이터가 많으면 모든 회원과 모든 주문을 메모리에 올리므로 성능과 메모리 사용량에 큰 문제가 생깁니다. 이 경고가 보이면 반드시 구조를 바꿔야 합니다.

7. 해결 방법 1: 부모만 페이징 + 자식 IN 조회 (권장)

핵심 아이디어: 부모 쿼리에는 join fetch 를 넣지 않아 LIMIT 이 정상 동작하게 합니다. 자식(orders)은 실제로 getOrders() 를 호출하는 시점에 로딩되는데, @BatchSize 를 붙이면 여러 회원의 주문을 IN (?, ?, ...) 한 번으로 묶어 가져옵니다.

7-1. Repository: fetch join 없는 일반 페이징 메서드

Java · MemberRepository.java (수정 코드) 
public interface MemberRepository extends JpaRepository<Member, Long> {

    // ✅ 수정 코드: 부모(Member)만 조회. join fetch 가 없으므로 LIMIT 이 회원 수 기준으로 정상 적용됨
    // 메서드 이름 findAll(Pageable) 은 Spring Data JPA 가 제공하는 기본 메서드이므로 별도 구현이 필요 없음
    // 내부적으로 SimpleJpaRepository.findAll(Pageable) 이 실행됨
    Page findAll(Pageable pageable);
}

7-2. Entity: 자식 컬렉션에 @BatchSize 추가

Java · Member.java (수정 부분만 표시) 
@Entity
@Table(name = "member")
public class Member {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @BatchSize(size = 100)                // ★ 추가: 지연 로딩 시 최대 100명분의 주문을 한 번의 IN 쿼리로 가져옴
    @OneToMany(mappedBy = "member")       // 기존 설정 그대로 (기본 LAZY)
    private List orders = new ArrayList<>();
}

7-3. Service: 부모 페이징 후 자식은 접근할 때 로딩

Java · MemberService.java 
@Service
public class MemberService {

    private final MemberRepository memberRepository;  // 생성자 주입으로 받은 Repository 객체

    public MemberService(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;     // 주입된 객체를 필드에 보관
    }

    @Transactional(readOnly = true)   // 트랜잭션 안에서 지연 로딩이 가능해야 하므로 필수
                                      // readOnly = true: 변경 감지를 끄고 조회 성능을 높임
    public Page findMembers(Pageable pageable) {
        Page page = memberRepository.findAll(pageable);
        // 이 시점 SQL 1: 회원 목록 LIMIT 쿼리 실행 (주문은 아직 조회 안 함)
        // 이 시점 SQL 2: 전체 건수 count 쿼리 실행

        for (Member member : page.getContent()) {
            member.getOrders().size();
            // getOrders() 를 처음 호출하는 순간 Hibernate 가 orders 를 조회해야 함
            // @BatchSize 덕분에 같은 페이지의 회원들 주문을 IN 쿼리 한 번으로 가져옴
        }
        return page;   // Controller 로 반환
    }
}

7-4. 실제로 실행되는 SQL 순서

SQL 로그 (예시) 
-- ① 부모 페이징 쿼리 (fetch join 없음 → LIMIT 정상 적용)
select m.id, m.name from member m limit 0, 2;

-- ② 전체 건수 쿼리
select count(m.id) from member m;

-- ③ 자식 조회: 위에서 가져온 회원 2명의 주문을 IN 으로 한 번에 조회
select o.member_id, o.id, o.amount from orders o where o.member_id in (1, 2);
정리 ① 은 회원 2명만 정확히 가져옵니다. ③ 은 SQL 이 2번이 아니라 1번으로 끝나므로 N+1 문제도 피합니다. 화면 결과는 김철수(주문 3건), 이영희(주문 2건)로 정확해집니다.
대안 설정 (전역 적용) 매번 @BatchSize 를 붙이기 번거롭다면 application.yml 에 아래를 설정하면 모든 지연 로딩 컬렉션에 같은 효과가 적용됩니다. 
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100

8. 해결 방법 2: 2단계 조회

핵심 아이디어: 1단계에서는 부모 id 만 페이징 조회하고, 2단계에서 그 id 목록으로 연관 데이터를 fetch join 해서 가져옵니다. 1단계는 행이 늘어나지 않으므로 LIMIT 이 정확합니다.

Java · MemberRepository.java 
public interface MemberRepository extends JpaRepository<Member, Long> {

    // 1단계: 회원 id 만 페이징 조회 (select 대상이 Member 엔티티가 아닌 id 값이므로 행 증식이 없음)
    @Query("select m.id from Member m order by m.id")
    Page findMemberIds(Pageable pageable);
    // countQuery 는 Spring Data 가 "select count(m.id) from Member m order by m.id" 형태로 자동 생성

    // 2단계: 1단계에서 얻은 id 목록에 해당하는 회원과 주문을 한 번에 조회
    // distinct: 같은 회원이 자식 행 수만큼 중복 반환되는 것을 제거
    @Query("select distinct m from Member m left join fetch m.orders where m.id in :ids")
    List findWithOrdersByIds(@Param("ids") List ids);
    // @Param("ids"): 메서드 인자 ids 를 JPQL 의 :ids 자리에 바인딩
}
Java · MemberService.java (호출부) 
@Transactional(readOnly = true)
public List findMembersWithOrders(Pageable pageable) {
    List ids = memberRepository.findMemberIds(pageable).getContent();
    // 1단계 결과 id 목록을 꺼냄 (예: [1, 2])

    if (ids.isEmpty()) {
        return List.of();   // id 가 없으면 2단계 쿼리 자체를 건너뜀 (IN () 은 SQL 오류)
    }

    List members = memberRepository.findWithOrdersByIds(ids);
    // 2단계 결과는 DB 가 돌려준 순서를 따르지 않으므로, 정렬이 필요하면 ids 순서대로 다시 정렬해야 함
    return members;
}
주의 2단계의 where ... in 결과 순서는 보장되지 않습니다. 목록 순서가 중요하다면 애플리케이션에서 1단계 id 순서대로 다시 정렬하세요. 또한 distinct 를 빼먹으면 회원이 주문 수만큼 중복되어 보입니다.

9. 해결 방법 3: DTO 로 필요한 값만 조회

핵심 아이디어: 화면에 필요한 값만 DTO 로 받으면 엔티티 컬렉션을 아예 들고 오지 않습니다. 단, 주문 목록을 회원 안에 배열로 묶어 보여주는 구조라면 DTO 에서도 "행 단위 결과를 회원별로 합치는" 코드가 추가로 필요합니다.

Java · MemberOrderDto.java 
public record MemberOrderDto(
        Long memberId,     // 회원 id
        String name,       // 회원 이름
        Long orderId,      // 주문 id (주문이 없으면 null)
        int amount         // 주문 금액 (주문이 없으면 0)
) {}
// record: 생성자, getter, equals 등을 자동 생성하는 Java 문법 (데이터 전달용 객체를 간결하게 작성)
Java · MemberRepository.java 
// DTO 를 바로 생성하는 JPQL: new 패키지경로.클래스명(...) 형태
// 엔티티가 아니므로 영속성 컨텍스트에 올라가지 않고, 필요한 컬럼만 SELECT 함
@Query("""
       select new com.example.dto.MemberOrderDto(m.id, m.name, o.id, o.amount)
         from Member m
         left join m.orders o
       """)

언제 쓰나 "주문 한 줄당 회원명과 금액을 표로 보여주기"처럼 행 단위 목록 화면에는 매우 적합합니다. "회원 1명 아래에 주문 목록을 접어서 보여주기"처럼 부모 기준 계층 화면에는 방법 1 이 더 자연스럽습니다.

10. 해결 방법 4: 자식 쪽에서 페이징

회원 한 명의 주문이 수천 건처럼 많다면, 컬렉션(member.getOrders())으로 가져오는 대신 주문 Repository 에서 직접 페이징하는 것이 가장 안전합니다. 엔티티 컬렉션 자체는 페이징할 수 없다는 점을 받아들이고, 자식 테이블을 독립적으로 조회하는 방식입니다.

Java · OrderRepository.java 
public interface OrderRepository extends JpaRepository<Order, Long> {

    // 특정 회원의 주문만 페이징 조회
    // 메서드 이름 규칙: findBy + 필드명(member.id) → where o.member.id = ? 로 자동 변환
    // Pageable 이 LIMIT / OFFSET 과 ORDER BY 를 자동 적용
    Page findByMemberId(Long memberId, Pageable pageable);
}

11. 추가 주의사항

항목설명대응
컬렉션 fetch join 2개 이상자식 컬렉션을 두 개 이상 fetch join 하면 행이 곱으로 늘어나고(카테시안 곱), 경고 및 중복 문제가 더 심해짐자식 컬렉션 하나만 fetch join 하거나, 나머지는 @BatchSize 사용
Sort 에 자식 필드 사용Pageable 의 정렬 조건에 orders.amount 같은 자식 필드를 넣으면 부모 기준 정렬이 깨짐부모 필드로만 정렬하거나 자식 Repository 에서 조회
@ManyToOne fetch joinN:1(예: Order → Member) 쪽은 행이 늘어나지 않으므로 fetch join 과 페이징을 함께 써도 LIMIT 이 정상 적용됨그대로 사용 가능
트랜잭션 밖 지연 로딩Service 밖에서 getOrders() 를 호출하면 영속성 컨텍스트가 닫혀 있어 LazyInitializationException 이 발생@Transactional 범위 안에서 접근하거나 DTO 로 변환해서 반환
Entity 를 JSON 으로 직접 반환양방향 연관관계에서 순환 참조가 생기고, 지연 로딩 컬렉션이 예상치 못하게 조회됨화면용 DTO 로 변환해서 반환

12. 방법 선택 체크리스트

상황추천 방법
회원 목록(부모) 을 페이징하고, 각 회원의 주문도 접어서 보여줌✅ 방법 1 (부모 페이징 + @BatchSize)
부모 id 와 자식을 정확히 통제하고 싶음, 쿼리를 명시적으로 보고 싶음✅ 방법 2 (2단계 조회)
주문 한 줄당 회원명·금액 등 평평한(flat) 목록 화면✅ 방법 3 (DTO)
회원 한 명의 주문이 매우 많아서 주문 목록을 따로 페이징해야 함✅ 방법 4 (자식 Repository 페이징)
fetch join + Pageable + 컬렉션 조합❌ 사용 금지 (HHH90003004 경고 발생)
실무 기본 원칙 1) 엔티티 연관관계는 기본적으로 LAZY 로 둔다. 2) 컬렉션은 fetch join 하지 않는다. 3) 페이징이 필요한 목록은 부모만 조회한다. 4) 자식 데이터는 @BatchSize 또는 별도 Repository 로 가져온다.
