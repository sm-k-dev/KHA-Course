## 2. 안전한 코딩 체크리스트 (여러 장을 묶은 것)

코드를 쓸 때 아래 항목을 본다. 각 항목 옆의 장에서 자세한 방법을 찾는다.

- [ ] **입력을 구조로 해석하지 않는다**: SQL은 `PreparedStatement`, 명령어는 인자 배열로 넘긴다(30장).
- [ ] **출력은 맥락에 맞게 인코딩한다**: HTML은 `th:text`, JavaScript는 `th:inline`처럼 맥락별 방법을 쓴다(24장, 99장).
- [ ] **로그인 사용자와 데이터의 주인을 비교한다**: 주소의 번호만 믿지 않는다(31장 3절, 99장).
- [ ] **외부에서 받은 값은 검증한다**: 형식, 길이, 허용 목록을 확인한다(22장, 57장).
- [ ] **비밀 정보는 코드와 저장소 밖에 둔다**: 환경 변수나 비밀 저장소를 쓴다(23장, 46장).
- [ ] **외부 호출에는 시간 제한과 허용 목록을 둔다**: SSRF를 막는다(57장, 99장).
- [ ] **권한은 필요한 만큼만 준다**: IAM 역할, 버킷 정책, DB 계정을 최소로 한다(43장, 44장).
- [ ] **오류 메시지에 내부 정보를 싣지 않는다**: 스택 트레이스는 서버 로그에만 남긴다(23장, 30장).
- [ ] **중복과 경쟁 상태를 DB에서 막는다**: 잔액과 쿠폰은 조건부 UPDATE, 중복은 유니크 제약(33장, 07장).
- [ ] **AI가 만든 결과와 코드도 검증한다**: 출력은 DB나 목록과 대조하고, 결함은 측정으로 확인한다(53장, 99장).

## 2-1. 보안 아키텍처: 방어 계층과 신뢰 경계 (정의)

**정의** — 보안 아키텍처는 시스템을 어떤 구획으로 나누고, 구획 사이의 신뢰 경계에 어떤 통제를 둘지 정하는 설계다. 하나의 방어가 뚫려도 다음 방어가 막도록 여러 계층에 나눠 두는 것(심층 방어, defense in depth)이 핵심이다.

**원칙**
- **심층 방어:** 네트워크(방화벽, 보안 그룹), 애플리케이션(인증, 입력 검증), 데이터(암호화, 접근 권한) 각각에 통제를 둔다.
- **최소 권한:** 사용자, 서비스, Agent에게 필요한 권한만 준다. 기본값은 거부다.
- **신뢰 경계 표시:** 인터넷과 내부망, 웹 서버와 DB, 모델과 도구 사이처럼 데이터가 권한 수준을 바꾸는 지점을 그림에 표시한다. 여기서 검증과 인가를 한다.
- **실패 시 안전:** 통제가 실패하면 열리지 않고 닫히도록 설계한다.

**구별:** 시큐어 코딩(102장)은 코드 한 줄의 실수를 막는 일이고, 보안 아키텍처는 구조에서 위험을 줄이는 일이다. 둘 다 필요하다.

**이 장과의 연결:** 신뢰 경계를 찾는 절차는 57장 4-1절(위협 모델링)과 같다. 접근 제어 세부는 31장, 네트워크 통제는 49장 11절에 있다.

**상태:** 정의와 원칙만 추가했다. 실제 시스템에 적용한 구조도는 아직 없다(미실행).

**면접 기준:** "보안 아키텍처는 신뢰 경계마다 통제를 두는 심층 방어와 최소 권한으로 설계합니다. 한 계층이 뚫려도 다음 계층이 막게 합니다."

## 3. 아직 부족한 부분

- **전용 시큐어 코딩 장이 없다.** 위 체크리스트는 여러 장의 내용을 묶은 것이다. 의존성 취약점 점검(예: 취약 라이브러리 검색 도구)과 보안 헤더(CSP 등)는 언급만 있고 실습이 없다.
- **Spring Security 설정은 실행 확인이 없다.** 31장의 설정 예는 Spring Security 의존성이 없는 환경에서 실행하지 않았다.
- **AWS와 네트워크 장비 설정은 실행하지 않았다.** 44장과 49장은 개념과 원칙 중심이다.

**면접 기준**: "보안은 입력, 출력, 권한, 비밀 정보, 외부 호출, 배포 권한의 여섯 경계에서 확인합니다. 각 경계마다 막는 방법과 확인 방법을 함께 말합니다."
