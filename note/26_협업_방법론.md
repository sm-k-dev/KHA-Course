## 1. 애자일과 Scrum

**정의** — 애자일은 계획을 길게 세우기보다 짧은 주기로 만들고 확인하며 바꾸는 개발 방식이다. Scrum은 애자일을 실행하는 대표적인 틀이다.

**Scrum의 기본 구성**
- **스프린트:** 보통 1~4주 단위의 개발 주기. 주기 안에서 정한 목표를 만든다.
- **제품 백로그:** 해야 할 일의 우선순위 목록. 제품 책임자가 관리한다.
- **스프린트 백로그:** 이번 스프린트에서 할 일.
- **데일리 스크럼:** 매일 짧게 어제 한 일, 오늘 할 일, 막힌 것을 공유한다.
- **스프린트 리뷰와 회고:** 결과를 보여 주고, 과정을 어떻게 개선할지 이야기한다.

**Kanban** — 할 일을 "대기 → 진행 중 → 완료" 같은 열(컬럼)에 올려 흐름을 본다. 진행 중인 일의 수를 제한(WIP 제한)해서 한 번에 너무 많은 일을 하지 않게 한다.

**구별:** Scrum은 주기와 역할이 정해져 있고, Kanban은 흐름 중심으로 유연하다.

---

## 2. Jira, Confluence, Slack

- **Jira:** 일감(이슈)을 만들고, 담당자를 정하고, 상태를 옮기고, 스프린트를 관리한다. 일감에는 목표, 완료 조건, 관련 PR을 적는다.
- **Confluence:** 설계 문서, 회의록, 결정 기록을 쌓는 문서 도구다. 나중에 "왜 이렇게 했는지"를 찾을 수 있게 한다.
- **Slack:** 빠른 대화와 알림. 중요한 결정은 Slack에만 두지 말고 Confluence나 Jira에 남긴다.

**일감 작성 기준:** 제목은 결과로 쓴다(예: "로그인 실패 시 401 응답"). 완료 조건을 두세 개로 적는다. 크기가 너무 크면 나눈다.

## 3. 코드 리뷰

**정의** — 병합 전에 다른 사람이 변경 내용을 읽고 질문하거나 개선점을 말하는 과정이다. 버그를 줄이고, 지식을 나누고, 설계를 맞춘다.

**리뷰어가 볼 것**
- 동작이 요구사항과 맞는가
- 예외와 경계 조건을 다뤘는가
- 이름과 구조가 읽기 쉬운가
- 테스트가 실제로 검증하는가
- 보안(권한 검사, 입력 검증, 비밀 정보) 문제가 없는가

**작성자가 할 것**
- PR 설명에 목적, 변경 범위, 확인 방법을 적는다.
- 리뷰 의견에 "왜 그렇게 했는지"로 답한다. 고칠 때는 같은 브랜치에 커밋해서 PR에 반영한다.

**예의:** 사람이 아니라 코드를 평가한다. 질문형으로 말한다("이 경우는 null이 될 수 있나요?").

---

## 4. 실습 과제

1. 최근 작업 하나를 Jira 일감 형식으로 적는다(제목, 완료 조건 세 개, 관련 PR).
2. 동료 코드(또는 이 저장소의 예제)를 리뷰하는 체크리스트로 세 가지 이상 의견을 적는다.
