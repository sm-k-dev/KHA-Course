## 1. 포트폴리오가 답해야 할 질문

면접관은 다음 질문에 답을 찾으려 한다.

1. 이 사람이 **무엇을 직접 만들었는가?**
2. 그 선택에 **이유가 있는가?**
3. 실제로 **돌아가는가, 측정했는가?**
4. 문제가 생겼을 때 **어떻게 고쳤는가?**

포트폴리오는 이 네 질문에 링크와 숫자로 답하는 문서 묶음이다. 화려한 기능 목록보다 이 질문에 답하는 것이 중요하다.

## 2. 기여 구분 표 (NEXORA, SentinelOps 기준)

목표 문서에 따르면 두 프로젝트는 **기존 구현과 신규 개발, 개인 기여와 팀 기여를 분리**해서 써야 한다.

| 구분 | 내용 | 근거 (커밋, PR, 문서) |
|---|---|---|
| 기존 구현 (이전 과정에서 만든 것) | 어떤 기능을 이미 만들었는가 | 해당 커밋 범위 |
| 신규 개발 (이번 기간에 추가) | 무엇을 새로 만들었는가 | 커밋 해시, PR 번호 |
| 개인 기여 | 내가 설계하고 구현한 부분 | 내 커밋, 내가 쓴 문서 |
| 팀 기여 | 같이 한 부분과 내 역할 | 리뷰, 회의록, 역할 표 |

**규칙**: 근거가 없는 항목은 쓰지 않는다. 팀 프로젝트는 다른 사람 커밋을 내 성과처럼 쓰지 않는다. 면접에서 "이 부분은 제가 설계했고, 저 부분은 팀원이 구현했습니다"라고 말할 수 있어야 한다.

**커밋으로 확인하는 법**: `git log --author="본인 이름" --oneline`으로 본인 커밋을 먼저 본다. 기간을 나눠 기존과 신규를 구분할 때는 `--since`와 `--until`을 쓴다.

## 3. README 구조

포트폴리오 저장소의 README는 면접관이 가장 먼저 읽는 문서다.

| 항목 | 내용 | 예 |
|---|---|---|
| 한 줄 소개 | 무엇을 하는 시스템인가 | "사내 문의를 분류하고 답변 초안을 만드는 API" |
| 주요 기능 | 3~5개, 사용자 관점 | 로그인, 문의 등록, 자동 분류 |
| 기술 스택과 선택 이유 | 기술마다 이유 한 줄 | Spring Boot 4: 기존 팀 표준, JPA: CRUD 중심 |
| 아키텍처 | 그림 한 장 | 클라이언트, API, DB, 외부 LLM |
| 실행 방법 | 명령 세 줄 이내 | `docker compose up` |
| 테스트 | 무엇을 어떻게 검증했나 | 단위 테스트 수, Testcontainers 사용 |
| 측정 결과 | 숫자 | p95 응답 시간, 실패율 (측정 환경 명시) |
| 결정 기록 | ADR 링크 | 39장 ADR 템플릿 |
| 한계와 다음 계획 | 솔직하게 | "캐시 무효화는 키 단위만 지원" |

**주의**: 비밀 값(키, 비밀번호)은 README에 넣지 않는다. 예시는 `.env.example`로 대체한다(23장).

## 4. 블로그 글 쓰기

블로그는 **결정과 실패**를 쓰는 곳이다. 기능 설명서가 아니다.

**글 구조 (기술 글)**

1. 문제: 무엇이 불편했고 어떤 증상이 있었는가
2. 시도한 방법과 결과: 처음 선택과 측정값
3. 원인: 왜 그랬는지 (추측이 아니라 확인한 내용)
4. 해결: 무엇을 바꿨고 결과가 어땠는가
5. 남은 문제: 아직 해결하지 못한 것

**예 제목**: "목록 API p95가 800ms에서 220ms로: 인덱스 하나보다 N+1이 먼저였다." 제목에 측정 결과를 넣으면 글의 가치가 드러난다.

**블로그 체크리스트**
- [ ] 측정 환경(버전, 데이터 양)을 적었다
- [ ] 코드는 재현 가능한 최소 예제로 줄였다
- [ ] 실패한 시도도 적었다
- [ ] 다른 사람이 따라 할 때 막히는 지점을 적었다
