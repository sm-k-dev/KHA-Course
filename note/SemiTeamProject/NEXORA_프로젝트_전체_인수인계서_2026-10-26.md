## 1. 프로젝트 한눈에 보기

**NEXORA**는 기업용 보안 서비스 사이트를 가정한 Java 웹 프로젝트입니다. 회원·커뮤니티·문의 기능과 함께, 애플리케이션 장애 및 웹·AI 입력의 의심 징후를 기록하고 관리자가 확인하도록 돕는 **탐지·관제·대응 지원 서비스**입니다.

프로젝트의 핵심 보안 원칙은 다음과 같습니다.

- 개발자가 정한 규칙이 이벤트 유형과 심각도 등 판정을 담당합니다.
- AI는 이벤트 내용을 요약하거나 대응 참고 정보를 제공하는 보조 역할입니다.
- AI가 보안 판정의 기준을 대신하거나 규칙 판정을 임의로 바꾸지 않습니다.
- 실제 방화벽이나 네트워크 장비처럼 모든 공격을 차단하는 제품이라고 표현하지 않습니다.
- 탐지에는 오탐·미탐이 있을 수 있으며, 실제 운영 데이터와 배포 환경에서의 검증이 필요합니다.

처음 기획에는 Web Hosting과 Web Payment도 있었지만, 인프라·계약·결제 운영 범위가 너무 커서 제외했습니다. 최종 방향은 **Web Security와 SentinelOps를 중심으로 한 보안 전문 서비스**입니다.

## 3. 기술 스택과 구조

### 기술 스택

| 구분 | 사용 기술 |
|---|---|
| 언어 | Java 17, JavaScript |
| 서버·웹 | Apache Tomcat 9, Servlet, JSP, JSTL |
| 구조 | MVC, Controller/Servlet, Service, DAO, DTO |
| 데이터베이스 | MySQL 8.x, JDBC, JNDI/DataSource 구성 |
| 화면 | HTML5, CSS3, JavaScript Fetch API |
| 외부 연동 | OpenRouter 호환 AI API, Slack Webhook, Daum 우편번호/주소 검색 |
| 문서/API | 이벤트 조회용 REST API, API Key 인증, JSON 응답 |

### 일반적인 처리 흐름

브라우저 요청은 Servlet/Controller에서 받고, Filter는 요청 또는 서버 오류 흐름을 관찰합니다. Service가 업무 규칙과 검증을 처리하고 DAO가 JDBC로 DB를 읽고 씁니다. JSP는 화면을 표시하고, DTO는 계층 간 데이터를 전달합니다. 일부 화면의 비동기 요청은 Fetch API로 보내고 JSON 응답을 처리합니다.

NEXORA의 REST API는 기존 JSP 웹사이트 전체를 REST로 바꾼 것이 아닙니다. SentinelOps 및 Security 관제 데이터의 일부를 API Key로 인증한 외부 시스템이 JSON으로 조회하는 읽기 중심 연동 기능입니다. 정확한 URL, HTTP 메서드, 인증 헤더, 응답 필드는 ZIP에서 확인해야 합니다.

## 4. 주요 기능과 구현 상태

아래 항목은 발표 자료와 과거 작업 기록에서 확인된 범위입니다. 최신 ZIP을 열어 실제 코드와 대조한 뒤 확정해야 합니다.

### 4.1 회원 기능

- 회원가입과 회원정보 수정 흐름
- 입력값 형식 및 중복 검증
- 로그인 세션을 기준으로 수정할 회원 식별
- 비밀번호 해시 저장 방식
- 주소/우편번호 검색 연동
- 관리자와 일반 회원의 권한 흐름

정확한 비밀번호 해시 알고리즘, 검증 위치, 세션 정책, 권한 체크 범위는 소스에서 다시 확인합니다. 비밀번호·개인정보를 문서나 테스트 결과에 복사하지 않습니다.

### 4.2 커뮤니티 게시판

- 게시글 목록, 검색, 카테고리 및 상세 화면
- 게시글 작성·수정·삭제 흐름
- 댓글과 첨부파일 연계
- 작성자/관리자 권한 확인
- 첨부파일의 확장자·크기 등 제한

게시판 상세 화면과 관리 권한의 실제 구현 범위는 ZIP에서 재검증합니다.

### 4.3 문의 및 고객지원

- 문의 등록과 내 문의 확인
- 관리자 문의 목록·상세 확인
- 문의와 인시던트 연결 흐름이 프로젝트에 포함됨
- 문의 첨부파일 관련 화면 및 처리

초기 담당 분담에는 별도 문의 담당이 있었지만, 팀 활동 상황 변화 뒤 사용자가 문의 기능 통합도 맡아 정리했습니다. 세부 기능과 최종 책임 표기는 결과보고서와 ZIP의 최신 상태를 기준으로 확인합니다.

### 4.4 SentinelOps 인시던트 대응

- Servlet Filter 등을 이용해 서버 예외 및 HTTP 5XX 계열 상황을 인시던트로 기록
- 개발자가 정의한 규칙에 따른 심각도 분류
- 이벤트 지문/중복 집계 및 상태 이력 관리 구조
- 관리자 인시던트 목록과 상세 확인
- AI를 이용한 이벤트 요약 또는 분석 보조
- 중요 이벤트의 Slack Webhook 알림
- 인시던트와 문의를 연결하는 대응 흐름
- 일부 인시던트 데이터를 API Key 인증 REST API로 조회

정확히 어떤 4XX/5XX가 저장되는지, 중복 집계 조건, Slack 발송 기준, AI 입력 데이터는 구현 코드와 설정 파일에서 확인합니다. 과거 기준으로 Slack은 중요 이벤트 위주로 설정했으나, 최신 조건을 다시 검증합니다.

### 4.5 Web Security 보안 관제

- 웹 요청 및 AI 프롬프트에서 의심 패턴을 규칙 기반으로 탐지
- SQL Injection, XSS, 경로 이동, SSRF, 프롬프트 인젝션 유형의 패턴을 다루도록 구성
- 탐지 이벤트를 DB에 기록하고 관리자 화면에서 조회
- 민감할 수 있는 증거 정보를 마스킹하는 방향
- AI 분석은 요약·대응 의견을 보조하고 규칙 기반 판정을 대체하지 않음
- 보안 이벤트 조회용 REST API 연동

이 모듈은 “탐지와 기록, 관제 지원” 범위입니다. 파이널 후보인 AI Gateway의 허용·마스킹·차단 요청 프록시와 동일한 구현이라고 간주하지 않습니다. URL 쿼리만 임의로 바꿔도 탐지되는지 등 실제 입력 경로는 Filter와 Servlet 매핑을 확인해야 합니다.

### 4.6 관리자·공통 화면

- 관리자 대시보드 및 좌측 메뉴
- 회원·게시판·문의·인시던트·보안 이벤트 관리 화면
- 공통 헤더 및 CSS 정리 작업
- 비동기 요청에 Fetch API를 사용하는 화면이 있음

화면별 공통 include, CSS 적용 상태, 권한 검증은 ZIP에서 다시 조사합니다. 이전에 수정했던 파일과 사용자가 별도로 고친 최신 파일이 다를 수 있습니다.

## 7. 파이널 프로젝트 확장 후보: NEXORA AI Gateway

### 현재 상태

2026년 10월 23일 대화에서 만든 한 페이지 스펙이 **설계 기준선 후보**로 정리되었습니다. 이 스펙은 기존 Servlet 프로젝트에 이미 구현된 기능이 아닙니다. 파이널 팀 구성과 기간도 기준일 현재 확정되지 않았으며, 파이널 주제로 최종 결정되었다고 말하지 않습니다.

### 제안된 주제

Spring Boot 기반 정책형 AI 요청 보안 게이트웨이. 클라이언트의 AI 요청을 API Key로 인증하고, 규칙 기반 검사 결과에 따라 허용·마스킹·차단한 뒤 감사 로그를 남기는 서비스입니다. NEXORA의 사후 탐지·관제를 AI 요청이 모델에 도달하기 전에 검사하는 구조로 확장하는 아이디어입니다.

### 요청 처리 흐름 초안

1. 클라이언트가 `/v1/chat`에 API Key와 프롬프트를 보냅니다.
2. API Key를 인증합니다. 인증 실패는 401이며, 요청 감사 로그와 분리된 보안 이벤트로 집계합니다.
3. 규칙 엔진이 메모리에서 프롬프트를 검사합니다.
4. 판정은 `ALLOW`, `MASK`, `BLOCK` 중 하나입니다.
5. 허용·마스킹은 `PENDING` 감사 로그를 먼저 저장한 뒤에만 모델(Mock 또는 설정된 LLM)을 호출합니다.
6. 호출 후 `SUCCESS` 또는 `MODEL_ERROR`로 로그 상태를 갱신합니다.
7. 차단은 `BLOCKED`로 기록하고 외부 모델은 호출하지 않습니다.
8. 응답을 반환합니다.

### 확정 스펙 후보의 보안·장애 원칙

- 원문 프롬프트는 DB·일반 로그·응답에 저장하지 않습니다.
- 모델 호출은 허용 또는 마스킹된 입력만 대상으로 합니다.
- 차단 응답에는 구체적인 규칙 정보를 노출하지 않습니다. 상세 규칙 코드는 관리자 로그에만 둡니다.
- 원본 API Key는 저장하지 않습니다. 해시 또는 비밀이 아닌 식별 정보만 사용합니다.
- 로그에는 판정, 상태, 정책 버전, 마스킹된 증거만 기록합니다.
- 정책 버전은 사람이 읽을 수 있는 버전과 설정 파일 해시를 함께 남깁니다.
- 허용·마스킹 요청의 최초 로그 저장이 실패하면 모델 호출을 중단하고 오류를 반환합니다.
- 최종 상태 갱신이 실패하면 성공 응답을 주지 않는 안이 제안되었습니다. 이 경우 모델은 응답했지만 클라이언트는 오류를 받는 트레이드오프를 문서화해야 합니다.
- 차단 로그 저장이 실패해도 차단은 유지하고, 저장 실패를 서버 운영 로그에 남깁니다.
- 인증 실패는 요청 감사 로그와 분리하고, 시간 버킷 기준으로 단순 집계합니다.
- 정책 파일을 읽지 못하면 잘못된 기본 정책으로 기동하지 않도록 서버 시작을 실패시키는 안입니다.
- 오래 남은 `PENDING` 레코드를 조회해 타임아웃·프로세스 중단 흔적을 찾습니다.
- 관리자 웹 로그인과 외부 API Key 인증을 별도 보안 필터 체인으로 분리하는 안입니다.

### MVP 초안

- API Key 인증(초기 데이터 또는 간단 발급)
- `/v1/chat` 전체 요청 흐름과 재현 가능한 Mock 응답
- 규칙 3~5개와 허용·마스킹·차단 판정
- 감사 로그와 상태 갱신
- 읽기 전용 설정 파일 정책과 정책 버전
- 관리자 로그 목록·상세 및 오래된 `PENDING` 조회
- OpenAPI/Swagger 문서
- 핵심 통합 테스트와 카나리 개인정보 테스트

여력 기능 후보: 키별 요청 한도, Actuator/Micrometer, Slack 알림, Mock과 전환 가능한 실제 LLM 연동. 제외 초안: Kafka, 완전한 멀티테넌트 분리, 결제, 게시판·문의 재구현. Redis 기반 한도와 정책 편집 UI도 초안 범위에서는 제외했습니다.

### 최소 통합 테스트 초안

- 키 없음/잘못된 키 → 401 및 별도 보안 이벤트 기록
- 정상 요청 → ALLOW, Mock 응답, SUCCESS 로그
- 개인정보 입력 → 모델에는 마스킹된 문자열만 전달, 응답은 MASK 표시
- 공격 패턴 → BLOCK, 모델 호출 횟수 0
- 기록 실패 정책에 따라 요청 중단 또는 차단 유지
- 어떤 감사 로그에도 원문 프롬프트가 저장되지 않음
- 고유 테스트용 개인정보 카나리가 모델 전달값, DB, 로그, 예외 메시지에 없는지 확인
- PENDING이 남은 요청을 관리자가 조회 가능

이 스펙은 파이널 착수 시 팀·기간·강의 요구사항에 맞춰 다시 확정합니다. 특히 실제 외부 LLM 호출, 데이터 보존, 인증 실패 집계, 로그 상태 전이, 오류 응답은 구현 전에 API 계약서와 테스트 기준으로 합의합니다.
