## 4. 트랜잭션·ACID

**정의** — 트랜잭션은 하나의 논리적 작업 단위로 취급하는 데이터베이스 연산 집합이며 ACID는 원자성·일관성·격리성·지속성의 성질을 가리킨다.

**목적과 책임** — 여러 변경이 부분적으로만 반영되지 않도록 제어한다.

**구별해야 할 개념 / 흔한 오해** — 원자성은 여러 SQL이 항상 동시에 실행된다는 뜻이 아니고, 격리성은 모든 동시성 문제가 자동으로 사라진다는 뜻도 아니다.

**실행·처리 흐름** — BEGIN → 변경 1 → 변경 2 → COMMIT 또는 ROLLBACK

**직접 구현·검증** — 계좌 이체에서 두 UPDATE 사이 오류를 발생시켜 ROLLBACK 검증. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 트랜잭션 격리 수준을 왜 설정하는가?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

트랜잭션은 함께 성공하거나 실패해야 하는 작업 단위다. 원자성·일관성·격리성·지속성은 트랜잭션의 성질이다. 일관성은 애플리케이션 규칙을 DB가 자동으로 모두 보장한다는 뜻이 아니다. 격리 수준은 동시성 이상과 성능 사이의 선택이며 DB 구현에 따라 실제 잠금·MVCC 동작이 다르다.

### 직접 읽고 구현하는 독립 예제

```sql
START TRANSACTION;
UPDATE account SET balance=balance-100 WHERE id=1 AND balance>=100;
-- 영향 행 수 확인 후 다음 문장 실행
UPDATE account SET balance=balance+100 WHERE id=2;
COMMIT;
```


### 실행 검증 체크포인트

첫 UPDATE가 0행이면 ROLLBACK하도록 애플리케이션 로직을 작성해야 한다. 예제 실행 전 account 테이블과 잔액을 준비한다.

### 스스로 작성할 변형 실습

두 연결에서 같은 계좌를 갱신하고 격리 수준별 결과를 비교한다.

### 면접 답변의 기준 문장

> 트랜잭션은 관련 작업의 원자적 완료를 위한 단위이고 ACID는 신뢰성 있게 처리하기 위한 성질입니다.


### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“트랜잭션은 하나의 논리적 작업 단위로 취급하는 데이터베이스 연산 집합이며 ACID는 원자성·일관성·격리성·지속성의 성질을 가리킨다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“원자성은 여러 SQL이 항상 동시에 실행된다는 뜻이 아니고, 격리성은 모든 동시성 문제가 자동으로 사라진다는 뜻도 아니다.”* 반례를 하나 만들어 본다.

**3차: 면접 재현.** *“트랜잭션 격리 수준을 왜 설정하는가?”*에 대해 **정의 → 왜 필요한가 → 무엇과 다른가 → 코드·상황 하나** 순서로 30~60초 말한다. 답을 읽지 않고 말한 뒤 원문과 대조한다.

## 5. 인덱스·실행 계획

**정의** — 인덱스는 특정 검색·정렬 접근을 빠르게 할 수 있도록 유지하는 보조 자료구조이며 실행 계획은 DBMS가 선택한 쿼리 처리 전략이다.

**목적과 책임** — 읽기 비용을 낮출 수 있지만 쓰기·저장 비용을 늘린다.

**구별해야 할 개념 / 흔한 오해** — 인덱스 존재만으로 항상 사용되지는 않는다. 복합 인덱스의 열 순서와 선택도가 중요하다.

**실행·처리 흐름** — SQL 파싱 → 최적화 → 접근 경로 선택 → 실행

**직접 구현·검증** — EXPLAIN으로 인덱스 전후 조회 계획을 비교. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 왜 모든 컬럼에 인덱스를 만들지 않는가?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

## 5-1. 커넥션 풀 HikariCP: 연결을 미리 만들어 빌려 쓴다 (2026-11-23 보강, MySQL 8.0 로컬에서 확인함)

**정의**: DB 연결을 만드는 일은 느리다(네트워크 왕복과 인증). 커넥션 풀은 연결을 미리 여러 개 만들어 두고, 요청이 빌려 쓰고 반납하는 구조다. Spring Boot는 기본 풀로 HikariCP를 쓴다.

**주요 설정**
- `maximumPoolSize`: 풀에 둘 최대 연결 수
- `connectionTimeout`: 빌릴 연결이 없을 때 기다리는 시간(ms). 넘으면 예외가 난다.

```java
import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;
import java.sql.Connection;
import java.sql.SQLException;

public class PoolDemo {
    public static void main(String[] args) throws Exception {
        HikariConfig cfg = new HikariConfig();
        cfg.setJdbcUrl("jdbc:mysql://localhost:3306/khac_pool_demo");
        cfg.setUsername("root");
        cfg.setPassword(System.getenv("MYSQL_PWD"));   // 비밀번호는 코드에 쓰지 않는다
        cfg.setMaximumPoolSize(2);
        cfg.setConnectionTimeout(1000);
        try (HikariDataSource ds = new HikariDataSource(cfg)) {
            Connection c1 = ds.getConnection();
            Connection c2 = ds.getConnection();
            System.out.println("borrowed 2 of max 2");
            try {
                ds.getConnection();                     // 풀이 가득 찼다
                System.out.println("3rd ok (unexpected)");
            } catch (SQLException e) {
                System.out.println("3rd failed: " + e.getMessage().split("\n")[0]);
            }
            c1.close();                                 // 반납하면 다시 빌릴 수 있다
            Connection c3 = ds.getConnection();
            System.out.println("after return, valid=" + c3.isValid(1));
            c2.close();
            c3.close();
        }
    }
}
```

필요한 jar: `HikariCP`, `mysql-connector-j`, `slf4j-api`(HikariCP가 로그에 사용한다. 없으면 `NoClassDefFoundError`가 난다).

**실행 결과 (확인함)**

```
borrowed 2 of max 2
3rd failed: HikariPool-1 - Connection is not available, request timed out after 1001ms (total=2, active=2, idle=0, waiting=0)
after return, valid=true
```

**읽는 법**
- 세 번째 요청은 1초를 기다리다가 실패했다. 메시지의 `total=2, active=2`가 풀이 가득 찼다는 뜻이다.
- `c1.close()`는 연결을 끊는 것이 아니라 풀에 **반납**한다. 그래서 다음 요청이 빌려 쓸 수 있다.

**흔한 실수**
- **반납 누락**: `close()`를 빼먹으면 풀이 금방 바닥난다. `try-with-resources`로 항상 닫는다([02-3장 6-2절](02-3_메모리_IO_enum.md)).
- **긴 트랜잭션**: 연결을 쥔 채 외부 API를 기다리면 풀이 막힌다.
- **무작정 키우기**: `maximumPoolSize`를 크게 잡으면 DB 쪽 최대 연결 수를 넘을 수 있다. DB와 서버 수를 함께 계산한다.

**면접 기준**: "커넥션 풀은 연결을 미리 만들어 재사용하는 구조입니다. 풀이 가득 차면 `connectionTimeout` 후 예외가 나므로, 연결을 반드시 반납하고 트랜잭션을 짧게 유지합니다."


## 6. 트랜잭션 격리 수준

동시에 실행되는 트랜잭션끼리 얼마나 간섭을 막을지 정하는 선택이다.

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read |
|---|---|---|---|
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| READ COMMITTED | 방지 | 발생 | 발생 |
| REPEATABLE READ | 방지 | 방지 | 표준상 발생 가능 (MySQL InnoDB는 대부분 방지) |
| SERIALIZABLE | 방지 | 방지 | 방지 |

- **Dirty Read:** 커밋되지 않은 값을 읽는 것.
- **Non-repeatable Read:** 같은 행을 두 번 읽었는데 값이 바뀐 것.
- **Phantom Read:** 같은 조건으로 조회했는데 행 개수가 바뀐 것.
- **MySQL InnoDB 기본값:** REPEATABLE READ.
- **실습 결과 (MySQL 8.0, 2026-11-23 실행):** 세션 A가 잔액을 100에서 200으로 바꾸고 4초 동안 커밋하지 않은 상태에서, 세션 B가 같은 행을 읽었다.
  - READ UNCOMMITTED: B가 200을 읽음 (Dirty Read 발생)
  - READ COMMITTED: B가 100을 읽음 (커밋 전 값은 안 보임)
  - READ COMMITTED에서 B가 두 번 읽는 사이 A가 300으로 커밋: 첫 번째 100, 두 번째 300 (Non-repeatable Read 발생)
  - REPEATABLE READ에서 같은 상황: 첫 번째 100, 두 번째 100 (반복 읽기 보장)
- **다시 해 보기:** 세션을 두 개 열고 한쪽에서 UPDATE 후 커밋하지 않은 상태에서 다른 쪽이 SELECT해 본다. 격리 수준을 `SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;`처럼 바꿔 결과를 비교한다.
- **면접 기준:** "격리 수준은 트랜잭션 간 간섭을 얼마나 막을지의 선택입니다. 많이 막을수록 동시성이 떨어집니다."
