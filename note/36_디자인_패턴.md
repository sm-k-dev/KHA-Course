# 디자인 패턴: 자주 나오는 변경 지점을 구조로 가둔다

> 중요도: **B** · 이 장의 목표: 전략(Strategy), 팩토리(Factory), 옵저버(Observer), 데코레이터(Decorator) 패턴의 문제 상황과 구조를 구분하고, 패턴을 쓸지 말지 판단한다.

> 2026-11-23 추가 장 (로드맵 2순위 "디자인 패턴" 항목, 35장 설계 원칙의 적용). 아래 예제는 JDK 25에서 실행해 결과를 확인했다. 패턴은 암기 대상이 아니라 **변경이 자주 일어나는 지점을 찾는 도구**다.

---

## 1. 패턴을 쓰기 전에 먼저 물어볼 것

- 지금 바뀌는 곳이 어디인가?
- 그 변경이 **실제로 자주 일어나는가**, 아니면 가정인가?
- 패턴을 넣으면 파일 수와 간접 참조가 늘어난다. 그 비용을 감당할 만한가?

35장의 **개방-폐쇄 원칙(OCP)**이 패턴의 바탕이다. 기존 코드를 고치지 않고 새 동작을 추가하게 만드는 것이 목표다.

---

## 2. 전략 패턴 (Strategy)

**문제**: 할인 방식이 자주 늘어난다. `if-else`가 계속 길어진다.

**구조**: 바뀌는 부분을 인터페이스로 빼고, 실행 시점에 구현체를 고른다.

```java
interface DiscountStrategy {
    int apply(int price);
}

class NoDiscount implements DiscountStrategy {
    public int apply(int price) { return price; }
}

class PercentDiscount implements DiscountStrategy {
    private final int percent;
    PercentDiscount(int percent) { this.percent = percent; }
    public int apply(int price) { return price * (100 - percent) / 100; }
}

class Checkout {
    private final DiscountStrategy strategy;
    Checkout(DiscountStrategy strategy) { this.strategy = strategy; }
    int total(int price) { return strategy.apply(price); }
}
```

**장점**: 새 할인 방식은 새 클래스만 추가하면 된다. `Checkout`은 바뀌지 않는다.

---

## 3. 팩토리 패턴 (Factory)

**문제**: 어떤 구현체를 만들지 결정하는 `switch`가 여러 곳에 흩어져 있다.

**구조**: 생성 규칙을 한곳에 모은다.

```java
static DiscountStrategy discountFor(String grade) {
    return switch (grade) {
        case "VIP" -> new PercentDiscount(20);
        case "GOLD" -> new PercentDiscount(10);
        default -> new NoDiscount();
    };
}
```

호출하는 쪽은 `new`를 몰라도 된다. 등급 정책이 바뀌면 이 메서드만 고친다.

---

## 4. 옵저버 패턴 (Observer)

**문제**: 주문이 완료되면 메일, 적립금, 알림을 모두 보내야 한다. 주문 코드가 이 모든 것을 알게 되면 결합이 커진다.

**구조**: 주문은 "완료됐다"는 사실만 알리고, 구독자들이 각자 반응한다.

```java
interface OrderListener {
    void onPlaced(String orderId);
}

class OrderPublisher {
    private final List<OrderListener> listeners = new ArrayList<>();
    void subscribe(OrderListener l) { listeners.add(l); }
    void placed(String orderId) { listeners.forEach(l -> l.onPlaced(orderId)); }
}
```

**주의**: 구독자가 예외를 던지면 뒤의 구독자는 실행되지 않는다. 실무에서는 비동기 큐나 이벤트 저장소로 분리해서 한 구독자의 실패가 다른 구독자에게 번지지 않게 한다. (42장 메시징 참고)

---

## 5. 데코레이터 패턴 (Decorator)

**문제**: 기본 기능에 로그, 압축, 암호화 같은 부가 기능을 조합해서 붙여야 한다. 조합마다 클래스를 만들면 폭발한다.

**구조**: 같은 인터페이스를 구현한 객체가 다른 객체를 감싼다.

```java
interface Notifier {
    String send(String msg);
}

class EmailNotifier implements Notifier {
    public String send(String msg) { return "email:" + msg; }
}

class TimestampDecorator implements Notifier {
    private final Notifier inner;
    TimestampDecorator(Notifier inner) { this.inner = inner; }
    public String send(String msg) { return "[t] " + inner.send(msg); }
}
```

**주의**: Java I/O(`BufferedReader(new InputStreamReader(...))`)가 이 패턴이다. Spring의 프록시(20장)도 같은 발상이다.

---

## 6. 패턴을 과하게 쓰면 생기는 문제

| 증상 | 원인 |
|---|---|
| 클래스가 한 메서드짜리 수십 개 | 변경 가능성이 없는 곳에 전략을 씀 |
| 호출 흐름을 따라가기 어려움 | 옵저버와 데코레이터를 여러 겹 씀 |
| 팀원이 구조를 모름 | 패턴 이름만 쓰고 문서화하지 않음 |

**판단 기준**: 같은 변경이 **세 번 이상** 생겼을 때 패턴을 도입한다. 한 번도 안 바뀐 곳에는 넣지 않는다.

## 7. 검증 코드

```java
import java.util.*;

public class PatternCheck {
    interface DiscountStrategy { int apply(int price); }
    static class NoDiscount implements DiscountStrategy { public int apply(int p) { return p; } }
    static class PercentDiscount implements DiscountStrategy {
        private final int percent;
        PercentDiscount(int percent) { this.percent = percent; }
        public int apply(int p) { return p * (100 - percent) / 100; }
    }
    static DiscountStrategy discountFor(String grade) {
        return switch (grade) {
            case "VIP" -> new PercentDiscount(20);
            case "GOLD" -> new PercentDiscount(10);
            default -> new NoDiscount();
        };
    }

    interface OrderListener { void onPlaced(String orderId); }
    static class OrderPublisher {
        private final List<OrderListener> listeners = new ArrayList<>();
        void subscribe(OrderListener l) { listeners.add(l); }
        void placed(String orderId) { listeners.forEach(l -> l.onPlaced(orderId)); }
    }

    interface Notifier { String send(String msg); }
    static class EmailNotifier implements Notifier { public String send(String m) { return "email:" + m; } }
    static class TimestampDecorator implements Notifier {
        private final Notifier inner;
        TimestampDecorator(Notifier inner) { this.inner = inner; }
        public String send(String m) { return "[t] " + inner.send(m); }
    }

    public static void main(String[] args) {
        System.out.println(discountFor("VIP").apply(10000));   // 8000
        System.out.println(discountFor("GOLD").apply(10000));  // 9000
        System.out.println(discountFor("BASIC").apply(10000)); // 10000

        OrderPublisher pub = new OrderPublisher();
        List<String> log = new ArrayList<>();
        pub.subscribe(id -> log.add("mail " + id));
        pub.subscribe(id -> log.add("point " + id));
        pub.placed("A1");
        System.out.println(log);                                // [mail A1, point A1]

        Notifier n = new TimestampDecorator(new EmailNotifier());
        System.out.println(n.send("hi"));                       // [t] email:hi
    }
}
```

**실행 결과 (확인함)**

```
8000
9000
10000
[mail A1, point A1]
[t] email:hi
```

## 8. 실습 과제

1. `PercentDiscount`와 같은 방식으로 `FixedDiscount(int amount)`를 추가한다. `discountFor`는 고치지 않고 등급만 추가한다고 생각해 보고, 실제로 고칠 곳이 어디인지 적는다.
2. `TimestampDecorator`를 감싸는 `UpperCaseDecorator`를 만들어 `send("hi")`의 결과를 적는다.
3. 최근 프로젝트 코드에서 `if-else`나 `switch`가 세 곳 이상 반복되는 부분을 찾고, 패턴이 필요한지 판단한 근거를 적는다.

## 단원 통과 기준

- [ ] 전략, 팩토리, 옵저버, 데코레이터가 각각 어떤 변경을 가두는지 설명할 수 있다.
- [ ] 패턴을 도입하기 전에 "변경이 실제로 반복되는가"를 묻는 이유를 설명할 수 있다.
- [ ] 옵저버에서 한 구독자의 실패가 다른 구독자에게 번지지 않게 하는 방법을 말할 수 있다.
- [ ] Java I/O가 데코레이터 패턴인 이유를 설명할 수 있다.
