【코드에서 확인한 해결 방식】
👍 집계 쿼리(count + group by)로 리뷰 수를 한 번에 계산함 — 리뷰 내용은 필요 없고 개수만 필요할 때 가장 알맞은 방법입니다.
👍 쿼리에서 바로 DTO(StoreListDto)를 만들어 필요한 값만 가져옴 — 엔티티를 거치지 않아 가볍습니다.
【바뀐 코드 (원본과 비교, - 지운 줄 / + 추가한 줄)】
📘 먼저 알아 둘 개념 (사건 1)
영속성 컨텍스트 · 1차 캐시
JPA 가 조회한 엔티티를 잠시 보관하는 메모리 상자입니다. 키는 @Id(기본키), 값은 엔티티 객체입니다. 같은 id 를 다시 찾으면 DB 에 가지 않고 여기서 꺼냅니다. 요청(트랜잭션)마다 새로 생기고 끝나면 사라집니다.
지연 로딩(LAZY) · 프록시
@OneToMany 의 기본값은 LAZY 입니다. Store 를 읽을 때 reviews 는 진짜 리뷰 대신 "프록시(빈 껍데기)"로 둡니다. getReviews().size() 처럼 실제로 쓰는 순간 그 맛집의 리뷰를 가져오는 SELECT 가 나갑니다.
1+N 문제
목록 1번 조회(1) 뒤에, 반복문이 항목마다 지연 로딩을 건드려 SELECT 가 N번 더 나가는 문제입니다. 맛집 50개면 1 + 50 = 51번입니다. 데이터가 늘수록 SQL 이 늘어나 느려집니다.
집계 쿼리 · DTO 조회
count(...) + group by 로 DB 가 개수를 계산하게 하고, select new ...Dto(...) 로 화면에 필요한 값만 받는 방법입니다. 엔티티가 아니므로 1차 캐시·프록시가 생기지 않고 SQL 은 1번입니다. 개수만 필요할 때 가장 알맞습니다.
fetch join · @EntityGraph
연관 엔티티(리뷰)까지 한 SQL 로 함께 가져와 프록시를 처음부터 채워 두는 방법입니다. SQL 은 1번이 되지만 리뷰 전체를 메모리에 올리므로, 개수만 필요하면 집계 쿼리보다 무겁습니다.

📘 먼저 알아 둘 개념 (사건 2)
요청마다 따로인 영속성 컨텍스트
두 사람이 동시에 찜하면 요청 A·B 는 각자의 트랜잭션과 각자의 1차 캐시를 가집니다. 서로의 메모리 값을 모릅니다.
스냅샷 · 변경 감지(dirty checking)
엔티티를 조회할 때 JPA 는 그때 값을 "스냅샷"으로 복사해 둡니다. 커밋 때 현재 값과 스냅샷을 비교해 달라졌으면 UPDATE 를 자동으로 만듭니다. 그래서 store.addZzimCount() 만 해도 UPDATE 가 나갑니다.
flush · commit
flush 는 모아 둔 SQL 을 DB 로 보내는 일, commit 은 그 결과를 확정하는 일입니다. @Transactional 메서드가 끝날 때 flush → commit 순서로 일어납니다.
갱신 손실(lost update)
A 와 B 가 둘 다 0 을 읽고 각자 1 로 만들어 저장하면, 두 번 찜했는데 결과는 1 입니다. 나중에 저장한 쪽이 앞의 결과를 덮어써서 1 이 사라집니다.
DB 에서 +1 (@Modifying update)
update store set zzim_count = zzim_count + 1 처럼 DB 가 "지금 값"에 1 을 더하게 하면, 같은 행을 바꾸는 요청은 DB 의 행 잠금으로 줄을 서서 하나씩 처리됩니다. 메모리 값·스냅샷을 쓰지 않으므로 덮어쓰기가 없습니다.
유니크 제약 · DataIntegrityViolationException
(member_id, store_id) 조합이 한 번만 저장되도록 DB 에 규칙을 거는 것입니다. 확인(exists)과 저장 사이에 다른 요청이 끼어들어도 두 번째 INSERT 는 DB 가 거절하고, 스프링은 DataIntegrityViolationException 을 던집니다. 이 예외를 잡아 "이미 찜함"으로 안내합니다.

  5. ⑤ A 커밋 → flush → 변경 감지. 스냅샷 0 ≠ 현재 1 이므로 JPA 가 update store set zzim_count = 1 을 만들어 보냅니다. (자습서 6-3)
  6. ⑥ B 커밋 → 같은 UPDATE. B 도 자기 스냅샷 0 과 비교해 zzim_count = 1 을 보냅니다. A 가 올린 1 위에 덮어써서 찜 2번인데 숫자는 1 (갱신 손실). 실제 측정(수사보고서): 100명 → 찜 수 17, zzim 행 27, 같은 회원 30번 → 행 2.
🎬 학생 코드에서 일어나는 일 (왜 이렇게 바뀌어야 하나)
  1. ① 유니크 제약 (회원, 맛집). A 의 INSERT 는 성공합니다. B 의 INSERT 는 DB 가 "이미 있는 (7, 1)" 이라며 거절합니다. 확인(exists)과 저장 사이에 끼어들어도 DB 가 마지막에 막아 줍니다.
  2. ② DB 가 직접 +1. @Modifying update 는 1차 캐시의 값·스냅샷을 쓰지 않고 DB 의 현재 값에 +1 합니다. A 가 행을 바꾸는 동안 B 는 DB 의 행 잠금 때문에 기다렸다가 A 의 결과(1) 위에 +1 합니다.
  3. ③ 변경 감지가 끼어들지 않음. 자바 객체를 고치는 addZzimCount()를 더 이상 부르지 않으므로, 커밋 때 스냅샷 비교로 zzim_count = 1 같은 덮어쓰기 UPDATE 가 만들어지지 않습니다. (clearAutomatically 는 1차 캐시의 옛 값을 비워 줌)
  4. 결과. 수사보고서 측정: 100명 → 찜 수 100, 행 100, 같은 회원 → 행 1 ✔
