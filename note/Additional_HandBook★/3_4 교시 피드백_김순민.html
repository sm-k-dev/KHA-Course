📘 용어 한 줄 풀이: 연관관계의 주인
두 엔티티가 서로를 가리킬 때(양방향), DB 외래키를 실제로 관리하는 쪽입니다. 외래키 컬럼이 있는 테이블의 엔티티(Review.store)가 주인이고, 반대쪽은 mappedBy 로 "나는 거울"이라고 표시합니다.
서술 1 · A 연관관계20 / 20점 ✔
양방향 연관관계에서 mappedBy 는 어느 쪽에 쓰는지 설명하고, 그 쪽 필드에만 값을 넣고 저장하면 DB 외래키가 어떻게 되는지 4~6줄로 쓰세요. 보기 단어: 주인, 읽기, 외래키, 반대
내 답안관계의 주인이 아닌 엔티티에 적는다. mappedBy가 있는 필드는 읽기전용임으로 해당 필드의 데이터는 변하지 않는다. 반대로 관계의 주인인 외래키 필드에 값을 넣고 저장하면 값이 변하게 된다.
뜻으로 본 채점 기준
✔ 외래키를 가진 쪽이 주인✔ mappedBy 는 주인이 아닌 반대쪽✔ mappedBy 쪽은 읽기 전용✘ 그쪽에만 넣으면 외래키가 저장되지 않음(null)

좋아요. 외래키를 가진 쪽이 연관관계의 주인이라는 점을 정확히 짚었어요. mappedBy 를 주인이 아닌 반대쪽(Store.reviews)에 쓴다는 위치도 맞게 썼어요. mappedBy 쪽은 읽기 전용(거울)이라는 핵심을 잘 이해했네요.

질문의 뒷부분, "그쪽에만 넣고 저장하면 DB 외래키가 어떻게 되나"에 대한 답이 빠졌어요. 정답은 "외래키가 저장되지 않고 null 로 남는다"예요.

이 문항은 만점이에요. 이렇게 설명할 수 있으면 실무에서도 충분히 통합니다.

모범 답안 양방향 관계에서 외래키를 가진 쪽(Review.store)이 연관관계의 주인이고, 주인이 아닌 쪽(Store.reviews)에 mappedBy = "store" 를 씁니다. mappedBy 쪽은 읽기 전용 거울이라, 여기에 값을 넣어도 DB 의 외래키는 바뀌지 않습니다. 저장·수정할 때는 반드시 주인 쪽에 값을 넣어야 합니다.
📘 용어 한 줄 풀이: 프록시
진짜 엔티티 대신 들어 있는 껍데기 객체입니다. id 만 알고 있다가, 다른 값을 처음 꺼낼 때 DB 에서 읽어 채웁니다(초기화).
서술 2 · B 지연로딩·N+120 / 20점 ✔
지연 로딩(LAZY)일 때 연관 엔티티 자리에 들어 있는 프록시는 무엇이며, 연관 데이터를 가져오는 SQL 은 언제 실행되는지 설명하세요. 보기 단어: 실제로, 프록시, select
내 답안지연 로딩 일때 연관 엔티티 자리에 실제로 들어 있는 값은 프록시이며 관계 엔티티의 id 이다. 연관 데이터를 가져오는 SQL은 관계 엔티티의 id를 읽어올때 select를 실행한다.
뜻으로 본 채점 기준
✔ 프록시 = 진짜 대신 들어 있는 껍데기 객체✔ 실제로 값을 쓰는 순간에 조회✔ 그때 SELECT(SQL) 로 DB 조회

좋아요. 프록시가 진짜 엔티티 대신 들어 있는 껍데기 객체라는 설명이 좋아요. SQL 이 "실제로 값을 꺼내 쓰는 순간" 나간다는 시점을 정확히 썼어요. 그 순간 DB 에 SELECT 가 나간다는 점도 함께 적었어요.

이 문항은 만점이에요. 이렇게 설명할 수 있으면 실무에서도 충분히 통합니다.

모범 답안 LAZY 는 연관된 객체를 당장 읽지 않고, 프록시(번호만 가진 껍데기) 로 채워 두었다가 실제로 값을 꺼내 쓰는 순간 SELECT 를 실행하는 방식입니다. 예: getReferenceById 직후와 getId() 는 SQL 0번, getName() 에서 1번.
📘 용어 한 줄 풀이: N+1
목록 1번 + 항목마다 N번 = SQL 1+N번. 지연 로딩된 연관 데이터를 반복문에서 꺼낼 때 생깁니다.
서술 3 · B 지연로딩·N+120 / 20점 ✔
N+1 문제가 무엇이고 왜 생기는지 설명하고, 해결 방법을 두 가지 이상 쓰세요. 보기 단어: 1번, n번, fetch join
내 답안목록을 읽어올때 SQL 쿼리가 1번 실행되고, 연관 엔티티를 읽어올때 n번 SQL 쿼리가 실행된다. 이것을 해결하기위해 1. fetch join을 사용하여 목록을 읽어올때 연관 엔티티를 함께 읽어온다. (페이징과 함께 쓰면 오류가 난다) 2. query 를 작성하여 select new DTO에 필요한 정보만 담아서 가져온다. (1차 캐시 공간 - 영속성 컨텍스트에 올라가지 않는다) 3. default_batch_fetch_size = n 을 통해 묶음으로 연관 엔티티를 읽어온다.
뜻으로 본 채점 기준
✔ 목록 조회 1번✔ 항목마다 추가로 N번✔ 원인: 지연 로딩을 반복문에서 사용✔ 해결 방법 두 가지 이상

좋아요. 처음 목록을 1번 조회한다는 출발점을 잘 썼어요. 항목마다 연관 데이터를 읽느라 SQL 이 N번 더 나간다는 설명이 정확해요. 왜 생기는지(지연 로딩된 연관 데이터를 반복문에서 꺼내기 때문)도 설명했어요. 해결 방법을 3가지(fetch join, 배치 조회(batch size), DTO·집계 쿼리) 적었어요.

이 문항은 만점이에요. 이렇게 설명할 수 있으면 실무에서도 충분히 통합니다.

모범 답안 목록을 1번 읽은 뒤, 반복하면서 각 항목의 연관 데이터를 읽느라 N번의 SQL 이 더 나가는 문제입니다(맛집 50개 → 51번). 해결: ① fetch join / EntityGraph 로 같이 읽기 ② default_batch_fetch_size 로 묶어서 읽기 ③ 필요한 값만 DTO(select new)로 한 번에 조회하기.
📘 용어 한 줄 풀이: 스냅샷
엔티티를 처음 읽은 순간의 값을 복사해 둔 것. 커밋 때 현재 값과 비교하는 기준입니다.
서술 4 · C 영속성 컨텍스트20 / 20점 ✔
영속성 컨텍스트란 무엇이며, 변경 감지(dirty checking) 로 save() 없이도 UPDATE 가 나가는 과정을 설명하세요. 보기 단어: 엔티티, 관리, 스냅샷, 커밋, update
내 답안영속성 컨텍스트란 Transaction session이 닫히기 전까지 엔티티를 관리하고 감시하는 공간으로, 그 안에 있는 데이터들의 변경사항은 스냅샷과 비교하여 dirty checking 되고 이는 영속성 컨텍스트가 닫히기 전 flush 되어 update되고 그 후 커밋된다.
뜻으로 본 채점 기준
✔ 엔티티를 관리·보관하는 곳(1차 캐시)✔ 처음 상태(스냅샷) 저장✔ 현재 값과 비교✔ 커밋(flush) 시점✔ UPDATE 자동 실행

좋아요. 영속성 컨텍스트가 엔티티를 관리·보관하는 곳(1차 캐시)이라는 정의가 정확해요. 조회할 때 처음 상태(스냅샷)를 함께 저장한다는 점을 잘 썼어요. 현재 값과 스냅샷을 비교한다는 과정을 설명했어요. 그 비교가 커밋(flush) 때 일어난다는 시점도 맞아요. 그래서 save() 없이도 UPDATE 가 자동으로 실행된다는 결론까지 정확해요.

이 문항은 만점이에요. 이렇게 설명할 수 있으면 실무에서도 충분히 통합니다.

모범 답안 영속성 컨텍스트는 트랜잭션 동안 엔티티를 관리·보관하는 곳(1차 캐시)입니다. 엔티티를 읽을 때 처음 상태(스냅샷)를 같이 저장해 두고, 커밋(플러시) 시점에 현재 값과 비교해 달라진 엔티티는 UPDATE 를 자동으로 실행합니다. 그래서 값을 바꾸기만 해도 save() 없이 저장됩니다.

좋아요. JPQL 은 엔티티(클래스)와 필드를 대상으로 쓴다는 핵심을 정확히 썼어요. SQL 은 테이블·컬럼을 대상으로 쓴다는 대비도 정확해요. JPA 가 JPQL 을 그 DB 에 맞는 SQL 로 바꿔 실행한다는 점도 잘 설명했어요.

이 문항은 만점이에요. 이렇게 설명할 수 있으면 실무에서도 충분히 통합니다.

모범 답안 SQL 은 테이블·컬럼을 대상으로 쓰고 DB 마다 문법 차이가 있습니다. JPQL 은 엔티티(클래스)·필드를 대상으로 쓰는 객체 지향 쿼리이며, JPA 가 이를 해당 DB 의 SQL 로 바꿔 실행합니다. 예: select s from Store s → select … from store ….
