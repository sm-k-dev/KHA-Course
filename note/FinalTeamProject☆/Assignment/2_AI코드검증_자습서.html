1-1. 실습용 DB 만들기

💡 왜 하나요?

실습 프로젝트는 MySQL에 데이터를 저장합니다. 실행용 DB와 테스트용 DB를 따로 만듭니다.

  1. MySQL Workbench를 열고 root 계정으로 접속합니다.
  2. 새 쿼리 탭에 아래 SQL을 붙여 넣습니다.
    MySQL Workbench
    CREATE DATABASE defectlab;
CREATE DATABASE defectlab_test;
CREATE USER 'lab'@'localhost' IDENTIFIED BY 'lab1234';
GRANT ALL ON defectlab.* TO 'lab'@'localhost';
GRANT ALL ON defectlab_test.* TO 'lab'@'localhost';
  3. 번개 모양 버튼(Execute)을 누릅니다.

    ✅ 성공 기준: 아래 Action Output에 초록색 체크가 5줄 나옵니다.

📖 defectlab_test — 테스트만 쓰는 DB입니다. 테스트가 데이터를 지우고 다시 만들어도 실행용 DB에는 영향이 없습니다.
⚠️ Operation CREATE USER failed 에러가 나면

lab 계정이 이미 있다는 뜻입니다. 아래를 실행한 뒤 처음 SQL을 다시 실행하세요.

DROP USER 'lab'@'localhost';

1-4. 요청이 지나가는 길 알기

💡 왜 하나요?

결함을 찾으려면 “지금 이 코드가 어느 단계에서 실행되는지” 알아야 합니다. 이 표를 보지 않고 그릴 수 있으면 결함 위치를 훨씬 빨리 찾습니다.

순서단계하는 일이 실습에서 생기는 결함
1브라우저주소로 요청을 보냄주소의 번호를 바꿀 수 있음 → ④ ⑦
2Security 필터 체인로그인했는지 검사 (어떤 데이터의 주인인지는 검사하지 않음)—
3DispatcherServlet주소에 맞는 컨트롤러 메서드를 찾아 호출—
4Controller요청 값을 받아 Service 호출, 결과를 Model에 담음—
5Service@Transactional 안에서 업무 처리, 외부 API·AI 호출주인 검사 누락 ④ ⑦, 동시성 ② ③ ⑥ ⑨, 마스킹 누락 ⑧, AI 결과 미검증 ⑩, 타임아웃 없음 ⑪
6Repository · Hibernate엔티티 작업을 SQL로 바꿔 MySQL에 실행SQL 반복 ①
7MySQL데이터 저장·조회, 행 잠금Deadlock ②
8ThymeleafModel 값으로 HTML을 만들어 응답스크립트 실행 ⑤
📖 필터 체인 — 요청이 컨트롤러에 도착하기 전에 차례로 거치는 검사 객체들의 묶음입니다. 로그인 여부는 여기서 검사하지만, “이 리뷰가 이 사람 것인지”는 검사하지 않습니다. 그 검사는 Service에서 직접 해야 합니다.

    private MaskingUtil() {
    }

    public static String phone(String phone) {
        // CustomerService.toView()에서 호출 → 가린 번호를 리턴
        if (phone == null) {

public interface CustomerRepository extends JpaRepository<Customer, Long> {

            throw new IllegalArgumentException("고객이 없습니다");
        }
        throw new IllegalStateException("포인트가 부족합니다");
    }

public void zzim(Long storeId, Long memberId) {

    if (zzimRepository.existsByMemberIdAndStoreId(memberId, storeId)) {
        throw new IllegalStateException("이미 찜한 맛집입니다");

    // ① 먼저 store 행을 update → 이 트랜잭션이 끝날 때까지 store 행에 배타 락
    //    같은 맛집 찜 요청은 여기서 한 줄로 기다리므로 Deadlock이 생기지 않는다
    if (updated == 0) {
        throw new IllegalArgumentException("맛집이 없습니다");

    Member member = memberRepository.getReferenceById(memberId);
    Store store = storeRepository.getReferenceById(storeId);

    //    중복이면 DataIntegrityViolationException → 트랜잭션 전체(①의 +1 포함)가 롤백된다

💡 힌트 1 보기

💡 힌트 2 보기

🔑 정답 코드 펼치기 (먼저 스스로 해 보세요)
WeatherService.java — 고친 후 전체
package com.academy.defectlab.trip;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.client.SimpleClientHttpRequestFactory;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.RestClientException;

@Service
public class WeatherService {

    public static final String FALLBACK = "날씨 정보를 불러오지 못했습니다";

    private final RestClient restClient;

    public WeatherService(@Value("${app.weather.url}") String weatherUrl) {
        // application.yml의 app.weather.url 값을 StandardEnvironment 객체가 찾아 넣는다
        SimpleClientHttpRequestFactory factory = new SimpleClientHttpRequestFactory();
        factory.setConnectTimeout(1000);
        // 연결 타임아웃 1초: 외부 서버에 1초 안에 연결되지 않으면 포기
        factory.setReadTimeout(1000);
        // 읽기 타임아웃 1초: 연결 후 1초 안에 응답이 오지 않으면 포기
        this.restClient = RestClient.builder()
                .baseUrl(weatherUrl)
                .requestFactory(factory)
                .build();
        // RestClient가 HTTP 요청을 보낼 때 위 타임아웃 설정을 가진 factory 객체를 사용한다
    }

    public String today() {
        // TripController.places()에서 호출 → model "weather" → places/list.html의 ${weather}
        try {
            return restClient.get()
                    .retrieve()
                    .body(String.class);
        } catch (RestClientException e) {
            // 타임아웃·연결 실패·에러 응답이면 RestClientException이 난다
            // 화면 전체를 멈추거나 500으로 만들지 않고 안내 문장을 대신 리턴한다
            return FALLBACK;
        }
    }
}

@SpringBootTest
@ActiveProfiles("test")
// 이 클래스에는 @Transactional을 붙이지 않는다 (준비 데이터가 커밋되어야 다른 스레드가 본다)
class ★동시성Test {

    @Autowired ★Service service;                 // 예: BookmarkService, PointService
    @Autowired JdbcTemplate jdbcTemplate;

    @Test
    void 동시에_100번_요청해도_숫자가_정확하다() throws InterruptedException {
        DbCleaner.clean(jdbcTemplate);
        // ★ 준비: 대상 데이터 1개 + (필요하면) 회원 100명 save

        AtomicInteger success = new AtomicInteger();
        ExecutorService pool = Executors.newFixedThreadPool(32);
        CountDownLatch ready = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(100);
        for (int i = 0; i < 100; i++) {
            int idx = i;
            pool.submit(() -> {
                try {
                    ready.await();                 // 모두 출발선에 선 뒤 동시에 시작
                    service.★동작(/* ★ 대상 id, 회원 id 등 */);
                    success.incrementAndGet();
                } catch (Exception ignored) {
                } finally {
                    done.countDown();
                }
            });
        }
        ready.countDown();
        done.await();
        pool.shutdown();

        // ★ DB에서 다시 읽어 기대값과 비교 (예: 북마크 수 100, 쿠폰 성공 1번)
        System.out.println("[측정] 성공 = " + success.get());
        // assertThat(★실제값).isEqualTo(★기대값);
    }
}

⚠️ 컨트롤러가 직접 만든 로그인 객체(예: CustomUserDetails)를 쓰면

user("이메일")은 기본 UserDetails만 만듭니다. 우리 팀이 만든 클래스를 쓰면 .with(user(new CustomUserDetails(회원)))처럼 그 객체를 넣으세요. JWT로 호출하는 /api 주소는 .header("Authorization", "Bearer " + 토큰)으로 보냅니다.

  1. 틀 하나를 골라 ★ 부분을 바꿉니다.
  2. 테스트를 실행해 먼저 빨간불이 나오는지 봅니다.

    빨간불이 나오면 진짜 결함입니다. Before 숫자를 검증일지에 적습니다. 초록불이 바로 나오면 결함이 없는 것이니, 그 사실도 “검증 완료”로 적어 둡니다.

  3. 실습에서 배운 방법으로 고치고 초록불을 확인합니다.

    After 숫자를 적고 상태를 “완료”로 바꿉니다.

10-4. 팀에 공유하기

💡 왜 하나요?

테스트와 기록을 PR로 올리면, 팀 전체가 같은 결함을 다시 만들지 않게 됩니다. 공지의 평가 항목인 “PR 리뷰 기록”과 “개인 기여”의 증거도 됩니다.

  1. AI 초안 커밋과 고친 커밋을 나눕니다.
    커밋 메시지 예시 (공지의 커밋 타입 feat · fix · test 사용)
    feat: 북마크 기능 구현 (AI 초안)
test: 북마크 동시 요청 테스트 추가 - 100건 중 34건 유실 확인
fix: 북마크 수 갱신 유실 - DB update로 변경 (34건 유실 → 0건)
  2. develop으로 PR을 올리고, 설명에 아래 표를 붙입니다.
    PR 설명 (검증일지 README표 시트에서 복사해도 됨)
    ## 검증 결과
| 결함 | 발견 근거 | Before | After | 테스트 |
|---|---|---|---|---|
| 북마크 수 갱신 유실 | 동시 요청 테스트 | 100건 중 34건 유실 | 0건 | BookmarkConcurrencyTest |
  3. 리뷰하는 팀원은 10-1 표로 코드를 한 번 더 확인하고 댓글을 남깁니다.
