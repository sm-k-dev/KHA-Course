Git - 수많은 소스 코드를 효율적으로 관리하기 위해 사용
Git의 핵심 기능
    - 버전 관리 (Version Control)
    - 백업 (Backup)
    - 협업 (Collaboration)

Git 프로그램 (Git Client Program) 종류: 깃은 제품군
    - 깃허브 데스크톱 (GitHub Desktop)
    - 토터스깃 (TortoiseGit)
    - 소스트리 (SourceTree)

커맨드 라인 인터페이스 (Command Line Interface, CLI)
    - 터미널 창에 직접 명령어를 입력해서 깃을 사용

    - 사용자 정보 입력

        git config --global user.email "메일 주소"

깃 저장소 만들기
    디렉토리 생성 or 디렉토리로 이동
        mkdir 디렉토리명
        cd 디렉토리명
    
    디렉토리 안의 내용을 살펴본다
        ls -la
    
    디렉토리에 저장소를 만들기 위해 다음과 같은 명령어 입력
    현재 디렉토리에서 깃을 사용하기 위해 초기화하는 것
        git init
    
    Initialized empty Git repository... 라는 메세지가 나타나면 디렉토리에서 깃을 사용 할 수 있다.
    터미널 이름, 경로의 끝부분에 (main) 혹은 (master) 라고 표시된다. 

    다시 ls -la를 사용해 디렉토리 안의 내용을 살펴본다.
        .git/ 라는 디렉토리가 생성된다. 깃을 사용하면서 버전이 저장될 저장소(repository)이다. 이 디렉토리는 감춰져 있다.

버전 만들기
    프로그램 개발에서는 수정 내용이 쌓이면 새로 번호를 붙여서 이전 상태과 구별한다.
    이렇게 번호 등을 통해 구별하는 것을 버전이라고 한다.
    깃에서도 문서를 수정할 때마다 버전을 만들면서 이전 상태와 구별한다.

    스테이지와 커밋
        작업 트리 (working tree)
            파일 수정, 저장 등의 작업을 하는 디렉토리
            깃 저장소를 만들때 mkdir 디렉토리명 중에 디렉토리명이 해당된다.
            즉, 우리 눈에 보이는 디렉토리이다.
        
        스테이지 (stage)
            버전으로 만들 파일이 대기하는 곳.
            스테이징 영역 (staging area)이라고도 한다.
            예를 들어 작업 트리에서 파일 10개를 수정 했는데, 4개만 버전으로 만들려면 이 파일 4개만 스테이지로 넘겨주면 된다.
            눈에 보이지 않는다.
        
        저장소 (repository)
            스테이지에서 대기하고 있던 파일들을 버전으로 만들어 저장하는 곳.
            눈에 보이지 않는다.
    
    작업 트리에서 문서 수정하기
        git bash를 사용해서 작업 트리로 이동한 뒤 git status 명령어를 사용하면 아래와 같은 세 줄이 출력된다.
            On branch main : 현재 main 브랜치에 있다.
            No comits yet : 아직 커밋한 파일이 없다
            nothing to commit : 현재 커밋할 파일이 없다.

        작업트리에서 vim을 사용해 새로운 파일을 만들고 저장한다.
            vim 파일명

        다시 git status 명령어를 사용하면 다음과 같은 내용이 추가되어 출력된다.
            untracked files : 깃에서 버전을 아직 한 번도 관리하지 않은 파일을 말한다
    
    수정한 파일을 스테이지에 올리기 - git add
        작업트리에서 파일을 만들거나 수정했다면 스테이지에 수정한 파일을 추가한다.
            이것을 스테이징 또는 스테이지에 올린다 라고 표현한다.
            스테이징 내용은 .git/index 파일에 저장됨으로 스테이징을 인덱스에 등록한다 라고도 한다.
        
        스테이징에 사용하는 명령어는 git add 이다.
        터미널에 다음과 같이 입력한다.
            git add 파일명
            git add . (작업 트리에서 수정한 파일 전부를 스테이지에 올린다.)
        
        다시 git status 명령어를 사용하면 아래와 같은 내용이 출력된다.
            Changes to be committed:
                (use "git rm --cached <file>..." to unstage)
                    new file: 파일명
        
        윈도우에서 스테이징시 생기는 경고
            윈도우에서 편집한 문서를 저장하면 줄 바꿈 자리에 CR 문자와 LF 문자가 삽입 (CRLF 문자) 하지만 리눅스나 맥에선 줄바꿈에서 LF 문자가 삽입
            깃은 자동으로 변환하지만 일단 경고를 띄워준다.
        
    스테이징한 파일 커밋하기 - git commit
        파일이 스테이징 영역에 있다면 이제 버전을 만들 수 있다.
        버전을 만드는 것을 깃에서는 커밋(commit)한다고 한다.
        커밋할 때는 버전의 변경 사항을 확인할 수 있도록 메세지를 함께 기록해야 한다.

        커밋 명령 커맨드는 git commit 이다. 그리고 -m 옵션을 추가해 커밋과 함께 저장할 메세지를 적는다
            git commit -m "변경사항"
        
        커밋 후 결과 메세지를 보면
            n file changed, n insertion (+)
            create mode 
        과 같이 나타난다

        커밋한 후 git status 를 사용하면 다음과 같은 내용이 출력된다.
            On branch main
            nothing to commit, working tree clean
            > 버전으로 만들 파일 없고 (nothing to commit), 작업트리도 수정사항 없이 깨끗하다 (working tree clean)
        
        버전이 제대로 만들어졌는지 확인 할 때에는 git log 커맨드를 사용한다.
        커밋한 버전을 설명하는 정보가 나타난다.
            커밋을 만든 사람, 시간, 커밋 메세지가 함게 보인다.
    
    스테이징과 커밋 한번에 처리하기 - git commit -am
        수정한 내용을 스테이지에 올리는 동시에 커밋까지 할 수 있다.
        -am 옵션 (-a: all, -m: message)을 사용한다.
        이 방법은 한 번이라도 커밋 한 적이 있는 파일을 다시 커밋할 때만 사용 할 수 있다.
            git commit -am "message"
        스테이징과 커밋 과정이 한번에 보인다.
            git log
        커밋한 버전과 정보를 확인한다.

커밋 내용 확인하기
    커밋 기록 자세히 보기 - git log
        커밋했던 기록을 살펴보는 명령어.
        지금까지 만든 버전과 각 버전별 설명이 출력된다.
        git log 명령을 입력했을 때 나오는 정보를 묶어 커밋 로그 라고 한다.

        커밋 해시 (commit hash) 또는 깃 해시 (git hash)
            커밋을 구별하는 아이디.
            커밋 해시 마지막엔 (HEAD -> main) 이라고 써져있는데 이 버전이 가장 최신이라는 표시이다.

    변경 사항 확인하기 - git diff
        작업 트리에 있는 파일과 스테이지에 있는 파일 비교
        스테이지에 있는 파일과 저장소에 있는 최신 커밋을 비교해서 수정한 파일을 커밋하기 전에 최종 검토

        파일을 수정하고 저장한 뒤 git status 명령어를 사용하면
            changes not staged for commit:
                modified: 파일명
        파일명 파일이 수정되었고 아직 스테이징 상태가 아니다.

        이때 git diff를 사용한다.
            빨간색으로 - 내용 부분이 삭제되었다는 뜻
            초록색으로 + 내용 부분이 추가되었다는 뜻

        비교후 수정 내용을 버전으로 만들려면 커밋하고
        수정 내용을 버리려면 git restore 명령을 사용한다.

버전 만드는 단계마다 파일 상태 알아보기
    git에서는 버전을 만드는 단계마다 파일 상태가 달라진다.

    tracked 파일 untracked 파일
        git status 명령을 사용하면 파일 상태와 관련된 메세지가 나타난다.
        작업 트리에 있는 파일은 tracked 상태와 untracked 상태로 나뉜다.
        tracked - git 저장소에 올라가있는 파일
        untracked - 새로 생성되어 저장소에 이력이 없는 파일

        파일을 모두 스테이지에 올리고 git status를 확인하면
        tracked 파일은 
            modified: 파일명 
        untracked 파일은 
            new file: 파일명 
        으로 표시된다

        커밋과 관련된 파일까지 함께 살펴보려면 git log --stat 명령어를 사용한다.
        --stat 옵션은 statics (통계)의 줄임말이다.
        가장 최근 커밋부터 순서대로 커밋 메세지와 관련 파일이 나열된다.
    
    .gitignore 파일로 버전관리에서 제외할 수 있다.
        한 디렉토리 안에서 버전 관리를 하지 않을 파일이나 디렉토리가 있다면 .gitignore 파일을 만들어 목록을 지정할 수 있다.
    
    unmodified, modified, stage 상태
        unmodified - working tree clean - 현재 작업 트리에 있는 모든 파일에 아무 변경 사항이 없다.
        modified - changes not staged for commit - 파일이 수정만 된 상태
        stage - changes to be committed - git add 명령을 사용해 변경된 파일을 스테이지에 올린 상태
        커밋하고 나면 unmodified 상태로 돌아간다.
    
    방금 커밋한 메시지 수정하기
        문서의 수정 내용을 기록해 둔 커밋 메세지를 잘못 입력했다면 커밋을 만들자마자 즉시 수정 할 수 있다.
        가장 최근 커밋 메세지를 수정하려면 git commit --amend 커맨드를 사용한다.
        명령어를 입력하면 기본 편집기가 실행되면서 원래 커밋 메세지가 화면 위쪽에 나타난다. i를 눌러 입력 모드로 바꾸면 메세지를 수정 할 수 있다.
        ex 모드로 돌아가 문서를 저장하고 종료한다.

작업 되돌리기
    git restore - 작업 트리에서 수정한 파일 되돌리기
    git restore --staged 파일명 - 스테이징 되돌리기
    git reset HEAD^ - 최신 커밋 되돌리기, 커밋을 취소하고 unstaged 상태로 작업 디렉토리에 보관
    git reset --soft HEAD^ - 커밋을 취소하고 파일을 staged 상태로 작업 디렉토리에 보관
    git reset --mixed HEAD^ - 커밋을 취소하고 파일을 unstaged 상태로 작업 디렉토리에 보관

    git reset --hard 되돌릴 버전의 해시 - 특정 커밋 (해시)로 되돌리기
    git revert 되돌릴 버전의 해시 - 특정 커밋으로 되돌릴 때 수정했던 것을 삭제해도 된다면 git reset을 사용해도 되지만, 나중에 사용할 것을 대비해서 기록을 남겨두려면 변경 사항만 취소하고 커밋은 남겨둘 수 있다. 명령어를 실행하면 커밋 메세지를 입력 할 수 있다. 커밋 메세지 맨 위에는 어떤 버전을 revert 했는지 나타난다. 커밋을 취소하면서 남겨 둘 내용을 입력하고 저장한다.

브랜치 (branch)
    깃으로 버전 관리를 시작하면 기본적으로 main 브랜치가 만들어진다.
    사용자가 커밋할 때 마다 main 브랜치는 어떤 게 최신 커밋인지 정보를 가진다.
    브랜치는 커밋을 가리키는 포인터와 비슷하다고 생각하면 된다.

    새 브랜치를 만들면, 기존 파일은 main 브랜치에 그대로 유지하면서, 새 브랜치에서 기존 파일 내용을 수정하거나 새로운 기능을 추가할 수 있다.
    이렇게 main 브랜치에서 새 브랜치를 만드는 것을 분기(branch)한다 라고 한다.

    기능 개발용 브랜치 (Feature Branch)
        목적: 새로운 기능(로그인, 결제 등)을 만들 때 사용
        기능이 완성되면 main에 합치고(Merge) 삭제하는 일회성 브랜치

    유지 보수 / 고객사별 브랜치
        롱러닝 브랜치 (Long running Branch) 혹은 릴리즈 브랜치
        목적: 제품은 하나인데 고객사별로 커스텀이 필요할 때 사용
        main은 순수한 기본 공통 제품만 유지, 고객사 브랜치는 삭제되지 않고 계속 유지

        main, A사, B사 가 있을때 A사나 B사 기능을 가져오고 싶을땐?
        1. 아예 공통 기능으로 격상 시키기 (브랜치의 기능이 너무 좋아 통합 시키고 싶을 때)
        2. 고객사 브랜치끼리 합치기 (소스코드를 브랜치끼리 통합)
        3. 체리픽 (Cherry Pick) - 필요한 부분만 뽑아서 브랜치에 합치기

브랜치 만들기 및 이동하기
    main 브랜치 만들기
        깃 저장소를 만들 위치에 원하는 폴더명으로 폴더명을 생성한다.
            mkdir 폴더명

        생성한 폴더로 이동한다
            cd 폴더명

        깃 저장소를 지정한다
            git init
        
        디렉토리를 따로 만들지 않고 git init 명령어로 디렉토리를 만들고 깃 저장소를 만들 수 있다.
            git init 만들려는 디렉토리명
        혹은 디렉토리 이동을 하지 않고 깃 저장소를 만들 수 있다.
            git init 디렉토리명을 포함한 디렉토리 경로
    
    새 브랜치 만들기
        깃에서 브랜치를 만들거나 확인하는 명령은 git branch 이다.
            git branch
            - git init을 실행한 폴더에서 git branch 커맨드를 실행하면 현재 branch의 정보가 뜬다.
        
        폴더 이동을 하지 않고 git branch 만들려는 브랜치 이름 을 적고 실행한다.
            git branch 만들려는 브랜치 이름

        그리고 다시 git branch로 현재 branch의 정보를 확인한다.
        그러면 
              만들려는 브랜치 이름
            * main
        과 같이 두개의 브랜치가 표시된다. main 앞에 *은 현재 작업하는 브랜치를 나타낸다.

        git log 명령을 사용하면 커밋 해시 끝 부분에 (HEAD -> main) 이었던 부분이
        (HEAD -> main, 만들려는 브랜치 이름) 으로 바뀌어 있다.
        여기서 HEAD -> 는 현재 작업하는 브랜치를 가리킨다.
    
    새 커밋을 추가하면?
        메인 브랜치에서 커밋을 한 뒤에 새로 브랜치를 만들었다면
        git log로 현재 커밋을 확인했을 때 커밋 해시 끝부분에 main 브랜치 뿐만 아니라 만들어둔 브랜치가 모두 표시된다. 이 뜻은 main뿐만 아니라 모든 브랜치의 최신 커밋이 같다는 것을 의미한다.

        여기서 새로 커밋을 하면 현재 작업중인 브랜치 (이동하지 않았다면 현재는 main)에만 커밋이 된다.
            이때 git log --oneline 을 사용하면 한줄에 한 커밋씩 보여준다.
        최신 커밋은 main 브랜치에만 적용되어 있고, 다른 브랜치는 이전 커밋 상태이다.
    
    브랜치 전환하기 - git switch
        브랜치가 여러 개라면 각각 서로 다른 커밋을 만들 수 있다. 그러기 위해선 브랜치를 오가면서 작업 할 수 있어야 한다.
        현재 브랜치에서 다른 브랜치로 이동하는 것을 브랜치를 전환한다 라고 하고 git switch를 사용한다 (git checkout도 사용 가능 하다.)

        git switch 이동할 브랜치 명
            커맨드 헤드 마지막 부분에 main 대신 이동된 브랜치 명이 표시된다.
        
-------------------------------------------------------------------------------------

    브랜치 정보 확인하기
        이동한 브랜치에서 작업을 하고 커밋을 한 뒤 git log --oneline을 사용하여 확인한다. 한 줄에 한 커밋을 확인 할 수 있다


    브랜치와 커밋 관계 알아보기
        git log 명령을 사용 할 때 --branches 옵션을 추가하면 브랜치마다 최신 커밋을 한눈에 살펴 볼 수 있다.
        이 명령어를 사용하면 각 브랜치의 커밋 상황을 확인 할 수 있다
            git log --oneline --branches
        
        git log --oneline --all
            --all 옵션은 최신 커밋 뿐 아니라 모든 커밋을 다 보여주기 위한 옵션이다.
        
        git log 명령어에 --graph 옵션을 추가하면 브랜치와 커밋 관계를 좀 더 보기 쉽게 그래프로 표시 할 수 있다.
            git log --oneline --branches --graph
        
    브랜치 사이의 차이점 살펴보기
        브랜치마다 커밋이 쌓이면 브랜치 사이에 어떤 차이가 있는지 확인하기 어렵다. 이럴때는 git log 명령에서 브랜치 이름 사이에 마침표 2개 (..)를 넣는 명령으로 브랜치 간의 차이를 쉽게 확인 할 수 있다.
            git log main..브랜치명
        
        반대로 브랜치에서 main과 비교 할 수 있다.
            git log 브랜치명..main

브랜치 병합하기
    브랜치 작업을 마무리하고 기존 브랜치와 합치는 것을 브랜치 병합 (merge)이라고 한다.

    * 서로 다른 파일 병합하기
        병합을 원하는 브랜치에서 git merge 명령어 뒤에 가져올 브랜치 이름을 적는다
            git merge 가져올브랜치 이름
        
        명령어를 실행하면 빔이 자동으로 실행되면서 Merge branch o2 라는 커밋 메세지가 나타난다.
        커밋을 수정해도 되고, 그대로 사용해도 된다.

        ls -al로 파일을 확인한다

        git log --oneline --branches --graph 명령어로 브랜치와 커밋이 어떻게 병합되었는지 확인 할 수도 있다.
    
    * 서로 다른 브랜치에서 한 문서의 다른 부분을 수정 했을 때 병합하기
        병합을 원하는 브랜치에서 git merge 명령어를 사용해 가져올 브랜치 이름을 적는다.
            git merge 가져올브랜치 이름
        
        빔이 자동으로 실행되며 커밋 메세지가 나타난다.
        메세지를 수정해도 되고, 그대로 사용해도 된다.

        터미널 창에 Auto-merging (문서명) 으로 시작하는 병합 완료 메세지가 나타난다.
        브랜치의 문서와 메인의 문서가 자연스럽게 하나의 파일에 합쳐진다.

        서로 다른 위치를 수정 했을 경우 자동으로 합쳐주는 기능이 있다.
    
    * 서로 다른 브랜치에서 한 문서의 같은 부분을 수정했을 때 병합하기
        병합을 원하는 브랜치에서 git merge 명령어를 사용해 가져올 브랜치 이름을 적는다.
            git merge 가져올브랜치 이름
        
        이전에 git merge를 실행했을 땐 자동으로 빔이 열렸지만, 이번엔 열리지 않고 경고 메세지가 나타난다.
        문서를 자동병합 하는 동안 충돌이 발생했다는 뜻이다.

        충돌이 생긴 문서는 자동으로 병합될 수 없으므로 사용자가 충돌 부분을 직접 해결한 후 커밋해야 한다.
        충돌이 생긴 문서를 열어보면
            <<<<<< HEAD
            병합을 원하는 브랜치에서 수정한 내용
            ========
            가져 올 브랜치에서 수정한 내용
            >>>>>> 브랜치명
        으로 나타난다.
        
        a나 i, insert를 눌러 문서의 내용을 원하는 형태로 수정한다.
        수정이 끝나면 문서에 있던 <<<<<< ====== >>>>>> 내용을 삭제한다.

        수정한 문서를 스테이지에 올리고 커밋하면 된다.

        git log --oneline --branches --graph 명령어를 통해 브랜치와 커밋관계를 확인한다.
    
    * 병합이 끝난 브랜치 삭제하기
        git branch를 사용하면 현재 저장소에 어떤 브랜치가 있는지 확인 할 수 있다.
        저장소의 기본 브랜치는 main (혹은 master) 이므로 브랜치를 삭제하려면 main 브랜치에서 해야한다.
            git switch main
        
        브랜치를 삭제할 때는 git branch 명령어 -d 옵션을 추가한 뒤 그 뒤에 삭제할 브랜치 이름을 적는다
            git branch -d 삭제할브랜치명
        
        Deleted branch 삭제할브랜치명 처럼 메세지가 나타나면 브랜치 삭제를 성공한 것.
    
    * cherry-pick으로 병합하기
        브랜치 전체를 합치는게 아니라, 특정 버전의 변경 내용만 합치려고 할 때 사용하는 기능이다.
            1, 2, 3 변경사항중에 2번을 가져오면 2번 변경사항만 가져온다. 2번보다 이전 버전이라고 1번을 함께 가져오진 않는다.
            1번 3번을 가져오고 싶다면, 1번 3번 해시를 동시에 적는다.

        병합할 브랜치에서 git cherry-pick 명령어를 사용해
            소스를 가져올 브랜치의
            가져오고 싶은 커밋의 해시를 적는다
        
            git cherry-pick 체리픽할해시
        
        ls를 사용해 파일이 가져와 졌는지 확인한다.

        git log --oneline --all --graph를 사용해 커밋도 확인한다.

    * 특정 파일만 가져오고 싶을 때
        git 2.23 이상(권장)
            git restore --source <커밋ID> <파일경로>
        이전버전
            git checkout <커밋ID> -- <파일경로>
        이 명령어는 해당 파일이 스테이징 영역과 워킹디렉토리에 반영된다, 이후 git commit으로 직접 커밋

        git cherry-pick -n 사용 (커밋 이력 활용)
            자동커밋 끄고 체리픽, -n 또는 --no-commit 옵션은 변경 사항만 워킹디렉토리에 스테이징하고 커밋은 생성하지 않는다.
                git cherry-pick -n <커밋ID>
            
            원하지 않는 파일 제외 (되돌리기)
                git restore --staged <제외할 파일 경로>
                git restore <제외할 파일 경로>
            
            원하는 파일만 남기고 커밋
                git commit -m "특정 파일만 체리픽 완료"
