## 1단계 (M07): SQL로 집계하기

데이터 분석의 첫걸음은 **묶어서 세고 더하는 것**이다. 8장의 `GROUP BY`, `HAVING`을 그대로 쓴다.

### 1.1 실습 데이터

```sql
CREATE TABLE sale (
  id       INT PRIMARY KEY,
  store    VARCHAR(20) NOT NULL,
  amount   INT NULL,           -- 아직 집계되지 않은 행은 NULL
  sold_on  DATE NOT NULL
);

INSERT INTO sale VALUES
 (1,'서울',1200,'2026-01-03'),(2,'서울',800,'2026-01-05'),(3,'서울',NULL,'2026-01-09'),
 (4,'부산',3400,'2026-01-04'),(5,'부산',600,'2026-02-10'),(6,'대구',800,'2026-02-11');
```

### 1.2 매장별 집계

```sql
SELECT store,
       COUNT(*)        AS rows_all,
       COUNT(amount)   AS rows_with_amount,
       SUM(amount)     AS total,
       ROUND(AVG(amount), 1) AS avg_amount
FROM sale
GROUP BY store
ORDER BY store;
```

**실행 결과 (MySQL 8.0 확인)**

| store | rows_all | rows_with_amount | total | avg_amount |
|---|---|---|---|---|
| 대구 | 1 | 1 | 800 | 800.0 |
| 부산 | 2 | 2 | 4000 | 2000.0 |
| 서울 | 3 | 2 | 2000 | 1000.0 |

**읽는 법**

- 서울의 `rows_all`은 3, `rows_with_amount`는 2다. `COUNT(*)`는 행을 세고, `COUNT(amount)`는 NULL이 아닌 값만 센다(7·8장 복습).
- `AVG(amount)`는 NULL을 **빼고** 계산한다. 서울의 평균은 (1200 + 800) / 2 = 1000이다. NULL을 0으로 보고 3으로 나누면 667이 되어 틀린다.

### 1.3 월별 집계와 HAVING

```sql
SELECT DATE_FORMAT(sold_on, '%Y-%m') AS ym,
       SUM(amount) AS total
FROM sale
GROUP BY ym
HAVING SUM(amount) >= 1000
ORDER BY ym;
```

| ym | total |
|---|---|
| 2026-01 | 5400 |
| 2026-02 | 1400 |

`WHERE`는 **묶기 전**의 행을 거르고, `HAVING`은 **묶은 뒤**의 결과를 거른다. 합계 조건은 `HAVING`에 써야 한다.

### 1.4 전체 평균과 행 수

```sql
SELECT AVG(amount) AS avg_all, COUNT(*) AS n
FROM sale
WHERE amount IS NOT NULL;
```

| avg_all | n |
|---|---|
| 1360.0000 | 5 |

(1200 + 800 + 3400 + 600 + 800) / 5 = 1360. 6행 중 NULL 한 개를 제외한 5행으로 계산했다.

## 2단계 (M16 전후): 기술 통계

**기술 통계**는 데이터를 요약하는 수치다. 대표값과 흩어진 정도를 함께 본다.

| 지표 | 뜻 | 주의 |
|---|---|---|
| 평균 (mean) | 합 / 개수 | 이상치에 크게 흔들린다 |
| 중앙값 (median) | 정렬했을 때 가운데 값 | 짝수 개면 가운데 두 값의 평균 |
| 분산 (variance) | 평균과의 차이 제곱의 평균 | 단위가 제곱이 된다 |
| 표준편차 (sd) | 분산의 제곱근 | 원래 단위로 돌아온다 |

### 2.1 검증한 계산

```java
double[] xs = {2, 4, 4, 4, 5, 5, 7, 9};
double mean = Arrays.stream(xs).average().orElse(Double.NaN);             // 5.0
double variance = Arrays.stream(xs)
        .map(x -> (x - mean) * (x - mean)).sum() / xs.length;              // 4.0 (모분산)
double sd = Math.sqrt(variance);                                           // 2.0
double median = (xs[3] + xs[4]) / 2;                                       // 4.5
```

이 계산은 Batch4 검증에서 평균 5, 모분산 4, 표준편차 2, 중앙값 4.5로 일치했다.

**모분산과 표본분산**: 데이터가 전체라면 `n`으로 나누고(모분산), 일부 표본으로 전체를 추정하면 `n − 1`로 나눈다(표본분산). 위 예제는 전체 8개를 다 가진 것으로 보고 모분산을 계산했다.

## 3단계 (M17): 해석의 함정

| 함정 | 예 | 막는 법 |
|---|---|---|
| 표본이 작다 | 3명 설문으로 "전체의 90%가 만족" | 신뢰구간(53장)과 표본 크기를 함께 보고한다 |
| 이상치가 평균을 끈다 | 연봉 평균에 임원 한 명 | 중앙값도 함께 본다 |
| 상관은 인과가 아니다 | 아이스크림 판매와 익사 사고 | 교란 변수를 확인한다 |
| 평균만 보고 분포를 안 본다 | 평균 50점이지만 0점과 100점이 반반 | 분포나 표준편차를 함께 본다 |
| 기간을 섞는다 | 1월 데이터와 2월 데이터를 같은 척도로 비교 | 같은 기간 기준으로 맞춘다 |

## 4. pandas

pandas는 Python에서 표 형식 데이터를 다루는 라이브러리다. SQL의 `GROUP BY`와 대응한다.

```python
import pandas as pd

df = pd.DataFrame({
    "store": ["서울", "서울", "서울", "부산", "부산", "대구"],
    "amount": [1200, 800, None, 3400, 600, 800],
})

print(df.groupby("store")["amount"].agg(["count", "sum", "mean"]))
```

| SQL | pandas |
|---|---|
| `GROUP BY store` | `groupby("store")` |
| `COUNT(amount)` | `count` (NaN은 제외됨) |
| `SUM(amount)` | `sum` |
| `AVG(amount)` | `mean` (NaN은 제외됨) |

**주의:** pandas의 `count`는 NaN을 세지 않는다. SQL의 `COUNT(*)`에 해당하는 것은 `size`다. 실행 결과 `count`는 서울 2, 부산 2, 대구 1이고 `size`는 서울 3이다. 평균과 합계는 1.2의 SQL 결과와 같다.

## 고객 등급 분석: RFM과 NTILE 윈도우 함수 (2026-11-24 보강, MySQL 8.0에서 확인함)

**출처**: 선생님 자료 `FinalTeamProject☆/tutorial_project/CrmTutorial.html`(단골 고객 관리 CRM, 대시보드의 RFM 표)의 SQL과 등급 규칙을 정리했다. 등급 규칙은 자료의 주석과 테스트 예시에서 보이는 부분만 옮겼다. 자료의 등급 함수 나머지 부분은 확인하지 못했다.

**RFM 정의**
- **R (Recency, 최근성)**: 마지막 방문일이 얼마나 가까운가
- **F (Frequency, 빈도)**: 방문 횟수가 얼마나 많은가
- **M (Monetary, 금액)**: 결제 합계가 얼마나 큰가

세 값을 각각 **1~5점**으로 나눈다. 5점이 가장 좋다. 점수를 매기는 데 `NTILE(5)` 윈도우 함수를 쓴다. 정렬한 순서대로 고객을 5묶음으로 나눠 번호를 붙인다.

```sql
SELECT t.customer_id, c.name, t.last_visit, t.visit_count, t.total_amount,
       NTILE(5) OVER (ORDER BY t.last_visit ASC)   AS r_score,
       NTILE(5) OVER (ORDER BY t.visit_count ASC)  AS f_score,
       NTILE(5) OVER (ORDER BY t.total_amount ASC) AS m_score
FROM (SELECT v.customer_id, MAX(v.visited_at) AS last_visit,
             COUNT(*) AS visit_count, SUM(v.amount) AS total_amount
      FROM visit v JOIN customer c2 ON c2.id = v.customer_id
      WHERE c2.store_id = 1
      GROUP BY v.customer_id) t
JOIN customer c ON c.id = t.customer_id
ORDER BY t.total_amount DESC;
```

**확인 결과 (샘플 고객 10명, 방문 16건, 확인함)**

| 고객 | 최근 방문 | 방문 수 | 결제 합계 | R | F | M |
|---|---|---|---|---|---|---|
| c5 | 11-24 | 3 | 210000 | 5 | 5 | 5 |
| c1 | 11-20 | 3 | 120000 | 4 | 5 | 5 |
| c9 | 11-19 | 1 | 45000 | 4 | 3 | 4 |
| c3 | 11-18 | 2 | 45000 | 3 | 4 | 4 |
| c10 | 11-21 | 2 | 34000 | 5 | 4 | 3 |
| c6 | 11-05 | 1 | 15000 | 2 | 2 | 3 |
| c2 | 10-01 | 1 | 10000 | 2 | 2 | 2 |
| c7 | 11-12 | 1 | 9000 | 3 | 3 | 2 |
| c4 | 09-01 | 1 | 5000 | 1 | 1 | 1 |
| c8 | 08-10 | 1 | 3000 | 1 | 1 | 1 |

**주의**: 같은 값이 여러 명이면(예: c3과 c9의 결제 합계 45000) `NTILE`의 순서가 정해지지 않는다. 그래서 점수가 실행마다 달라질 수 있다. 정확히 하려면 정렬 기준에 고객 번호 같은 **보조 키**를 추가한다.

**등급 규칙 (자료 기준)**
- R이 1~2이고 F가 3 이하이면 **이탈 위험**
- R+F+M 합계가 13 이상이면 **VIP**
- 합계가 10 이상이면 **단골**
- 나머지는 **일반**

자료의 테스트 예시와 맞는다: `(5,5,5)`는 VIP, `(4,3,3)`은 단골, `(1,2,5)`는 이탈 위험, `(3,2,2)`는 일반. 위 표에 적용하면 c5와 c1은 VIP, c9·c3·c10은 단골, c6·c2·c4·c8은 이탈 위험, c7은 일반이다.

**읽는 법**: 점수는 **고객끼리의 상대 순위**다. 모든 고객이 좋아도 가장 나쁜 묶음은 1점을 받는다. 그래서 등급은 절대 기준이 아니라 현재 데이터 안의 비교다.

**면접 기준**: "고객 등급은 최근성, 빈도, 금액을 NTILE로 나눠 점수를 매기고, 합계로 등급을 정하는 RFM 분석입니다. 같은 값의 순서가 정해지지 않으므로 보조 키를 두고, 점수는 상대 순위라는 점을 설명합니다."
