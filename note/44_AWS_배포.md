## 1. 컴퓨팅·DB·네트워크

**정의** — 클라우드 컴퓨팅은 필요에 따라 네트워크로 컴퓨팅 자원을 제공받는 모델이다. 서버·DB·네트워크·스토리지 자원은 서로 다른 책임을 갖는다.

**목적과 책임** — 애플리케이션 실행과 데이터 지속성·접근 경로를 구성한다.

**구별해야 할 개념 / 흔한 오해** — 퍼블릭 IP가 있다고 서비스가 안전하게 공개된 것은 아니다.

**실행·처리 흐름** — DNS → 네트워크 규칙 → 서버 → 앱 → DB

**직접 구현·검증** — 서버·DB 연결을 그림으로 그리고 허용 포트 최소화. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 보안 그룹/방화벽은 무엇을 제어하는가?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

### 깊이 이해하기 — 개념의 경계와 설계 판단

클라우드 컴퓨팅 자원은 애플리케이션 실행 환경, 관리형 DB는 데이터 저장·운영 기능, 네트워크는 서비스 간 통신 경로를 제공한다. 보안 그룹은 네트워크 접근 규칙을 제어하며 애플리케이션 인증을 대신하지 않는다.

### 직접 읽고 구현하는 독립 예제

```text
Browser --HTTPS--> Load Balancer/Server
                         |
                         +--> App --> DB (private network)
```


### 실행 검증 체크포인트

서버와 DB의 인바운드 규칙을 구분하고 DB의 공용 접근 필요성을 검토한다.

### 스스로 작성할 변형 실습

서버에 접속되지 않을 때 DNS·포트·방화벽·애플리케이션 로그 순서로 점검한다.

### 면접 답변의 기준 문장

> 컴퓨팅은 실행, DB는 영속 저장, 네트워크는 연결을 담당하며 각 보안 경계가 다릅니다.


### 정의를 읽고 넘어가지 않기 — 능동 확인

**1차: 정확한 문장 완성.** 다음 문장을 보지 않고 스스로 말한다. *“클라우드 컴퓨팅은 필요에 따라 네트워크로 컴퓨팅 자원을 제공받는 모델이다. 서버·DB·네트워크·스토리지 자원은 서로 다른 책임을 갖는다.”* 문장 속 주요 용어를 각각 설명하지 못하면 정의를 외운 것이 아니라 읽은 것이다.

**2차: 경계 구분.** 다음 설명이 어떤 오해를 막는지 자기 말로 설명한다. *“퍼블릭 IP가 있다고 서비스가 안전하게 공개된 것은 아니다.”* 반례를 하나 만들어 본다.

**3차: 면접 재현.** *“보안 그룹/방화벽은 무엇을 제어하는가?”*에 대해 **정의 → 왜 필요한가 → 무엇과 다른가 → 코드·상황 하나** 순서로 30~60초 말한다. 답을 읽지 않고 말한 뒤 원문과 대조한다.

## 2. 배포·모니터링·백업

**정의** — 배포는 빌드 결과를 실행 환경에 반영하는 과정이고 모니터링은 상태·성능·오류를 관찰하는 활동이다. 백업은 복구 가능한 데이터 사본을 보존한다.

**목적과 책임** — 변경 실패의 영향과 데이터 손실을 줄인다.

**구별해야 할 개념 / 흔한 오해** — 서버가 기동했다는 사실만으로 정상 배포가 검증된 것은 아니다.

**실행·처리 흐름** — 빌드 → 테스트 → 배포 → 헬스 체크 → 로그 확인 → 롤백 대비

**직접 구현·검증** — /health 확인, 오류 로그 점검, DB 백업 복원 계획 작성. 실행 결과를 캡처하거나 테스트 로그로 남기고, 예상과 실제 결과가 다르면 이유를 기록한다.

**면접 질문** — 운영 배포 후 반드시 검증할 항목은?

**30초 답변 연습** — 위 정의를 첫 문장으로 말하고, 목적·구별점·실제 예시 순서로 3~4문장으로 설명한다.

배포는 검증된 빌드를 실행 환경에 적용하는 과정이다. 모니터링은 상태와 이상 징후를 관찰하고 백업은 장애·삭제 후 복구할 수 있도록 데이터를 별도로 보존하는 작업이다. 백업 파일 존재만으로 복구 가능성을 증명할 수 없다.

### 직접 읽고 구현하는 독립 예제



### 실행 검증 체크포인트

배포 전후 헬스체크와 롤백 조건을 문서화한다.

백업 복원 테스트에서 RPO와 RTO를 어떻게 확인할지 설계한다.

### 면접 답변의 기준 문장

> 배포는 실행 버전 변경, 모니터링은 상태 관찰, 백업은 복구 가능성 확보입니다.

# 핵심 개념을 오해 없이 이해하기 위한 기초 연결

## 필수 기초 연결: 개발 환경과 배포 환경의 경계

로컬에서 DB 접속이 성공했다는 사실은 배포 환경의 네트워크 경로, 보안 그룹, DB 사용자 권한, 환경 변수, TLS 구성이 정상이라는 증거가 아니다. EC2는 컴퓨팅 자원, RDS는 관리형 관계형 DB 서비스, 보안 그룹은 인바운드/아웃바운드 트래픽 규칙을 관리한다. **인증 정보가 맞음**과 **네트워크 접근 가능**은 서로 다른 조건이다.

**점검 순서:** (1) DNS 이름 해석 (2) 대상 호스트·포트 연결 (3) TLS 설정 (4) DB 인증 (5) 스키마·권한 (6) 애플리케이션 쿼리. 실패 로그를 구분하여 기록한다.

**실습:** 실제 클라우드 비용이 들지 않도록 로컬 Docker 또는 테스트 환경에서 DB 포트를 차단한 경우와 비밀번호가 틀린 경우의 오류 메시지를 비교한다. 운영 보안 그룹을 무분별하게 `0.0.0.0/0`으로 열지 않는다.

## 개념 경계 정밀 보강 — 실제 코드에서 헷갈리는 지점


### 경계 1. 서버 / EC2 / RDS / DB

**흔한 오해:** “EC2가 데이터베이스 그 자체다”

**정확한 구분:** EC2는 가상 서버 컴퓨팅 서비스, RDS는 관리형 관계형 DB 서비스다. EC2에 DB를 직접 설치할 수도 있지만 서비스 역할은 구분해야 한다.

**코드·명령 해석:**

```bash
브라우저 → EC2(Spring Boot) → RDS(MySQL)
```

**확인 방법:** 애플리케이션 포트와 DB 포트를 각각 어디서 열어야 하는지 구분한다.

**직접 구현:** DB를 인터넷 전체에 공개하지 않는 네트워크 구성을 그려라.

**면접 점검:** “서버 / EC2 / RDS / DB”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 2. 배포 / 실행 / 운영

**흔한 오해:** “로컬에서 실행되면 배포가 완료된 것이다”

**정확한 구분:** 로컬 실행은 개발 환경 검증이다. 배포는 운영 환경에 산출물을 설치·설정·시작하는 과정이며 운영은 모니터링·백업·복구·보안 등을 포함한다.

**코드·명령 해석:**

```bash
java -jar app.jar --spring.profiles.active=prod
```

**확인 방법:** 환경 변수, 방화벽, DB 접근, 로그, 재시작 정책을 별도 점검한다.

**직접 구현:** 운영 배포 전후 체크리스트를 작성하라.

**면접 점검:** “배포 / 실행 / 운영”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.


### 경계 3. 보안 그룹 / 방화벽 / HTTPS

**흔한 오해:** “HTTPS를 쓰면 DB 포트를 공개해도 안전하다”

**정확한 구분:** HTTPS는 전송 구간의 암호화/서버 인증에 기여한다. 보안 그룹은 네트워크 접근 규칙이다. DB 공개 범위와 계정 권한은 별도로 제한해야 한다.

**코드·명령 해석:**

```bash
인바운드: 443 → 웹 공개 / 3306 → 애플리케이션 서버에서만
```

**확인 방법:** 보안 그룹의 인바운드/아웃바운드 규칙을 구분한다.

**직접 구현:** 운영 DB 접속 허용 대상을 최소화하라.

**면접 점검:** “보안 그룹 / 방화벽 / HTTPS”의 각 용어를 각각 정의하고, 위 코드에서 어느 계층·시점·값에 해당하는지 60초 안에 설명해 보자.

## 3. 컨테이너, IaC, 쿠버네티스 개념

- **컨테이너:** 앱과 실행 환경을 한 덩어리로 묶는다. Dockerfile로 이미지를 만들고, 이미지를 실행하면 컨테이너가 된다. "내 컴퓨터에서는 되는데"를 줄이는 방법이다.
- **Docker Compose:** 앱과 MySQL 같은 여러 컨테이너를 한 파일로 함께 띄운다.
- **IaC (Terraform):** 서버, 네트워크(VPC), 보안 그룹을 코드로 선언한다. `plan`으로 바뀔 내용을 미리 보고, `apply`로 적용한다.
- **Kubernetes:** 여러 컨테이너를 여러 서버에 나눠 배치하고, 죽으면 다시 띄운다. 기본 개념은 Pod(실행 단위), Deployment(원하는 개수 유지), Service(접근 주소)다.
- **로드밸런서와 HSRP/VRRP 비교:** ALB나 Nginx는 헬스체크로 정상인 인스턴스에만 요청을 보낸다. HSRP/VRRP는 게이트웨이 주소를 두 장비가 나눠 갖는 이중화 방식이라 목적이 다르다.

### 3-1. Docker 실습: Dockerfile → 이미지 → 컨테이너 (2026-11-23 보강)

**정의**
- **이미지**: 앱과 실행 환경을 담은 읽기 전용 묶음이다. 여러 층(layer)으로 쌓인다.
- **컨테이너**: 이미지를 실행한 인스턴스다. 종료하면 그 안의 변경은 사라진다.

**확인 범위**: 아래 `docker build`, `docker run`, `docker inspect`는 이 PC의 Docker Desktop(29.9.3)에서 실행해 확인했다. 베이스 이미지는 이미 로컬에 있던 `postgres:17`을 썼다. 새 이미지를 내려받지 않았다.

```dockerfile
FROM postgres:17
LABEL course="khac-demo"
COPY hello.txt /hello.txt
```

```powershell
docker build -t khac-demo:1.0 .
docker run --rm khac-demo:1.0 cat /hello.txt
docker inspect khac-demo:1.0 --format '{{index .Config.Labels "course"}}'
docker rmi khac-demo:1.0
```

**실행 결과 (확인함)**

```
hello from image layer
khac-demo
```

- `docker build -t 이름:태그 .`: 현재 폴더의 `Dockerfile`로 이미지를 만든다.
- `docker run --rm`: 실행이 끝나면 컨테이너를 지운다.
- `docker rmi`: 이미지를 지운다.

**Git Bash에서 주의**: Git Bash는 `/hello.txt`를 Windows 경로로 바꿔 버린다. Git Bash에서 컨테이너 안의 절대 경로를 쓸 때는 `MSYS_NO_PATHCONV=1`을 먼저 설정하거나 PowerShell을 쓴다.

**Java 앱을 이미지로 만드는 형태 (미실행)**: 아래는 여러 단계(multi-stage) Dockerfile의 골격이다. 베이스 이미지(`eclipse-temurin`)를 새로 내려받아야 해서 이 PC에서는 실행하지 않았다.

```dockerfile
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY . .
RUN ./gradlew build -x test

FROM eclipse-temurin:21-jre
COPY --from=build /app/build/libs/app.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

**읽는 법**: 빌드 단계에서 JDK로 jar를 만들고, 실행 단계에는 JRE만 복사한다. 최종 이미지가 작아지고 빌드 도구가 들어가지 않는다.

**면접 기준**: "Dockerfile로 이미지를 만들고, 이미지를 실행한 것이 컨테이너입니다. 여러 단계로 빌드해 실행 이미지에는 jar와 JRE만 넣습니다."

### 3-2. Elastic Beanstalk 배포 흐름과 필요한 역할 (2026-11-23 보강, 선생님 자료 기반, 미실행)

**출처**: 선생님 자료 `springboot4☆/12장_AwsBeanstalkDeployTutorial.html`, `12장_S3Upload흐름.html`. 이 PC에서는 AWS 계정에 접속하지 않았다(미실행).

**구성 요소**
- **EC2**: jar가 실행되는 가상 서버
- **Elastic Beanstalk(빈스톡)**: EC2, 보안 그룹, 로드 밸런서 등을 한 화면에서 만들고 jar를 올려 실행해 주는 서비스
- **RDS**: 데이터베이스
- **S3**: 파일 저장소. 버킷 하나가 저장소 한 개다. 블로그 이미지 같은 파일을 여기에 둔다.
- **IAM**: 누가 무엇을 할 수 있는지 정하는 권한 관리. 권한 묶음을 **역할(Role)**이라고 한다.

**역할 2개가 필요하다**

| 역할 이름 | 누가 쓰나 | 사용 사례 |
|---|---|---|
| `aws-elasticbeanstalk-instance-role` | 빈스톡이 만든 EC2 서버 | Elastic Beanstalk - Compute |
| `elasticbeanstalk-service-role` | 빈스톡 서비스 자신 | Elastic Beanstalk - Environment |

**배포 흐름**
1. 역할 2개를 만든다.
2. 빈스톡 환경(웹 서버 환경)을 만든다. 처음에는 샘플 애플리케이션으로 동작을 확인한다.
3. jar를 올리고, 필요하면 환경 속성(DB 주소, 키)을 넣는다. 비밀 값은 코드에 쓰지 않고 환경 속성으로 주입한다(23장).
4. 파일 업로드는 S3에 저장하고, 앱에는 S3 주소를 저장한다.

**자주 막히는 곳**
- **리전**: 다른 리전에서 만든 환경과 버킷은 지금 보는 리전 화면에 나타나지 않는다. 화면이 비어 보이면 리전부터 확인한다.
- **권한 부족**: 역할이 없거나 정책이 빠지면 환경 생성이 실패한다.
- **비용**: 실습을 마치면 환경을 종료하거나 삭제한다. 켜 둔 채로 두면 요금이 계속 나온다.

**면접 기준**: "빈스톡은 EC2와 보안 그룹을 자동으로 만들어 jar를 실행하는 서비스입니다. 빈스톡이 EC2를 만들 권한과 EC2가 쓸 권한을 역할로 나눠 주고, 파일은 S3에 둡니다."

## 4. IAM (권한 관리)

- **정의:** 클라우드에서 누가(사용자, 서비스) 어떤 자원에 어떤 작업을 할 수 있는지 정하는 권한 체계다.
- **구성:** 사용자(User), 그룹(Group), 역할(Role), 정책(Policy). 정책은 "허용 또는 거부", "어떤 작업", "어떤 자원"을 적은 문서다.
- **최소 권한 원칙:** 필요한 작업과 자원만 허용한다. `*` 권한을 주지 않는다.
- **흔한 실수:** 액세스 키를 코드나 저장소에 넣는다. 서버에는 키 대신 역할(Role)을 붙인다.
- **면접 기준:** "IAM은 누가 무엇을 할 수 있는지 정하는 클라우드 권한 체계입니다. 최소 권한으로 주고, 키 대신 역할을 씁니다."
