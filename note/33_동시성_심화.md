## 1. 경쟁 조건 (Race Condition)

**정의** — 여러 스레드가 같은 데이터를 동시에 읽고 쓸 때, 실행 순서에 따라 결과가 달라지는 상태다.

**원인** — `value++`는 한 줄처럼 보여도 실제로는 "읽기 → 더하기 → 쓰기" 세 단계다. 두 스레드가 같은 값을 읽고 각자 더하면 한 번의 증가가 사라진다.

**구현 (검증 완료): 경쟁 조건 재현과 해결**

```java
static class UnsafeCounter { int value; void inc() { value++; } }    // 보호 없음

static class SafeCounter {
    private int value;
    synchronized void inc() { value++; }                             // 한 번에 한 스레드만 실행
    synchronized int get() { return value; }
}
```

- **확인:** 두 스레드가 각각 100,000번 증가시키면 기대값은 200,000이다. 보호 없는 카운터는 실행마다 다른 값(예: 196,871, 197,501)이 나온다. `synchronized`, `AtomicInteger`, `ReentrantLock` 카운터는 항상 200,000이다.
- **주의:** 경쟁 조건은 항상 틀리지 않고, 가끔 틀린다. 그래서 테스트에 잘 안 걸린다. 재현하려면 반복 횟수를 늘리고 여러 번 돌려야 한다.

---

## 2. 해결 도구

| 도구 | 특징 | 언제 쓰나 |
|---|---|---|
| `synchronized` | 블록/메서드 단위 상호 배제. 간단하다 | 단순한 공유 상태 |
| `ReentrantLock` | 시간 제한 락, 공정성 옵션, `tryLock` 가능 | 락을 더 세밀하게 제어할 때 |
| `AtomicInteger` 같은 원자 클래스 | 락 없이 한 연산을 원자적으로 수행 (CAS) | 카운터처럼 단일 값 |
| `ConcurrentHashMap` | 맵을 여러 스레드가 안전하게 사용 | 공유 맵 |

**흔한 실수**
- 락을 잡은 채로 DB 호출이나 네트워크 호출을 해서 대기 시간이 길어진다.
- 락을 잡는 순서가 스레드마다 달라서 **교착 상태(deadlock)** 가 생긴다. 모든 스레드가 같은 순서로 락을 잡게 한다.
- `synchronized`를 붙였는데 읽기 메서드에는 빠뜨린다. 쓰기와 읽기를 함께 보호한다.

## 3. 스레드 풀

**정의** — 작업마다 스레드를 새로 만들지 않고, 미리 만들어 둔 스레드들이 작업 큐에서 일을 가져가 처리하는 구조다.

**목적과 책임** — 스레드 생성 비용을 줄이고, 동시에 실행되는 작업 수를 제한한다. 제한하지 않으면 요청이 몰릴 때 메모리와 CPU가 바닥난다.

**구현 (검증 완료)**

```java
ExecutorService pool = Executors.newFixedThreadPool(4);          // 스레드 4개
List<Future<Integer>> results = new ArrayList<>();
for (int i = 1; i <= 10; i++) {
    final int n = i;
    results.add(pool.submit(() -> n * n));                        // 작업 제출, 결과는 Future로 받음
}
int sum = 0;
for (Future<Integer> f : results) sum += f.get();                 // 결과 대기
pool.shutdown();                                                  // 새 작업을 받지 않고 끝냄
```

- **확인:** 1²부터 10²까지의 합은 385다. 스레드 4개가 10개의 작업을 나눠 처리해도 결과가 같다.
- **주의:** `Executors.newFixedThreadPool`의 큐는 제한이 없어서 메모리가 쌓일 수 있다. 운영에서는 `ThreadPoolExecutor`로 큐 크기를 제한하는 것을 검토한다.
- **Spring:** `@Async`나 웹 서버의 요청 스레드 풀도 같은 원리다. 풀 크기를 정하는 기준은 CPU 코어 수와 작업이 I/O를 기다리는 비율이다.

## 4. DB 락 (개념)

**정의** — 데이터베이스가 행이나 테이블에 거는 잠금이다. 여러 트랜잭션이 같은 행을 동시에 수정하지 못하게 막는다.

**종류**
- **공유 락(S):** 읽기용. 여러 트랜잭션이 함께 가질 수 있다.
- **배타 락(X):** 쓰기용. 다른 트랜잭션은 읽기도 쓰기도 기다려야 한다(잠금 읽기 기준).
- **낙관적 락:** 버전 번호로 충돌을 나중에 감지한다. 충돌이 적을 때 쓴다. JPA의 `@Version`이 여기에 해당한다.
- **비관적 락:** 읽을 때 바로 락을 건다. `SELECT ... FOR UPDATE`가 여기에 해당한다. 충돌이 많을 때 쓴다.

**예 (재고 차감):** 재고 1개를 두 사람이 동시에 주문하면, 락 없이 둘 다 "재고 있음"을 읽고 둘 다 차감해서 재고가 -1이 될 수 있다. `FOR UPDATE`로 읽으면 한 사람이 끝날 때까지 다른 사람은 기다린다.

**실습 (선택):** MySQL 세션 두 개에서 같은 행에 `SELECT ... FOR UPDATE`를 실행하고, 두 번째 세션이 기다리는지 확인한다.

---

## 5. 정리: 어떤 도구를 쓸까

- 같은 JVM 안의 공유 변수 → `synchronized`, 원자 클래스, `ConcurrentHashMap`
- 여러 서버에 걸친 데이터 → DB 락 또는 낙관적 락, 필요하면 분산 락(Redis 등)
- 작업을 나눠 처리 → 스레드 풀과 작업 큐

**면접 기준:** "경쟁 조건은 공유 상태를 여러 스레드가 동시에 바꿀 때 생깁니다. 같은 JVM이면 락이나 원자 연산으로, 여러 서버면 DB 락이나 낙관적 락으로 막습니다."

## DB에서 갱신 유실 막기: 확인과 변경을 한 문장으로 (2026-11-23 보강, MySQL 8.0 로컬에서 확인함)

**출처**: 선생님 자료 `AI_Code_Defect★/JPA + AI 코드 검증 시험공부 자습서`의 결함 ③(포인트)·⑥(쿠폰)과 같은 원리다.

**정의**: "잔액이 충분한지 SELECT로 확인하고, 나중에 UPDATE로 차감하는" 방식은 두 명령 사이에 다른 요청이 끼어들면 틀린다. 이것이 **갱신 유실(lost update)**이다. 해결은 확인과 변경을 **UPDATE 한 문장**으로 묶고, 바뀐 행 수(`executeUpdate()`의 반환값)로 성공을 판단하는 것이다.

```java
// 잘못된 방식: SELECT 후 UPDATE (사이에 틈이 있다)
int point = select("SELECT point FROM customer WHERE id = 1");
if (point < amount) return false;
Thread.sleep(30);                       // 다른 요청이 끼어들 수 있는 구간
update("UPDATE customer SET point = ? WHERE id = 1", point - amount);

// 올바른 방식: 조건을 UPDATE 안에 넣는다
int rows = update("UPDATE customer SET point = point - ? WHERE id = 1 AND point >= ?", amount, amount);
return rows == 1;                       // 0이면 잔액 부족 또는 이미 사용됨
```

쿠폰도 같다. 사용 여부를 조건에 넣는다.

```sql
UPDATE coupon SET used = 1 WHERE id = 1 AND used = 0;   -- 바뀐 행 수가 1이면 성공
```

**확인 방법 (MySQL 8.0 로컬, 스레드 20개 동시 요청)**: 임시 DB `khac_conc_demo`에 `customer(id, point CHECK (point >= 0))`와 `coupon(id, used)` 테이블을 만들고 아래 코드를 실행했다. 끝나고 DB는 삭제했다. 비밀번호는 `MYSQL_PWD` 환경 변수로 넘긴다. 실행에는 mysql-connector-j 드라이버가 필요하다.

```java
import java.sql.*;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class ConcDemo {
    static final String URL = "jdbc:mysql://localhost:3306/khac_conc_demo";
    static Connection conn() throws SQLException {
        return DriverManager.getConnection(URL, "root", System.getenv("MYSQL_PWD"));
    }

    static void reset(int point, int coupon) throws SQLException {
        try (Connection c = conn(); Statement s = c.createStatement()) {
            s.executeUpdate("UPDATE customer SET point = " + point + " WHERE id = 1");
            s.executeUpdate("UPDATE coupon SET used = " + (coupon == 0 ? 0 : 1) + " WHERE id = 1");
        }
    }

    static int run(int threads, Callable<Boolean> task) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(threads);
        CountDownLatch start = new CountDownLatch(1);
        AtomicInteger ok = new AtomicInteger();
        List<Future<?>> fs = new ArrayList<>();
        for (int i = 0; i < threads; i++) {
            fs.add(pool.submit(() -> { start.await(); if (task.call()) ok.incrementAndGet(); return null; }));
        }
        start.countDown();
        for (Future<?> f : fs) f.get();
        pool.shutdown();
        return ok.get();
    }

    // 잘못된 방식: 확인(SELECT)하고 나서 따로 변경(UPDATE)
    static boolean badPoint(int amount) throws Exception {
        try (Connection c = conn()) {
            int point;
            try (PreparedStatement ps = c.prepareStatement("SELECT point FROM customer WHERE id = 1");
                 ResultSet rs = ps.executeQuery()) { rs.next(); point = rs.getInt(1); }
            if (point < amount) return false;
            Thread.sleep(30);                                   // 다른 요청이 끼어들 틈을 넓힌다
            try (PreparedStatement ps = c.prepareStatement("UPDATE customer SET point = ? WHERE id = 1")) {
                ps.setInt(1, point - amount); ps.executeUpdate();
            }
            return true;
        }
    }

    // 올바른 방식: 확인과 변경을 UPDATE 한 문장으로 합치고, 바뀐 행 수로 성공을 판단
    static boolean goodPoint(int amount) throws Exception {
        try (Connection c = conn();
             PreparedStatement ps = c.prepareStatement(
                 "UPDATE customer SET point = point - ? WHERE id = 1 AND point >= ?")) {
            ps.setInt(1, amount); ps.setInt(2, amount);
            return ps.executeUpdate() == 1;
        }
    }

    static boolean badCoupon() throws Exception {
        try (Connection c = conn()) {
            int used;
            try (PreparedStatement ps = c.prepareStatement("SELECT used FROM coupon WHERE id = 1");
                 ResultSet rs = ps.executeQuery()) { rs.next(); used = rs.getInt(1); }
            if (used == 1) return false;
            Thread.sleep(30);
            try (PreparedStatement ps = c.prepareStatement("UPDATE coupon SET used = 1 WHERE id = 1")) { ps.executeUpdate(); }
            return true;
        }
    }

    static boolean goodCoupon() throws Exception {
        try (Connection c = conn();
             PreparedStatement ps = c.prepareStatement("UPDATE coupon SET used = 1 WHERE id = 1 AND used = 0")) {
            return ps.executeUpdate() == 1;
        }
    }

    static int pointNow() throws SQLException {
        try (Connection c = conn(); Statement s = c.createStatement();
             ResultSet rs = s.executeQuery("SELECT point FROM customer WHERE id = 1")) { rs.next(); return rs.getInt(1); }
    }

    public static void main(String[] args) throws Exception {
        reset(1000, 0);
        int okBad = run(20, () -> badPoint(100));
        System.out.println("[bad point] 20 requests x 100 from 1000 -> success=" + okBad + ", remaining=" + pointNow());

        reset(1000, 0);
        int okGood = run(20, () -> goodPoint(100));
        System.out.println("[good point] 20 requests x 100 from 1000 -> success=" + okGood + ", remaining=" + pointNow());

        reset(0, 0);
        int cBad = run(10, ConcDemo::badCoupon);
        System.out.println("[bad coupon] 10 requests -> success=" + cBad);

        reset(0, 0);
        int cGood = run(10, ConcDemo::goodCoupon);
        System.out.println("[good coupon] 10 requests -> success=" + cGood);
    }
}
```

**실행 결과 (확인함)**

```
[bad point] 20 requests x 100 from 1000 -> success=20, remaining=900
[good point] 20 requests x 100 from 1000 -> success=10, remaining=0
[bad coupon] 10 requests -> success=10
[good coupon] 10 requests -> success=1
```

잘못된 방식의 결과는 실행마다 조금 다를 수 있다. 다만 "성공 횟수가 정상보다 많다"는 현상은 여러 번 나왔다. 아래 표는 한 번 실행한 결과를 정리한 것이다.

| 방식 | 요청 | 성공 횟수 | 남은 포인트 | 정상 결과 |
|---|---|---|---|---|
| SELECT 후 UPDATE (잘못됨) | 20건 × 100점 | **20** | **900** | 성공 10, 남은 0 |
| 조건부 UPDATE (올바름) | 20건 × 100점 | 10 | 0 | 성공 10, 남은 0 |
| 쿠폰 SELECT 후 UPDATE (잘못됨) | 10건 | **10** | - | 성공 1 |
| 쿠폰 조건부 UPDATE (올바름) | 10건 | 1 | - | 성공 1 |

잘못된 방식은 성공이 20건이나 나왔는데 포인트는 100점만 줄었다. 20번 차감 중 19번이 사라진 것이다.

**읽는 법**
- 원인은 "확인 시점의 값"을 가지고 계산해 "저장 시점에 덮어쓰는" 구조다. 동시에 실행되면 같은 옛 값을 기준으로 계산한다.
- DB의 한 문장 UPDATE는 행을 잠근 채 조건과 변경을 한 번에 처리한다. 그래서 조건을 바꿔 넣는 것만으로 해결된다.
- 위 실험의 `customer` 테이블에는 `CHECK (point >= 0)`을 걸었다. 이번 실험에서 잔액은 음수가 되지 않았다. 다만 제약이 음수 저장을 막는 것을 따로 시험하지는 않았다. 제약은 마지막 안전장치이고, 주된 방어는 조건을 UPDATE 안에 넣는 것이다.
- 중복 찜처럼 "같은 회원이 같은 맛집에 한 번만"이라는 규칙은 **유니크 제약**(`UNIQUE (member_id, store_id)`)으로 DB가 막게 한다. 선생님 자료의 사건 2와 7-3이 이 방식이다.

**주의**: 이 방식은 한 행을 바꾸는 간단한 경우에 맞다. 여러 행을 묶는 송금처럼 여러 단계가 함께 성공해야 하면 트랜잭션과 격리 수준(7장)을 함께 본다.

**면접 기준**: "잔액이나 쿠폰처럼 한 번만 바뀌어야 하는 값은 SELECT 후 UPDATE 대신 조건을 넣은 UPDATE 한 문장으로 바꾸고, 영향 행 수로 성공을 판단합니다. 중복 방지는 유니크 제약으로 DB가 막게 합니다."

## 단원 통과 기준

- [ ] `value++`가 세 단계라는 것을 설명하고, 경쟁 조건을 재현할 수 있다.
- [ ] `synchronized`와 `AtomicInteger`의 차이를 말할 수 있다.
- [ ] 스레드 풀의 목적과 큐 제한의 필요성을 설명할 수 있다.
- [ ] 낙관적 락과 비관적 락의 차이를 재고 예로 설명할 수 있다.
