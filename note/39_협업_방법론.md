## 1. 애자일과 Scrum

**정의** — 애자일은 계획을 길게 세우기보다 짧은 주기로 만들고 확인하며 바꾸는 개발 방식이다. Scrum은 애자일을 실행하는 대표적인 틀이다.

**Scrum의 기본 구성**
- **스프린트:** 보통 1~4주 단위의 개발 주기. 주기 안에서 정한 목표를 만든다.
- **제품 백로그:** 해야 할 일의 우선순위 목록. 제품 책임자(PO)가 관리한다.
- **스프린트 백로그:** 이번 스프린트에서 할 일.
- **데일리 스크럼:** 매일 짧게 어제 한 일, 오늘 할 일, 막힌 것을 공유한다. 15분을 넘기지 않는다.
- **스프린트 리뷰와 회고:** 결과를 보여 주고, 과정을 어떻게 개선할지 이야기한다.

**역할 (Scrum 기준)**

| 역할 | 하는 일 |
|---|---|
| 제품 책임자 (PO) | 백로그 우선순위를 정하고, 무엇을 만들지 결정한다 |
| 스크럼 마스터 (SM) | 절차를 지키게 돕고, 막힌 일을 치운다 |
| 개발자 | 스프린트 목표를 구현하고 검증한다 |

소규모 팀에서는 한 사람이 여러 역할을 맡기도 한다. 그래도 **무엇을 만들지 정하는 사람**과 **어떻게 만들지 정하는 사람**의 구분은 유지한다.

**Kanban** — 할 일을 "대기 → 진행 중 → 검토 → 완료" 같은 열(컬럼)에 올려 흐름을 본다. 진행 중인 일의 수를 제한(WIP 제한)해서 한 번에 너무 많은 일을 하지 않게 한다.

**구별:** Scrum은 주기와 역할이 정해져 있고, Kanban은 흐름 중심으로 유연하다. 실무에서는 Scrum 주기 안에 Kanban 보드를 쓰는 경우가 많다.

## 2. Jira, Confluence, Slack

- **Jira:** 일감(이슈)을 만들고, 담당자를 정하고, 상태를 옮기고, 스프린트를 관리한다. 일감에는 목표, 완료 조건, 관련 PR을 적는다.
- **Confluence:** 설계 문서, 회의록, 결정 기록을 쌓는 문서 도구다. 나중에 "왜 이렇게 했는지"를 찾을 수 있게 한다.
- **Slack:** 빠른 대화와 알림. 중요한 결정은 Slack에만 두지 말고 Confluence나 Jira에 남긴다.

### 2.1 좋은 일감 작성 기준

| 항목 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 제목 | "로그인 수정" | "잘못된 비밀번호면 401 응답" |
| 완료 조건 | 없음 | "실패 시 401, 본문에 오류 코드 포함, 테스트 추가" |
| 크기 | "회원 기능 전체" | 1~3일 안에 끝나는 단위로 쪼갬 |
| 관련 자료 | 없음 | 설계 문서 링크, PR 링크 |

**완료 조건(Definition of Done)** 은 팀이 같이 정한다. 예: "코드 리뷰 승인, 테스트 통과, 배포 스테이징 확인, 문서 갱신".

## 3. 코드 리뷰

**정의** — 병합 전에 다른 사람이 변경 내용을 읽고 질문하거나 개선점을 말하는 과정이다. 버그를 줄이고, 지식을 나누고, 설계를 맞춘다.

**리뷰어가 볼 것**
- 동작이 요구사항과 맞는가
- 예외와 경계 조건을 다뤘는가 (빈 값, null, 0, 최대 길이)
- 이름과 구조가 읽기 쉬운가
- 테스트가 실제로 검증하는가 (통과만 하는 테스트인지 확인)
- 보안(권한 검사, 입력 검증, 비밀 정보, SQL 조립 방식) 문제가 없는가
- 변경 범위가 PR 설명과 맞는가 (관계없는 수정이 섞였는지)

**작성자가 할 것**
- PR 설명에 목적, 변경 범위, 확인 방법을 적는다.
- 리뷰 의견에 "왜 그렇게 했는지"로 답한다. 고칠 때는 같은 브랜치에 커밋해서 PR에 반영한다.
- PR을 작게 유지한다. 보통 수백 줄 이내가 리뷰하기 좋다.

### 3.1 코멘트 예시

| 상황 | 좋은 코멘트 | 피할 코멘트 |
|---|---|---|
| 잠재 버그 | "이 경로에서 `user`가 null이면 NPE가 날 수 있을까요?" | "이거 버그예요." |
| 개선 제안 | "`Optional.orElseThrow`로 의도를 드러내면 어떨까요?" | "이렇게 쓰면 안 돼요." |
| 취향 | "(선택) 이름을 `count`에서 `activeUserCount`로 바꾸면 더 명확할 것 같아요." | 승인 조건처럼 강요 |

**예의:** 사람이 아니라 코드를 평가한다. 질문형으로 말하고, 구분을 표시한다. (필수 / 제안 / 질문)

## 4. 회고 (Retrospective)

스프린트 끝에 세 가지를 모은다.

| 구분 | 질문 | 예 |
|---|---|---|
| Keep | 계속 할 것은? | 아침 리뷰 시간 고정 |
| Problem | 문제였던 것은? | 일감 크기가 제각각이라 예측이 빗나감 |
| Try | 다음에 시도할 것은? | 1일 넘는 일감은 쪼개서 등록 |

**규칙**: Try는 **하나 또는 두 개만** 정한다. 다음 회고에서 실행 여부를 확인한다. 실행하지 않은 Try가 쌓이면 회고는 형식이 된다.

## 5. Git 협업 흐름 (임시 저장소 검증)

팀에서 `main`을 직접 고치지 않고, 브랜치에서 작업한 뒤 PR로 합치는 것이 기본이다. 01장(Git)의 명령을 그대로 쓴다.

```bash
git switch -c feature/123-login-401        # 일감 번호를 브랜치 이름에 넣는다
# 작업과 커밋
git push -u origin feature/123-login-401   # PR 생성
# 리뷰 반영은 같은 브랜치에 추가 커밋
git switch main && git pull               # 병합 후 main 갱신
git branch -d feature/123-login-401       # 병합된 브랜치 정리
```

**충돌이 났을 때의 순서**
1. `git pull`로 최신 `main`을 가져온다.
2. 충돌 파일을 열어 양쪽 의도를 확인한다. 기계적으로 한쪽만 고르지 않는다.
3. 테스트를 돌려 두 변경이 함께 동작하는지 확인한다.
4. 커밋하고 push한다.

**검증 결과 (임시 저장소)**: `main`, `develop`, `feature/search` 세 브랜치로 같은 파일을 서로 다르게 고치고 병합하자 `CONFLICT`가 발생했다. 충돌 표시를 보고 한쪽을 골라 해결하는 과정을 확인했다.

**브랜치 전략 선택**

| 전략 | 특징 | 맞는 팀 |
|---|---|---|
| Git Flow | `develop`, `release`, `hotfix` 브랜치를 나눔 | 릴리스 주기가 정해진 팀 |
| Trunk-based | 짧은 브랜치와 자주 병합, 배포는 `main` 기준 | 배포를 자주 하는 팀 |

팀 규칙은 이 장을 쓰는 사람이 아니라 **팀이 같이 정한다.** 정하고 나면 README나 CONTRIBUTING 문서에 적는다.

## 6. 면접 답변 틀 (STAR)

협업 경험을 물으면 다음 순서로 답한다.

- **S (상황):** 어떤 프로젝트, 어떤 팀이었는지
- **T (과제):** 내가 맡은 목표는 무엇이었는지
- **A (행동):** 내가 실제로 한 것. 리뷰, 일감 쪼개기, 회고 개선 등 구체적으로
- **R (결과):** 숫자나 변화로 말한다. "리뷰 시간이 하루에서 두 시간으로 줄었다"

**주의:** "우리 팀이 잘했다"로 끝내면 내 역할이 보이지 않는다. A에 나를 주어로 쓴다.

## 7. 실습 과제

1. 최근 작업 하나를 Jira 일감 형식으로 적는다. (제목, 완료 조건 세 개, 관련 PR)
2. 임시 저장소를 만들어 `feature` 브랜치에서 `main`과 다른 줄을 고치고 병합해서 충돌을 만든 뒤 해결해 본다.
3. 동료 코드(또는 이 저장소의 예제)를 리뷰하고, 필수·제안·질문 세 종류로 의견을 나눠 적는다.
4. 지난 스프린트(또는 과제 주기)를 KPT 회고로 정리하고, Try를 하나만 고른다.
