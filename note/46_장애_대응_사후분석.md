# 장애 대응과 사후 분석: 감지, 복구, 원인을 기록하고 재발을 막는다

> 중요도: **A** · 이 장의 목표: 장애 대응 단계(감지, 분류, 완화, 복구, 사후 분석)를 설명하고, 심각도를 나누고, MTTD와 MTTR을 계산하고, 비난 없는 사후 분석 문서를 쓴다.

> 2026-11-23 추가 장 (목표 점검 결과 보강: 목표 문서 성취 기준의 "장애 진단"과 4장 관측성의 후속). MTTD·MTTR 계산은 JDK 25에서 실행해 확인했다. 장애 상황은 실제로 만들지 않았다. 실습은 허가된 테스트 환경에서만 한다.

---

## 1. 장애 대응 단계

| 단계 | 질문 | 예 |
|---|---|---|
| 감지 (Detect) | 언제 알았는가 | 알림, 사용자 문의, 대시보드 |
| 분류 (Triage) | 얼마나 심각한가 | 심각도 SEV1~SEV4 |
| 완화 (Mitigate) | 피해를 먼저 줄였는가 | 문제 기능 끄기, 이전 버전 롤백, 트래픽 차단 |
| 복구 (Recover) | 정상으로 돌렸는가 | 원인 수정 배포, 데이터 복구 |
| 사후 분석 (Review) | 왜 생겼고 어떻게 막을까 | 포스트모템 문서, 후속 조치 |

**원칙**: 원인을 찾는 것보다 **먼저 피해를 줄인다.** 로그를 파고드는 동안 사용자 피해가 계속되면 안 된다. 롤백은 원인 분석보다 빠른 완화 수단이다(45장 배포 체크리스트).

---

## 2. 심각도 기준

| 등급 | 기준 | 대응 |
|---|---|---|
| SEV1 | 전체 서비스 중단, 데이터 손실 위험 | 즉시 전원 호출, 공지 |
| SEV2 | 핵심 기능 일부 중단 | 담당자 즉시, 공지 |
| SEV3 | 일부 사용자, 우회 가능 | 업무 시간 내 처리 |
| SEV4 | 불편하지만 기능은 정상 | 백로그 등록 |

심각도는 **사용자 영향**으로 정한다. "서버 CPU 90%"는 원인 지표이지 심각도 기준이 아니다.

---

## 3. 시간 지표: MTTD와 MTTR

- **MTTD (Mean Time To Detect)**: 장애가 시작된 시각부터 감지까지 평균 시간.
- **MTTR (Mean Time To Recover)**: 감지부터 복구까지 평균 시간. 복구 시간 기준은 팀이 정한다(완화 시각 또는 정상화 시각).

```
MTTD = 감지 시각 − 장애 시작 시각
MTTR = 복구 시각 − 감지 시각
```

**해석**: MTTD가 길면 알림이 부족하다. MTTR이 길면 롤백 절차나 권한, 문서가 부족하다. 두 값을 분리해서 줄인다.

---

## 4. 사후 분석 (포스트모템)

**비난 없는 문화(blameless)**: 사람을 탓하지 않고 **시스템과 절차의 빈틈**을 찾는다. "A가 실수했다"가 아니라 "배포 전에 검사할 방법이 없었다"로 쓴다.

**문서 구조**

| 항목 | 내용 |
|---|---|
| 요약 | 무엇이, 언제, 얼마나 영향을 줬는지 3문장 |
| 타임라인 | 시각별 사건(감지, 판단, 조치, 복구) |
| 영향 | 사용자 수, 실패 요청 수, 데이터 영향 |
| 근본 원인 | 직접 원인과 그것을 허용한 구조적 원인 |
| 잘된 점 | 빨리 감지하거나 막은 것 |
| 개선 조치 | 담당자와 기한이 있는 후속 작업 |

**원인 찾기 (5 Whys)**: "왜?"를 반복한다. 한 단계에서 멈추지 않고 **절차나 시스템** 수준까지 간다.

```
결제 실패 → 설정 값이 잘못 배포됨 → 배포 전 검증이 없음 → 설정 검증 단계가 파이프라인에 없음 → 근본 원인
```

**주의**: 원인이 "사람 실수"로 끝나면 분석이 덜 된 것이다. 같은 실수가 다시 날 수 없게 시스템을 바꾸는 조치를 적는다.

## 4.1 타임라인 예시

| 시각 (KST) | 사건 |
|---|---|
| 10:02 | 설정 변경 배포 (v1.4.2) |
| 10:09 | 결제 실패율 알림 발생 (MTTD 기준 시작점은 10:02 장애 시작) |
| 10:12 | 담당자 확인, 롤백 결정 |
| 10:18 | v1.4.1로 롤백, 실패율 정상화 |
| 10:40 | 사후 분석 시작 |

이 예에서 장애 시작은 10:02, 감지는 10:09, 복구(롤백 완료)는 10:18이다.

---

## 5. 검증 코드 (JDK 25에서 실행)

```java
import java.time.*;
import java.util.*;

public class IncidentCheck {
    record Incident(String name, LocalTime start, LocalTime detected, LocalTime recovered) {
        long mttdMinutes() { return Duration.between(start, detected).toMinutes(); }
        long mttrMinutes() { return Duration.between(detected, recovered).toMinutes(); }
    }

    public static void main(String[] args) {
        List<Incident> incidents = List.of(
                new Incident("INC-101", LocalTime.of(10, 2), LocalTime.of(10, 9), LocalTime.of(10, 18)),
                new Incident("INC-102", LocalTime.of(14, 30), LocalTime.of(14, 33), LocalTime.of(15, 5)),
                new Incident("INC-103", LocalTime.of(2, 0), LocalTime.of(2, 45), LocalTime.of(3, 0)));

        for (Incident i : incidents) {
            System.out.println(i.name() + " MTTD=" + i.mttdMinutes() + "m MTTR=" + i.mttrMinutes() + "m");
        }
        double avgMttd = incidents.stream().mapToLong(Incident::mttdMinutes).average().orElse(0);
        double avgMttr = incidents.stream().mapToLong(Incident::mttrMinutes).average().orElse(0);
        System.out.printf("avg MTTD=%.1fm avg MTTR=%.1fm%n", avgMttd, avgMttr);

        // 감지가 장애 시작보다 빠를 수 없다: 데이터 오류 점검
        Incident bad = new Incident("INC-X", LocalTime.of(11, 0), LocalTime.of(10, 50), LocalTime.of(11, 10));
        System.out.println("INC-X valid: " + (bad.mttdMinutes() >= 0));
    }
}
```

**실행 결과 (확인함)**

```
INC-101 MTTD=7m MTTR=9m
INC-102 MTTD=3m MTTR=32m
INC-103 MTTD=45m MTTR=15m
avg MTTD=18.3m avg MTTR=18.7m
INC-X valid: false
```

**결과 읽기**
- INC-103은 감지가 45분 늦었다. 알림이 없는 시간대(새벽)였을 가능성을 사후 분석에서 확인한다.
- INC-102는 복구에 32분이 걸렸다. 롤백 절차가 문서화되어 있었는지 확인한다.
- 감지 시각이 장애 시작보다 빠른 기록은 입력 오류다. 계산 전에 걸러낸다.

## 6. 실습 과제

1. 최근 겪은 실패(프로젝트 버그, 배포 오류 등) 하나를 타임라인으로 적고 MTTD와 MTTR을 계산한다.
2. 위 사후 분석 구조로 그 사건의 근본 원인을 5 Whys로 찾는다. 마지막 원인이 사람이 아니라 절차인지 확인한다.
3. 개선 조치를 하나 정하고, 담당자와 기한을 적는다.

## 단원 통과 기준

- [ ] 장애 대응의 다섯 단계를 순서대로 말하고, 완화가 원인 분석보다 먼저인 이유를 설명할 수 있다.
- [ ] 심각도를 사용자 영향 기준으로 나눌 수 있다.
- [ ] MTTD와 MTTR을 계산하고, 각각 길 때 무엇을 점검할지 말할 수 있다.
- [ ] 비난 없는 사후 분석 문서의 항목을 채울 수 있고, 5 Whys로 절차 수준의 원인을 찾을 수 있다.
