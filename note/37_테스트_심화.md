# 테스트 심화: Testcontainers, 계약 테스트, 품질 게이트

> 중요도: **A** · 이 장의 목표: 테스트 계층을 나누고, 실제 DB로 통합 테스트하고, API 계약을 검증하고, 보안 검사를 파이프라인에 넣는다.

## 1. 테스트 계층 다시 보기

| 계층 | 무엇을 확인 | 도구 예 | 속도 |
|---|---|---|---|
| 단위 테스트 | 클래스 하나의 로직 (의존 객체는 가짜) | JUnit 5, Mockito | 빠름 |
| 통합 테스트 | 여러 구성 요소가 실제로 연결된 동작 (실제 DB 포함) | Spring Boot Test, Testcontainers | 느림 |
| 계약 테스트 | 프론트와 백엔드가 약속한 API 모양이 맞는지 | OpenAPI 검증, Pact | 중간 |
| E2E 테스트 | 사용자 화면에서 전체 흐름 | Playwright, Selenium | 가장 느림 |

**원칙:** 아래로 갈수록 적게, 위로 갈수록 많이 쓴다(테스트 피라미드). 단위 테스트가 빠르게 많은 버그를 잡고, E2E는 핵심 흐름만 확인한다.

## 2. Testcontainers: 실제 DB로 통합 테스트

**정의** — 테스트를 실행할 때 Docker 컨테이너로 실제 데이터베이스(MySQL 등)를 띄우고, 테스트가 끝나면 지우는 라이브러리다.

**왜 필요한가** — H2 같은 메모리 DB는 MySQL과 문법과 동작이 다르다. 실제 DB로 테스트해야 인덱스, 제약 조건, 트랜잭션 동작을 확인할 수 있다. 30장에서 말한 "Mock 테스트만으로는 DB 제약을 검증했다고 볼 수 없다"의 해결책이다.

**예 (Spring과 연결하는 형태. 이 부분은 미검증)**

```java
@Testcontainers
@SpringBootTest
class PostRepositoryIT {
    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0");

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry r) {
        r.add("spring.datasource.url", mysql::getJdbcUrl);
        r.add("spring.datasource.username", mysql::getUsername);
        r.add("spring.datasource.password", mysql::getPassword);
    }

    @Test void 저장한_글을_다시_찾을_수_있음() {
        // 실제 MySQL 컨테이너에 대해 저장과 조회를 검증한다
    }
}
```

- **주의:** 테스트마다 컨테이너를 새로 띄우면 느리다. 같은 컨테이너를 여러 테스트가 쓰게 하고, 테스트 데이터는 각자 정리한다.

---

### 2-1. 실제 실행 검증 결과 (2026-11-23)

Docker Desktop에서 실제 MySQL 8.0 컨테이너를 띄워 다음 테스트를 실행했고, 통과했다.

```java
@Testcontainers
class PostRepositoryTest {
    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0");

    @Test
    void 저장한_글을_다시_찾을_수_있고_제약이_실제로_동작함() throws Exception {
        try (Connection c = DriverManager.getConnection(mysql.getJdbcUrl(), mysql.getUsername(), mysql.getPassword());
             Statement st = c.createStatement()) {
            st.execute("CREATE TABLE post (id BIGINT PRIMARY KEY, title VARCHAR(100) NOT NULL)");
            st.execute("INSERT INTO post VALUES (1, 'hello')");
            try (ResultSet rs = st.executeQuery("SELECT title FROM post WHERE id = 1")) {
                assertTrue(rs.next());
                assertEquals("hello", rs.getString(1));
            }
            // NOT NULL 제약이 DB에서 실제로 막히는지 확인 (Mock으로는 확인할 수 없는 부분)
            assertThrows(SQLException.class, () -> st.execute("INSERT INTO post VALUES (2, NULL)"));
        }
    }
}
```

- **환경 문제와 해결:** Testcontainers 1.20.4는 Docker Desktop 29의 Docker 엔진과 맞지 않아서 `400 Bad Request`가 났다. Testcontainers를 1.21.3으로 올리고, 테스트 JVM에 `-Dapi.version=1.44`를 넘기자 통과했다.
- **실행 시간:** 컨테이너 시작을 포함해 약 46초. 그래서 컨테이너는 테스트 클래스 하나가 공유하게 한다.
- **Maven 파일 이름:** Surefire는 기본적으로 `*Test.java`를 테스트로 잡는다. `*IT.java`는 기본 설정에서 실행되지 않는다.
## 3. 계약 테스트: API 모양 약속 지키기

**정의** — 제공하는 쪽(백엔드)과 사용하는 쪽(프론트)이 API의 요청과 응답 모양에 합의하고, 그 합의를 자동으로 검사하는 테스트다.

**방법**
- **OpenAPI 명세 기준:** 명세 파일(YAML)을 먼저 쓰고, 구현이 명세와 같은지 테스트로 확인한다. 응답 필드 이름, 타입, 상태 코드를 검사한다.
- **소비자 주도 계약 (Pact):** 프론트가 필요한 모양을 계약 파일로 남기고, 백엔드가 그 계약을 지키는지 검사한다.

**예:** 명세에 `title`이 문자열이라고 적혀 있는데 백엔드가 숫자로 바꾸면, 계약 테스트가 배포 전에 실패한다.

**면접 기준:** "계약 테스트는 API 모양을 명세와 대조해 프론트와 백엔드가 어긋나는 것을 배포 전에 잡습니다."

## 4. 품질 게이트 (CI에서 자동 검사)

파이프라인에서 다음을 통과해야 병합할 수 있게 한다.

- **단위·통합 테스트 통과**
- **정적 분석 (SAST):** 소스 코드에서 보안 취약점 패턴을 찾는다. 예: 하드코딩된 비밀번호, 위험한 함수 사용.
- **비밀정보 검사:** 커밋에 키나 토큰이 들어갔는지 확인한다.
- **의존성 점검:** 알려진 취약점이 있는 라이브러리를 찾는다.
- **커버리지:** 테스트가 얼마나 많은 코드를 지나가는지 본다. 숫자보다 핵심 로직이 빠졌는지가 중요하다.

**흔한 실수:** 커버리지 숫자만 높이고 검증(assert)을 빼는 것. 실행만 되고 확인하지 않는 테스트는 의미가 없다.

### MockMvc로 웹 요청 테스트 (2026-11-23 보강)

컨트롤러를 실제 서버 없이 테스트하는 도구가 `MockMvc`다. 요청을 만들어 필터·인터셉터·컨트롤러·예외 처리를 함께 실행하고, 상태 코드와 본문을 검사한다. 실행 확인한 코드와 순서 검증은 **20장 6-2**에 있다.

```java
// Spring Boot 테스트 (미실행: 이 PC에서 Spring Boot 전체 기동은 확인하지 않았다)
@WebMvcTest(HelloController.class)
class HelloControllerTest {
    @Autowired MockMvc mvc;

    @Test
    void hello() throws Exception {
        mvc.perform(get("/hello"))
           .andExpect(status().isOk())
           .andExpect(content().string("hi"));
    }
}
```

**MockMvc 예제 모음 (이 장을 기준으로 본다)**

| 장 | 예제 | 확인하는 것 |
|---|---|---|
| 18장 REST | 메모 CRUD (201·200·404·204) | 상태 코드와 응답 계약 |
| 20장 동작 원리 | 필터 → 인터셉터 → 컨트롤러 → 어드바이스 | 요청 처리 순서 |
| 22장 검증 | 폼 제출과 `BindingResult` | 항목별 검증 오류 |
| 18장 요청 값 | `@RequestParam`, `ResponseEntity`, 응답 형식 | 응답 본문과 Content-Type |

**구분할 것**
- `standaloneSetup`(20장 6-2에서 실행): 컨트롤러 한 개와 필요한 설정만 직접 등록한다. 빠르고 의존성이 적다.
- `@WebMvcTest`(미실행): Spring Boot가 웹 계층 빈만 올린다. 실무에서 자주 쓰는 형태다.
- 둘 다 실제 포트를 열지 않으므로 소켓 제한이 있는 환경에서도 실행할 수 있다.

**면접 기준**: "MockMvc는 실제 서버를 띄우지 않고 HTTP 요청을 흉내 내어 컨트롤러와 필터, 예외 처리를 테스트합니다."

## JUnit 5 생명주기, AssertJ, Given-When-Then, 실패 메시지 (2026-11-23 보강, 확인함)

**참고**: 원본 자료와 출처, 확인 범위는 [부록 92](92_선별근거_원본연결.md)의 이 장 항목을 본다.

**정의**
- **`@BeforeEach` / `@AfterEach`**: 각 `@Test` 메서드 전에 준비하고 끝난 뒤 정리한다. 테스트마다 반복된다.
- **AssertJ `assertThat`**: `assertThat(실제값).isEqualTo(기대값)`처럼 **무엇을 검사하는지**가 앞에 오는 문장이다. `assertEquals(기대, 실제)`는 순서를 헷갈리기 쉽다.
- **Given-When-Then**: 준비(Given), 실행(When), 확인(Then)의 세 칸으로 테스트를 나눈다.

```java
import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import java.util.ArrayList;
import java.util.List;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

class Calculator {
    int add(int a, int b) { return a + b; }
    int divide(int a, int b) {
        if (b == 0) throw new IllegalArgumentException("0으로 나눌 수 없다");
        return a / b;
    }
}

public class CalcTest {
    static final List<String> LOG = new ArrayList<>();
    Calculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new Calculator();            // 각 테스트 전에 새로 준비한다
        LOG.add("before");
    }

    @AfterEach
    void tearDown() {
        LOG.add("after");
    }

    @Test
    void addReturnsSum() {
        // Given
        int a = 2, b = 3;
        // When
        int result = calculator.add(a, b);
        // Then
        assertThat(result).isEqualTo(5);
        assertThat(String.valueOf(result)).startsWith("5");
    }

    @Test
    void divideByZeroThrows() {
        assertThatThrownBy(() -> calculator.divide(10, 0))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessageContaining("0으로");
    }

    @Test
    void listChecks() {
        List<String> names = List.of("kim", "lee");
        assertThat(names).hasSize(2).contains("kim");
    }
}
```

**실행 결과 (확인함)**: 테스트 3개가 모두 통과했다. 생명주기 로그는 `[before, after, before, after, before, after]`였다. 테스트마다 준비와 정리가 한 번씩 돌았다.

**실패 메시지 읽기 (확인함)**: `assertThat(2 + 2).isEqualTo(5);`가 실패하면 다음 메시지가 나온다.

```
expected: 5
 but was: 4
```

위쪽(`expected`)이 기대값, 아래쪽(`but was`)이 실제값이다. 실패 메시지는 **기대와 실제를 비교해 읽는 것**이 출발점이다.

**주의**
- 테스트 실행 순서에 기대지 않는다. 각 테스트는 `@BeforeEach`에서 필요한 것을 스스로 준비해야 한다.
- 실행 순서에 기대면 테스트를 혼자 돌렸을 때 실패한다. 공유 상태(`static` 변수)를 쓸 때 특히 조심한다. 위 예제의 `LOG`는 학습용으로 `static`에 둔 것이다.

**면접 기준**: "테스트는 Given-When-Then으로 나눠 쓰고, 준비는 `@BeforeEach`로 테스트마다 새로 합니다. AssertJ로 기대값과 실제값을 비교하고, 실패 메시지는 expected와 but was를 나란히 읽습니다."
