# 분산 시스템, 메시징, 캐시

> 중요도: **A** · 이 장의 목표: CAP과 일관성 모델을 트레이드오프로 설명하고, 캐시 전략과 샤딩을 구현하고, 메시지 큐의 역할을 구별한다.

## 1. 분산 시스템이란

**정의** — 여러 대의 컴퓨터가 네트워크로 연결되어 하나의 서비스처럼 동작하는 시스템이다.

**왜 어려운가** — 네트워크는 느리고 끊길 수 있다. 메시지가 사라지거나 늦게 도착하고, 어떤 서버가 죽었는지 바로 알 수 없다. 이 불확실성이 모든 설계 문제의 뿌리다.

---

## 2. CAP 정리

네트워크가 나뉘어(파티션) 서버끼리 연락이 안 되는 상황에서, 시스템은 다음 둘 중 하나를 골라야 한다.

- **C (Consistency, 일관성):** 모든 노드가 같은 최신 데이터를 준다.
- **A (Availability, 가용성):** 모든 요청에 응답한다. 응답이 최신이 아닐 수 있다.
- **P (Partition tolerance, 분할 허용):** 네트워크가 나뉘어도 시스템이 계속 동작한다.

**핵심** — 파티션은 현실에서 피할 수 없으므로 실제로는 **C와 A 중 무엇을 택할지**의 문제다. 파티션이 생기면 일관성을 지키려면 응답을 거부하고(CP), 응답을 주려면 오래된 값을 줄 수 있다(AP).

**오해:** "CAP는 셋 중 둘만 고르는 것"이라는 설명은 부정확하다. 파티션이 없을 때는 둘 다 가능하다.

**예:** 은행 잔액은 CP 쪽이 맞다. SNS 좋아요 수는 AP 쪽이 맞다.

---

## 3. 일관성 모델

- **강한 일관성:** 쓰기가 끝나면 모든 읽기가 바로 새 값을 본다.
- **최종 일관성:** 쓰기 후 시간이 지나면 모든 노드가 같은 값으로 수렴한다. 그 사이에는 오래된 값을 볼 수 있다.

**면접 기준:** "강한 일관성은 쓰기 직후 모든 읽기가 새 값을 보는 것이고, 최종 일관성은 시간이 지나야 같아지는 것입니다. 어느 쪽을 쓸지는 업무가 오래된 값을 허용하는지로 정합니다."

## 4. 복제와 샤딩

**복제 (Replication)** — 같은 데이터를 여러 서버에 복사해서 읽기를 나누고 장애에 대비한다. 대표 구성은 주(primary)가 쓰기를 받고 복제본(replica)이 읽기를 나눠 받는 방식이다. 복제본은 주보다 늦게 따라가므로 최종 일관성이 된다.

**샤딩 (Sharding)** — 데이터를 여러 서버에 나눠 저장한다. 키를 기준으로 어느 서버에 둘지 정한다.

**문제: 단순 나머지 연산(`key % 서버 수`)** — 서버가 하나 늘면 거의 모든 키의 위치가 바뀐다. 그래서 캐시나 샤드를 옮기는 비용이 크다.

**해결: 일관성 해싱 (Consistent Hashing)** — 서버와 키를 같은 해시 링에 올리고, 키는 시계 방향으로 가장 가까운 서버에 둔다. 서버가 하나 추가되면 옮겨지는 키는 대략 `1/(서버 수)` 정도다. 가상 노드(서버 하나를 여러 점으로 나눠 놓는 것)를 쓰면 부하가 고르게 나뉜다.

**구현 (검증 완료): 해시 링**

```java
// String.hashCode()는 비슷한 문자열끼리 값이 몰리므로, 링에서는 MD5 앞 4바이트를 쓴다
static int hash(String s) {
    try {
        byte[] d = java.security.MessageDigest.getInstance("MD5").digest(s.getBytes(java.nio.charset.StandardCharsets.UTF_8));
        return ((d[0] & 0xff) << 24) | ((d[1] & 0xff) << 16) | ((d[2] & 0xff) << 8) | (d[3] & 0xff);
    } catch (java.security.NoSuchAlgorithmException e) { throw new RuntimeException(e); }
}

static class HashRing {
    private final TreeMap<Integer, String> ring = new TreeMap<>();
    private final int virtualNodes;
    HashRing(int virtualNodes) { this.virtualNodes = virtualNodes; }
    void addNode(String node) {
        for (int i = 0; i < virtualNodes; i++) ring.put(hash(node + "#" + i), node);
    }
    String nodeFor(String key) {
        Map.Entry<Integer, String> e = ring.ceilingEntry(hash(key));
        return (e != null) ? e.getValue() : ring.firstEntry().getValue();   // 링의 끝을 넘으면 처음으로
    }
}
```

- **확인:** 서버 3대(가상 노드 100개씩)에 키 10,000개를 배치한 뒤 서버 1대를 추가하면, 옮겨진 키는 약 20%다(검증 완료). 서버가 4대이므로 1/4에 가깝다.
- **흔한 실수:** 해시 함수 품질을 확인하지 않는다. `String.hashCode()`는 비슷한 키에서 값이 몰려 링이 고르지 않게 된다.

## 5. 캐시

**정의** — 자주 읽는 데이터를 빠른 저장소(예: Redis, 메모리)에 두고 원본 DB 부하를 줄이는 방법이다.

**캐시-어사이드 (Cache-Aside)** — 애플리케이션이 캐시를 직접 관리한다.
1. 읽을 때: 캐시를 먼저 보고, 없으면 DB에서 읽어 캐시에 넣는다.
2. 쓸 때: DB를 먼저 갱신하고, 캐시 항목을 지운다(무효화).

**구현 (검증 완료)**

```java
static class CacheAside {
    final Map<String, String> db = new HashMap<>();
    final Map<String, String> cache = new HashMap<>();
    int dbReads = 0;
    String get(String key) {
        if (cache.containsKey(key)) return cache.get(key);   // 캐시 히트
        dbReads++;
        String v = db.get(key);                               // 미스 -> DB 조회
        if (v != null) cache.put(key, v);
        return v;
    }
    void update(String key, String value) {
        db.put(key, value);
        cache.remove(key);                                    // 쓰기 후 무효화
    }
}
```

- **확인:** 첫 조회는 DB를 한 번 읽고, 두 번째 조회는 캐시에서 나와 DB 읽기 횟수가 늘지 않는다. 값을 바꾸면 캐시가 지워져서 새 값이 보인다(검증 완료).

**흔한 문제**
- **캐시 스탬피드:** 인기 있는 키가 만료되는 순간 많은 요청이 동시에 DB로 몰린다. 만료 시간을 흩뜨리거나 한 요청만 DB를 읽게 막는다.
- **갱신 순서 문제:** DB를 바꾸고 캐시를 지우기 전에 다른 요청이 옛 값을 캐시에 다시 넣을 수 있다. TTL을 짧게 두어 피해를 제한한다.
- **Redis:** 메모리 기반 키-값 저장소다. 캐시, 세션, 분산 락, 간단한 큐로 쓰인다. (실행 환경이 없어 이 장에서는 개념만 다룬다.)

### 5-1. 스프링 캐시 추상화 @Cacheable (2026-11-23 보강, 확인함)

Spring은 캐시 저장소(메모리, Redis 등)를 `@Cacheable`로 감싸는 추상화를 제공한다. 메서드 결과를 캐시에 넣고, 같은 키로 다시 호출하면 메서드 본문을 실행하지 않는다. 이 장에서는 저장소를 메모리 맵으로 두고 확인했다. Redis 연결은 **미실행**이다.

```java
import org.springframework.cache.annotation.Cacheable;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.cache.concurrent.ConcurrentMapCacheManager;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class SpringCache {
    static int dbCalls = 0;

    @Configuration
    @EnableCaching
    static class Config {
        @Bean
        ConcurrentMapCacheManager cacheManager() { return new ConcurrentMapCacheManager("products"); }
        @Bean
        ProductService productService() { return new ProductService(); }
    }

    static class ProductService {
        @Cacheable("products")
        public String findName(long id) {
            dbCalls++;                       // 캐시가 없을 때만 실행되는 "DB 조회"
            return "product-" + id;
        }
    }

    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(Config.class)) {
            ProductService svc = ctx.getBean(ProductService.class);
            System.out.println(svc.findName(1));
            System.out.println(svc.findName(1));
            System.out.println(svc.findName(2));
            System.out.println("dbCalls=" + dbCalls);
        }
    }
}
```

**실행 결과 (확인함)**

```
product-1
product-1
product-2
dbCalls=2
```

세 번 호출했지만 `dbCalls`는 2다. `findName(1)`의 두 번째 호출은 캐시에서 나왔다.

**주의**
- 캐시는 **같은 키**일 때만 재사용한다. `findName(1)`과 `findName(2)`는 따로 저장된다.
- 데이터가 바뀌면 캐시를 지워야 한다. `@CacheEvict`로 수정·삭제 시점에 키를 지운다. 지우지 않으면 오래된 값이 계속 나온다(캐시 일관성 문제).
- 20장 5절과 같다. 같은 클래스 안에서 `this.findName()`으로 부르면 프록시를 거치지 않아 캐시가 적용되지 않는다.

**면접 기준**: "`@Cacheable`은 메서드 결과를 키로 저장해 DB 조회를 줄이는 Spring 캐시 추상화입니다. 갱신 시점에는 `@CacheEvict`로 지우고, 같은 클래스 내부 호출에서는 프록시를 거치지 않아 적용되지 않는 점을 주의합니다."

## 6. 메시지 큐와 이벤트 (개념)

**정의** — 서비스끼리 직접 호출하지 않고, 메시지를 큐나 로그에 넣어 전달하는 방식이다. 보내는 쪽은 받는 쪽이 바쁘거나 죽어 있어도 메시지를 맡길 수 있다.

**RabbitMQ와 Kafka의 차이**

| 항목 | RabbitMQ | Kafka |
|---|---|---|
| 모델 | 큐. 소비하면 보통 사라진다 | 로그. 보관 기간 동안 여러 번 읽을 수 있다 |
| 강점 | 작업 분배, 라우팅, 복잡한 메시지 흐름 | 대량 이벤트 스트림, 재처리, 여러 소비자 |
| 흔한 용도 | 주문 처리 작업, 알림 발송 | 로그 수집, 이벤트 기록, 데이터 파이프라인 |

**멱등성 (Idempotency)** — 같은 메시지를 두 번 받아도 결과가 한 번 처리한 것과 같아야 한다. 메시지 전달은 "최소 한 번"인 경우가 많아서 중복이 생길 수 있다. 메시지 ID를 저장해 두고 이미 처리한 것은 건너뛴다.

**실습 (선택):** 같은 메시지를 두 번 처리해도 잔액이 한 번만 바뀌는 로직을 만든다.

## 7. 서비스 구조 패턴

- **MSA (마이크로서비스):** 기능별로 서비스를 나누고 각자 배포한다. 장점은 독립 배포, 단점은 네트워크 호출과 장애 전파가 늘어난다.
- **EIP (Enterprise Integration Patterns):** 기업 시스템이 메시지로 연결될 때 쓰는 디자인 패턴 모음(메시지 채널, 변환기, 라우터 등). Spring Integration과 Apache Camel이 이를 코드로 구현한다.
- **로드밸런서와 이중화:** 같은 서비스의 여러 인스턴스에 요청을 나눠 보낸다. ALB나 Nginx는 헬스체크로 정상인 인스턴스에만 보낸다. HSRP와 VRRP는 게이트웨이 주소를 두 장비가 나눠 갖는 방식이라 목적이 다르다.
