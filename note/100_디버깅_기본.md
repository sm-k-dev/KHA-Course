# 디버깅 기본: 중단점으로 값을 보며 버그 잡기

> 중요도: **A** · 이 부록의 목표: `System.out.println`을 여기저기 찍는 대신, 중단점에서 멈춰 변수 값을 보고 한 줄씩 실행하며 버그 위치를 찾는다. IntelliJ 디버거의 개념을 익히고, 같은 동작을 JDK의 명령줄 디버거(`jdb`)로 직접 확인한다.

> 2026-11-23 추가 부록. 단축키와 실습 흐름은 선생님 자료 `Additional_HandBook★/IntelliJDebuggingSpringJpa.html`(카페 주문 버그 3개 실습)을 바탕으로 정리했다. 아래 `jdb` 실행 결과와 수정 결과는 이 PC의 JDK 25에서 확인했다. IntelliJ 화면 자체는 이 환경에서 실행하지 않았다.

---

## 1. 왜 디버거인가

`println`은 **미리 찍어 둔 곳**만 보여 준다. 디버거는 **멈춘 순간의 모든 변수**를 보여 준다. 버그가 어디서 엇나가는지 모를 때 훨씬 빠르다.

| 방식 | 장점 | 한계 |
|---|---|---|
| `println` | 설정 없이 바로 찍는다 | 찍은 곳만 보이고, 찍을 때마다 코드를 고쳐야 한다 |
| 디버거 | 멈춘 곳의 모든 값을 보고, 한 줄씩 따라간다 | 실행이 느려지고 설정이 필요하다 |

---

## 2. 중단점과 단축키

**중단점(Breakpoint)**: 프로그램을 **그 줄을 실행하기 직전에** 멈추게 하는 표시다. 줄 번호 왼쪽을 클릭하거나 `Ctrl+F8`을 누른다.

| 동작 | IntelliJ 단축키 | 뜻 |
|---|---|---|
| Step Over | `F8` | 다음 줄로. 메서드 안은 건너뛴다 |
| Step Into | `F7` | 호출한 메서드 안으로 들어간다 |
| Step Out | `Shift+F8` | 지금 메서드를 끝까지 실행하고 밖으로 나온다 |
| Resume | `F9` | 다음 중단점까지 실행한다 |
| Run to Cursor | `Alt+F9` | 커서가 있는 줄까지 빨리 감는다 |
| Evaluate Expression | `Alt+F8` | 멈춘 상태에서 식을 직접 실행해 본다 |

**주의**: 줄 중단점은 그 줄을 **실행하기 직전**에 멈춘다. 그 줄에서 바뀔 값은 아직 이전 값으로 보인다.

## 3. 명령줄 디버거 `jdb`로 직접 해 보기

### 3-1. 버그가 있는 프로그램

카페 주문 합계를 구한다. 정답은 `4500×2 + 4000×1 + 6000×1 = 19000`이다.

```java
import java.util.List;

public class Cafe {
    record Order(String item, int price, int qty) {}

    static int totalSales(List<Order> orders) {
        int total = 0;
        for (int i = 0; i < orders.size() - 1; i++) {   // 버그: 마지막 주문이 빠진다
            Order o = orders.get(i);
            total += o.price() * o.qty();
        }
        return total;
    }

    public static void main(String[] args) {
        List<Order> orders = List.of(
                new Order("latte", 4500, 2),
                new Order("americano", 4000, 1),
                new Order("cake", 6000, 1));
        int sum = totalSales(orders);
        System.out.println("total=" + sum);            // 정답은 19000
    }
}
```

**실행 결과 (확인함)**: `total=13000`. 6000원짜리 케이크가 빠져 있다.

### 3-2. 중단점에서 멈추기 (확인함)

`-g` 옵션을 줘서 컴파일하면 디버거가 변수 이름을 읽을 수 있다. `jdb`는 명령을 표준 입력으로 받는다.

```powershell
javac -g -d out Cafe.java
jdb -classpath out Cafe
```

실행 중 확인한 명령과 결과(핵심만):

```
> stop at Cafe:10            ← 10번 줄(total += ...)에 중단점
> run
Breakpoint hit: "thread=main", Cafe.totalSales(), line=10
main[1] locals
Local variables:
total = 0
i = 0
o = instance of Cafe$Order
main[1] next
Step completed: "thread=main", Cafe.totalSales(), line=8
main[1] cont
total=13000
```

**읽는 법**
- `locals`로 지금 멈춘 곳의 변수 값을 본다. `total = 0`, `i = 0`에서 멈췄다.
- `next`는 Step Over에 해당한다. 한 줄 실행 후 다음 줄로 간다.
- `cont`는 Resume이다. 끝까지 실행하면 `total=13000`이 나온다.

> 참고: 명령을 파이프로 넘길 때는 프로그램이 멈출 시간을 줘야 한다. 명령이 너무 빨리 들어가면 중단점 전에 입력이 끝나 세션이 종료된다. IntelliJ에서는 이 문제가 없다.

### 3-3. 원인과 수정 (확인함)

- **원인**: 반복문 조건 `i < orders.size() - 1`이 마지막 원소를 건너뛴다. 중단점에서 `i`가 0부터 시작해 마지막 인덱스(2)에 도달하지 않는다는 것을 보면 찾을 수 있다.
- **수정**: `i < orders.size()`로 바꾼다.

```powershell
# 수정 후 실행 결과 (확인함)
total=19000
```

**디버깅 순서 요약**: 기대값(19000)과 실제값(13000)의 차이를 먼저 적는다 → 차이가 나는 값을 본다 → 값이 엇나간 줄에 중단점을 건다 → 한 줄씩 따라가며 `locals`로 확인한다 → 원인을 한 문장으로 적는다.

## 5. 흔한 실수

| 실수 | 결과 | 고치는 방법 |
|---|---|---|
| `-g` 없이 컴파일 | 디버거에서 변수 이름이 안 보인다 | IntelliJ는 기본으로 켜 준다. `javac`는 `-g`를 붙인다 |
| 메서드 중단점을 많이 건다 | 실행이 눈에 띄게 느려진다 | 메서드 첫 줄에 줄 중단점을 건다 |
| 중단점에서 값이 옛 값이라고 놀란다 | 실행 전에 멈춘 것이다 | 다음 줄로 한 번 넘긴 뒤 값을 본다 |
| 디버거만 믿고 테스트를 안 쓴다 | 같은 버그가 다시 생긴다 | 버그를 고친 뒤 실패하던 입력을 테스트로 남긴다 |

## 7. 브라우저 디버깅: DevTools의 Console, Sources, Network (선생님 자료 기반, Console·Network는 확인함, Sources 중단점은 미실행)

**출처**: 선생님 자료 `Additional_HandBook★/javascript_실무보충_자습서.html`의 8장(Console·Sources)과 9장(Network). 아래 내용은 자료의 흐름과 개념을 정리한 것이다.

**실행 확인 (2026-11-24, 내장 브라우저)**: 27장의 React 목록 화면(Vite 5174)과 Boot API(8092)를 띄우고, 브라우저 도구로 Console과 Network를 읽었다. 개발자 도구의 Console·Network 탭과 같은 정보를 읽는 방식이다.

| 상황 | 무엇을 했나 | 확인한 결과 |
|---|---|---|
| 정상 흐름 | 화면을 열었다 | Network에 `GET /api/posts → 200 OK`가 두 번 찍혔고, Console에는 오류가 없었다 |
| CORS | 화면(5174)에서 API(8092)를 프록시 없이 직접 불렀다 | Console: `blocked by CORS policy: No 'Access-Control-Allow-Origin' header`. Network: 상태 코드 없이 `[FAILED: net::ERR_FAILED]` |
| 404 | 화면에서 `/api/nope`를 불렀다 | Network: `404 Not Found`. 응답 본문은 `{"status":404,"error":"Not Found","path":"/api/nope"}` |

**해석**
- CORS는 서버가 응답하지 않은 것이 아니다. 서버는 응답했지만, 브라우저가 허용 헤더가 없다고 판단해서 화면에 넘기지 않았다. 그래서 Network에 상태 코드가 남지 않는다. 이 차이를 확인하는 것이 이 절의 핵심이다.
- 404는 서버가 응답한 것이다. 상태 코드와 본문으로 주소가 틀렸다는 것을 바로 알 수 있다.
- **Sources 중단점 (사용자 PC, Chrome 개발자 도구, 2026-11-24, 확인함)**: `PostList.tsx`의 `const res = await fetch(...DELETE...)` 줄(25행)에 중단점을 걸고 `삭제 2`를 눌렀다.
  - 멈춘 순간 Scope의 `Local`에 `id: 2`가 보였다. 아직 `res`는 값이 없었다(`<value unavailable>`).
  - `F10`(Step over)으로 한 줄 넘기자 `res`가 `Response` 객체로 채워졌다. `status: 204`, `statusText: "No Content"`, `ok: true`, `url: .../api/posts/2`였다.
  - 즉 중단점에서 값이 생기는 순서(줄 실행 전에는 없고, 줄 실행 후에는 있다)와 응답 상태를 Scope에서 바로 확인할 수 있었다. 이 절의 "Sources에서 한 줄씩 따라가기" 설명이 실제로 맞다.

**DevTools 여는 법**: 크롬에서 `F12`를 누른다. 자주 쓰는 탭은 세 가지다.

| 탭 | 무엇을 보나 | 언제 쓰나 |
|---|---|---|
| Console | 에러 문장, `console.log` 출력 | 에러 문장을 먼저 읽을 때 |
| Sources | 코드 파일, 중단점 | 값을 보며 한 줄씩 따라갈 때 |
| Network | 요청과 응답(주소, 메서드, 상태 코드, 본문) | 서버와 주고받는 데이터가 맞는지 볼 때 |

**Console 출력 메서드**: `console.log`(일반 값), `console.warn`(주의), `console.error`(오류), `console.table`(배열과 객체를 표로), `console.group`/`groupEnd`(출력을 묶기). 표는 객체 목록을 한눈에 볼 때 편하다. Node에서도 `console.table`은 같은 모양으로 나온다.

**Sources 중단점**: 줄 번호를 클릭하면 중단점이다. 멈추면 Scope에서 변수 값을 보고, `Step over`(다음 줄)와 `Step into`(함수 안)로 따라간다. 자료의 흐름은 Java 디버거(100장 3절)와 같다.

**Network 탭으로 원인 구별**
- **상태 코드**: `200`은 성공, `400`은 보낸 내용 문제, `401`/`403`은 인증·권한 문제, `404`는 주소 문제, `500`은 서버 내부 오류다.
- **CORS 에러 vs 서버 에러**: 콘솔에 `blocked by CORS policy`가 나오면 서버가 응답했더라도 브라우저가 막은 것이다. Network 탭에서 요청이 서버까지 갔는지, 응답 헤더에 허용 정보가 있는지 본다(18장, 27장).
- **Payload와 Response**: 보낸 JSON(Payload)과 받은 응답 본문(Response)을 나란히 본다. 응답이 HTML이면 JSON 파싱 에러가 난다(14장 표).

**면접 기준**: "에러는 Console에서 문장을 읽고, 요청이 맞는지는 Network에서 Payload와 상태 코드를 봅니다. CORS 에러는 서버 오류가 아니라 브라우저가 교차 출처 응답을 막은 것입니다."

## 6. 실습 과제

1. 3-1의 `Cafe`를 `jdb`로 열고, `stop at Cafe:9`에 중단점을 걸어 `o`의 값을 세 번 확인한다.
2. `Step Into`(jdb에서는 `step`)로 `o.price()` 안으로 들어가 본다.
3. 버그를 고친 뒤 기대값 19000이 나오는지 확인하고, 이 입력을 테스트로 남긴다.
4. IntelliJ에서 같은 프로젝트를 열고 `F8`, `F7`, `Shift+F8`을 각각 한 번씩 눌러 차이를 적는다.
